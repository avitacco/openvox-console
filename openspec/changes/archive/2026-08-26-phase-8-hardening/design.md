## Context

See proposal.md for motivation. Current state, confirmed by direct investigation rather than assumption:

- `internal/rbac.Revoker` (`revoke.go`) is already a correct multi-instance-safe pattern: an in-memory map for zero-latency checks, Postgres (`PersistRevocation`/`UnexpiredRevocations`) as the durable source of truth, and NATS pub/sub (`rbac.revoked` subject) propagating a revocation to every other running instance's memory immediately, with no restart. This is the reference pattern the rest of this design follows where applicable.
- `internal/nodetransport.Registry` (`session.go`) holds `sessions map[string]*session` purely in-process - an agent connected to instance A is invisible to instance B. Already documented in architecture-summary.md as deferred to Phase 7 federation.
- `internal/orchestrator.Dispatcher` (`dispatcher.go`) holds `pending map[string]pendingRequest` (message ID -> job/target) purely in-process too, for the same underlying reason: a response only ever arrives on the connection the dispatching instance itself holds. This has not been documented anywhere before this change.
- `go.mod` has no metrics library today (no Prometheus, no OpenTelemetry, no expvar). Logging is `log/slog` throughout via `internal/runtime.NewLogger`. `internal/runtime.HealthHandler` exists (checks Postgres + NATS) but reports nothing metrics-shaped, and there is no way to see connected-agent counts, in-flight dispatch counts, or revocation-list size except via logs or a direct database query.
- `internal/persistence` uses a plain `pgxpool.New(ctx, dsn)` with no explicit reconnection handling beyond whatever `pgxpool` already does internally (a pool that lazily reconnects idle/broken connections, but nothing at the application layer that distinguishes "Postgres briefly unreachable" from any other query error).
- `internal/rbac/keys.go` (`LoadSigningKey`) loads exactly one ES256 private key from one PEM file, used for both signing and verification. `Makefile`'s `rbac-keys` target generates it via plain `openssl ecparam`, unencrypted. There is no `kid` claim, no multi-key verification - replacing the key file today instantly invalidates every outstanding token.
- Postgres replication is entirely greenfield: `docker-compose.yml` runs a single `postgres:18-alpine` instance for the console database, with no replica, no streaming replication configuration, anywhere in the repo.

## Goals / Non-Goals

**Goals:**
- Make the console's actual multi-instance behavior explicit and correct where it's supposed to be correct, rather than assumed.
- Give an operator a real, standard (Prometheus-compatible) way to monitor this service, including the operational state that was previously invisible outside logs/DB queries.
- Make a Postgres failover survivable without a manual restart, and make the replication setup itself a documented, tested procedure rather than untested infrastructure-as-someday.
- Make JWT key rotation an operational non-event instead of a mass logout.

**Non-Goals** (see proposal.md's "Impact" note):
- Fixing the node transport's / orchestrator dispatcher's single-instance state - that's Phase 7 federation's job. This change only documents the boundary precisely.
- Backfilling the missing `node-transport`/`orchestrator` main specs (a pre-existing gap from Phase 6's archive never being synced) - a separate future change.
- A full APM/tracing story (OpenTelemetry spans, distributed tracing) - Prometheus metrics only, matching what "observability" concretely asked for in phased-build-plan.md.
- Encryption-at-rest for the signing key file itself - that's the operator's filesystem/secrets-manager's job, not this application's; this change's key-rotation work is about *tolerating* rotation without an outage, not about how the key material is stored.
- Automated Postgres failover orchestration (e.g. Patroni/repmgr) - this change documents and tests a manual/scripted failover against a real streaming-replication fixture; automating failover triggering is a larger, separate operational decision left to whoever deploys this.

## Decisions

**Prometheus via `github.com/prometheus/client_golang`, exposed at `GET /metrics`, unauthenticated - same trust posture as the existing `/health` endpoint.** Alternative considered: OpenTelemetry metrics - rejected as materially heavier setup (a collector, an exporter pipeline) for what phased-build-plan.md actually asks for (metrics + structured logs, which the project already has via `log/slog`); Prometheus's client library is the de facto standard for exactly this shape of Go service and scrapes directly with zero additional infrastructure. Unauthenticated matches `/health`'s own existing precedent and standard Prometheus practice (network-perimeter-protected scraping, not per-request auth) - and everything this endpoint reports (aggregate counts, not per-agent identity/certnames) is low-sensitivity by design (see the service-runtime spec's own scoping to counts, not lists).

**Broker/orchestrator visibility ships as metrics gauges, not a separate introspection endpoint.** Originally drafted as its own authenticated JSON endpoint; simplified during design because everything it would report (connected-agent count, in-flight dispatch count, revocation-list size) is exactly what a metrics gauge is for, and a second bespoke endpoint next to a real metrics endpoint would be redundant machinery for the same operator workflow (a Grafana dashboard, not a hand-rolled JSON viewer). `nodetransport.Registry` gains a `Len()`-style accessor; `orchestrator.Dispatcher` gains the equivalent for its `pending` map; `rbac.Revoker` gains one for its in-memory revocation set - each guarded by the mutex already protecting that map, read on each scrape.

**Postgres reconnection resilience is verified behavior, not new retry machinery.** `pgxpool` already recovers a broken connection on its own; what's missing is proof that this project's actual call sites (which mostly propagate a query error straight to an HTTP 502, per the existing `writeError` pattern used throughout) recover cleanly once Postgres comes back, without the console needing a restart. This change's work here is a real, scripted test against a real primary/standby fixture (kill the primary, promote the standby, confirm the console's own `/health` and a real write path recover within the pool's normal retry behavior with no process restart) plus documenting the runbook - not new code, unless that test reveals a real gap.

**Postgres replication fixture: streaming replication (one primary, one standby), added as a new opt-in `docker-compose.yml` profile.** Mirrors the project's existing pattern of profile-gated optional infrastructure (`openvox`, `oidc` profiles already exist) - the default `make up` stays a single instance for everyday dev work; `make postgres-replication-up` (new) brings up the primary+standby pair for testing this specific scenario. Alternative considered: logical replication - rejected, since streaming (physical) replication is the standard HA pattern for "promote a standby to primary on failure," which is exactly the scenario being tested, and logical replication solves a different problem (selective table replication) not needed here.

**JWT key rotation: a small ordered list of verification keys plus one designated active signing key, selected by `kid`.** `internal/rbac.Issuer` gains a `kid` alongside its existing signing key; `internal/rbac.Verifier` gains a small `map[string]*ecdsa.PublicKey` (kid -> key) instead of its current single key, matched against the token's header `kid` before signature verification. Configuration: `CONSOLE_RBAC_SIGNING_KEY_FILE`/`CONSOLE_RBAC_SIGNING_KEY_ID` (active, signs new tokens) plus an optional `CONSOLE_RBAC_VERIFICATION_KEYS_DIR` (additional `kid`-named PEM files, verification-only) - both file-based, consistent with how the signing key is already configured, no new secrets-management dependency. `make rbac-keys` gains a rotation-friendly variant that generates a new key without clobbering the active one, and the operational runbook documents the rotation sequence (generate new key -> add to verification set -> make it the active signer -> after the old key's longest-lived outstanding token would have expired, remove it from the verification set).

## Risks / Trade-offs

- **[Risk]** An unauthenticated `/metrics` endpoint could leak more than intended if network perimeter controls aren't actually in place at deployment. **Mitigation:** every metric this change adds is a low-sensitivity aggregate count (see Decisions above); the operational runbook explicitly calls out that `/metrics` (like `/health`) is meant to be reachable only from a monitoring network, not the public internet.
- **[Risk]** Documenting the node transport/orchestrator single-instance boundary makes an existing limitation more visible without fixing it, which could read as a regression to someone skimming the docs. **Mitigation:** frame it explicitly as "documented, not new" in the runbook, cross-referencing architecture-summary.md's existing Phase 7 deferral.
- **[Risk]** A real primary/standby failover test could reveal that some call site doesn't actually recover without a restart (the Goals above assume this will just work, but it's unverified). **Mitigation:** this is exactly what the test is for; if it finds a real gap, that becomes an in-scope fix here rather than a surprise later, and tasks.md sequences the test before claiming the requirement is met.
- **[Trade-off]** File-based verification-key configuration (a directory of PEM files) is simpler to operate than a KMS/secrets-manager integration, but doesn't solve encryption-at-rest - consistent with this change's stated Non-Goal, but worth naming as a real limitation an operator in a stricter environment should know about.

## Migration Plan

- New environment variables, all optional with backward-compatible defaults: `CONSOLE_RBAC_SIGNING_KEY_ID` (defaults to a fixed value if unset, so an existing single-key deployment keeps working unchanged), `CONSOLE_RBAC_VERIFICATION_KEYS_DIR` (unset = today's single-key behavior exactly).
- No breaking change to any existing token: a token issued before this change has no `kid` in its claims; the verifier treats a missing `kid` as "the configured primary signing key," so already-issued tokens keep verifying through their natural expiry without any operator action.
- No database migration - metrics/introspection state is derived from existing in-memory structures, not persisted.
- The Postgres replication fixture is entirely opt-in (a new compose profile) - `make up`'s default single-instance behavior is unchanged.
- Rollback: revert the code; the new env vars and compose profile are additive and can simply go unused.
