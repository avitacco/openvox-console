Nutzung

Pläne ausführen

Erstellen Sie einen Plan – eine Liste von Puppet-Läufen und Tasks, die der Reihe nach ausgeführt werden –, bewahren Sie ihn auf, führen Sie ihn auf den Nodes Ihrer Wahl aus und verfolgen Sie jeden Schritt.

Ein Plan ist eine Liste von Schritten, die der Reihe nach auf denselben Nodes ausgeführt werden. Jeder Schritt ist ein Puppet-Lauf oder ein Task, genau so, wie Sie ihn von Hand starten würden – siehe Jobs ausführen. Ein Plan wird in der Konsole aufbewahrt, damit er erneut ausgeführt werden kann, jedes Mal auf anderen Nodes.

Pläne zu sehen erfordert orchestrator:read. Sie zu erstellen, zu ändern, zu löschen und auszuführen erfordert orchestrator:run.

Ein Plan ist hier eine in der Konsole erstellte Liste von Schritten. Er ist kein in der Puppet-Sprache geschriebener Plan, den die Konsole nicht ausführt. Ein in YAML geschriebener Plan in Ihren eigenen Modulen wird von derselben Seite aus ausgeführt: siehe Pläne aus Ihrem Code ausführen.

Einen Plan erstellen

Öffnen Sie Jobs, dann Pläne und dann Neuer Plan.

  1. Geben Sie ihm einen Namen und, wenn Sie möchten, eine Beschreibung. Ein Name kann nur von einem Plan verwendet werden.
  2. Fügen Sie Schritte mit Puppet-Lauf als Schritt hinzufügen und Task als Schritt hinzufügen hinzu. Ein Plan hat zwischen 1 und 20 Schritte.
    • Ein Puppet-Lauf-Schritt nimmt die Laufoptionen entgegen: No-op, Debug und ein Environment.
    • Ein Task-Schritt nimmt ein Environment, einen Task, dessen Parameter und ein Timeout entgegen, wie in Einen Task ausführen.
  3. Bringen Sie die Schritte mit Nach oben und Nach unten in die richtige Reihenfolge. Was Sie in einen Schritt eingegeben haben, wandert mit ihm.
  4. Plan speichern.

Die Konsole prüft beim Speichern jeden Schritt, so wie sie den Lauf oder Task prüfen würde, wenn Sie ihn jetzt starteten. Ein abgelehnter Schritt wird mit der Begründung markiert, und nichts von Ihren Eingaben geht verloren.

Ein Plan legt nicht fest, auf welchen Nodes er läuft. Das wird bei jeder Ausführung gewählt.

Sensible Task-Werte

Ein als sensitive markierter Task-Parameter – ein Passwort, ein Token – wird nie in einem Plan aufbewahrt. Sein Feld fehlt im Editor, und der Wert wird bei jeder Ausführung des Plans abgefragt. Der Grund: Ein Plan wird geteilt, jeder, der Jobs ausführen darf, kann ihn öffnen.

Wer einen Plan ändern darf

Jeder mit orchestrator:run kann jeden Plan ändern oder löschen, unabhängig davon, auf welchen Node-Gruppen seine Rolle gewährt ist. Ein Plan nennt keine Nodes, also gibt es darin nichts, was Node-Gruppen begrenzen könnten. Worauf eine Person einen Plan ausführen kann, ist wie bei jedem Job begrenzt. Eine Person, deren Rolle auf einige Tasks beschränkt ist, kann einen Plan nur mit Tasks speichern, die sie ausführen darf.

Einen Plan ausführen

Wählen Sie auf der Seite Pläne neben einem Plan Ausführen, oder öffnen Sie den Plan und wählen Sie Ausführen.

  1. Wählen Sie die Nodes: eine Liste, eine Abfrage oder eine Node-Gruppe, wie in Die Nodes wählen. Nodes anzeigen zeigt, worauf er laufen würde.
  2. Geben Sie alle sensiblen Werte ein, nach denen die Schritte fragen. Jeder ist mit seinem Schritt beschriftet.
  3. Plan ausführen. Die Job-Seite des Plans öffnet sich.

Die Nodes werden einmal ermittelt, beim Start des Plans, und jeder Schritt läuft auf diesen Nodes. Ist Ihre Rolle auf bestimmten Node-Gruppen gewährt, wird eine Abfrage oder Gruppe auf Ihre Nodes eingeengt, und eine Liste, die einen Node außerhalb davon nennt, wird wie bei jedem Job vollständig abgelehnt.

Jeder Schritt wird geprüft, bevor irgendetwas startet. Würde einer abgelehnt – etwa ein Task, der inzwischen aus dem Code entfernt wurde –, wird der Plan mit Nennung des Schritts abgelehnt, und nichts läuft.

Ein Plan mit einem Schritt, der nicht mehr ausgeführt werden kann, zeigt bei diesem Schritt eine Warnung. Bearbeiten Sie den Plan, bevor Sie ihn ausführen.

Tasks, die Ihre Rollen nicht erlauben

Ist Ihre Rolle auf einige Tasks beschränkt – siehe Eine Rolle auf einige Tasks beschränken –, kann ein Plan, den jemand anderes gespeichert hat, einen Task enthalten, den Sie nicht ausführen dürfen. Sie sehen trotzdem jeden Schritt, und die, die Sie nicht ausführen dürfen, sind mit Ihre Rollen erlauben den Task ... nicht markiert. Ausführen ist für diesen Plan ausgeschaltet, und die API lehnt ihn mit 403 ab, mit Nennung des Schritts und des Tasks. Den Plan zu bearbeiten hilft nicht, es sei denn, Sie entfernen diese Schritte; ihn mit ihnen zu speichern wird auf dieselbe Weise abgelehnt.

Ist das Ziel eine Abfrage oder eine Node-Gruppe, läuft der Plan auf den Nodes, auf denen Sie jeden Task-Schritt ausführen dürfen, sodass alle seine Schritte weiterhin eine Menge von Nodes teilen. Puppet-Lauf-Schritte sind nicht eingeschränkt.

Einen Plan verfolgen

Die Job-Seite eines Plans listet seine Schritte der Reihe nach auf. Jeder zeigt, was er tut, seinen Zustand, wann er begonnen und geendet hat, und das Ergebnis jedes Nodes. Die Seite aktualisiert sich selbst, während der Plan läuft.

Zustand Bedeutung
Wartet ein früherer Schritt ist noch nicht abgeschlossen
Läuft an die Nodes gesendet, und nicht alle haben geantwortet
Erfolgreich auf jedem Node abgeschlossen
Fehlgeschlagen auf mindestens einem Node fehlgeschlagen
Nicht ausgeführt ein früherer Schritt ist fehlgeschlagen, daher wurde dieser nie an einen Node gesendet

Die Nummer eines Schritts verlinkt auf die eigene Job-Seite dieses Schritts, die zurück zum Plan verlinkt. Die Liste Jobs zeigt einen Plan als eine Zeile, nicht als eine pro Schritt.

Wenn ein Schritt fehlschlägt

Ein Schritt schlägt fehl, wenn er auf einem seiner Nodes fehlschlägt, auch auf einem Node, der nicht verbunden war. Der Plan hält dort an: Die nachfolgenden Schritte werden als Nicht ausgeführt markiert, und für sie wird an keinen Node etwas gesendet. Der Job des Plans ist fehlgeschlagen.

Es gibt keine Option, nach einem fehlgeschlagenen Schritt weiterzumachen, die fehlgeschlagenen Nodes zu überspringen oder einen Schritt erneut zu versuchen. Beheben Sie, was fehlgeschlagen ist, und führen Sie den Plan erneut aus; ein Plan, der seine ersten Schritte nicht wiederholen soll, kann in zwei aufgeteilt werden.

Einen Plan planen

Wählen Sie im Dialog „Plan ausführen“ Stattdessen planen, oder erstellen Sie einen Zeitplan und wählen Sie Einen Plan ausführen – siehe Jobs planen.

Ein Zeitplan behält eine eigene Kopie der Schritte des Plans, angefertigt beim Speichern des Zeitplans. Wird der Plan danach geändert oder gelöscht, führt der Zeitplan weiterhin die Schritte aus, mit denen er gespeichert wurde. Um eine Änderung zu übernehmen, bearbeiten Sie den Zeitplan, wählen den Plan erneut und speichern.

Das ist Absicht. Ein Zeitplan läuft mit dem Zugriff seines Besitzers, und jeder, der Jobs ausführen darf, kann einen Plan ändern. Folgte ein Zeitplan dem Plan, könnte jemand, der auf wenige Nodes beschränkt ist, ändern, was der Zeitplan eines Administrators auf jedem Node ausführt.

Über die API

Gespeicherte Pläne:

Anfrage Bewirkt
GET /api/v1/orchestrator/saved-plans listet Pläne auf, ohne ihre Schritte
GET /api/v1/orchestrator/saved-plans/<id> ein Plan mit seinen Schritten
POST /api/v1/orchestrator/saved-plans legt einen Plan an
PUT /api/v1/orchestrator/saved-plans/<id> ersetzt einen Plan
DELETE /api/v1/orchestrator/saved-plans/<id> löscht einen Plan
curl -X POST https://console.example.com/api/v1/orchestrator/saved-plans \ -H "Authorization: Bearer <access token>" \ -H 'Content-Type: application/json' \ -d '{"name":"Restart web tier", "description":"Check first, then restart", "steps":[ {"kind":"run","options":{"noop":true}}, {"kind":"task","taskName":"service","environment":"production", "params":{"name":"nginx","action":"restart"},"timeoutSeconds":300} ]}'

Ein gelesener Plan listet bei jedem Task-Schritt die sensiblen Parameter auf, die beim Ausführen anzugeben sind (needs), sowie ein problem, falls sein Task nicht mehr gefunden werden kann.

Es gibt keine Anfrage, die einen Plan über seine ID ausführt. Um einen auszuführen, senden Sie seine Schritte – mit den sensiblen Werten in den params jedes Schritts – und die Nodes:

curl -X POST https://console.example.com/api/v1/orchestrator/plans \ -H "Authorization: Bearer <access token>" \ -H 'Content-Type: application/json' \ -d '{"name":"Restart web tier", "group":12, "steps":[ {"kind":"run","options":{"noop":true}}, {"kind":"task","taskName":"service", "params":{"name":"nginx","action":"restart"}} ]}'

Die Nodes sind targets, query oder group. Die Antwort ist der Job des Plans. Lesen Sie ihn mit GET /api/v1/orchestrator/jobs/<id>, das seine steps zurückgibt, jeden mit einem state von waiting, running, succeeded, failed oder not_run.

Eine abgelehnte Anfrage antwortet mit 400 (oder 403 für einen Node außerhalb Ihrer Node-Gruppen) und einem error. Ist ein bestimmter Schritt die Ursache, enthält sie außerdem step, ab 1 gezählt, und bei den Parametern eines Tasks fields.

GET /api/v1/orchestrator/jobs listet die Schritte eines Plans nicht mehr als eigene Jobs auf. Fügen Sie ?parent=<plan job id> hinzu, um sie aufzulisten.

In einer aufgeteilten Installation

Ein in der Konsole gestarteter Plan wird Schritt für Schritt von der Instanz gesendet und verfolgt, die die Anfrage entgegengenommen hat: in einer aufgeteilten Installation einer web-Instanz (siehe Betriebsmodi). Stoppt diese Instanz, bevor der Plan endet, werden die noch laufenden Schritte als fehlgeschlagen markiert und die übrigen als nicht ausgeführt abgeschlossen; starten Sie den Plan erneut. Ein geplanter Plan wird auf dieselbe Weise von einer orchestrator-Instanz gestartet und verfolgt.
