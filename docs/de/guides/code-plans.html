Nutzung

Pläne aus Ihrem Code ausführen

Führen Sie YAML-Pläne aus, die in Ihren Modulen liegen, mit typisierten Parametern, zwischen Schritten weitergegebenen Ergebnissen und jedem Task gegen Ihre Node-Gruppen geprüft.

Ein Code-Plan ist eine YAML-Datei im Verzeichnis plans eines Moduls, im Format, das Bolt und Puppet Enterprise verwenden. Die Konsole liest ihn aus dem Code, den sie deployt hat, und führt ihn selbst aus: einen Schritt nach dem anderen, wobei Ergebnisse von Schritt zu Schritt weitergegeben werden. Sie braucht dafür weder Bolt noch die Puppet-Sprache.

Das unterscheidet sich von einem gespeicherten Plan, der eine feste Liste von Puppet-Läufen und Tasks ist, die Sie in der Konsole erstellen und die auf einer Menge von Nodes läuft. Ein Code-Plan lebt bei Ihrem Code, nimmt eigene Parameter entgegen und bestimmt die Ziele jedes Schritts aus den vorherigen Schritten.

Die Liste der Pläne zu lesen erfordert orchestrator:read. Einen auszuführen erfordert orchestrator:run. Es ist keine neue Berechtigung beteiligt.

Woher Pläne stammen

Die Konsole sucht in den Modulen jedes Environments, in der Reihenfolge des modulepath in environment.conf (modules, falls keiner angegeben ist), nach <module>/plans/<name>.yaml. Ein Plan heißt module::name oder einfach module für init.yaml. Kommt ein Name in zwei Verzeichnissen vor, gewinnt der erste, wie in Puppet.

Die Dateien werden aus dem Code-Verzeichnis der Konsoleninstanz gelesen, die Ihren Code deployt (CONSOLE_CODE_DIR_PATH). Eine Instanz, die den deployten Code nicht hält, kann keine Pläne auflisten oder ausführen und sagt das, statt eine leere Liste zu zeigen. Führen Sie Pläne von der deployenden Instanz aus.

Öffnen Sie Jobs und dann Pläne: Der Abschnitt Pläne im Code listet die Pläne eines Environments auf. Ein Plan, den die Konsole nicht ausführen kann, wird mit Begründung und Nennung des Schritts aufgeführt.

Was ein Plan tun kann

Ein Plan hat eine description, parameters, steps und ein return:

description: Restart a service, then check it parameters: targets: type: TargetSpec description: Where to restart it service: type: String[1] default: nginx token: type: Optional[Sensitive[String]] steps: - name: restart description: Restart the service task: service::restart targets: $targets parameters: name: $service - name: status task: service::status targets: $restart.ok_targets parameters: name: $service - message: "checked ${status.targets}" return: restarted: $restart.ok_targets healthy: $status.ok

Parameter deklarieren einen type, einen optionalen default und eine description. Typen sind die, die auch Tasks verwenden (String, Integer[1, 10], Boolean, Array[String], Enum['a','b'], Optional[...], ...), dazu TargetSpec (Nodes) und Sensitive[...]. Ein Parameter ohne Default, der nicht Optional ist, ist erforderlich. Die Konsole lehnt einen Lauf mit fehlendem, unbekanntem oder falsch typisiertem Parameter ab, bevor irgendetwas startet, und nennt ihn.

Schritte tun genau eines von Folgendem:

  • task: module::task, mit targets und parameters. Führt den Task aus.
  • plan: module::plan, mit parameters. Führt einen anderen Plan als Teil dieses Plans aus. Ein Plan kann Pläne bis zu fünf Ebenen tief aufrufen, aber nie sich selbst.
  • message: text. Schreibt Text in den Datensatz des Laufs.

Ein Schritt kann einen name haben, der sein Ergebnis späteren Schritten als $name zur Verfügung stellt, sowie eine description.

Referenzen sind $name, $name.field, $name[0] und $name['field'], auf einen Parameter oder einen früheren Schritt. Ein String, der nur aus einer Referenz besteht, behält den Typ des Werts (eine Liste bleibt eine Liste). In Text schreiben Sie ${name.field}; für ein Dollarzeichen schreiben Sie $$. Das ist die gesamte Syntax: Es gibt keine Operatoren, keine Bedingungen, keine Funktionen. Setzen Sie in einer einzeilig geschriebenen YAML-Liste oder -Zuordnung eine Referenz, die [ oder , enthält, in Anführungszeichen.

Das Ergebnis eines Schritts hat:

Feld Enthält
ok jedes Ziel war erfolgreich
results target, ok, value und error jedes Ziels
targets, ok_targets, error_targets Node-Namen
value das Ergebnis des Tasks, bei einem Schritt auf einem einzelnen Node

Der value eines Tasks ist das, was er als JSON ausgegeben hat, oder sein Text als _output.

Schlägt ein Task-Schritt auf einem Ziel fehl, schlägt der Plan dort fehl: Die nachfolgenden Schritte werden als nicht ausgeführt verzeichnet, und nichts weiter wird gesendet. Ein Schritt mit leeren Zielen (etwa weil ein früherer Schritt keine Erfolge hatte) führt nichts aus und gilt als erfolgreich.

Nicht unterstützt: command-, script-, upload-, download-, resources- und eval-Schritte, Ausdrücke in der Puppet-Sprache, parallel laufende Schritte, Wiederholen und Abfangen von Fehlern sowie das zeitgesteuerte Ausführen eines Code-Plans. Ein Plan, der eines davon verwendet, wird mit Begründung als unbrauchbar aufgeführt. Bolts Pläne in der Puppet-Sprache (.pp) werden nicht ausgeführt.

Einen ausführen

Wählen Sie Ausführen neben einem Plan. Das Formular wird aus seinen Parametern erstellt; lassen Sie ein Feld leer, um den Default zu verwenden. Nodes (TargetSpec) werden als Liste von Namen, als Abfrage oder als Node-Gruppe angegeben, einmalig beim Start des Plans aufgelöst und zuerst als Vorschau gezeigt. Der Lauf öffnet sich als Job; seine Seite zeigt jeden Schritt, während er geschieht: seinen Status, den gestarteten Job, was eine Nachricht ausgegeben hat und warum ein Schritt fehlgeschlagen ist, zusammen mit dem Wert, den der Plan zurückgegeben hat, und den Parametern, die er erhalten hat.

Umfang und Berechtigungen

Ein Plan kann nichts tun, was Sie nicht auch von Hand tun könnten. Wenn Sie ihn starten:

  • der Task, den jeder Schritt nennt, muss existieren und von Ihren Rollen erlaubt sein, sonst wird die Anfrage mit Nennung des Schritts abgelehnt;
  • von Ihnen genannte Nodes müssen in Ihren Node-Gruppen liegen, sonst wird die gesamte Anfrage abgelehnt;
  • sobald jeder Schritt erreicht wird, werden seine Ziele gegen Ihre Node-Gruppen und der Task gegen Ihre Allowlist geprüft, genau wie bei einem Task, den Sie selbst gestartet haben. Ein Schritt, der abgelehnt würde, lässt den Plan dort mit Begründung fehlschlagen.

Agentenlose Ziele können in Task-Schritten verwendet werden.

Ein Leser, der auf einige Node-Gruppen beschränkt ist, sieht einen Planlauf nur, wenn er auf seinen Nodes lief, und nicht, was er ausgegeben, zurückgegeben oder erhalten hat, wenn er auch auf anderen lief.

Sensible Werte

Ein als Sensitive[...] typisierter Parameter wird nie aufgeschrieben: Er ist [redacted] in den gespeicherten Parametern, im Trace, in Nachrichten, im Rückgabewert, in Logs und Audit-Einträgen und erreicht nur den Task-Parameter, an den er übergeben wird. Ein sensibler Wert kann nur an einen Parameter weitergegeben werden, der selbst Sensitive ist.

Lange Läufe

Ein Plan kann stundenlang laufen, bis zu 24 Stunden. Die Konsole meldet dem Job während des Laufs, dass er lebt. Stoppt die Konsoleninstanz, die ihn verfolgt, wird der Plan zehn Minuten nach dem letzten Lebenszeichen als fehlgeschlagen markiert; bereits gestartete Schritte laufen auf ihren Nodes weiter. Ein Lauf ist auf 200 Schritte begrenzt und ein Schritt auf 1000 Ziele; eine überschrittene Grenze lässt den Plan fehlschlagen, mit Nennung der Grenze.

Der Start eines Plans und sein Ende sind Audit-Einträge mit der Person, dem Plan und Environment sowie den Namen der übergebenen Parameter, nie ihren Werten.
