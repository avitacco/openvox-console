Nutzung

KI-Agenten die Konsole nutzen lassen

Geben Sie einem KI-Agenten ein eigenes, eingeschränktes Token, lassen Sie ihn die Flotte lesen und Änderungen anfordern, und genehmigen Sie jede Änderung selbst, bevor irgendetwas läuft.

Die Konsole hat einen Endpunkt für KI-Agenten, aufgebaut auf MCP (dem Model Context Protocol), unter /mcp. Ein damit verbundener Agent kann Ihre Nodes, Node-Gruppen, Tasks und Jobs ansehen. Wenn er etwas ändern möchte – einen Task ausführen, Puppet ausführen, einen Plan ausführen oder Nodes patchen –, startet er nichts. Er fragt, und die Anfrage wartet auf der Seite Genehmigungen, bis eine Person sie genehmigt.

Alles, was ein Agent sehen oder anfordern kann, ist durch sein eigenes Token begrenzt: welche Berechtigungen es hat, welche Node-Gruppen es erreichen kann und welche Tasks es anfordern darf. Alles, was er tut, steht unter seinem eigenen Namen im Audit-Protokoll.

Den Endpunkt einschalten

Der Endpunkt ist ausgeschaltet. Setzen Sie CONSOLE_MCP_ENABLED=true auf der Konsole und starten Sie sie neu. Bis dahin existiert /mcp nicht: Es antwortet wie jeder unbekannte Pfad.

Einstellung Bedeutung Standard
CONSOLE_MCP_ENABLED /mcp bereitstellen aus
CONSOLE_MCP_RATE_LIMIT Aufrufe pro Minute, die ein Token machen darf 60
CONSOLE_AGENT_REQUEST_TTL wie lange eine Anfrage auf eine Entscheidung wartet, etwa 30m 1h
CONSOLE_AGENT_TOKEN_MAX_DAYS die längste Gültigkeitsdauer eines Agent-Tokens 90

Die Ratenbegrenzung wird von jeder Konsoleninstanz einzeln geführt, sodass ein Token auf jeder Instanz so viele Aufrufe pro Minute machen kann. Stellen Sie den Endpunkt hinter TLS, wie den Rest der Konsole: Das Token ist ein Bearer-Credential.

Ein Token für einen Agenten ausstellen

Ein Agent-Token ist eine eigene Token-Art. Es ist kein Service-Token: Es läuft ab, ist auf Node-Gruppen beschränkt und funktioniert nur unter /mcp. Ein nach außen gelangtes Token kann nicht gegen den Rest der Konsolen-API verwendet werden.

  1. Öffnen Sie Verwaltung und dann Agent-Tokens.
  2. Benennen Sie das Token nach dem Agenten, für den es bestimmt ist, etwa ops-assistant.
  3. Wählen Sie seine Berechtigungen. Ein Agent-Token kann nur nodes:read, classifier:read, orchestrator:read, orchestrator:run und vulnerabilities:read tragen. orchestrator:run lässt den Agenten nichts ausführen: Es lässt ihn fragen.
  4. Wählen Sie die Node-Gruppen, die es erreichen darf. Ein Token ohne Gruppen erreicht keine Nodes. Alles, was der Agent liest oder anfordert, ist auf diese Gruppen und die Gruppen darunter beschränkt.
  5. Listen Sie optional unter Tasks, die es anfragen darf die Tasks auf, die es anfordern darf, ein Muster pro Zeile, wie bei einer Rolle. Lassen Sie das Feld leer, um jeden Task zu erlauben. Sowohl die Node-Gruppen als auch die Tasks werden bei der Erstellung des Tokens festgelegt.
  6. Legen Sie fest, wie viele Tage es gilt. Ein Token muss ablaufen und kann nicht länger gelten als CONSOLE_AGENT_TOKEN_MAX_DAYS. Dreißig Tage sind ein guter Anfang.
  7. Wählen Sie Agent-Token erstellen und kopieren Sie das Token: Es wird nur einmal angezeigt.

Widerrufen auf derselben Seite beendet das Token sofort, auf jeder Konsoleninstanz. Seine Anfragen bleiben als Nachweis auf der Seite „Genehmigungen“, und alle noch wartenden werden als fehlgeschlagen markiert.

Einen Agenten verbinden

Geben Sie dem Agenten die Adresse der Konsole mit /mcp am Ende und das Token als Bearer-Token. Der Endpunkt spricht Streamable HTTP und beantwortet jede per POST gesendete Nachricht direkt. Für Claude Code zum Beispiel:

claude mcp add --transport http openvox https://console.example.com/mcp \ --header "Authorization: Bearer <the token>"

Dem Agenten werden nur die Werkzeuge angeboten, die sein Token erlaubt.

Werkzeug Erfordert Was sie kann
list_nodes, get_node, get_node_reports nodes:read Nodes, ihre Facts und Reports ansehen
get_node_patches, get_patch_inventory nodes:read ausstehende Betriebssystem-Updates
list_groups, get_group, get_group_nodes classifier:read Node-Gruppen
list_tasks, get_task, list_code_plans, get_code_plan orchestrator:read was der deployte Code anbietet, und die Parameter von jedem
list_jobs, get_job orchestrator:read Jobs und ihre Ergebnisse
resolve_targets orchestrator:run welche Nodes ein Ziel benennen würde
request_task, request_puppet_run, request_plan, request_patch_run, request_code_plan orchestrator:run etwas zur Ausführung anfordern (siehe unten)
get_request, list_requests orchestrator:run die eigenen Anfragen des Agenten und wie über sie entschieden wurde

Alles, was ein Agent liest, kommt mit seinem Token über die eigenen Endpunkte der Konsole, sodass er genau das sieht, was eine Person mit den Berechtigungen und Node-Gruppen dieses Tokens sähe, und sensible Werte sind wie überall maskiert. Ein langes Ergebnis wird gekürzt, mit einem Hinweis, wie der Agent weniger anfordern kann.

Genehmigen, was ein Agent anfordert

Wenn ein Agent eines der request_-Werkzeuge aufruft, prüft die Konsole die Anfrage genau so, wie sie Ihre prüfen würde – den Task und seine Parameter, die Nodes, die Node-Gruppen und die Task-Liste des Agenten –, und speichert sie, wenn sie besteht, und teilt dem Agenten mit, dass sie auf Genehmigung wartet. Nichts läuft. Eine Anfrage, die eine Prüfung nicht besteht, wird mit Begründung abgelehnt, sodass der Agent sie korrigieren kann.

Öffnen Sie Jobs und dann Genehmigungen (der Tab zeigt, wie viele warten, ebenso die Navigation). Prüfen Sie eine Anfrage, um Folgendes zu sehen:

  • welcher Agent wann angefragt hat und wann die Anfrage abläuft
  • der Task, der Plan oder die Art des Laufs und sein Environment
  • die genauen Nodes, aufgelöst zum Zeitpunkt der Anfrage des Agenten
  • die Parameter, mit maskierten sensiblen Werten

Wählen Sie Genehmigen und ausführen, um den Job zu starten, oder Ablehnen, auf Wunsch mit einer Notiz: Der Agent wird benachrichtigt. Die Genehmigung startet genau das, was Sie gesehen haben – Parameter und Nodes werden bei der Anfrage eingefroren –, als das Token des Agenten. Der Job zeigt, dass ein KI-Agent ihn angefordert hat und wer ihn genehmigt hat, und Jobs lässt sich auf so gestartete Jobs eingrenzen.

Eine Anfrage, über die niemand entscheidet, läuft ab, nach einer Stunde, sofern Sie CONSOLE_AGENT_REQUEST_TTL nicht setzen, und kann dann nicht mehr genehmigt werden. Ein Agent kann nur eine begrenzte Zahl wartender Anfragen gleichzeitig haben.

Wer genehmigen darf

Zwei Berechtigungen, die auf Rollen für Personen gehören und keinem Agent-Token gegeben werden können:

Berechtigung Erlaubt
agent-requests:read Anfragen auf der Seite „Genehmigungen“ sehen
agent-requests:approve sie genehmigen und ablehnen

Eine genehmigende Person braucht außerdem orchestrator:run über jeden Node, auf den die Anfrage wirkt, und muss den Task ausführen dürfen. Sie können keine Anfrage für Nodes genehmigen, auf denen Sie den Task nicht selbst ausführen könnten. Wer nur einige Node-Gruppen sehen kann, sieht nur die Anfragen, die Nodes darin nennen.

Die Person, die das Token eines Agenten ausgestellt hat, kann dessen Anfragen nicht genehmigen, wohl aber ablehnen. Gibt es nur einen Administrator, legen Sie ein zweites Konto zum Genehmigen an.

Eine in einer neueren Konsolenversion hinzugekommene Berechtigung wird bestehenden Rollen nicht automatisch hinzugefügt. Gewähren Sie nach einem Upgrade agent-requests:read und agent-requests:approve auf der Seite Rollen den Rollen, die sie haben sollen. Der Bootstrap-Administrator einer neuen Installation hat beide.

Wurde das Token eines Agenten bis zu Ihrer Genehmigung widerrufen oder ist es abgelaufen, wird nichts gestartet, und die Anfrage nennt den Grund.

Pläne aus Code

request_code_plan beantragt, einen Plan aus Ihrem Code auszuführen. Ein solcher Plan wählt seine Nodes während der Ausführung selbst, innerhalb dessen, was das Token des Agenten erreicht. Seine Genehmigung erfordert daher orchestrator:run über alles, was dieses Token erreicht. Pläne laufen nur auf der Konsoleninstanz, die Ihren Code deployt; genehmigen Sie sie also dort, sonst schlägt die Anfrage mit genau dieser Begründung fehl.

Was verzeichnet wird

Das Audit-Protokoll verzeichnet auf der Stufe der Kategorie „orchestrator“ jede Anfrage sowie jede Genehmigung, Ablehnung und jeden Ablauf, mit dem Agenten als agent:<token name>, der entscheidenden Person und der Nummer der Anfrage. Lesezugriffe eines Agenten werden wie jeder Lesezugriff unter demselben Namen auditiert. Sensible Werte erscheinen nie im Audit-Protokoll, im Aktivitätsprotokoll oder in der Anfrage selbst: Sie werden mit dem Secrets-Schlüssel der Konsole (CONSOLE_SECRETS_KEY) verschlüsselt aufbewahrt, ohne den eine Anfrage mit einem solchen Wert abgelehnt wird.

Die API-Beschreibung

/api/v1/openapi.json beschreibt die REST-API für Programme, die Sie selbst schreiben, und steht jedem angemeldeten Benutzer offen. Agent-Tokens können diese API nicht aufrufen, und ein Programm mit einem Service-Token muss nicht auf eine Genehmigung warten. Damit ein Agent mit der Genehmigung einer Person handelt, verbinden Sie ihn mit /mcp.
