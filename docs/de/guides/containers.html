Installation

Installation mit Containern

Betreiben Sie openvoxserver, openvoxdb, beide Datenbanken und die Konsole mit Docker Compose – vom leeren Host bis zu einer Konsole, die bereit für Nodes ist.

Diese Anleitung betreibt den gesamten Stack aus der Produktions-Compose-Datei und den veröffentlichten Images des Projekts. Auf dem Host wird nichts gebaut. Klären Sie die Namen in Eine Installation planen, bevor Sie beginnen.

Sie brauchen einen Linux-Host mit Docker Engine und dem Compose-Plugin sowie einen Benutzer, der docker ohne sudo ausführen kann.

Die Compose-Datei holen

docker-compose.yml im Projekt-Repository ist der Produktions-Stack: die Konsole, beide Datenbanken, openvoxserver und openvoxdb. Kopieren Sie diese eine Datei auf den Host, in ein eigenes Verzeichnis, das Ihrem Benutzer gehört:

sudo mkdir -p /opt/openvox-console sudo chown "$USER": /opt/openvox-console mkdir -p /opt/openvox-console/secrets /opt/openvox-console/certs cd /opt/openvox-console curl -fsSLO https://raw.githubusercontent.com/avitacco/openvox-console/main/docker-compose.yml

Deployen Sie nicht aus einem Checkout des Repositorys. Ein Checkout enthält zusätzlich docker-compose.override.yml, den Entwicklungs-Stack, den ein einfaches docker compose up stillschweigend lädt: Wegwerfpasswörter, offene Datenbankports und automatisches Signieren von Zertifikaten. Jeder Befehl in dieser Anleitung übergibt -f docker-compose.yml, sodass immer nur die Produktionsdatei gelesen wird.

Die eigenen Werte der Installation festlegen

Legen Sie .env neben der Compose-Datei an. Die Compose-Datei verweigert den Start, solange eine der ersten drei Variablen nicht gesetzt ist, sodass eine Installation nicht mit einem Platzhalter hochfahren kann:

CONSOLE_BASE_URL=https://console.example.com CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 OPENVOXDB_POSTGRES_PASSWORD=<a strong password> # Every name nodes or the console use to reach openvoxserver, beyond its # own name "openvoxserver" - see Plan a deployment. OPENVOXSERVER_DNS_ALT_NAMES=puppet.example.com # The Puppet server a node should enroll against, written into the node # install script. Must be one of the names above. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # The first admin user, created only while there are no users. Its # password is a secret file, below. Without this name no admin is # created and nobody can log in. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin # The console's plain-HTTP port, published on loopback only, so the # TLS proxy in front of it is the only way in. See "Put TLS in front of # the console" below. CONSOLE_HTTP_PORT=127.0.0.1:8080

Wählen Sie, welches Konsolen-Image Sie betreiben. CONSOLE_IMAGE_TAG ist standardmäßig main, das dem neuesten Commit folgt. Für eine Installation, die stillhalten soll, legen Sie stattdessen das unveränderliche Tag eines einzelnen Commits fest:

CONSOLE_IMAGE_TAG=sha-a1b2c3d

Versions-Tags wie v1.2.3 sowie latest werden erst veröffentlicht, wenn ein Release erstellt wird. Bis dahin schlägt eine Anfrage nach latest mit manifest unknown fehl.

Die Secrets schreiben

Secrets sind Dateien in secrets/, ein Wert pro Datei, statt Umgebungsvariablen, sodass sie nie in docker inspect erscheinen:

printf '%s' '<console database password>' > secrets/console_postgres_password printf 'postgres://console:%s@console-postgres:5432/console?sslmode=disable' '<console database password>' \ > secrets/console_postgres_dsn printf '%s' '<a strong password, 12 characters or more>' > secrets/console_bootstrap_admin_password chmod 600 secrets/*

Die Datenbank-Verbindungszeichenfolge der Konsole muss dasselbe Passwort wie console_postgres_password verwenden. sslmode=disable ist Absicht: Der Postgres-Container läuft ohne TLS, und die Verbindung verlässt nie das Compose-Netzwerk. TLS zu verlangen würde also nur dazu führen, dass die Konsole keine Verbindung aufbauen kann.

openvoxserver braucht außerdem eine Token-Datei, enc_bridge_token, die Sie befüllen, sobald die Konsole läuft. Legen Sie sie vorerst leer an, denn ohne sie startet openvoxserver nicht:

: > secrets/enc_bridge_token

Die Zertifizierungsstelle starten

openvoxserver ist die CA, von der das Zertifikat jedes anderen Teils stammt. Er startet daher zuerst und allein:

docker compose -f docker-compose.yml up -d openvoxserver

Beim ersten Start wird die CA erzeugt, was ein bis zwei Minuten dauert. Warten Sie, bis er meldet, dass er läuft:

docker compose -f docker-compose.yml exec openvoxserver \ curl -ksS https://127.0.0.1:8140/status/v1/simple

Die Antwort lautet running.

Das Volume openvoxserver-ca ist Ihre Zertifizierungsstelle. Geht es verloren, muss sich jeder Node erneut registrieren. Sichern Sie es und entfernen Sie es nie mit docker compose down -v.

Die Zertifikate der Konsole ausstellen

Die Konsole braucht zwei Zertifikate von der CA und optional ein drittes. Stellen Sie sie im laufenden openvoxserver-Container aus und kopieren Sie sie nach certs/, wo die Compose-Datei sie für die Konsole einbindet.

Das Client-Zertifikat für openvoxdb

So authentifiziert sich die Konsole gegenüber openvoxdb:

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname console docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console.pem certs/console-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console.pem certs/console-key.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/ca.pem certs/ca.pem

puppetserver ca generate gibt zu Beginn Error: Signed certificate console could not be found on the CA aus. Damit prüft der Befehl, ob der Name frei ist; das ist kein Fehlschlag. Entscheidend sind die Zeilen danach, die mit Successfully saved certificate enden.

Das Zertifikat für den Node-Transport

Nodes prüfen dieses Zertifikat, wenn sie sich mit der Konsole verbinden. Es muss daher genau den Namen tragen, den sie anwählen: den Host-Teil von CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR.

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/node-transport.pem certs/node-transport-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/node-transport.pem certs/node-transport-key.pem

Nodes authentifizieren sich ihrerseits mit eigenen Zertifikaten derselben CA, weshalb die Konsole für sie keine weitere Datei braucht.

Der Token-Signaturschlüssel

Die Konsole signiert ihre eigenen Login-Tokens mit einem ES256-Schlüssel. Dieser stammt nicht von der CA. Erzeugen Sie ihn auf einer beliebigen Maschine mit OpenSSL:

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

Sichern Sie diese Datei. Ihr Verlust macht jedes ausgestellte Token ungültig und meldet damit alle ab; gelangt sie nach außen, kann jeder Tokens erzeugen. Siehe Den Token-Signaturschlüssel rotieren, um sie sicher zu ersetzen.

Erzeugen Sie ihn direkt in certs/:

openssl ecparam -genkey -name prime256v1 -noout -out certs/rbac-signing-key.pem

Die Zertifikatsadministrator-Berechtigung (optional)

Diese Berechtigung ermöglicht es der Seite Nodes, den Zertifikatsstatus anzuzeigen und Zertifikate zu signieren, zu widerrufen und zu bereinigen. Ohne sie listet die Konsole nur Nodes auf, die sich bereits verbunden oder gemeldet haben. Ein Node, der darauf wartet, dass sein Zertifikat signiert wird, erscheint überhaupt nicht, weil die CA der einzige Teil ist, der von seiner Existenz weiß.

Diese Berechtigung bedeutet vollen CA-Administratorzugriff. openvoxserver schützt jeden CA-Endpunkt mit einer einzigen Autorisierungserweiterung, sodass ein Zertifikat, das Status lesen kann, auch das Zertifikat jedes Nodes signieren, widerrufen und bereinigen kann. Eine Nur-Lese-Variante gibt es nicht. Bewahren Sie sie nur dort auf, wo die Konsole läuft, und lesen Sie Node-Zertifikate verwalten, bevor Sie sie ausstellen.

Das Ausstellen schreibt in den CA-Zustand, in den auch ein laufender openvoxserver schreibt. Stoppen Sie daher zuerst openvoxserver und stellen Sie es aus einem einmaligen Container mit denselben Volumes aus. Compose benennt Volumes nach dem Projektverzeichnis, prüfen Sie also zuerst die genauen Namen:

docker volume ls | grep openvoxserver

Dann, mit den beiden ausgegebenen Namen:

docker compose -f docker-compose.yml stop openvoxserver docker run --rm --entrypoint "" \ -v openvox-console_openvoxserver-ssl:/etc/puppetlabs/puppet/ssl \ -v openvox-console_openvoxserver-ca:/etc/puppetlabs/puppetserver/ca \ ghcr.io/avitacco/openvox-console-server:main \ puppetserver ca generate --ca-client --force --certname console-ca-client docker compose -f docker-compose.yml start openvoxserver

--force ist hier erforderlich. Vor dem Signieren prüft der Befehl, ob der Server wirklich gestoppt ist, und in einem nackten Container kann er das nicht feststellen. Ohne --force gibt er daher „Could not determine whether Puppet Server is online“ aus und beendet sich, ohne etwas erzeugt zu haben. Lesen Sie seine Ausgabe, statt anzunehmen, dass es funktioniert hat.

Er meldet, dass er seine Dateien unter einem langen .puppetlabs-Pfad ablegt. Ignorieren Sie das: In den Volumes landen sie am üblichen Ort. Kopieren Sie sie heraus:

docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem certs/ca-client-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem certs/ca-client-key.pem

Teilen Sie der Konsole dann in .env mit, wo die CA ist. Innerhalb des Compose-Netzwerks erreicht die Konsole openvoxserver über seinen Containernamen, der immer im Zertifikat von openvoxserver steht:

CONSOLE_CA_CLIENT_URL=https://openvoxserver:8140

Prüfen Sie aus openvoxserver heraus, ob die Berechtigung akzeptiert wird:

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://openvoxserver:8140/puppet-ca/v1/certificate_statuses/all

HTTP 200 bedeutet, dass die CA es akzeptiert.

Tasks

Das Ausführen von Puppet-Tasks braucht nichts weiter. Die Konsole fragt openvoxserver unter https://openvoxserver:8140, welche Tasks Ihr deployter Code enthält, mit dem bereits ausgestellten openvoxdb-Client-Zertifikat; openvoxserver lässt jedes Zertifikat seiner CA Tasks lesen. Um Tasks auszuschalten, setzen Sie die Adresse in .env auf einen leeren Wert:

CONSOLE_PUPPET_SERVER_URL=

Siehe Jobs ausführen zum Ausführen.

Die Klassenliste

Die Seite einer Node-Gruppe bietet die Klassen an, die Ihr deployter Code definiert, mit ihren Parametern, sodass sie ausgewählt statt eingetippt werden. Die Konsole liest sie über dieselbe Verbindung wie Tasks von openvoxserver.

openvoxserver lässt standardmäßig kein Zertifikat Klassen lesen. Das Server-Image in der Compose-Datei fügt die Regel bei jedem Start hinzu und erlaubt das Zertifikat namens console – das oben ausgestellte openvoxdb-Client-Zertifikat. Haben Sie es unter einem anderen Namen ausgestellt, setzen Sie diesen Namen in .env:

CLASS_DISCOVERY_CERTNAME=my-console-cert

Prüfen Sie es aus openvoxserver heraus, mit dem Zertifikat der Konsole. HTTP 200 bedeutet, dass die Liste gelesen werden kann:

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ 'https://openvoxserver:8140/puppet/v3/environment_classes?environment=production'

HTTP 403 bedeutet, dass die Regel dieses Zertifikat nicht nennt. Nichts anderes hängt davon ab: Die Gruppenseite meldet dann, dass die Liste nicht verfügbar ist, und Klassen werden per Namen eingegeben, wie vor der Einführung der Liste. Siehe Nodes klassifizieren.

Alles Übrige starten

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

openvoxdb fordert beim ersten Start sein eigenes Zertifikat bei der CA an. Die Compose-Datei signiert genau diese eine Anfrage automatisch, über eine Allowlist, die nur openvoxdb enthält; Nodes werden nie auf diese Weise signiert. openvoxdb wartet dann auf seine Datenbank, und die Konsole wartet auf beide. Beobachten Sie, wie sie hochfahren:

docker compose -f docker-compose.yml ps

Jeder Dienst erreicht innerhalb weniger Minuten healthy.

Wenn openvoxdb nie gesund wird

openvoxdb gibt auf, wenn seine Zertifikatsanfrage nicht innerhalb von zwei Minuten signiert wird, und schreibt in diesem Fall den Fehler in seine eigene Zertifikatsdatei. Jeder Neustart danach sieht eine Zertifikatsdatei, überspringt die Registrierung und schlägt mit No certs found in 'ssl-cert' file fehl. Es erholt sich nicht von selbst. Setzen Sie seine Identität zurück, statt es neu zu starten:

docker compose -f docker-compose.yml rm -sf openvoxdb docker volume rm openvox-console_openvoxdb-ssl docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca clean --certname openvoxdb docker compose -f docker-compose.yml up -d openvoxdb

Der Volume-Name richtet sich nach dem Namen des Projektverzeichnisses; prüfen Sie ihn mit docker volume ls. Wird ca clean übersprungen, hält die CA ein signiertes Zertifikat für openvoxdb ohne passenden Schlüssel, und der Neustart schlägt mit No keypair on disk and CA already has signed certificate fehl.

TLS vor die Konsole stellen

Die Konsole stellt ihre Weboberfläche und API über einfaches HTTP bereit. Die https://-Basis-URL wird über einen Reverse Proxy erreicht, der TLS terminiert und Anfragen an die Konsole weiterreicht. Jeder Reverse Proxy funktioniert. Hier wird Caddy auf dem Host der Konsole verwendet:

Debian und Ubuntusudo apt-get install -y caddy RHEL, Rocky und AlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

Dies ist dann die gesamte /etc/caddy/Caddyfile:

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

Lauscht die Konsole auf einem anderen Port, weil sie sich einen Host mit openvoxdb teilt, tragen Sie stattdessen diesen Port in reverse_proxy ein.

Für einen Namen, den das Internet auflösen kann, beschafft und erneuert Caddy das Zertifikat selbst. Für einen internen Namen geben Sie ihm mit einer Zeile tls <cert file> <key file> innerhalb des Blocks ein Zertifikat Ihrer eigenen CA. Für einen Test lässt tls internal Caddy eines aus einer eigenen lokalen CA ausstellen, wovor Browser warnen.

Nur die Weboberfläche läuft über den Proxy. Der Node-Transport auf Port 8142 bringt sein eigenes TLS mit und prüft das Zertifikat jedes Nodes selbst, daher müssen Nodes ihn direkt erreichen. Stellen Sie ihn niemals hinter den Proxy.

Erstmals anmelden

Beim ersten Start legt die Konsole ihr Datenbankschema an und erstellt dann den Bootstrap-Administrator, solange die Benutzertabelle noch leer ist. Sobald sie läuft, zeigt ihr Log drei Zeilen:

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

Prüfen Sie, ob sie sich als gesund meldet, zuerst direkt auf dem Host der Konsole, dann über den TLS-Proxy unter ihrer Basis-URL:

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

Jede Antwort führt jede Abhängigkeit als ok auf. Schlägt nur die zweite fehl, ist die Konsole in Ordnung, der Proxy aber nicht. Verwenden Sie in der ersten den eigenen Port der Konsole, falls Sie sie von 8080 verlegt haben. Öffnen Sie dann die Basis-URL der Konsole, melden Sie sich als Bootstrap-Administrator an und ändern Sie sofort dessen Passwort.

Das Passwort des Bootstrap-Administrators muss mindestens 12 Zeichen haben und darf nicht mit seinem Benutzernamen übereinstimmen. Andernfalls wird kein Administrator angelegt, und niemand kann sich anmelden. Das Log sagt es:

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

Setzen Sie ein längeres Passwort und starten Sie die Konsole erneut. Siehe Passwörter und Sperre.

Sobald Sie sich angemeldet und das Passwort geändert haben, entfernen Sie die Bootstrap-Administrator-Einstellungen aus der Konfiguration der Konsole. Sie werden nur gelesen, solange die Benutzertabelle leer ist, aber es gibt keinen Grund, ein Passwort herumliegen zu lassen.

Klassifizierung anbinden

openvoxserver fragt die Konsole über Puppets standardmäßigen exec-Node-Terminus, welche Klassen jeder Node erhält. Ein kleines Programm, enc-bridge, stellt diese Anfrage im Namen von openvoxserver und braucht dafür ein Token.

enc-bridge ein Token ausstellen

Ein Service-Token trägt einen festen Satz von Berechtigungen, die bei seiner Erstellung gewählt werden, ohne dass eine Rolle beteiligt ist. Erstellen Sie eines, das nur Klassifizierung lesen darf:

  1. Öffnen Sie in der Konsole Verwaltung und dann Service-Tokens.
  2. Benennen Sie es unter Neues Service-Token enc-bridge und geben Sie ihm nur die Berechtigung enc:read.
  3. Wählen Sie Service-Token erstellen.

Das Token wird einmal angezeigt. Kopieren Sie es jetzt.

Dasselbe über die API, mit einem Access-Token aus einer Administrator-Anmeldung: curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

openvoxserver das Token geben

Das openvoxserver-Image enthält bereits enc-bridge, die Puppet-Konfiguration, die es nutzt, und die Hiera-Funktion, mit der Nodes Konfigurationsdaten lesen können, sodass es nur noch das Token braucht. Schreiben Sie es in die Secret-Datei, die Sie zuvor leer angelegt haben:

printf '%s' '<the enc:read service token>' > secrets/enc_bridge_token

openvoxserver läuft in seinem Container nicht als root, und Compose bindet Secret-Dateien mit ihren Eigentumsrechten auf dem Host ein. Eine Datei, die nur Ihr eigener Benutzer lesen kann, ist für openvoxserver daher nicht lesbar, und die Klassifizierung schlägt fehl. Geben Sie stattdessen Gruppe 0 Lesezugriff und schützen Sie das Verzeichnis:

sudo chgrp 0 secrets/enc_bridge_token chmod 640 secrets/enc_bridge_token chmod 700 secrets

Erstellen Sie openvoxserver neu, damit er das neue Token liest:

docker compose -f docker-compose.yml up -d --force-recreate openvoxserver

Klassifizierung prüfen

Fragen Sie enc-bridge direkt ab, so wie openvoxserver es ausführt. Das prüft das Programm, das Token, die Dateiberechtigungen und die Antwort der Konsole in einem einzigen Befehl:

docker compose -f docker-compose.yml exec -u puppet:0 openvoxserver \ /usr/local/bin/enc-bridge <a certname>

{} bedeutet, dass die Klassifizierung funktioniert und dieser Node noch zu keiner Gruppe passt. Legen Sie auf der Seite Gruppen der Konsole eine Node-Gruppe an, die diesen Certname fest zuordnet, führen Sie denselben Befehl erneut aus, und seine Klassen werden zurückgegeben:

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

Ein Fehler an dieser Stelle ist genau das, was Sie abfangen wollen. permission denied bedeutet, dass das Token für den Benutzer, unter dem openvoxserver läuft, nicht lesbar ist, und ein 401 bedeutet, dass das Token falsch ist oder ihm enc:read fehlt.

Wenn der nächste Puppet-Lauf eines Nodes mit Could not find class <name> fehlschlägt, funktioniert die Klassifizierung: Die Konsole hat openvoxserver angewiesen, eine Klasse einzubinden, die Ihr Puppet-Code noch nicht definiert.

openvoxserver speichert Environments zwischen. Leeren Sie daher nach dem Hinzufügen von Puppet-Code seinen Cache, sonst bleibt derselbe Fehler bestehen:

docker compose -f docker-compose.yml exec openvoxserver sh -c \ 'curl -ksS -X DELETE \ --cert /etc/puppetlabs/puppet/ssl/certs/openvoxserver.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/openvoxserver.pem \ https://127.0.0.1:8140/puppet-admin-api/v1/environment-cache'

Später aktualisieren

Um auf eine neuere Konsole zu wechseln, ändern Sie CONSOLE_IMAGE_TAG (oder ziehen Sie erneut, wenn Sie main folgen) und fahren Sie den Stack wieder hoch. Compose erstellt nur neu, was sich geändert hat:

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

Die Compose-Datei veröffentlicht den Port von openvoxdb nicht. Fragen Sie es für die folgende Prüfung daher aus seinem Container heraus ab: docker compose -f docker-compose.yml exec openvoxdb curl -ksS https://127.0.0.1:8081/status/v1/simple
