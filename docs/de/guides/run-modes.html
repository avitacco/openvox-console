Skalierung

Betriebsmodi

Was jeder Betriebsmodus der Konsole bedient und betreibt und was jeder davon an Konfiguration braucht.

Ein Image, ein Binary. CONSOLE_RUN_MODE wählt, welche Teile der Konsole eine Instanz betreibt, damit Teile mit sehr unterschiedlicher Last getrennt skaliert und platziert werden können. Nicht gesetzt ist er all: alles in einer Instanz, was eine Installation mit einer Instanz immer betreibt.

Was jeder Modus betreibt

Modus Bedient Lauscht auf Läuft im Hintergrund
all (der Standard) alles HTTP, Node-Transport jede Hintergrundaufgabe
web die Konsole, ihre API, Code-Deploy-Webhooks und Klassifizierung HTTP Verfolgen der darüber gestarteten Jobs
enc nur Klassifizierung HTTP nichts
orchestrator nichts außer Health und Metriken HTTP, Node-Transport Job-Verteilung, geplante Jobs, der erste Lauf neuer Nodes und Upgrades des Node-Agenten
worker nichts außer Health und Metriken HTTP Synchronisierungen von Sicherheitslücken und Aufräumen verwaister Jobs

Jeder Modus stellt /health und /metrics bereit, sodass jede Instanz geprüft werden kann, ohne ihren Modus zu kennen, und /health meldet den Modus, in dem sie läuft.

Zwei Entscheidungen in dieser Tabelle sind bewusst getroffen:

  • web beantwortet ebenfalls Klassifizierungsanfragen. enc existiert, damit die Klassifizierung eigenständig neben den Compilern laufen kann, nicht damit sie überall sonst fehlt. Eine Aufteilung, die stillschweigend aufhört, Nodes zu klassifizieren, wäre weit schlimmer, als dass web einen Teil dieser Last trägt.
  • orchestrator stellt keine API bereit. Er hält die Node-Verbindungen und schickt Jobs darüber. Einen Job zu starten ist Aufgabe von web, und web erreicht diese Verbindungen über den Cluster.
  • Ein Job wird von der Instanz verfolgt, die ihn gestartet hat. Ein in der Konsole gestarteter Lauf, Task oder Plan wird von der web-Instanz gesendet und verfolgt, die die Anfrage entgegengenommen hat. web-Instanzen müssen daher mit den orchestrator-Instanzen geclustert sein, um einen Node zu erreichen. Stoppt diese web-Instanz, bevor der Job endet, markiert eine worker-Instanz den Job als fehlgeschlagen.

Was jeder Modus braucht

Jeder Modus verlangt nur, was er nutzt, und verweigert ohne es den Start, wobei er die fehlende Einstellung nennt:

Modus Erfordert
jeder Modus CONSOLE_POSTGRES_DSN und die vier CONSOLE_OPENVOXDB_*-Einstellungen
all, web CONSOLE_RBAC_SIGNING_KEY_FILE: Nur diese Modi stellen Login-Tokens aus
enc, orchestrator, worker CONSOLE_RBAC_VERIFICATION_KEYS_DIR: Sie prüfen Tokens, stellen aber nie welche aus
orchestrator CONSOLE_NODE_TRANSPORT_ADDR: Ohne Node-Listener würde jeder Job auf einer gesund wirkenden Instanz mit „not connected“ fehlschlagen

Dem Scheduler geben, was geplante Jobs nutzen

Geplante Jobs werden von all- und orchestrator-Instanzen gestartet, nicht von web. Eine orchestrator-Instanz startet auch ohne Folgendes, aber ein Zeitplan, der es braucht, wird mit Begründung übersprungen, bis die Instanz es hat:

  • CONSOLE_PUPPET_SERVER_URL, um einen geplanten Task zu starten: Der Task wird beim Start des Zeitplans im deployten Code nachgeschlagen.
  • CONSOLE_SECRETS_KEY_FILE, derselbe Schlüssel wie auf web, um einen geplanten Task mit einem sensiblen Parameter zu starten.

Betreiben mehrere Instanzen den Scheduler, wird jeder Fälligkeitszeitpunkt von genau einer davon gestartet. Läuft keine, wenn ein Zeitplan fällig wird, startet er, sobald eine läuft – es sei denn, das ist mehr als 15 Minuten zu spät; dann wird dieser Zeitpunkt als verpasst verzeichnet.

Nicht ausstellenden Modi die Verifizierungsschlüssel geben

Eine Instanz, die Tokens nur prüft, liest die Schlüssel, gegen die sie prüft, aus einem Verzeichnis, eine Datei pro Schlüssel, benannt nach der ID des Schlüssels. Eine Installation, die ihren Schlüssel nie rotiert hat, verwendet die ID default. Das Verzeichnis enthält also eine Datei, default.pem, die die Signaturschlüsseldatei selbst ist:

sudo install -d -m 0750 -o root -g openvox-console /etc/openvox-console/rbac-verification-keys sudo install -m 0640 -o root -g openvox-console \ rbac-signing-key.pem /etc/openvox-console/rbac-verification-keys/default.pem CONSOLE_RUN_MODE=enc CONSOLE_RBAC_VERIFICATION_KEYS_DIR=/etc/openvox-console/rbac-verification-keys

Das Verifizierungsverzeichnis akzeptiert Schlüssel derzeit nur im selben Format wie den Signaturschlüssel: den privaten Schlüssel, von dem die Konsole nur die öffentliche Hälfte nutzt. Eine Instanz, die das Verzeichnis erhält, hält also auch einen Schlüssel, der Tokens signieren könnte. Schützen Sie ihn auf jedem Host genau wie den Signaturschlüssel, auch auf enc-Instanzen neben den Compilern.

Wenn Sie den Signaturschlüssel rotieren, braucht auch das Verifizierungsverzeichnis jeder Instanz den neuen Schlüssel; Den Token-Signaturschlüssel rotieren beschreibt die Reihenfolge.

Den Modus einer Instanz ändern

Setzen Sie CONSOLE_RUN_MODE und starten Sie die Instanz neu. Es werden keine Daten verschoben: Jeder Modus liest und schreibt dieselbe Datenbank. Den Wert wieder auf all zu setzen macht die Änderung rückgängig.

Eine einzelne Instanz kann ihren Modus wechseln, aber ein anderer Modus als all ergibt nur unter geclusterten Instanzen Sinn, die zusammen jeden Modus betreiben. Siehe Weitere Instanzen betreiben.
