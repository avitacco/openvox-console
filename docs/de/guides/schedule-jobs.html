Nutzung

Jobs planen

Speichern Sie einen Puppet-Lauf, einen Task oder einen Plan, um ihn später zu starten, einmal oder wiederholt, auf Nodes, die bei jedem Start neu ermittelt werden.

Ein Zeitplan ist ein Puppet-Lauf, ein Task oder ein Plan, der so gespeichert ist, dass er von selbst startet: einmal, zu einer von Ihnen gewählten Zeit, oder wiederholt. Er tut, was derselbe Job täte, wenn Sie ihn in diesem Moment von Hand starten würden – siehe Jobs ausführen –, und bei jedem Start wird er wie jeder andere als Job verzeichnet.

Zeitpläne zu erstellen und zu ändern erfordert orchestrator:run; sie zu sehen erfordert orchestrator:read.

Einen Zeitplan erstellen

Öffnen Sie Jobs, dann Geplante Jobs und dann Neuer Zeitplan. Oder füllen Sie irgendwo Puppet ausführen, Task ausführen oder Plan ausführen aus und wählen Sie Stattdessen planen, was dasselbe Formular mit Ihren Eingaben öffnet. Von der Seite einer Node-Gruppe aus plant das die Gruppe ein, nicht die Nodes, die heute darin sind.

  1. Geben Sie ihm einen Namen. Von ihm gestartete Jobs werden damit beschriftet.
  2. Wählen Sie Was ausgeführt wird: Puppet, mit beliebigen Laufoptionen; einen Task mit seinen Parametern; oder einen Plan, ausgewählt aus den gespeicherten Plänen.
  3. Wählen Sie Welche Nodes: eine Liste, eine Abfrage oder eine Node-Gruppe, wie in Die Nodes wählen. Nodes anzeigen zeigt, worauf er jetzt laufen würde.
  4. Wählen Sie Wann: die Startzeit und, falls er sich wiederholen soll, wie oft.
  5. Zeitplan speichern.

Die Konsole prüft einen Zeitplan beim Speichern genau so, wie sie den Job prüfen würde, wenn Sie ihn jetzt starteten, und lehnt ihn mit der Begründung neben dem fehlerhaften Teil ab. Ein Unterschied: Eine Abfrage oder Gruppe, die noch auf keine Nodes zutrifft, kann gespeichert werden.

Nodes werden jedes Mal neu ermittelt

Eine Abfrage oder eine Node-Gruppe wird bei jedem Start des Zeitplans neu ausgewertet. Ein Node, der der Gruppe nächste Woche beitritt, ist nächste Woche dabei; ein Node, der nicht mehr auf die Abfrage passt, bleibt außen vor.

Zeiten und Wiederholung

Zeiten werden in der Zeitzone Ihres Browsers eingegeben und angezeigt, die das Formular nennt. Jemand in einer anderen Zone sieht denselben Zeitpunkt in seiner.

Ein Zeitplan ohne Wiederholung startet einmal und wird danach als Abgeschlossen angezeigt. Ein wiederkehrender Zeitplan startet zu seiner Startzeit und danach alle so und so viele Minuten, Stunden, Tage oder Wochen. Die kürzeste Wiederholung beträgt 5 Minuten.

Eine Wiederholung ist eine feste Zeitspanne: Ein Tag sind 24 Stunden und eine Woche sieben davon. Wo die Uhren für die Sommerzeit umgestellt werden, hält ein täglicher Zeitplan seine Zeit in UTC und verschiebt sich auf der lokalen Uhr um eine Stunde. Kalenderregeln wie „der erste Montag“ gibt es nicht.

Einem wiederkehrenden Zeitplan kann eine Startzeit in der Vergangenheit gegeben werden. Er startet dann bei seiner ersten noch bevorstehenden Wiederholung.

Als wer ein Zeitplan läuft

Ein Zeitplan läuft als sein Besitzer: die Person, die ihn zuletzt gespeichert hat. Bei jedem Start wendet die Konsole die Rollen des Besitzers so an, wie sie in diesem Moment sind, nicht wie zum Zeitpunkt des Speicherns:

  • Kann der Besitzer keine Jobs mehr ausführen – weil seine Rolle entfernt oder sein Konto oder Service-Token gelöscht wurde –, wird nichts gestartet.
  • Ist die Rolle des Besitzers auf bestimmten Node-Gruppen gewährt, liefert eine Abfrage oder eine Gruppe die passenden Nodes in diesen Gruppen. In einer Liste genannte Nodes müssen alle noch darin sein, sonst wird nichts gestartet.
  • Ist die Rolle des Besitzers auf einige Tasks beschränkt, startet der Zeitplan nur Tasks, die er noch ausführen darf, und nur auf den Nodes, auf denen er sie ausführen darf. Das Speichern eines Zeitplans für einen Task, den Sie nicht ausführen dürfen, wird mit Nennung des Tasks abgelehnt.

Das Speichern einer Änderung an einem Zeitplan macht Sie zu seinem Besitzer, und das Formular weist darauf hin, wenn Sie den einer anderen Person öffnen. So übernehmen Sie einen Zeitplan von jemandem, der gegangen ist: Öffnen und speichern Sie ihn. Pausieren und Fortsetzen ändern den Besitzer nicht.

Sie können die Zeitpläne sehen und ändern, die Ihnen gehören. Jemand, dessen Rolle auf All Nodes gewährt ist, kann die aller sehen und ändern. Siehe Benutzer, Rollen und Tokens.

Wenn ein Zeitplan nicht startet

Die Seite eines Zeitplans listet auf, was jedes Mal geschehen ist, wenn er fällig wurde.

Ergebnis Was es bedeutet
Gestartet Ein Job wurde gestartet. Die Zeile verlinkt darauf.
Übersprungen Es wurde nichts gestartet, aus dem angezeigten Grund. Der Zeitplan setzt zu seinem nächsten Zeitpunkt fort.
Verpasst Als er fällig wurde, lief keine Konsole mit dem Scheduler, und als wieder eine lief, war es mehr als 15 Minuten zu spät.
Unterbrochen Die Konsoleninstanz, die ihn starten sollte, wurde gestoppt, bevor sie es konnte.

Ein Zeitplan wird übersprungen, wenn:

  • seine Abfrage oder Gruppe auf keine Nodes zutrifft oder auf keine, auf die der Besitzer wirken darf;
  • sein Besitzer keine Jobs mehr ausführen darf oder ein von ihm genannter Node die Node-Gruppen des Besitzers verlassen hat;
  • sein Task oder einer der Tasks seines Plans von den Rollen seines Besitzers nicht mehr erlaubt wird (die Auslösung nennt den Task und bei einem Plan den Schritt) – siehe Eine Rolle auf einige Tasks beschränken;
  • sein Task, ein Task-Parameter, sein Environment oder seine Node-Gruppe nicht mehr so existiert, wie der Zeitplan sie beschreibt;
  • openvoxdb oder der Puppet-Server nicht erreichbar war, um die Nodes oder den Task zu ermitteln;
  • der Job, den er beim letzten Mal gestartet hat, noch läuft.

Eine Auslösung, die nicht gestartet ist, wird nie wiederholt. Ein Lauf für 02:00 Uhr startet nicht um 09:00 Uhr, weil die Konsole über Nacht ausgefallen war, und ein Task wird für einen Fälligkeitszeitpunkt nie zweimal gestartet. Ein wiederkehrender Zeitplan, der über mehrere Wiederholungen hinweg verpasst wurde, verzeichnet eine verpasste Auslösung und setzt zu seinem nächsten Zeitpunkt fort.

Übersprungene und verpasste Auslösungen werden außerdem auf der Seite Aktivität verzeichnet, und die Liste Geplante Jobs zeigt das letzte Ergebnis jedes Zeitplans.

Ein Node, der beim Start eines Zeitplans nicht verbunden ist, schlägt in diesem Job mit „agent not connected“ fehl, wie bei einem von Hand gestarteten Job; für die anderen Nodes startet der Job trotzdem.

Ein geplanter Plan behält seine eigenen Schritte

Wenn Sie einen Plan wählen, übernimmt der Zeitplan eine Kopie seiner Schritte und zeigt sie an. Ab dann führt der Zeitplan diese Kopie aus. Das Ändern oder Löschen des gespeicherten Plans ändert nicht, was der Zeitplan ausführt.

Um eine Änderung am Plan zu übernehmen, bearbeiten Sie den Zeitplan, wählen unter Plan erneut den Plan und speichern. Bleibt Plan auf „Die unten gezeigten Schritte behalten“, bleibt die Kopie unverändert.

Der Grund ist, dass ein Zeitplan mit dem Zugriff seines Besitzers läuft, während jeder, der Jobs ausführen darf, einen Plan ändern kann – siehe Pläne ausführen.

Kann ein Schritt nicht mehr ausgeführt werden, wenn der Zeitplan fällig wird – etwa weil sein Task aus dem Code entfernt wurde –, wird nichts gestartet, und dieser Zeitpunkt wird als Übersprungen verzeichnet, mit Nennung des Schritts.

Einen Zeitplan pausieren, ändern oder löschen

Auf der Seite des Zeitplans:

  • Pausieren verhindert, dass er fällig wird. Fortsetzen startet ihn wieder ab seinem nächsten noch bevorstehenden Zeitpunkt; für die verstrichenen Zeitpunkte wird nichts gestartet. Ein Zeitplan ohne Wiederholung, dessen Zeitpunkt während der Pause verstrichen ist, braucht stattdessen eine neue Startzeit.
  • Bearbeiten öffnet das Formular. Beim Speichern wird es erneut geprüft, wie ein neuer Zeitplan.
  • Löschen entfernt ihn. Die Jobs, die er gestartet hat, bleiben im Job-Verlauf und nennen ihn weiterhin.

Das Löschen einer Node-Gruppe löscht nicht die Zeitpläne, die sie als Ziel haben. Diese werden übersprungen, mit dem Hinweis, dass die Gruppe nicht mehr existiert, bis Sie sie ändern oder löschen.

Sensible Task-Parameter

Ein als sensitive markierter Task-Parameter – ein Passwort, ein Token – muss bis zum Start des Zeitplans aufbewahrt werden. Die Konsole speichert ihn mit ihrem Secrets-Schlüssel verschlüsselt und zeigt überall dort, wo der Zeitplan oder seine Jobs erscheinen, Sensitive [value redacted]. Dasselbe gilt für die sensiblen Werte der Task-Schritte eines geplanten Plans, die das Zeitplanformular unter jedem Schritt abfragt.

  • Ohne Secrets-Schlüssel wird ein Zeitplan mit einem sensiblen Wert abgelehnt. Setzen Sie CONSOLE_SECRETS_KEY_FILE – siehe Sicherheitslücken verfolgen, das denselben Schlüssel verwendet – auf jeder Instanz, die die Konsole bereitstellt oder den Scheduler betreibt.
  • Wenn Sie Ihren eigenen Zeitplan bearbeiten, lassen Sie ein sensibles Feld leer, um den gespeicherten Wert zu behalten.
  • Wenn Sie den Zeitplan einer anderen Person speichern, müssen Sie dessen sensible Werte erneut eingeben. Die Konsole gibt ein gespeichertes Secret nicht an einen neuen Besitzer weiter.
  • Ändert sich der Secrets-Schlüssel, können die gespeicherten Werte nicht mehr gelesen werden. Der Zeitplan wird mit entsprechendem Hinweis übersprungen, bis er erneut mit den Werten gespeichert wird.

Über die API

curl -X POST https://console.example.com/api/v1/orchestrator/schedules \ -H "Authorization: Bearer <access token>" \ -H 'Content-Type: application/json' \ -d '{"name":"Weekly no-op", "kind":"run", "options":{"noop":true}, "group":12, "startAt":"2026-01-04T03:00:00Z", "repeat":{"every":1,"unit":"week"}}'

kind ist run (mit options), task (mit task, params, environment und timeoutSeconds, wie in einer Task-Anfrage) oder plan (mit planName und steps, wie in einer Plan-Anfrage). Die Nodes sind targets, query oder group. repeat.unit ist minute, hour, day oder week; lassen Sie repeat für einen Zeitplan weg, der einmal startet.

Anfrage Bewirkt
GET /api/v1/orchestrator/schedules listet die Zeitpläne auf, die Sie sehen können
GET /api/v1/orchestrator/schedules/<id> ein Zeitplan, mit dem, was jedes Mal geschah, wenn er fällig wurde
PUT /api/v1/orchestrator/schedules/<id> ersetzt ihn und macht Sie zu seinem Besitzer
POST /api/v1/orchestrator/schedules/<id>/pause und /resume pausiert ihn oder setzt ihn fort
DELETE /api/v1/orchestrator/schedules/<id> löscht ihn

Eine abgelehnte Anfrage antwortet mit 400 (oder 403 für einen Node außerhalb Ihrer Node-Gruppen), einem error und einem field, das den betroffenen Teil des Zeitplans nennt – und bei einem Plan mit dem abgelehnten step. Ein Zeitplan, der einem Service-Token gehört, läuft, solange dieses Token existiert und orchestrator:run hält.

Wo Zeitpläne gestartet werden

Zeitpläne werden von Instanzen in den Betriebsmodi all und orchestrator gestartet. Laufen mehrere, wird jeder Fälligkeitszeitpunkt von genau einer davon gestartet.
