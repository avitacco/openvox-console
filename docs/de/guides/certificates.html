Nodes

Node-Zertifikate verwalten

Node-Zertifikate aus der Konsole signieren, widerrufen und bereinigen, und was jede Aktion mit einem verbundenen Node macht.

Die Identität jedes Nodes ist ein Zertifikat der CA von openvoxserver. Mit konfigurierter Zertifikatsadministrator-Berechtigung zeigt die Seite Nodes der Konsole den Zustand jedes Zertifikats und lässt Sie damit arbeiten.

Zertifikatsverwaltung einschalten

Die Zertifikatsverwaltung braucht die Zertifikatsadministrator-Berechtigung, die bei der Installation ausgestellt wird. Beide Installationsanleitungen beschreiben, wie sie ausgestellt wird. Die Konsole verwendet sie, wenn alle vier Einstellungen vorhanden sind:

Einstellung Was es ist
CONSOLE_CA_CLIENT_URL Adresse von openvoxserver, wie die Konsole ihn erreicht
CONSOLE_CA_CLIENT_CERT_FILE das Zertifikat der Berechtigung
CONSOLE_CA_CLIENT_KEY_FILE sein privater Schlüssel
CONSOLE_CA_CLIENT_CA_FILE das CA-Bundle, um openvoxserver zu verifizieren

Ist auch nur eine davon nicht gesetzt, lautet der Zertifikatszustand jedes Nodes unknown, und der Rest der Konsole funktioniert wie gewohnt.

Die Berechtigung bedeutet vollen CA-Administratorzugriff: Alles, was sie nutzen kann, kann das Zertifikat jedes Nodes signieren, widerrufen und bereinigen. openvoxserver bietet keine engere Variante. Halten Sie ihren Schlüssel nur für die Konsole lesbar.

Festlegen, wer mit Zertifikaten arbeiten darf

Zwei Berechtigungen sind beteiligt, und sie liegen bewusst weit auseinander:

Berechtigung Erlaubt
nodes:read jeden Node und seinen Zertifikatszustand ansehen
nodes:certs:manage Zertifikate signieren, widerrufen und bereinigen

nodes:certs:manage zu gewähren entspricht einem Shell-Zugang zur CA: Es gibt keine Möglichkeit, das Signieren zu erlauben, das Widerrufen aber nicht, oder einen Node, einen anderen aber nicht. Geben Sie diese Berechtigung bestimmten vertrauenswürdigen Operatoren, nicht jedem, der den Node-Status sehen muss.

Ein Team seine eigenen Nodes signieren lassen

Eine Rolle, die auf bestimmten Node-Gruppen gewährt ist, kann nur auf Zertifikate von Nodes in diesen Gruppen wirken – siehe Benutzer, Rollen und Tokens. Ein neuer Node, der auf Signierung wartet, hat noch nie Puppet ausgeführt, hat also keine Facts und fällt unter keine Gruppenregel. Damit ein Team ihn signieren kann, weisen Sie seinen Namen zuerst fest der Gruppe des Teams zu:

  1. Öffnen Sie Gruppen und die Gruppe des Teams. Die Gruppe muss direkt unter All Nodes stehen; eine feste Zuweisung in einer tieferen Gruppe zählt nur, wenn der Node auch jeder Gruppe darüber fest zugewiesen ist.
  2. Fügen Sie unter Fest zugewiesene Nodes den Namen des Nodes genau so hinzu, wie er sich registrieren wird, und speichern Sie. Das erfordert classifier:write.
  3. Die Inhaber von nodes:certs:manage im Team sehen die Anfrage nun auf der Seite Nodes und können sie signieren.

Sobald der Node Puppet ausgeführt hat, ordnen seine Facts ihn wie gewohnt Gruppen zu, und die feste Zuweisung kann entfernt werden. Jeder, dessen Rolle auf All Nodes gewährt ist, signiert wie bisher jede Anfrage.

Signieren, widerrufen oder bereinigen

Auf der Seite Nodes ist der Zertifikatszustand jedes Nodes einer von requested, signed, revoked oder unknown, und die angebotenen Aktionen ergeben sich daraus:

Aktion Verfügbar, wenn Was sie kann
Signieren requested Stellt das Zertifikat des Nodes aus, damit er sich authentifizieren kann
Widerrufen signed Sorgt dafür, dass das Zertifikat nirgends mehr akzeptiert wird, endgültig
Bereinigen jeder bekannte Zustand Widerruft das Zertifikat bei Bedarf und entfernt dann den Eintrag der CA für den Certname vollständig

„Bereinigen“ verwenden Sie, bevor sich ein Node unter demselben Namen erneut registriert: Sobald der Eintrag weg ist, kann der Certname eine neue Anfrage stellen.

Eine Aktion, die die CA ablehnt, etwa das Signieren eines Zertifikats, das nicht auf Signierung wartet, schlägt mit Begründung fehl und ändert nichts. Jede abgeschlossene Aktion wird als node.certificate.signed, node.certificate.revoked oder node.certificate.cleaned ins Audit-Protokoll geschrieben.

Was ein Widerruf mit einem verbundenen Node macht

Ein über die Konsole widerrufener oder bereinigter Node wird sofort abgeschnitten. Jede Konsoleninstanz wird benachrichtigt, und diejenige, die die Verbindung des Nodes hält, schließt sie. Jede Instanz ruft außerdem zuerst die aktuelle Sperrliste der CA ab, sodass sich der Node nicht einfach neu verbinden kann.

Zertifikate, die außerhalb der Konsole mit puppetserver ca revoke auf dem CA-Host widerrufen werden, werden ebenfalls erfasst: Jede Instanz liest die Sperrliste jede Minute neu und trennt jede aktive Verbindung, die sie nun als widerrufen erkennt.

Die Sperrliste stammt aus einer von zwei Quellen:

  • die in CONSOLE_NODE_TRANSPORT_CRL_FILE angegebene Datei, typischerweise die crl.pem des eigenen Puppet-Agenten auf dem Konsolen-Host, die der Agent aktuell hält. Ist diese Einstellung gesetzt, die Datei aber nicht lesbar, verweigert die Konsole den Start;
  • andernfalls die CA selbst, über die Zertifikatsadministrator-Berechtigung.

Ist keine von beiden vorhanden, protokolliert die Konsole beim Start eine Warnung: Ein widerrufenes Node-Zertifikat kann sich dann weiterhin verbinden.

Infrastrukturzertifikate

Die Seite „Nodes“ listet jeden Certname auf, den die CA kennt, einschließlich der eigenen Zertifikate der Konsole und derer der Server, mit denen sie spricht: console, node-transport, console-ca-client, openvoxdb und openvoxserver bei einer Standardinstallation. Diese werden automatisch erkannt und standardmäßig ausgeblendet. Infrastruktur-Zertifikate anzeigen blendet sie markiert ein, und das Widerrufen oder Bereinigen eines davon verlangt eine Bestätigung, die nennt, was dadurch kaputtginge.

Die Zertifikatsadministrator-Berechtigung ausmustern

Da sie vollen CA-Administratorzugriff gewährt, bereinigen Sie die Berechtigung, sobald sie nicht mehr gebraucht wird, etwa wenn eine Konsoleninstanz außer Betrieb genommen wird. Auf dem CA-Host:

sudo /opt/puppetlabs/bin/puppetserver ca clean --certname console-ca-client

Entfernen Sie dann die vier CONSOLE_CA_CLIENT_*-Einstellungen aus jeder Konsole, die noch damit konfiguriert ist. Eine Konsole, die noch die bereinigte Berechtigung hält, meldet einfach jedes Zertifikat als unknown; sonst funktioniert alles weiter.
