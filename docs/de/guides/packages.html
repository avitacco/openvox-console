Installation

Installation aus Paketen und Binaries

Installieren Sie openvoxserver, openvoxdb und Postgres aus Paketen, bauen Sie die Konsole und betreiben Sie sie als systemd-Dienst.

Diese Anleitung installiert openvoxserver, openvoxdb und Postgres aus den OpenVox- und Distributionspaketen und betreibt die Konsole als einzelnes Binary unter systemd. Klären Sie die Namen in Eine Installation planen, bevor Sie beginnen.

Die Befehle gelten für Debian und Ubuntu, mit dem Gegenstück für RHEL, Rocky Linux und AlmaLinux daneben, wo es abweicht. Die Teile können auf einem oder mehreren Hosts liegen; wo ein Schritt auf einen bestimmten Host gehört, ist das angegeben.

openvoxserver installieren

openvoxserver ist die Zertifizierungsstelle, von der das Zertifikat jedes anderen Teils stammt, daher kommt er zuerst. Fügen Sie das Repository für OpenVox 8 hinzu und installieren Sie ihn:

Debian und Ubuntu. /etc/os-release curl -fsSL -o /tmp/openvox8-release.deb \ "https://apt.voxpupuli.org/openvox8-release-${ID}${VERSION_ID}.deb" sudo apt-get install -y /tmp/openvox8-release.deb sudo apt-get update && sudo apt-get install -y openvox-server RHEL, Rocky und AlmaLinuxsudo dnf install -y https://yum.voxpupuli.org/openvox8-release-el-9.noarch.rpm sudo dnf install -y openvox-server

Das Paket erzeugt die CA nicht selbst. Sein erster Start erzeugt die CA und das eigene Zertifikat dieses Servers, ausgestellt für den Certname des Hosts, normalerweise seinen vollqualifizierten Namen. Im Normalfall müssen Sie ihn nur noch starten:

sudo systemctl enable --now puppetserver

Führen Sie puppetserver ca setup nicht auf einem Host aus, der bereits eine CA hat. Der Befehl erstellt nur eine CA, die noch nicht existiert, und bei einer vorhandenen bricht er mit „Existing file at .../ca_crt.pem“ ab. Diese Dateien zu löschen, wie die Meldung nahelegt, zerstört Ihre CA und jedes Zertifikat, das sie je ausgestellt hat, einschließlich der Zertifikate aller registrierten Nodes.

Die CA alternative Namen signieren lassen

Das Node-Transport-Zertifikat der Konsole und, falls Sie es unten neu ausstellen, das eigene Zertifikat dieses Servers tragen mehr als einen Namen. Standardmäßig verweigert die CA das Signieren einer solchen Anfrage und lässt sie warten; erlauben Sie es daher einmalig. Fügen Sie in /etc/puppetlabs/puppetserver/conf.d/ca.conf die Einstellung innerhalb des Blocks certificate-authority hinzu:

certificate-authority: { allow-subject-alt-names: true ... } sudo systemctl restart puppetserver

Die Namen seines Zertifikats prüfen

Ein Zertifikat gilt immer für seinen eigenen Certname. Wenn Nodes und Konsole diesen Server beide über seinen Certname erreichen, müssen Sie nichts ändern. Andernfalls prüfen Sie, welche Namen das Zertifikat bereits abdeckt:

sudo openssl x509 -in /etc/puppetlabs/puppet/ssl/certs/$(hostname -f).pem \ -noout -subject -ext subjectAltName

Fehlt ein Name aus Ihrem Plan, stellen Sie nur das eigene Zertifikat dieses Servers neu aus, niemals die CA. dns_alt_names nachträglich zu setzen ändert ein bereits vorhandenes Zertifikat nicht. Bereinigen und erzeugen Sie es daher neu, während der Server läuft:

sudo /opt/puppetlabs/bin/puppetserver ca clean --certname $(hostname -f) sudo /opt/puppetlabs/bin/puppetserver ca generate --certname $(hostname -f) \ --subject-alt-names puppet.example.com,openvoxserver sudo systemctl restart puppetserver

Auf einem frischen Host können Sie die Namen stattdessen vor dem ersten Start setzen und diesen Start das Zertifikat damit erzeugen lassen: sudo /opt/puppetlabs/bin/puppet config set --section server dns_alt_names puppet.example.com,openvoxserver

Prüfen, ob er läuft

curl -ksS https://puppet.example.com:8140/status/v1/simple

Die Antwort lautet running.

openvoxdb und seine Datenbank installieren

Den Host von openvoxdb registrieren

openvoxdb fordert selbst kein Zertifikat an: Seine Einrichtung kopiert das, das sein Host bereits hat. Hat openvoxdb einen eigenen Host, registrieren Sie diesen Host zuerst bei der CA und signieren Sie dann seine Anfrage auf der CA, falls die CA nicht automatisch signiert:

sudo /opt/puppetlabs/bin/puppet ssl bootstrap --server puppet.example.com # on the CA host: sudo /opt/puppetlabs/bin/puppetserver ca sign --certname <openvoxdb host>

Überspringen Sie dies, wenn openvoxdb sich einen Host mit openvoxserver teilt, der bereits ein Zertifikat hat.

Seine Datenbank anlegen

openvoxdb braucht eine eigene Postgres-Datenbank, die das Paket nicht anlegt:

Debian und Ubuntusudo apt-get install -y postgresql sudo systemctl enable --now postgresql RHEL, Rocky und AlmaLinuxsudo dnf install -y postgresql-server postgresql-contrib sudo postgresql-setup --initdb # Accept passwords over local connections, which are refused by the # default "ident" rules, and store passwords to match. sudo sed -i -E 's/^(host .*)(ident)$/\1scram-sha-256/' /var/lib/pgsql/data/pg_hba.conf echo "password_encryption = 'scram-sha-256'" | sudo tee -a /var/lib/pgsql/data/postgresql.conf sudo systemctl enable --now postgresql

Unter RHEL und seinen Nachbauten stammt pg_trgm weiter unten aus postgresql-contrib, und die Passwortänderung muss vor dem Anlegen der Benutzer erfolgen: Ein vorher gespeichertes Passwort kann von den neuen Regeln nicht geprüft werden.

sudo -u postgres createuser --pwprompt puppetdb sudo -u postgres createdb --owner=puppetdb puppetdb # openvoxdb refuses to start without this extension, and creating it # needs superuser rights - so it is run as postgres, not as puppetdb. sudo -u postgres psql -d puppetdb -c 'CREATE EXTENSION IF NOT EXISTS pg_trgm;'

Prüfen Sie, ob Postgres Verbindungen annimmt:

pg_isready

Die Antwort endet mit accepting connections.

Unter Debian und Ubuntu zeigt systemctl status postgresql active (exited) an, und das ist normal: Diese Unit startet nur die eigentliche Unit pro Cluster. pg_lsclusters zeigt den Cluster selbst als online.

openvoxdb installieren und starten

Debian und Ubuntusudo apt-get install -y openvoxdb RHEL, Rocky und AlmaLinuxsudo dnf install -y openvoxdb

Teilen Sie ihm mit, wo seine Datenbank ist. Ohne diese Datei startet es nicht und beendet sich mit No subname set in the "database" config.:

[database] subname = //localhost:5432/puppetdb username = puppetdb password = <the password you set above>

Speichern Sie das als /etc/puppetlabs/puppetdb/conf.d/database.ini, mit dem Namen des Datenbank-Hosts statt localhost, falls dieser anderswo steht, und schränken Sie den Zugriff ein:

sudo chown puppetdb:puppetdb /etc/puppetlabs/puppetdb/conf.d/database.ini sudo chmod 640 /etc/puppetlabs/puppetdb/conf.d/database.ini

Kopieren Sie dann die Zertifikate des Hosts an ihren Platz und starten Sie es:

sudo /opt/puppetlabs/bin/puppetdb ssl-setup sudo systemctl enable --now puppetdb

Startet er nicht, steht der eigentliche Grund in /var/log/puppetlabs/puppetdb/puppetdb.log; der Fehler von systemd ist meist nur die Folge.

Kataloge und Reports dorthin senden

Installieren Sie auf dem openvoxserver-Host den Terminus, der Kataloge und Reports an openvoxdb sendet:

Debian und Ubuntusudo apt-get install -y openvoxdb-termini RHEL, Rocky und AlmaLinuxsudo dnf install -y openvoxdb-termini

Prüfen, ob er läuft

Der HTTPS-Port von openvoxdb verlangt ein Client-Zertifikat, fragen Sie also mit dem eigenen Zertifikat des Hosts. Ohne eines lautet die Antwort certificate required:

H=$(hostname -f) sudo curl -sS --cert /etc/puppetlabs/puppet/ssl/certs/$H.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/$H.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://$H:8081/status/v1/simple

Die Antwort lautet running. Das Log meldet möglicherweise, dass „the read-database user is not configured properly“. Das betrifft einen separaten Nur-Lese-Benutzer, den diese Anleitung nicht einrichtet, und openvoxdb läuft ohne ihn.

Die Datenbank der Konsole anlegen

Die Konsole hält ihre eigenen Daten in einer von openvoxdb getrennten Datenbank. Ihr Schema legt sie beim ersten Start selbst an; sie braucht nur eine leere Datenbank und eine Rolle, der sie gehört. Auf dem Postgres-Host:

sudo -u postgres createuser --pwprompt console sudo -u postgres createdb --owner=console console

Läuft die Konsole auf einem anderen Host, muss Postgres auch im Netzwerk lauschen. Standardmäßig lauscht es nur auf localhost, daher wird eine entfernte Verbindung abgelehnt, obwohl pg_isready lokal erfolgreich ist. Erlauben Sie den Host oder das Subnetz der Konsole und passen Sie den Adressbereich an:

Debian und Ubuntusudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /etc/postgresql/*/main/pg_hba.conf sudo systemctl restart postgresql@*-main.service RHEL, Rocky und AlmaLinuxsudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /var/lib/pgsql/data/pg_hba.conf sudo systemctl restart postgresql

Prüfen Sie vom Host der Konsole aus, ob sich die Rolle der Konsole verbinden kann (psql kommt dort mit dem Paket postgresql-client):

PGPASSWORD='<password>' psql -h <postgres host> -U console -d console -c 'select 1;'

Behalten Sie die einfachen Anführungszeichen bei. Ein Passwort mit $ wird sonst von der Shell expandiert, bevor psql es sieht.

Die Zertifikate der Konsole ausstellen

Die Konsole braucht zwei Zertifikate von der CA und optional ein drittes. Erzeugen Sie sie auf dem openvoxserver-Host und kopieren Sie sie dann auf den Host der Konsole, nach /etc/openvox-console/. Legen Sie dieses Verzeichnis zuerst auf dem Host der Konsole an, mit dem Benutzer, unter dem die Konsole laufen wird:

sudo useradd --system --home-dir /nonexistent --shell /usr/sbin/nologin openvox-console sudo install -d -m 0750 -o root -g openvox-console /etc/openvox-console

Das Client-Zertifikat für openvoxdb

So authentifiziert sich die Konsole gegenüber openvoxdb:

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname console

puppetserver ca generate gibt zu Beginn Error: Signed certificate console could not be found on the CA aus. Damit prüft der Befehl, ob der Name frei ist; das ist kein Fehlschlag. Entscheidend sind die Zeilen danach, die mit Successfully saved certificate enden.

Es schreibt drei Dateien, die die Konsole braucht. Kopieren Sie sie unter diesen Namen hinüber:

Auf dem openvoxserver-Host Auf dem Konsolen-Host
/etc/puppetlabs/puppet/ssl/certs/console.pem /etc/openvox-console/console-cert.pem
/etc/puppetlabs/puppet/ssl/private_keys/console.pem /etc/openvox-console/console-key.pem
/etc/puppetlabs/puppet/ssl/certs/ca.pem /etc/openvox-console/ca.pem

Das Zertifikat für den Node-Transport

Nodes prüfen dieses Zertifikat, wenn sie sich mit der Konsole verbinden. Es muss daher genau den Namen tragen, den sie anwählen: den Host-Teil von CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR.

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport

Kopieren Sie certs/node-transport.pem und private_keys/node-transport.pem auf dieselbe Weise hinüber, als node-transport-cert.pem und node-transport-key.pem. Nodes authentifizieren sich ihrerseits mit eigenen Zertifikaten derselben CA, daher braucht die Konsole für sie nichts weiter.

Der Token-Signaturschlüssel

Die Konsole signiert ihre eigenen Login-Tokens mit einem ES256-Schlüssel. Dieser stammt nicht von der CA. Erzeugen Sie ihn auf einer beliebigen Maschine mit OpenSSL:

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

Sichern Sie diese Datei. Ihr Verlust macht jedes ausgestellte Token ungültig und meldet damit alle ab; gelangt sie nach außen, kann jeder Tokens erzeugen. Siehe Den Token-Signaturschlüssel rotieren, um sie sicher zu ersetzen.

Erzeugen Sie ihn auf dem Host der Konsole, in /etc/openvox-console/.

Die Zertifikatsadministrator-Berechtigung (optional)

Diese Berechtigung ermöglicht es der Seite Nodes, den Zertifikatsstatus anzuzeigen und Zertifikate zu signieren, zu widerrufen und zu bereinigen. Ohne sie listet die Konsole nur Nodes auf, die sich bereits verbunden oder gemeldet haben. Ein Node, der darauf wartet, dass sein Zertifikat signiert wird, erscheint überhaupt nicht, weil die CA der einzige Teil ist, der von seiner Existenz weiß.

Diese Berechtigung bedeutet vollen CA-Administratorzugriff. openvoxserver schützt jeden CA-Endpunkt mit einer einzigen Autorisierungserweiterung, sodass ein Zertifikat, das Status lesen kann, auch das Zertifikat jedes Nodes signieren, widerrufen und bereinigen kann. Eine Nur-Lese-Variante gibt es nicht. Bewahren Sie sie nur dort auf, wo die Konsole läuft, und lesen Sie Node-Zertifikate verwalten, bevor Sie sie ausstellen.

Das Ausstellen schreibt in den CA-Zustand, in den auch der laufende Server schreibt. Stoppen Sie daher openvoxserver, während es ausgestellt wird:

sudo systemctl stop puppetserver sudo /opt/puppetlabs/bin/puppetserver ca generate --ca-client --certname console-ca-client sudo systemctl start puppetserver

Kopieren Sie certs/console-ca-client.pem und private_keys/console-ca-client.pem als ca-client-cert.pem und ca-client-key.pem hinüber. Prüfen Sie dann vom Host der Konsole aus, ob die CA sie akzeptiert:

curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/ca-client-cert.pem \ --key /etc/openvox-console/ca-client-key.pem \ --cacert /etc/openvox-console/ca.pem \ https://puppet.example.com:8140/puppet-ca/v1/certificate_statuses/all

HTTP 200 bedeutet, dass es funktioniert.

Die Konsole bauen

Die Konsole ist ein einzelnes Binary mit eingebauter Weboberfläche. Es gibt kein Paket davon; bauen Sie sie aus dem Quell-Repository. Sie brauchen Go in der in go.mod genannten Version sowie git.

git clone https://github.com/avitacco/openvox-console.git cd openvox-console

Die Konsole stellt außerdem den Node-Agenten bereit, den Nodes installieren, aus ihrem eigenen Paket-Repository, und diese Agenten sind in das Binary der Konsole eingebaut. Bauen Sie sie zuerst, sonst schlägt jede Node-Installation mit einem 404 fehl:

make agent-binaries make agent-packages make build

Übrig bleiben bin/console und bin/enc-bridge. Installieren Sie die Konsole auf ihrem Host:

sudo install -m 0755 bin/console /usr/local/bin/console

Die Konsole konfigurieren

Die Konsole wird ausschließlich über Umgebungsvariablen konfiguriert, in einer Datei im Verzeichnis /etc/openvox-console/, das Sie für ihre Zertifikate angelegt haben.

Sechs Einstellungen sind erforderlich, und ohne sie verweigert die Konsole den Start und nennt die fehlende. Tragen Sie sie in /etc/openvox-console/console.env ein:

CONSOLE_POSTGRES_DSN=postgres://console:<password>@<postgres host>:5432/console?sslmode=require CONSOLE_OPENVOXDB_URL=https://<openvoxdb host>:8081 CONSOLE_OPENVOXDB_CERT_FILE=/etc/openvox-console/console-cert.pem CONSOLE_OPENVOXDB_KEY_FILE=/etc/openvox-console/console-key.pem CONSOLE_OPENVOXDB_CA_FILE=/etc/openvox-console/ca.pem CONSOLE_RBAC_SIGNING_KEY_FILE=/etc/openvox-console/rbac-signing-key.pem

sslmode=require setzt voraus, dass Ihr Postgres TLS anbietet, was es tun sollte, sobald die Verbindung den Host verlässt. Wenn sich Konsole und Postgres einen Host teilen und Postgres kein Zertifikat hat, verwenden Sie sslmode=disable.

Der Rest ist optional, und jede optionale Funktion schaltet sich selbst ab, statt den Start zu blockieren. Für eine echte Installation ergänzen Sie:

# Where the console listens, and how the outside world reaches it. It # listens on loopback only: the TLS proxy in front of it is the way in. # On a host shared with openvoxdb, which holds 8080, use 127.0.0.1:8088. CONSOLE_HTTP_ADDR=127.0.0.1:8080 CONSOLE_BASE_URL=https://console.example.com # The first admin user, created only while there are no users. The # password needs at least 12 characters. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin CONSOLE_BOOTSTRAP_ADMIN_PASSWORD=<a strong password> # The node transport. ADDR is what the console binds; PUBLIC_ADDR is what # a node dials, and its host must be in the node transport certificate. CONSOLE_NODE_TRANSPORT_ADDR=:8142 CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 CONSOLE_NODE_TRANSPORT_CERT_FILE=/etc/openvox-console/node-transport-cert.pem CONSOLE_NODE_TRANSPORT_KEY_FILE=/etc/openvox-console/node-transport-key.pem CONSOLE_NODE_TRANSPORT_CA_FILE=/etc/openvox-console/ca.pem # The Puppet server a node should enroll against, written into the node # install script. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # Certificate management from the Nodes page (the optional credential). CONSOLE_CA_CLIENT_URL=https://puppet.example.com:8140 CONSOLE_CA_CLIENT_CERT_FILE=/etc/openvox-console/ca-client-cert.pem CONSOLE_CA_CLIENT_KEY_FILE=/etc/openvox-console/ca-client-key.pem CONSOLE_CA_CLIENT_CA_FILE=/etc/openvox-console/ca.pem # Puppet tasks: where the console asks which tasks your deployed code # contains. Uses the openvoxdb client certificate above unless you name # another with CONSOLE_PUPPET_SERVER_CERT_FILE, _KEY_FILE and _CA_FILE. CONSOLE_PUPPET_SERVER_URL=https://puppet.example.com:8140

Tasks brauchen kein eigenes Zertifikat: openvoxserver lässt jedes Zertifikat seiner CA Tasks lesen, sodass das openvoxdb-Client-Zertifikat genügt. Richten Sie sie nicht auf die Zertifikatsadministrator-Berechtigung, die weit mehr kann, als das Lesen von Tasks erfordert. Siehe Jobs ausführen zum Ausführen.

Die Konsole die Klassenliste lesen lassen

Die Seite einer Node-Gruppe bietet die Klassen an, die Ihr deployter Code definiert, mit ihren Parametern, sodass sie ausgewählt statt eingetippt werden. Die Konsole liest sie über dieselbe Verbindung wie Tasks von openvoxserver, aber openvoxserver lässt kein Zertifikat Klassen lesen, bis eine Regel es erlaubt.

Fügen Sie auf dem Host von openvoxserver diese Regel zur Liste rules in /etc/puppetlabs/puppetserver/conf.d/auth.conf hinzu, oberhalb der abschließenden Regel puppetlabs deny all. console ist der Name des oben ausgestellten openvoxdb-Client-Zertifikats:

{ match-request: { path: "/puppet/v3/environment_classes" type: path method: get } allow: "console" sort-order: 500 name: "openvox console class discovery" },

Laden Sie dann openvoxserver neu:

sudo systemctl reload puppetserver

Prüfen Sie es vom Host der Konsole aus. HTTP 200 bedeutet, dass die Liste gelesen werden kann:

sudo curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/console-cert.pem \ --key /etc/openvox-console/console-key.pem \ --cacert /etc/openvox-console/ca.pem \ 'https://puppet.example.com:8140/puppet/v3/environment_classes?environment=production'

HTTP 403 bedeutet, dass die Regel fehlt oder ein anderes Zertifikat nennt. Nichts anderes hängt von diesem Schritt ab: Ohne ihn meldet die Gruppenseite, dass die Liste nicht verfügbar ist, und Klassen werden per Namen eingegeben. Siehe Nodes klassifizieren.

Secrets in Dateien aufbewahren

Jede Einstellung kann stattdessen aus einer Datei gelesen werden: Geben Sie die Datei in einer Einstellung an, deren Name auf _FILE endet. So bleiben Passwörter aus der Prozessumgebung heraus:

CONSOLE_POSTGRES_DSN_FILE=/etc/openvox-console/postgres-dsn CONSOLE_BOOTSTRAP_ADMIN_PASSWORD_FILE=/etc/openvox-console/bootstrap-admin-password

Ein abschließender Zeilenumbruch in der Datei wird ignoriert. Eine angegebene Datei, die nicht gelesen werden kann, verhindert den Start der Konsole, statt sie mit stillschweigend leerem Wert starten zu lassen.

Machen Sie zum Schluss jede Datei für den Benutzer der Konsole lesbar und für niemanden sonst:

sudo sh -c 'chown root:openvox-console /etc/openvox-console/* && chmod 0640 /etc/openvox-console/*'

Das sh -c ist wichtig: Ihre eigene Shell kann dieses Verzeichnis nicht auflisten, daher schlägt ein einfaches sudo chown ... /etc/openvox-console/* mit „No such file or directory“ fehl.

Unter systemd betreiben

Legen Sie /etc/systemd/system/openvox-console.service an:

[Unit] Description=OpenVox Console After=network-online.target Wants=network-online.target [Service] EnvironmentFile=/etc/openvox-console/console.env ExecStart=/usr/local/bin/console Restart=on-failure User=openvox-console Group=openvox-console [Install] WantedBy=multi-user.target

Starten Sie sie dann:

sudo systemctl daemon-reload sudo systemctl enable --now openvox-console journalctl -u openvox-console -f

TLS vor die Konsole stellen

Die Konsole stellt ihre Weboberfläche und API über einfaches HTTP bereit. Die https://-Basis-URL wird über einen Reverse Proxy erreicht, der TLS terminiert und Anfragen an die Konsole weiterreicht. Jeder Reverse Proxy funktioniert. Hier wird Caddy auf dem Host der Konsole verwendet:

Debian und Ubuntusudo apt-get install -y caddy RHEL, Rocky und AlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

Dies ist dann die gesamte /etc/caddy/Caddyfile:

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

Lauscht die Konsole auf einem anderen Port, weil sie sich einen Host mit openvoxdb teilt, tragen Sie stattdessen diesen Port in reverse_proxy ein.

Für einen Namen, den das Internet auflösen kann, beschafft und erneuert Caddy das Zertifikat selbst. Für einen internen Namen geben Sie ihm mit einer Zeile tls <cert file> <key file> innerhalb des Blocks ein Zertifikat Ihrer eigenen CA. Für einen Test lässt tls internal Caddy eines aus einer eigenen lokalen CA ausstellen, wovor Browser warnen.

Nur die Weboberfläche läuft über den Proxy. Der Node-Transport auf Port 8142 bringt sein eigenes TLS mit und prüft das Zertifikat jedes Nodes selbst, daher müssen Nodes ihn direkt erreichen. Stellen Sie ihn niemals hinter den Proxy.

Erstmals anmelden

Beim ersten Start legt die Konsole ihr Datenbankschema an und erstellt dann den Bootstrap-Administrator, solange die Benutzertabelle noch leer ist. Sobald sie läuft, zeigt ihr Log drei Zeilen:

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

Prüfen Sie, ob sie sich als gesund meldet, zuerst direkt auf dem Host der Konsole, dann über den TLS-Proxy unter ihrer Basis-URL:

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

Jede Antwort führt jede Abhängigkeit als ok auf. Schlägt nur die zweite fehl, ist die Konsole in Ordnung, der Proxy aber nicht. Verwenden Sie in der ersten den eigenen Port der Konsole, falls Sie sie von 8080 verlegt haben. Öffnen Sie dann die Basis-URL der Konsole, melden Sie sich als Bootstrap-Administrator an und ändern Sie sofort dessen Passwort.

Das Passwort des Bootstrap-Administrators muss mindestens 12 Zeichen haben und darf nicht mit seinem Benutzernamen übereinstimmen. Andernfalls wird kein Administrator angelegt, und niemand kann sich anmelden. Das Log sagt es:

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

Setzen Sie ein längeres Passwort und starten Sie die Konsole erneut. Siehe Passwörter und Sperre.

Sobald Sie sich angemeldet und das Passwort geändert haben, entfernen Sie die Bootstrap-Administrator-Einstellungen aus der Konfiguration der Konsole. Sie werden nur gelesen, solange die Benutzertabelle leer ist, aber es gibt keinen Grund, ein Passwort herumliegen zu lassen.

Klassifizierung anbinden

openvoxserver fragt die Konsole über Puppets standardmäßigen exec-Node-Terminus, welche Klassen jeder Node erhält. Ein kleines Programm, enc-bridge, stellt diese Anfrage im Namen von openvoxserver und braucht dafür ein Token.

enc-bridge ein Token ausstellen

Ein Service-Token trägt einen festen Satz von Berechtigungen, die bei seiner Erstellung gewählt werden, ohne dass eine Rolle beteiligt ist. Erstellen Sie eines, das nur Klassifizierung lesen darf:

  1. Öffnen Sie in der Konsole Verwaltung und dann Service-Tokens.
  2. Benennen Sie es unter Neues Service-Token enc-bridge und geben Sie ihm nur die Berechtigung enc:read.
  3. Wählen Sie Service-Token erstellen.

Das Token wird einmal angezeigt. Kopieren Sie es jetzt.

Dasselbe über die API, mit einem Access-Token aus einer Administrator-Anmeldung: curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

enc-bridge auf dem Host von openvoxserver installieren

Kopieren Sie bin/enc-bridge aus Ihrem Build auf den openvoxserver-Host und installieren Sie es:

sudo install -m 0755 enc-bridge /usr/local/bin/enc-bridge

Speichern Sie das Token so, dass nur der Benutzer von openvoxserver es lesen kann:

printf '%s' '<the enc:read service token>' | sudo tee /etc/puppetlabs/enc-bridge-token >/dev/null sudo chown root:puppet /etc/puppetlabs/enc-bridge-token sudo chmod 0640 /etc/puppetlabs/enc-bridge-token

enc-bridge liest den Ort der Konsole und sein Token aus seiner Umgebung, die es von openvoxserver erbt. Geben Sie openvoxserver beides mit sudo systemctl edit puppetserver:

[Service] Environment=ENC_BRIDGE_URL=https://console.example.com Environment=ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token

enc-bridge prüft das Zertifikat der Konsole gegen den System-Zertifikatsspeicher des openvoxserver-Hosts. Stammt das Zertifikat des Proxys von Ihrer eigenen CA, fügen Sie diese CA dem Speicher hinzu, sonst schlägt die Klassifizierung mit certificate signed by unknown authority fehl:

Debian und Ubuntusudo cp <your CA>.crt /usr/local/share/ca-certificates/ sudo update-ca-certificates RHEL, Rocky und AlmaLinuxsudo cp <your CA>.crt /etc/pki/ca-trust/source/anchors/ sudo update-ca-trust

Richten Sie dann Puppet darauf, im Abschnitt [server] von /etc/puppetlabs/puppet/puppet.conf, und starten Sie openvoxserver neu:

[server] node_terminus = exec external_nodes = /usr/local/bin/enc-bridge sudo systemctl restart puppetserver

Nodes Konfigurationsdaten lesen lassen

Optional. Damit können Nodes die auf Node-Gruppen gesetzten Konfigurationsdaten mit lookup() lesen, vor den Hiera-Daten Ihres Control-Repos. Die Funktion führt enc-bridge --data aus und verwendet daher dieselbe Konsolenadresse und dasselbe Token wie die Klassifizierung; weitere Konfiguration ist nicht nötig. Sie braucht ein enc-bridge, das aus dieser Version gebaut wurde.

Die Funktion muss im eigenen Funktionsverzeichnis von Puppet installiert werden, dem einzigen Ort, aus dem openvoxserver eine globale Hiera-Funktion lädt. Aus dem Checkout Ihres Builds:

sudo install -m 0644 openvoxserver-init/console_config_data.rb \ /opt/puppetlabs/puppet/lib/ruby/vendor_ruby/puppet/functions/console_config_data.rb

Fügen Sie sie dann der globalen Hiera-Konfiguration /etc/puppetlabs/puppet/hiera.yaml hinzu, als Erstes in der Hierarchie, damit Konsolendaten gewinnen. Das Paket installiert dort eine Platzhalterdatei; haben Sie diese nicht geändert, ersetzen Sie sie hierdurch:

--- version: 5 hierarchy: - name: "Console configuration data" data_hash: console_config_data

Haben Sie bereits eine globale hiera.yaml, fügen Sie den Eintrag dort hinzu und behalten Sie Ihre eigenen Einträge danach.

sudo systemctl restart puppetserver

Prüfen Sie nach einem Upgrade des Pakets openvox-agent, ob die Datei noch vorhanden ist, und installieren Sie sie andernfalls erneut. Schlägt der Lauf eines Nodes mit „Unable to find 'data_hash' function named 'console_config_data'“ fehl, liegt die Funktion nicht in diesem Verzeichnis. Das Container-Image erledigt all das bei jedem Start selbst.

Klassifizierung prüfen

Führen Sie enc-bridge so aus, wie openvoxserver es tut: als dessen Benutzer, mit denselben Einstellungen. Das prüft das Programm, das Token, die Dateiberechtigungen und die Antwort der Konsole in einem einzigen Befehl:

sudo -u puppet env ENC_BRIDGE_URL=https://console.example.com \ ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token \ /usr/local/bin/enc-bridge <a certname>

{} bedeutet, dass die Klassifizierung funktioniert und dieser Node noch zu keiner Gruppe passt. Legen Sie auf der Seite Gruppen der Konsole eine Node-Gruppe an, die diesen Certname fest zuordnet, führen Sie denselben Befehl erneut aus, und seine Klassen werden zurückgegeben:

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

Ein Fehler an dieser Stelle ist genau das, was Sie abfangen wollen. permission denied bedeutet, dass das Token für den Benutzer, unter dem openvoxserver läuft, nicht lesbar ist, und ein 401 bedeutet, dass das Token falsch ist oder ihm enc:read fehlt.

Wenn der nächste Puppet-Lauf eines Nodes mit Could not find class <name> fehlschlägt, funktioniert die Klassifizierung: Die Konsole hat openvoxserver angewiesen, eine Klasse einzubinden, die Ihr Puppet-Code noch nicht definiert.

Später aktualisieren

Um auf eine neuere Konsole zu wechseln, holen Sie den Quellcode, bauen in derselben Reihenfolge neu, installieren das neue Binary und starten neu:

git pull make agent-binaries make agent-packages make build sudo install -m 0755 bin/console /usr/local/bin/console sudo systemctl restart openvox-console
