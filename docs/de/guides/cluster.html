Skalierung

Weitere Instanzen betreiben

Clustern Sie eine zweite Konsoleninstanz, teilen Sie Instanzen in Betriebsmodi auf und platzieren Sie die Klassifizierung neben den Compilern.

Mehrere Konsoleninstanzen teilen sich eine Datenbank und treten einem Cluster bei. Über den Cluster teilen sie einander mit, was jede Instanz sofort erreichen muss – ein widerrufenes Login, ein widerrufenes Node-Zertifikat –, und über ihn erreicht ein auf einer Instanz gestarteter Job einen Node, der mit einer anderen verbunden ist.

Alles Dauerhafte liegt in Postgres. Sobald die Instanzen geclustert sind, kann daher jede Instanz jede Anfrage beantworten, und ein Load Balancer kann Anfragen an die jeweils gesunde schicken.

Instanzen, die sich eine Datenbank teilen, müssen geclustert sein. Eine nicht geclusterte Instanz erfährt von einem widerrufenen Login erst, wenn sie die Widerrufe das nächste Mal aus der Datenbank liest, bis zu 30 Sekunden später, und sie kann die mit einer anderen Instanz verbundenen Nodes nicht erreichen.

Wie Instanzen einander finden

Jede Instanz betreibt einen eingebetteten NATS-Server. Die Core-Modi (all, web, orchestrator und worker) verbinden sich direkt miteinander, als geroutete Peers. enc-Instanzen hängen sich stattdessen als Leaves an: Die Verbindung läuft nur nach außen, von der enc-Instanz zu einer Core-Instanz, sodass der Core nie einen Weg in das Netzwerk braucht, in dem die Compiler stehen.

web-1 --+ web-2 --+-- routed peers (:6222) orch-1 -+ worker -+ ^ | leaf connections, outbound only | (to a core instance's leaf listener, :6223) | enc-1, enc-2 (beside the compilers)

Ein Leaf überträgt die eigenen Nachrichten der Konsole zwischen Instanzen, etwa Widerrufe und Status, und niemals Node-Verkehr: Eine enc-Instanz kann nie einen verwalteten Node erreichen.

Bevor Sie beginnen

Jede Peer-Verbindung ist verschlüsselt und auf zwei Arten authentifiziert:

  • gegenseitiges TLS, mit dem Zertifikat jeder Instanz von der CA. Standardmäßig verwendet eine Instanz dasselbe Zertifikat wie für openvoxdb, das aus CONSOLE_OPENVOXDB_CERT_FILE, sodass nichts Neues ausgestellt werden muss. Ein Peer, der eine Instanz anwählt, prüft, ob ihr Zertifikat für den angewählten Namen gilt. Jede Instanz muss daher unter einem Namen erreicht werden, den ihr Zertifikat trägt.
  • ein gemeinsames Secret, auf jeder Core-Instanz gleich. Auch ein verwalteter Node besitzt ein Zertifikat der CA, und das Secret sorgt dafür, dass sein Zertifikat zum Beitreten nicht ausreicht.

Geben Sie einer Instanz statt des gemeinsamen ein eigenes Zertifikat, muss openvoxserver ihr auch das Lesen der Klassenliste erlauben: Seine Regel nennt das erlaubte Zertifikat, standardmäßig console, und lehnt jedes andere mit HTTP 403 ab. Fügen Sie den Certname jeder web- und all-Instanz zu dieser Regel hinzu, sonst meldet die Gruppenseite auf diesen Instanzen, dass die Liste nicht verfügbar ist. Siehe Installation aus Paketen und Binaries.

Leaves verwenden ein eigenes zweites Secret, das sich vom Cluster-Secret unterscheiden muss: Ein enc-Host ist der am wenigsten vertrauenswürdige Ort, an dem eine Konsole läuft, und darf nicht als vollwertiger Peer beitreten können.

Erzeugen Sie beide Secrets und halten Sie sie mit der _FILE-Form jeder Einstellung aus der Prozessumgebung heraus:

openssl rand -base64 32 > cluster-secret openssl rand -base64 32 > cluster-leaf-secret

Eine zweite Instanz hinzufügen

Beginnen Sie mit zwei all-Instanzen. So wird das Clustering erprobt, bevor eine Rolle ausgelagert wird.

Öffnen Sie auf der ersten Instanz einen Peer-Listener und starten Sie sie neu:

CONSOLE_CLUSTER_ADDR=:6222 CONSOLE_CLUSTER_SECRET_FILE=/etc/openvox-console/cluster-secret

Geben Sie der zweiten dieselbe Datenbank, denselben Token-Signaturschlüssel und dieselben Secrets, einen eigenen Peer-Listener und die erste Instanz als Peer, unter einem Namen aus dem Zertifikat der ersten Instanz:

CONSOLE_CLUSTER_ADDR=:6222 CONSOLE_CLUSTER_PEERS=console-1.example.com:6222 CONSOLE_CLUSTER_SECRET_FILE=/etc/openvox-console/cluster-secret

Nur eine Seite muss die andere benennen. Jede später beitretende Instanz benennt eine beliebige vorhandene, und der Cluster verbindet den Rest.

Die zweite Instanz braucht außerdem einen eigenen Node-Listener und ein eigenes Node-Transport-Zertifikat, falls sich Nodes mit ihr verbinden werden, und jede Instanz braucht dieselbe CONSOLE_BASE_URL, damit Links und Installationsskripte über den Load Balancer zeigen.

Instanzen erfahren die Adressen der anderen über den Cluster selbst, und standardmäßig sind das IP-Adressen, die ein Zertifikat selten enthält. Setzen Sie bei drei oder mehr gerouteten Instanzen mit jeweils eigenem Zertifikat auf jeder CONSOLE_CLUSTER_ADVERTISE auf einen Namen aus ihrem eigenen Zertifikat, etwa console-2.example.com:6222.

Prüfen, ob der Cluster entstanden ist

Jede Instanz protokolliert beim Start cluster joined mit den Peers, die ihr übergeben wurden. Öffnen Sie dann als Benutzer mit der Berechtigung status:read in der Konsole System. Der Tab Flottenstatus listet jede Instanz auf, die geantwortet hat, nach Modus gruppiert; beide Instanzen erscheinen dort.

status:read wird bestehenden Rollen nicht automatisch hinzugefügt. Gewähren Sie es auf der Seite Rollen den Rollen, die die Seite sehen sollen.

Instanzen in Modi aufteilen

Sobald zwei all-Instanzen zusammen laufen, lagern Sie Rollen je nach Last aus: Hintergrundarbeit an worker, Node-Verbindungen an orchestrator, alles, was eine Person nutzt, an web. Setzen Sie auf jeder Instanz CONSOLE_RUN_MODE und starten Sie sie neu; unter Betriebsmodi steht, was jeder Modus braucht, einschließlich der Verifizierungsschlüssel für Modi, die keine Tokens ausstellen.

Jeder Modus kann als mehrere Instanzen laufen:

  • Arbeit, die nur einmal geschehen darf, etwa eine Synchronisierung von Sicherheitslücken, ein Code-Deploy eines Environments oder das Aufräumen verwaister Jobs, wird über die Datenbank koordiniert, sodass nie zwei worker-Instanzen sie beide erledigen;
  • Widerrufe erreichen jede Instanz, sodass die Sicht jeder einzelnen aktuell bleibt;
  • Aktivitäten werden einmal verzeichnet, von der Instanz, auf der sie stattfanden.

Richten Sie den Load Balancer für die Konsole und ihre API auf die web-Instanzen, und richten Sie Nodes über CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR auf den Node-Transport der orchestrator-Instanzen.

Die Klassifizierung neben die Compiler stellen

enc-Instanzen beantworten Klassifizierungsanfragen für die Compiler, neben denen sie stehen, und hängen sich als Leaves an den Cluster.

Öffnen Sie auf einer oder mehreren Core-Instanzen einen Leaf-Listener, geschützt durch das Leaf-Secret:

CONSOLE_CLUSTER_LEAF_ADDR=:6223 CONSOLE_CLUSTER_LEAF_SECRET_FILE=/etc/openvox-console/cluster-leaf-secret

Verbinden Sie sich auf jeder enc-Instanz mit dem Leaf-Listener einer Core-Instanz. Sie hält nur das Leaf-Secret, niemals das Cluster-Secret:

CONSOLE_RUN_MODE=enc CONSOLE_CLUSTER_MODE=leaf CONSOLE_CLUSTER_PEERS=console-1.example.com:6223 CONSOLE_CLUSTER_LEAF_SECRET_FILE=/etc/openvox-console/cluster-leaf-secret CONSOLE_RBAC_VERIFICATION_KEYS_DIR=/etc/openvox-console/rbac-verification-keys

Richten Sie dann das enc-bridge jedes Compilers mit ENC_BRIDGE_URL auf die enc-Instanz daneben.

Die gesamte Flotte prüfen

Der Tab Flottenstatus erstellt sein Bild live, indem er jede Instanz fragt und sammelt, was innerhalb einer Sekunde antwortet. Zwei Dinge daran sollten Sie wissen:

  • Haben weniger Instanzen geantwortet als erwartet, steht das über der Liste, etwa „1 of 4 instances did not reply within 1s“. Nehmen Sie das ernst: Eine Instanz, die läuft, aber die anderen nicht erreicht, hängt meist fest.
  • Jede Abhängigkeit, etwa openvoxdb oder die CA, wird so angezeigt, wie die antwortende Instanz sie sieht. Eine, bei der sich Instanzen uneinig sind, ist als je Instanz unterschiedlich markiert. Das heißt, einige Instanzen erreichen sie und andere nicht.

Die Seite aktualisiert sich nicht selbst; laden Sie sie neu, um ein aktuelles Bild zu erhalten.

Auf verworfene Nachrichten achten

console_nats_async_errors_total auf dem /metrics jeder Instanz zählt Probleme auf ihren Cluster-Verbindungen. Entscheidend ist ein Subscriber, der zurückfällt und dadurch Nachrichten verwirft; jeder solche Fall wird außerdem auf Fehlerebene als „NATS subscriber fell behind; messages were dropped“ protokolliert. Ein steigender Zähler verdient einen Blick.

Rückgängig machen

Jeder Schritt lässt sich rückgängig machen: Setzen Sie CONSOLE_RUN_MODE=all und entfernen Sie die Cluster-Einstellungen. Nichts in der Datenbank hängt von der Aufteilung ab.
