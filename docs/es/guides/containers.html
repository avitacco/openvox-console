Instalar

Instalar con contenedores

Ejecute openvoxserver, openvoxdb, las dos bases de datos y la consola con Docker Compose, de un host vacío a una consola lista para recibir Nodes.

Esta guía ejecuta todo el stack a partir del archivo compose de producción del proyecto y de sus imágenes publicadas. No se compila nada en el host. Fije los nombres en Planificar un despliegue antes de empezar.

Necesita un host Linux con Docker Engine y el plugin de Compose, y un usuario que pueda ejecutar docker sin sudo.

Obtener el archivo compose

docker-compose.yml, en el repositorio del proyecto, es el stack de producción: la consola, las dos bases de datos, openvoxserver y openvoxdb. Copie solo ese archivo al host, en un directorio propio cuyo propietario sea su usuario:

sudo mkdir -p /opt/openvox-console sudo chown "$USER": /opt/openvox-console mkdir -p /opt/openvox-console/secrets /opt/openvox-console/certs cd /opt/openvox-console curl -fsSLO https://raw.githubusercontent.com/avitacco/openvox-console/main/docker-compose.yml

No despliegue desde un checkout del repositorio. Un checkout incluye también docker-compose.override.yml, el stack de desarrollo, que un simple docker compose up carga sin avisar: contraseñas desechables, puertos de base de datos abiertos y firma automática de certificados. Todos los comandos de esta guía pasan -f docker-compose.yml para que solo se lea el archivo de producción.

Definir los valores propios del despliegue

Cree .env junto al archivo compose. El archivo compose se niega a arrancar mientras falte cualquiera de las tres primeras, así que un despliegue no puede levantarse con un valor de relleno:

CONSOLE_BASE_URL=https://console.example.com CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 OPENVOXDB_POSTGRES_PASSWORD=<a strong password> # Every name nodes or the console use to reach openvoxserver, beyond its # own name "openvoxserver" - see Plan a deployment. OPENVOXSERVER_DNS_ALT_NAMES=puppet.example.com # The Puppet server a node should enroll against, written into the node # install script. Must be one of the names above. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # The first admin user, created only while there are no users. Its # password is a secret file, below. Without this name no admin is # created and nobody can log in. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin # The console's plain-HTTP port, published on loopback only, so the # TLS proxy in front of it is the only way in. See "Put TLS in front of # the console" below. CONSOLE_HTTP_PORT=127.0.0.1:8080

Elija qué imagen de la consola ejecutar. CONSOLE_IMAGE_TAG vale por defecto main, que sigue el último commit. Para un despliegue que quiera mantener fijo, fije en su lugar la etiqueta inmutable de un commit concreto:

CONSOLE_IMAGE_TAG=sha-a1b2c3d

Las etiquetas de versión como v1.2.3, y latest, solo se publican cuando se crea una release. Hasta entonces, pedir latest falla con manifest unknown.

Escribir los secretos

Los secretos son archivos en secrets/, un valor por archivo, y no variables de entorno, de modo que nunca aparecen en docker inspect:

printf '%s' '<console database password>' > secrets/console_postgres_password printf 'postgres://console:%s@console-postgres:5432/console?sslmode=disable' '<console database password>' \ > secrets/console_postgres_dsn printf '%s' '<a strong password, 12 characters or more>' > secrets/console_bootstrap_admin_password chmod 600 secrets/*

La cadena de conexión a la base de datos de la consola debe usar la misma contraseña que console_postgres_password. sslmode=disable es deliberado: el contenedor de Postgres funciona sin TLS y la conexión nunca sale de la red de compose, así que pedir TLS solo haría que la consola no pudiera conectarse.

openvoxserver también necesita un archivo de token, enc_bridge_token, que rellenará cuando la consola esté en marcha. Créelo vacío por ahora, porque openvoxserver no arranca sin él:

: > secrets/enc_bridge_token

Arrancar la autoridad de certificación

openvoxserver es la CA de la que procede el certificado de todas las demás partes, así que arranca primero y por sí solo:

docker compose -f docker-compose.yml up -d openvoxserver

Su primer arranque crea la CA, lo que tarda uno o dos minutos. Espere hasta que indique que está en marcha:

docker compose -f docker-compose.yml exec openvoxserver \ curl -ksS https://127.0.0.1:8140/status/v1/simple

La respuesta es running.

El volumen openvoxserver-ca es su autoridad de certificación. Perderlo obliga a que todos los Nodes se incorporen de nuevo. Haga copia de seguridad de él y nunca lo elimine con docker compose down -v.

Emitir los certificados de la consola

La consola necesita dos certificados de la CA y, opcionalmente, un tercero. Emítalos dentro del contenedor de openvoxserver en marcha y cópielos en certs/, donde el archivo compose los monta para la consola.

El certificado de cliente de openvoxdb

Así es como la consola se autentica ante openvoxdb:

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname console docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console.pem certs/console-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console.pem certs/console-key.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/ca.pem certs/ca.pem

puppetserver ca generate empieza imprimiendo Error: Signed certificate console could not be found on the CA. Es la comprobación de que el nombre está libre, no un fallo. Lo que importa son las líneas siguientes, que terminan en Successfully saved certificate.

El certificado del transporte de Nodes

Los Nodes comprueban este certificado al conectarse a la consola, así que debe llevar exactamente el nombre al que se conectan: la parte del host de CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR.

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/node-transport.pem certs/node-transport-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/node-transport.pem certs/node-transport-key.pem

Los Nodes se autentican a su vez con sus propios certificados de la misma CA, por lo que la consola no necesita ningún otro archivo para ellos.

La clave de firma de tokens

La consola firma sus propios tokens de inicio de sesión con una clave ES256. Esta no procede de la CA. Genérela en cualquier máquina con OpenSSL:

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

Haga copia de seguridad de este archivo. Perderlo invalida todos los tokens emitidos, lo que cierra la sesión de todo el mundo; filtrarlo permite a cualquiera fabricar tokens. Consulte Rotar la clave de firma de tokens para sustituirlo de forma segura.

Genérelo directamente en certs/:

openssl ecparam -genkey -name prime256v1 -noout -out certs/rbac-signing-key.pem

La credencial de administración de certificados (opcional)

Esta credencial es la que permite a la página Nodes mostrar el estado de los certificados y firmar, revocar y limpiar certificados. Sin ella, la consola solo lista los Nodes que ya se han conectado o han enviado un Report. Un Node que espera la firma de su certificado no aparece en absoluto, porque la CA es la única parte que sabe que existe.

Esta credencial otorga administración completa de la CA. openvoxserver protege todos los endpoints de la CA con una única extensión de autorización, así que un certificado que puede leer estados también puede firmar, revocar y limpiar el certificado de cualquier Node. No existe una variante de solo lectura. Guárdela solo donde se ejecuta la consola, y lea Gestionar los certificados de los Nodes antes de emitirla.

Emitirlo escribe en el estado de la CA, que un openvoxserver en marcha también escribe, así que detenga primero openvoxserver y emítalo desde un contenedor puntual que use los mismos volúmenes. Compose nombra los volúmenes según el directorio del proyecto, así que compruebe antes los nombres exactos:

docker volume ls | grep openvoxserver

Después, con los dos nombres que imprimió:

docker compose -f docker-compose.yml stop openvoxserver docker run --rm --entrypoint "" \ -v openvox-console_openvoxserver-ssl:/etc/puppetlabs/puppet/ssl \ -v openvox-console_openvoxserver-ca:/etc/puppetlabs/puppetserver/ca \ ghcr.io/avitacco/openvox-console-server:main \ puppetserver ca generate --ca-client --force --certname console-ca-client docker compose -f docker-compose.yml start openvoxserver

Aquí --force es obligatorio. Antes de firmar, el comando comprueba que el servidor está realmente detenido, y dentro de un contenedor sin más no puede saberlo, así que sin --force imprime "Could not determine whether Puppet Server is online" y termina sin haber creado nada. Lea su salida en lugar de dar por hecho que funcionó.

Indica que escribe sus archivos bajo una ruta .puppetlabs larga. Ignórelo: en los volúmenes acaban en el lugar habitual. Cópielos fuera:

docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem certs/ca-client-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem certs/ca-client-key.pem

Después indique a la consola dónde está la CA, en .env. Dentro de la red de compose, la consola accede a openvoxserver por su nombre de contenedor, que siempre figura en el certificado de openvoxserver:

CONSOLE_CA_CLIENT_URL=https://openvoxserver:8140

Confirme, desde dentro de openvoxserver, que la credencial se acepta:

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://openvoxserver:8140/puppet-ca/v1/certificate_statuses/all

HTTP 200 significa que la CA la acepta.

Tasks

Ejecutar Tasks de Puppet no necesita nada más. La consola pregunta a openvoxserver, en https://openvoxserver:8140, qué Tasks contiene su código desplegado, usando el certificado de cliente de openvoxdb que ya emitió; openvoxserver permite que cualquier certificado de su CA lea los Tasks. Para desactivar los Tasks, deje vacía la dirección en .env:

CONSOLE_PUPPET_SERVER_URL=

Consulte Ejecutar Jobs para ejecutarlos.

La lista de clases

La página de un grupo de Nodes ofrece las clases que define su código desplegado, con sus parámetros, para elegirlas en lugar de escribirlas. La consola las lee de openvoxserver por la misma conexión que los Tasks.

Por defecto, openvoxserver no deja que ningún certificado lea clases. La imagen del servidor del archivo compose añade la regla en cada arranque, permitiendo el certificado llamado console, el certificado de cliente de openvoxdb que emitió antes. Si lo emitió con otro nombre, defina ese nombre en .env:

CLASS_DISCOVERY_CERTNAME=my-console-cert

Compruébelo desde dentro de openvoxserver, con el certificado de la consola. HTTP 200 significa que la lista puede leerse:

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ 'https://openvoxserver:8140/puppet/v3/environment_classes?environment=production'

HTTP 403 significa que la regla no nombra este certificado. Nada más depende de ello: la página del grupo indica entonces que la lista no está disponible, y las clases se introducen por nombre, como antes de que existiera la lista. Consulte Clasificar Nodes.

Arrancar todo lo demás

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

openvoxdb solicita su propio certificado a la CA en su primer arranque. El archivo compose firma automáticamente esa única solicitud, mediante una lista de permitidos que solo contiene openvoxdb; los Nodes nunca se firman así. Después openvoxdb espera a su base de datos, y la consola espera a ambos. Observe cómo se levantan:

docker compose -f docker-compose.yml ps

Todos los servicios llegan a healthy en pocos minutos.

Si openvoxdb nunca llega a estar sano

openvoxdb se rinde si su solicitud de certificado no se firma en dos minutos y, cuando lo hace, escribe el fallo en su propio archivo de certificado. Cada reinicio posterior ve un archivo de certificado, se salta la incorporación y falla con No certs found in 'ssl-cert' file. No se recupera por sí solo. Restablezca su identidad en lugar de reiniciarlo:

docker compose -f docker-compose.yml rm -sf openvoxdb docker volume rm openvox-console_openvoxdb-ssl docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca clean --certname openvoxdb docker compose -f docker-compose.yml up -d openvoxdb

El nombre del volumen sigue el nombre del directorio del proyecto; compruébelo con docker volume ls. Si se salta el ca clean, la CA conserva un certificado firmado para openvoxdb sin clave que le corresponda, y el nuevo arranque falla con No keypair on disk and CA already has signed certificate.

Poner TLS delante de la consola

La consola sirve su interfaz web y su API por HTTP sin cifrar. A la URL base https:// se llega a través de un proxy inverso que termina el TLS y pasa las peticiones a la consola. Sirve cualquier proxy inverso. Aquí se usa Caddy, en el host de la consola:

Debian y Ubuntusudo apt-get install -y caddy RHEL, Rocky y AlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

Este es entonces el /etc/caddy/Caddyfile completo:

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

Si la consola escucha en otro puerto porque comparte host con openvoxdb, ponga en su lugar ese puerto en reverse_proxy.

Para un nombre que se puede resolver desde internet, Caddy obtiene y renueva el certificado por sí solo. Para un nombre interno, dele un certificado de su propia CA con una línea tls <cert file> <key file> dentro del bloque. Para una prueba, tls internal hace que Caddy emita uno desde una CA local propia, sobre la que los navegadores advierten.

Solo la interfaz web pasa por el proxy. El transporte de Nodes, en el puerto 8142, lleva su propio TLS y comprueba él mismo el certificado de cada Node, así que los Nodes deben alcanzarlo directamente. No lo ponga nunca detrás del proxy.

Iniciar sesión por primera vez

En su primer arranque, la consola crea el esquema de su base de datos y después crea el administrador inicial mientras la tabla de usuarios sigue vacía. Cuando está en marcha, su log muestra tres líneas:

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

Compruebe que se declara en buen estado, primero directamente en el host de la consola y después a través del proxy TLS, en su URL base:

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

Cada respuesta muestra cada dependencia como ok. Si solo falla la segunda, la consola está bien y el proxy no. En la primera, use el puerto propio de la consola si lo cambió del 8080. Después abra la URL base de la consola, inicie sesión como administrador inicial y cambie su contraseña de inmediato.

La contraseña del administrador inicial debe tener al menos 12 caracteres y no puede ser igual a su nombre de usuario. Si no cumple esto, no se crea ningún administrador y nadie puede iniciar sesión. El log lo indica:

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

Defina una contraseña más larga y vuelva a arrancar la consola. Consulte Contraseñas y bloqueo.

Una vez que haya iniciado sesión y cambiado la contraseña, quite de la configuración de la consola los ajustes del administrador inicial. Solo se leen mientras la tabla de usuarios está vacía, pero no hay motivo para dejar una contraseña por ahí.

Conectar la clasificación

openvoxserver pregunta a la consola qué clases recibe cada Node, mediante el node terminus exec estándar de Puppet. Un pequeño programa, enc-bridge, hace esa petición en nombre de openvoxserver, y necesita un token para ello.

Emitir un token para enc-bridge

Un token de servicio lleva un conjunto fijo de permisos elegido al crearlo, sin que intervenga ningún rol. Cree uno que solo pueda leer la clasificación:

  1. En la consola, abra Administración y después Tokens de servicio.
  2. En Nuevo token de servicio, llámelo enc-bridge y concédale solo el permiso enc:read.
  3. Elija Crear token de servicio.

El token se muestra una sola vez. Cópielo ahora.

Lo mismo a través de la API, con un token de acceso de un inicio de sesión de administrador: curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

Dar el token a openvoxserver

La imagen de openvoxserver ya contiene enc-bridge, la configuración de Puppet que lo usa y la función de Hiera que permite a los Nodes leer los datos de configuración, así que solo necesita el token. Escríbalo en el archivo de secreto que creó vacío antes:

printf '%s' '<the enc:read service token>' > secrets/enc_bridge_token

openvoxserver no se ejecuta como root dentro de su contenedor, y Compose monta los archivos de secretos con el propietario que tienen en el host. Un archivo que solo puede leer su propio usuario resulta por tanto ilegible para openvoxserver, y la clasificación falla. Dé permiso de lectura al grupo 0 y proteja en su lugar el directorio:

sudo chgrp 0 secrets/enc_bridge_token chmod 640 secrets/enc_bridge_token chmod 700 secrets

Recree openvoxserver para que lea el nuevo token:

docker compose -f docker-compose.yml up -d --force-recreate openvoxserver

Comprobar la clasificación

Consulte a enc-bridge directamente, tal como lo ejecuta openvoxserver. Así se comprueban el programa, el token, los permisos de los archivos y la respuesta de la consola en un solo comando:

docker compose -f docker-compose.yml exec -u puppet:0 openvoxserver \ /usr/local/bin/enc-bridge <a certname>

{} significa que la clasificación funciona y que ese Node aún no coincide con ningún grupo. Cree en la página Grupos de la consola un grupo de Nodes que fije ese certname, vuelva a ejecutar el mismo comando y aparecerán sus clases:

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

Un error aquí es justo el fallo que hay que detectar. permission denied significa que el usuario con el que se ejecuta openvoxserver no puede leer el token, y un 401 significa que el token es incorrecto o no tiene enc:read.

Si la siguiente ejecución de Puppet de un Node falla con Could not find class <name>, la clasificación funciona: la consola le indicó a openvoxserver que incluyera una clase que su código de Puppet todavía no define.

openvoxserver guarda los Environments en caché, así que, tras añadir código de Puppet, vacíe su caché o el mismo error persistirá:

docker compose -f docker-compose.yml exec openvoxserver sh -c \ 'curl -ksS -X DELETE \ --cert /etc/puppetlabs/puppet/ssl/certs/openvoxserver.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/openvoxserver.pem \ https://127.0.0.1:8140/puppet-admin-api/v1/environment-cache'

Actualizar más adelante

Para pasar a una consola más reciente, cambie CONSOLE_IMAGE_TAG (o vuelva a hacer pull si sigue main) y levante de nuevo el stack. Compose recrea solo lo que ha cambiado:

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

El archivo compose no publica el puerto de openvoxdb, así que, para la comprobación de abajo, pregúntele desde dentro de su contenedor: docker compose -f docker-compose.yml exec openvoxdb curl -ksS https://127.0.0.1:8081/status/v1/simple
