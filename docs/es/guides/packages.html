Instalar

Instalar desde paquetes y binarios

Instale openvoxserver, openvoxdb y Postgres desde paquetes, compile la consola y ejecútela como servicio de systemd.

Esta guía instala openvoxserver, openvoxdb y Postgres a partir de los paquetes de OpenVox y de la distribución, y ejecuta la consola como un único binario con systemd. Fije los nombres en Planificar un despliegue antes de empezar.

Los comandos son para Debian y Ubuntu, con el equivalente para RHEL, Rocky Linux y AlmaLinux al lado cuando difiere. Las partes pueden estar en un host o en varios; cuando un paso corresponde a un host concreto, se indica.

Instalar openvoxserver

openvoxserver es la autoridad de certificación de la que procede el certificado de todas las demás partes, así que va primero. Añada el repositorio de OpenVox 8 e instálelo:

Debian y Ubuntu. /etc/os-release curl -fsSL -o /tmp/openvox8-release.deb \ "https://apt.voxpupuli.org/openvox8-release-${ID}${VERSION_ID}.deb" sudo apt-get install -y /tmp/openvox8-release.deb sudo apt-get update && sudo apt-get install -y openvox-server RHEL, Rocky y AlmaLinuxsudo dnf install -y https://yum.voxpupuli.org/openvox8-release-el-9.noarch.rpm sudo dnf install -y openvox-server

El paquete no crea la CA por sí mismo. Su primer arranque crea la CA y el certificado propio de este servidor, emitido para el certname del host, que normalmente es su nombre completo (FQDN). En el caso habitual no hay que hacer nada más que arrancarlo:

sudo systemctl enable --now puppetserver

No ejecute puppetserver ca setup en un host que ya tenga una CA. Solo crea una CA que aún no existe, y sobre una existente se detiene con "Existing file at .../ca_crt.pem". Borrar esos archivos como sugiere el mensaje destruye su CA y todos los certificados que haya emitido, incluidos los de todos los Nodes incorporados.

Permitir que la CA firme nombres alternativos

El certificado del transporte de Nodes de la consola, y el propio de este servidor si lo vuelve a emitir más abajo, llevan más de un nombre. Por defecto, la CA se niega a firmar una solicitud así y la deja en espera, así que permítalo una vez. En /etc/puppetlabs/puppetserver/conf.d/ca.conf, añada el ajuste dentro del bloque certificate-authority:

certificate-authority: { allow-subject-alt-names: true ... } sudo systemctl restart puppetserver

Comprobar los nombres de su certificado

Un certificado siempre es válido para su propio certname. Si tanto los Nodes como la consola acceden a este servidor por su certname, no hay nada que cambiar. Si no, compruebe qué nombres cubre ya el certificado:

sudo openssl x509 -in /etc/puppetlabs/puppet/ssl/certs/$(hostname -f).pem \ -noout -subject -ext subjectAltName

Si falta un nombre de su plan, vuelva a emitir solo el certificado propio de este servidor, nunca la CA. Definir dns_alt_names a posteriori no cambia un certificado que ya existe, así que límpielo y regenérelo con el servidor en marcha:

sudo /opt/puppetlabs/bin/puppetserver ca clean --certname $(hostname -f) sudo /opt/puppetlabs/bin/puppetserver ca generate --certname $(hostname -f) \ --subject-alt-names puppet.example.com,openvoxserver sudo systemctl restart puppetserver

En un host nuevo, puede en su lugar definir los nombres antes del primer arranque y dejar que ese arranque cree el certificado con ellos: sudo /opt/puppetlabs/bin/puppet config set --section server dns_alt_names puppet.example.com,openvoxserver

Comprobar que está en marcha

curl -ksS https://puppet.example.com:8140/status/v1/simple

La respuesta es running.

Instalar openvoxdb y su base de datos

Incorporar el host de openvoxdb

openvoxdb no solicita un certificado por sí mismo: su configuración copia el que ya tiene su host. Si openvoxdb tiene un host propio, incorpore primero ese host a la CA y después firme su solicitud en la CA si esta no firma automáticamente:

sudo /opt/puppetlabs/bin/puppet ssl bootstrap --server puppet.example.com # on the CA host: sudo /opt/puppetlabs/bin/puppetserver ca sign --certname <openvoxdb host>

Omita este paso si openvoxdb comparte host con openvoxserver, que ya tiene un certificado.

Crear su base de datos

openvoxdb necesita una base de datos Postgres propia, que el paquete no crea:

Debian y Ubuntusudo apt-get install -y postgresql sudo systemctl enable --now postgresql RHEL, Rocky y AlmaLinuxsudo dnf install -y postgresql-server postgresql-contrib sudo postgresql-setup --initdb # Accept passwords over local connections, which are refused by the # default "ident" rules, and store passwords to match. sudo sed -i -E 's/^(host .*)(ident)$/\1scram-sha-256/' /var/lib/pgsql/data/pg_hba.conf echo "password_encryption = 'scram-sha-256'" | sudo tee -a /var/lib/pgsql/data/postgresql.conf sudo systemctl enable --now postgresql

En RHEL y sus derivadas, el pg_trgm de más abajo procede de postgresql-contrib, y el cambio de contraseñas tiene que hacerse antes de crear los usuarios: una contraseña guardada antes no puede comprobarse con las nuevas reglas.

sudo -u postgres createuser --pwprompt puppetdb sudo -u postgres createdb --owner=puppetdb puppetdb # openvoxdb refuses to start without this extension, and creating it # needs superuser rights - so it is run as postgres, not as puppetdb. sudo -u postgres psql -d puppetdb -c 'CREATE EXTENSION IF NOT EXISTS pg_trgm;'

Compruebe que Postgres acepta conexiones:

pg_isready

La respuesta termina en accepting connections.

En Debian y Ubuntu, systemctl status postgresql muestra active (exited), y es normal: esa unidad solo arranca la unidad real de cada clúster. pg_lsclusters muestra el propio clúster como online.

Instalar y arrancar openvoxdb

Debian y Ubuntusudo apt-get install -y openvoxdb RHEL, Rocky y AlmaLinuxsudo dnf install -y openvoxdb

Indíquele dónde está su base de datos. Sin este archivo no arranca, y termina con No subname set in the "database" config.:

[database] subname = //localhost:5432/puppetdb username = puppetdb password = <the password you set above>

Guárdelo como /etc/puppetlabs/puppetdb/conf.d/database.ini, con el nombre del host de la base de datos en lugar de localhost si está en otro sitio, y restrinja sus permisos:

sudo chown puppetdb:puppetdb /etc/puppetlabs/puppetdb/conf.d/database.ini sudo chmod 640 /etc/puppetlabs/puppetdb/conf.d/database.ini

Después copie los certificados del host en su sitio y arránquelo:

sudo /opt/puppetlabs/bin/puppetdb ssl-setup sudo systemctl enable --now puppetdb

Si no arranca, /var/log/puppetlabs/puppetdb/puppetdb.log contiene el motivo real; el error de systemd suele ser solo la consecuencia.

Enviarle catálogos y Reports

En el host de openvoxserver, instale el terminus que envía catálogos y Reports a openvoxdb:

Debian y Ubuntusudo apt-get install -y openvoxdb-termini RHEL, Rocky y AlmaLinuxsudo dnf install -y openvoxdb-termini

Comprobar que está en marcha

El puerto HTTPS de openvoxdb exige un certificado de cliente, así que pregunte con el del propio host. Sin él, la respuesta es certificate required:

H=$(hostname -f) sudo curl -sS --cert /etc/puppetlabs/puppet/ssl/certs/$H.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/$H.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://$H:8081/status/v1/simple

La respuesta es running. Puede que el log indique que "the read-database user is not configured properly". Se refiere a un usuario de solo lectura aparte que esta guía no configura, y openvoxdb funciona sin él.

Crear la base de datos de la consola

La consola guarda sus propios datos en una base de datos separada de la de openvoxdb. Crea ella misma su esquema en el primer arranque; solo necesita una base de datos vacía y un rol que sea su propietario. En el host de Postgres:

sudo -u postgres createuser --pwprompt console sudo -u postgres createdb --owner=console console

Si la consola va a ejecutarse en otro host, Postgres también tiene que escuchar en la red. Por defecto solo escucha en localhost, así que una conexión remota se rechaza aunque pg_isready funcione en local. Permita el host o la subred de la consola, ajustando el rango de direcciones:

Debian y Ubuntusudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /etc/postgresql/*/main/pg_hba.conf sudo systemctl restart postgresql@*-main.service RHEL, Rocky y AlmaLinuxsudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /var/lib/pgsql/data/pg_hba.conf sudo systemctl restart postgresql

Compruebe, desde el host de la consola, que el rol de la consola puede conectarse (allí, psql viene con el paquete postgresql-client):

PGPASSWORD='<password>' psql -h <postgres host> -U console -d console -c 'select 1;'

Conserve las comillas simples. Si no, la shell expande una contraseña que contenga $ antes de que psql la vea.

Emitir los certificados de la consola

La consola necesita dos certificados de la CA y, opcionalmente, un tercero. Genérelos en el host de openvoxserver y después cópielos al host de la consola, en /etc/openvox-console/. Cree antes ese directorio en el host de la consola, junto con el usuario con el que se ejecutará la consola:

sudo useradd --system --home-dir /nonexistent --shell /usr/sbin/nologin openvox-console sudo install -d -m 0750 -o root -g openvox-console /etc/openvox-console

El certificado de cliente de openvoxdb

Así es como la consola se autentica ante openvoxdb:

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname console

puppetserver ca generate empieza imprimiendo Error: Signed certificate console could not be found on the CA. Es la comprobación de que el nombre está libre, no un fallo. Lo que importa son las líneas siguientes, que terminan en Successfully saved certificate.

Escribe tres archivos que necesita la consola. Cópielos con estos nombres:

En el host de openvoxserver En el host de la consola
/etc/puppetlabs/puppet/ssl/certs/console.pem /etc/openvox-console/console-cert.pem
/etc/puppetlabs/puppet/ssl/private_keys/console.pem /etc/openvox-console/console-key.pem
/etc/puppetlabs/puppet/ssl/certs/ca.pem /etc/openvox-console/ca.pem

El certificado del transporte de Nodes

Los Nodes comprueban este certificado al conectarse a la consola, así que debe llevar exactamente el nombre al que se conectan: la parte del host de CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR.

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport

Copie certs/node-transport.pem y private_keys/node-transport.pem de la misma forma, como node-transport-cert.pem y node-transport-key.pem. Los Nodes se autentican a su vez con sus propios certificados de la misma CA, así que la consola no necesita nada más para ellos.

La clave de firma de tokens

La consola firma sus propios tokens de inicio de sesión con una clave ES256. Esta no procede de la CA. Genérela en cualquier máquina con OpenSSL:

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

Haga copia de seguridad de este archivo. Perderlo invalida todos los tokens emitidos, lo que cierra la sesión de todo el mundo; filtrarlo permite a cualquiera fabricar tokens. Consulte Rotar la clave de firma de tokens para sustituirlo de forma segura.

Genérela en el host de la consola, en /etc/openvox-console/.

La credencial de administración de certificados (opcional)

Esta credencial es la que permite a la página Nodes mostrar el estado de los certificados y firmar, revocar y limpiar certificados. Sin ella, la consola solo lista los Nodes que ya se han conectado o han enviado un Report. Un Node que espera la firma de su certificado no aparece en absoluto, porque la CA es la única parte que sabe que existe.

Esta credencial otorga administración completa de la CA. openvoxserver protege todos los endpoints de la CA con una única extensión de autorización, así que un certificado que puede leer estados también puede firmar, revocar y limpiar el certificado de cualquier Node. No existe una variante de solo lectura. Guárdela solo donde se ejecuta la consola, y lea Gestionar los certificados de los Nodes antes de emitirla.

Emitirlo escribe en el estado de la CA, que el servidor en marcha también escribe, así que detenga openvoxserver mientras se emite:

sudo systemctl stop puppetserver sudo /opt/puppetlabs/bin/puppetserver ca generate --ca-client --certname console-ca-client sudo systemctl start puppetserver

Copie certs/console-ca-client.pem y private_keys/console-ca-client.pem como ca-client-cert.pem y ca-client-key.pem. Después confirme, desde el host de la consola, que la CA la acepta:

curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/ca-client-cert.pem \ --key /etc/openvox-console/ca-client-key.pem \ --cacert /etc/openvox-console/ca.pem \ https://puppet.example.com:8140/puppet-ca/v1/certificate_statuses/all

HTTP 200 significa que funciona.

Compilar la consola

La consola es un único binario con su interfaz web integrada. No hay paquete de ella; compílela desde el repositorio de código fuente. Necesita Go en la versión indicada en go.mod, y git.

git clone https://github.com/avitacco/openvox-console.git cd openvox-console

La consola también sirve el agente de Node que instalan los Nodes, desde su propio repositorio de paquetes, y esos agentes van integrados en el binario de la consola. Compílelos primero, o todas las instalaciones de Nodes fallarán con un 404:

make agent-binaries make agent-packages make build

Eso deja bin/console y bin/enc-bridge. Instale la consola en su host:

sudo install -m 0755 bin/console /usr/local/bin/console

Configurar la consola

La consola se configura solo con variables de entorno, en un archivo dentro del directorio /etc/openvox-console/ que creó para sus certificados.

Hay seis ajustes obligatorios, y la consola se niega a arrancar sin ellos, indicando el que falta. Póngalos en /etc/openvox-console/console.env:

CONSOLE_POSTGRES_DSN=postgres://console:<password>@<postgres host>:5432/console?sslmode=require CONSOLE_OPENVOXDB_URL=https://<openvoxdb host>:8081 CONSOLE_OPENVOXDB_CERT_FILE=/etc/openvox-console/console-cert.pem CONSOLE_OPENVOXDB_KEY_FILE=/etc/openvox-console/console-key.pem CONSOLE_OPENVOXDB_CA_FILE=/etc/openvox-console/ca.pem CONSOLE_RBAC_SIGNING_KEY_FILE=/etc/openvox-console/rbac-signing-key.pem

sslmode=require supone que su Postgres sirve TLS, como debería en cuanto la conexión sale del host. Si la consola y Postgres comparten host y Postgres no tiene certificado, use sslmode=disable.

El resto es opcional, y cada función opcional se desactiva sola en lugar de bloquear el arranque. Para un despliegue real, añada:

# Where the console listens, and how the outside world reaches it. It # listens on loopback only: the TLS proxy in front of it is the way in. # On a host shared with openvoxdb, which holds 8080, use 127.0.0.1:8088. CONSOLE_HTTP_ADDR=127.0.0.1:8080 CONSOLE_BASE_URL=https://console.example.com # The first admin user, created only while there are no users. The # password needs at least 12 characters. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin CONSOLE_BOOTSTRAP_ADMIN_PASSWORD=<a strong password> # The node transport. ADDR is what the console binds; PUBLIC_ADDR is what # a node dials, and its host must be in the node transport certificate. CONSOLE_NODE_TRANSPORT_ADDR=:8142 CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 CONSOLE_NODE_TRANSPORT_CERT_FILE=/etc/openvox-console/node-transport-cert.pem CONSOLE_NODE_TRANSPORT_KEY_FILE=/etc/openvox-console/node-transport-key.pem CONSOLE_NODE_TRANSPORT_CA_FILE=/etc/openvox-console/ca.pem # The Puppet server a node should enroll against, written into the node # install script. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # Certificate management from the Nodes page (the optional credential). CONSOLE_CA_CLIENT_URL=https://puppet.example.com:8140 CONSOLE_CA_CLIENT_CERT_FILE=/etc/openvox-console/ca-client-cert.pem CONSOLE_CA_CLIENT_KEY_FILE=/etc/openvox-console/ca-client-key.pem CONSOLE_CA_CLIENT_CA_FILE=/etc/openvox-console/ca.pem # Puppet tasks: where the console asks which tasks your deployed code # contains. Uses the openvoxdb client certificate above unless you name # another with CONSOLE_PUPPET_SERVER_CERT_FILE, _KEY_FILE and _CA_FILE. CONSOLE_PUPPET_SERVER_URL=https://puppet.example.com:8140

Los Tasks no necesitan certificado propio: openvoxserver permite que cualquier certificado de su CA lea los Tasks, así que sirve el certificado de cliente de openvoxdb. No los apunte a la credencial de administración de certificados, que puede hacer mucho más de lo que requiere leer Tasks. Consulte Ejecutar Jobs para ejecutarlos.

Permitir que la consola lea la lista de clases

La página de un grupo de Nodes ofrece las clases que define su código desplegado, con sus parámetros, para elegirlas en lugar de escribirlas. La consola las lee de openvoxserver por la misma conexión que los Tasks, pero openvoxserver no deja que ningún certificado lea clases hasta que una regla lo permita.

En el host de openvoxserver, añada esta regla a la lista rules de /etc/puppetlabs/puppetserver/conf.d/auth.conf, por encima de la regla final puppetlabs deny all. console es el nombre del certificado de cliente de openvoxdb que emitió antes:

{ match-request: { path: "/puppet/v3/environment_classes" type: path method: get } allow: "console" sort-order: 500 name: "openvox console class discovery" },

Después recargue openvoxserver:

sudo systemctl reload puppetserver

Compruébelo desde el host de la consola. HTTP 200 significa que la lista puede leerse:

sudo curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/console-cert.pem \ --key /etc/openvox-console/console-key.pem \ --cacert /etc/openvox-console/ca.pem \ 'https://puppet.example.com:8140/puppet/v3/environment_classes?environment=production'

HTTP 403 significa que falta la regla o que nombra otro certificado. Nada más depende de este paso: sin él, la página del grupo indica que la lista no está disponible, y las clases se introducen por nombre. Consulte Clasificar Nodes.

Guardar los secretos en archivos

Cualquier ajuste puede leerse en su lugar desde un archivo: indique el archivo en el nombre del ajuste seguido de _FILE. Así las contraseñas quedan fuera del entorno del proceso:

CONSOLE_POSTGRES_DSN_FILE=/etc/openvox-console/postgres-dsn CONSOLE_BOOTSTRAP_ADMIN_PASSWORD_FILE=/etc/openvox-console/bootstrap-admin-password

Un salto de línea final en el archivo se ignora. Un archivo indicado que no se puede leer impide que la consola arranque, en lugar de dejarla arrancar con el valor vacío sin avisar.

Por último, haga que todos los archivos sean legibles por el usuario de la consola y por nadie más:

sudo sh -c 'chown root:openvox-console /etc/openvox-console/* && chmod 0640 /etc/openvox-console/*'

El sh -c es importante: su propia shell no puede listar ese directorio, así que un simple sudo chown ... /etc/openvox-console/* falla con "No such file or directory".

Ejecutarla con systemd

Cree /etc/systemd/system/openvox-console.service:

[Unit] Description=OpenVox Console After=network-online.target Wants=network-online.target [Service] EnvironmentFile=/etc/openvox-console/console.env ExecStart=/usr/local/bin/console Restart=on-failure User=openvox-console Group=openvox-console [Install] WantedBy=multi-user.target

Después arránquela:

sudo systemctl daemon-reload sudo systemctl enable --now openvox-console journalctl -u openvox-console -f

Poner TLS delante de la consola

La consola sirve su interfaz web y su API por HTTP sin cifrar. A la URL base https:// se llega a través de un proxy inverso que termina el TLS y pasa las peticiones a la consola. Sirve cualquier proxy inverso. Aquí se usa Caddy, en el host de la consola:

Debian y Ubuntusudo apt-get install -y caddy RHEL, Rocky y AlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

Este es entonces el /etc/caddy/Caddyfile completo:

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

Si la consola escucha en otro puerto porque comparte host con openvoxdb, ponga en su lugar ese puerto en reverse_proxy.

Para un nombre que se puede resolver desde internet, Caddy obtiene y renueva el certificado por sí solo. Para un nombre interno, dele un certificado de su propia CA con una línea tls <cert file> <key file> dentro del bloque. Para una prueba, tls internal hace que Caddy emita uno desde una CA local propia, sobre la que los navegadores advierten.

Solo la interfaz web pasa por el proxy. El transporte de Nodes, en el puerto 8142, lleva su propio TLS y comprueba él mismo el certificado de cada Node, así que los Nodes deben alcanzarlo directamente. No lo ponga nunca detrás del proxy.

Iniciar sesión por primera vez

En su primer arranque, la consola crea el esquema de su base de datos y después crea el administrador inicial mientras la tabla de usuarios sigue vacía. Cuando está en marcha, su log muestra tres líneas:

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

Compruebe que se declara en buen estado, primero directamente en el host de la consola y después a través del proxy TLS, en su URL base:

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

Cada respuesta muestra cada dependencia como ok. Si solo falla la segunda, la consola está bien y el proxy no. En la primera, use el puerto propio de la consola si lo cambió del 8080. Después abra la URL base de la consola, inicie sesión como administrador inicial y cambie su contraseña de inmediato.

La contraseña del administrador inicial debe tener al menos 12 caracteres y no puede ser igual a su nombre de usuario. Si no cumple esto, no se crea ningún administrador y nadie puede iniciar sesión. El log lo indica:

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

Defina una contraseña más larga y vuelva a arrancar la consola. Consulte Contraseñas y bloqueo.

Una vez que haya iniciado sesión y cambiado la contraseña, quite de la configuración de la consola los ajustes del administrador inicial. Solo se leen mientras la tabla de usuarios está vacía, pero no hay motivo para dejar una contraseña por ahí.

Conectar la clasificación

openvoxserver pregunta a la consola qué clases recibe cada Node, mediante el node terminus exec estándar de Puppet. Un pequeño programa, enc-bridge, hace esa petición en nombre de openvoxserver, y necesita un token para ello.

Emitir un token para enc-bridge

Un token de servicio lleva un conjunto fijo de permisos elegido al crearlo, sin que intervenga ningún rol. Cree uno que solo pueda leer la clasificación:

  1. En la consola, abra Administración y después Tokens de servicio.
  2. En Nuevo token de servicio, llámelo enc-bridge y concédale solo el permiso enc:read.
  3. Elija Crear token de servicio.

El token se muestra una sola vez. Cópielo ahora.

Lo mismo a través de la API, con un token de acceso de un inicio de sesión de administrador: curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

Instalar enc-bridge en el host de openvoxserver

Copie bin/enc-bridge de su compilación al host de openvoxserver e instálelo:

sudo install -m 0755 enc-bridge /usr/local/bin/enc-bridge

Guarde el token donde solo pueda leerlo el usuario de openvoxserver:

printf '%s' '<the enc:read service token>' | sudo tee /etc/puppetlabs/enc-bridge-token >/dev/null sudo chown root:puppet /etc/puppetlabs/enc-bridge-token sudo chmod 0640 /etc/puppetlabs/enc-bridge-token

enc-bridge lee de su entorno dónde está la consola y cuál es su token, y ese entorno lo hereda de openvoxserver. Dé ambas cosas a openvoxserver con sudo systemctl edit puppetserver:

[Service] Environment=ENC_BRIDGE_URL=https://console.example.com Environment=ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token

enc-bridge comprueba el certificado de la consola contra el almacén de certificados del sistema del host de openvoxserver. Si el certificado del proxy procede de su propia CA, añada esa CA al almacén, o la clasificación fallará con certificate signed by unknown authority:

Debian y Ubuntusudo cp <your CA>.crt /usr/local/share/ca-certificates/ sudo update-ca-certificates RHEL, Rocky y AlmaLinuxsudo cp <your CA>.crt /etc/pki/ca-trust/source/anchors/ sudo update-ca-trust

Después apunte Puppet hacia él, en la sección [server] de /etc/puppetlabs/puppet/puppet.conf, y reinicie openvoxserver:

[server] node_terminus = exec external_nodes = /usr/local/bin/enc-bridge sudo systemctl restart puppetserver

Permitir que los Nodes lean los datos de configuración

Opcional. Esto permite que los Nodes lean con lookup() los datos de configuración definidos en los grupos de Nodes, antes que los datos de Hiera de su repositorio de control. La función ejecuta enc-bridge --data, así que usa la misma dirección de la consola y el mismo token que la clasificación y no necesita configurar nada más. Necesita un enc-bridge compilado a partir de esta versión.

La función tiene que instalarse en el propio directorio de funciones de Puppet, el único lugar desde el que openvoxserver carga una función global de Hiera. Desde el checkout de su compilación:

sudo install -m 0644 openvoxserver-init/console_config_data.rb \ /opt/puppetlabs/puppet/lib/ruby/vendor_ruby/puppet/functions/console_config_data.rb

Después añádala a la configuración global de Hiera, /etc/puppetlabs/puppet/hiera.yaml, la primera en la jerarquía para que prevalezcan los datos de la consola. El paquete instala ahí un archivo de ejemplo; si no lo ha cambiado, sustitúyalo por esto:

--- version: 5 hierarchy: - name: "Console configuration data" data_hash: console_config_data

Si ya tiene un hiera.yaml global, añádale la entrada y mantenga sus propias entradas a continuación.

sudo systemctl restart puppetserver

Tras actualizar el paquete openvox-agent, compruebe que el archivo sigue ahí, y vuelva a instalarlo si no. Si la ejecución de un Node falla con "Unable to find 'data_hash' function named 'console_config_data'", la función no está en ese directorio. La imagen de contenedor hace todo esto por sí sola en cada arranque.

Comprobar la clasificación

Ejecute enc-bridge como lo hace openvoxserver: con su usuario y los mismos ajustes. Así se comprueban el programa, el token, los permisos de los archivos y la respuesta de la consola en un solo comando:

sudo -u puppet env ENC_BRIDGE_URL=https://console.example.com \ ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token \ /usr/local/bin/enc-bridge <a certname>

{} significa que la clasificación funciona y que ese Node aún no coincide con ningún grupo. Cree en la página Grupos de la consola un grupo de Nodes que fije ese certname, vuelva a ejecutar el mismo comando y aparecerán sus clases:

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

Un error aquí es justo el fallo que hay que detectar. permission denied significa que el usuario con el que se ejecuta openvoxserver no puede leer el token, y un 401 significa que el token es incorrecto o no tiene enc:read.

Si la siguiente ejecución de Puppet de un Node falla con Could not find class <name>, la clasificación funciona: la consola le indicó a openvoxserver que incluyera una clase que su código de Puppet todavía no define.

Actualizar más adelante

Para pasar a una consola más reciente, actualice el código fuente, vuelva a compilar en el mismo orden, instale el nuevo binario y reinicie:

git pull make agent-binaries make agent-packages make build sudo install -m 0755 bin/console /usr/local/bin/console sudo systemctl restart openvox-console
