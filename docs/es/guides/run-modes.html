Modos de ejecución

Qué sirve y qué ejecuta cada uno de los modos de ejecución de la consola, y qué configuración necesita cada uno.

Una imagen, un binario. CONSOLE_RUN_MODE selecciona qué partes de la consola ejecuta una instancia, de modo que las partes con cargas muy distintas pueden escalarse y ubicarse por separado. Sin definir, vale all: todo en una instancia, que es lo que ejecuta siempre un despliegue de una sola instancia.

Qué ejecuta cada modo

Modo Sirve Escucha Se ejecuta en segundo plano
all (el valor por defecto) todo HTTP, transporte de Nodes todas las tareas en segundo plano
web la consola, su API, los webhooks de despliegue de código y la clasificación HTTP seguir los Jobs iniciados a través de ella
enc solo la clasificación HTTP nada
orchestrator nada aparte de salud y métricas HTTP, transporte de Nodes el envío de Jobs, los Jobs programados, la primera ejecución de los Nodes nuevos y las actualizaciones del agente de Node
worker nada aparte de salud y métricas HTTP sincronizaciones de vulnerabilidades y limpieza de Jobs abandonados

Todos los modos sirven /health y /metrics, así que cualquier instancia puede comprobarse sin conocer su modo, y /health indica el modo en el que se ejecuta.

Dos decisiones de esa tabla son deliberadas:

  • web también responde a la clasificación. enc existe para que la clasificación pueda ejecutarse por separado, junto a los compiladores, no para que falte en todos los demás sitios. Una división que dejara de clasificar Nodes sin avisar sería mucho peor que que web asuma parte de esa carga.
  • orchestrator no sirve ninguna API. Mantiene las conexiones de los Nodes y envía los Jobs por ellas. Iniciar un Job es tarea de web, y web llega a esas conexiones a través del clúster.
  • La instancia que inicia un Job es la que lo sigue. Una ejecución, un Task o un Plan iniciados en la consola los envía y los sigue la instancia web que recibió la petición, así que las instancias web deben estar en clúster con las instancias orchestrator para llegar a cualquier Node. Si esa instancia web se detiene antes de que termine el Job, una instancia worker marca el Job como fallido.

Qué necesita cada modo

Cada modo exige solo lo que usa, y se niega a arrancar sin ello, indicando el ajuste que falta:

Modo Requiere
todos los modos CONSOLE_POSTGRES_DSN y los cuatro ajustes CONSOLE_OPENVOXDB_*
all, web CONSOLE_RBAC_SIGNING_KEY_FILE: son los únicos modos que emiten tokens de inicio de sesión
enc, orchestrator, worker CONSOLE_RBAC_VERIFICATION_KEYS_DIR: comprueban tokens, pero nunca los emiten
orchestrator CONSOLE_NODE_TRANSPORT_ADDR: sin un listener de Nodes, todos los Jobs fallarían con "not connected" en una instancia aparentemente sana

Dar al programador lo que usan los Jobs programados

Los Jobs programados los inician las instancias all y orchestrator, no web. Una instancia orchestrator arranca sin estos ajustes, pero una programación que necesite alguno se omite, indicando el motivo, hasta que la instancia lo tenga:

  • CONSOLE_PUPPET_SERVER_URL, para iniciar un Task programado: el Task se busca en el código desplegado cuando arranca la programación.
  • CONSOLE_SECRETS_KEY_FILE, la misma clave que en web, para iniciar un Task programado que tenga un parámetro sensible.

Cuando varias instancias ejecutan el programador, cada hora prevista la inicia exactamente una de ellas. Si no hay ninguna en marcha cuando vence una programación, arranca cuando haya una, salvo que eso suponga más de 15 minutos de retraso, en cuyo caso esa hora se registra como perdida.

Dar las claves de verificación a los modos que no emiten tokens

Una instancia que solo comprueba tokens lee de un directorio las claves con las que comprobarlos, un archivo por clave, con el nombre del ID de la clave. Un despliegue que nunca ha rotado su clave usa el ID default, así que el directorio contiene un archivo, default.pem, que es el propio archivo de la clave de firma:

sudo install -d -m 0750 -o root -g openvox-console /etc/openvox-console/rbac-verification-keys sudo install -m 0640 -o root -g openvox-console \ rbac-signing-key.pem /etc/openvox-console/rbac-verification-keys/default.pem CONSOLE_RUN_MODE=enc CONSOLE_RBAC_VERIFICATION_KEYS_DIR=/etc/openvox-console/rbac-verification-keys

Por ahora, el directorio de verificación solo acepta claves en el mismo formato que la clave de firma: la clave privada, de la que la consola solo usa la mitad pública. Así que una instancia que recibe el directorio tiene también una clave que podría firmar tokens. Protéjalo en cada host exactamente igual que la clave de firma, incluidas las instancias enc junto a los compiladores.

Cuando rote la clave de firma, el directorio de verificación de cada instancia también necesita la nueva clave; Rotar la clave de firma de tokens explica el orden.

Cambiar el modo de una instancia

Defina CONSOLE_RUN_MODE y reinicie la instancia. No se mueve ningún dato: todos los modos leen y escriben en la misma base de datos. Volver a definirlo como all deshace el cambio.

Una instancia aislada puede cambiar de modo, pero un modo distinto de all solo tiene sentido entre instancias en clúster que, entre todas, ejecutan todos los modos. Consulte Ejecutar más instancias.

OpenVox Console se distribuye como imágenes de contenedor, compiladas para amd64 y arm64 en cada push, y como un único binario. Las guías de instalación le llevan de un host vacío a un despliegue funcional (openvoxserver, openvoxdb, Postgres y la consola) con contenedores o con paquetes.
