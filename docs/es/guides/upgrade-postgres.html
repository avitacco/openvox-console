Actualizar las bases de datos de los contenedores a Postgres 18

Pase las dos bases de datos de un despliegue en contenedores de Postgres 17 a 18 volcándolas y restaurándolas.

El archivo compose de producción ejecuta las dos bases de datos en Postgres 18. Las imágenes de Postgres 18 guardan sus datos en un directorio con el número de versión dentro del volumen, así que los volúmenes se montan en /var/lib/postgresql, no en /var/lib/postgresql/data como antes.

Un contenedor de Postgres 18 arrancado sobre un volumen que aún contiene datos de Postgres 17 se niega a arrancar, con un error que empieza por Error: in 18+, these Docker images are configured to store database data in a format which is compatible with "pg_ctlcluster". Es una negativa, no un daño: los datos antiguos están intactos. Esta guía los traslada.

La actualización consiste en volcar y restaurar: pg_upgrade necesitaría las dos versiones en una imagen, y estas imágenes llevan solo una.

Volcar las dos bases de datos

Hágalo con los contenedores de Postgres 17 todavía en marcha. Detenga lo que escribe en ellos y deje las bases de datos levantadas:

docker compose -f docker-compose.yml stop console openvoxdb docker compose -f docker-compose.yml exec -T openvoxdb-postgres \ pg_dumpall -U openvoxdb > openvoxdb-17.sql docker compose -f docker-compose.yml exec -T console-postgres \ pg_dumpall -U console > console-17.sql

Compruebe que los dos archivos están ahí y no están vacíos antes de continuar:

ls -l openvoxdb-17.sql console-17.sql

Sustituir los volúmenes

Esto borra los datos de Postgres 17. A partir de aquí, los dos archivos de volcado son la única copia, y por eso la comprobación anterior va primero.

 docker compose -f docker-compose.yml down docker volume rm openvox-console_openvoxdb-postgres-data openvox-console_console-postgres-data

Los nombres de los volúmenes siguen el nombre del directorio del proyecto; compruébelos con docker volume ls.

Restaurar en Postgres 18

Arranque solo las bases de datos. Arrancan vacías, y la de openvoxdb recibe del archivo compose la extensión pg_trgm que necesita:

docker compose -f docker-compose.yml up -d openvoxdb-postgres console-postgres docker compose -f docker-compose.yml exec -T openvoxdb-postgres \ psql -U openvoxdb < openvoxdb-17.sql docker compose -f docker-compose.yml exec -T console-postgres \ psql -U console < console-17.sql

Después arranque todo lo demás:

docker compose -f docker-compose.yml up -d

Si openvoxdb dice que falta pg_trgm

openvoxdb se niega a arrancar sin la extensión pg_trgm. El archivo compose solo la añade cuando se crea la base de datos por primera vez, así que a una base de datos que ya existía hay que añadírsela a mano:

docker compose -f docker-compose.yml exec openvoxdb-postgres \ psql -U openvoxdb -c 'CREATE EXTENSION IF NOT EXISTS pg_trgm;'

Quedarse en Postgres 17

Quedarse en 17 exige dos cambios, no uno: defina OPENVOXDB_POSTGRES_VERSION=17-alpine (y su equivalente para la consola, CONSOLE_POSTGRES_VERSION) y devuelva el punto de montaje de cada volumen a /var/lib/postgresql/data. Cambiar solo la versión produce el error anterior.
