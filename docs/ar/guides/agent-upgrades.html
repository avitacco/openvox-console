Nodes

إبقاء وكلاء الـ Nodes محدَّثين

كيف ترقّي وحدة التحكم وكيل الـ Node على الـ Nodes لديك بنفسها، وكيف ترى الـ Nodes المتأخرة، والخطوة التي تُجرى مرة واحدة للـ Nodes المثبّتة قبل وجود هذه الميزة.

وكيل الـ Node هو الخدمة الصغيرة التي يضعها سكربت التثبيت على كل Node. يحتفظ باتصال الـ Node بوحدة التحكم وينفّذ التشغيلات والـ Tasks التي تبدؤها. ويُبنى مع وحدة التحكم ويُوزَّع بداخلها، لذا فإن وحدة التحكم الأحدث تأتي عادةً بوكيل Node أحدث.

ترقّي وحدة التحكم وكيل الـ Node على الـ Nodes لديك نيابة عنك. حين يتصل Node، تسأل وحدة التحكم عن إصدار بناء الوكيل الذي يشغّله. وإذا كان ذلك الإصدار أقدم من الذي توزّعه وحدة التحكم، تطلب وحدة التحكم من الـ Node الترقية، فينزّل الـ Node الإصدار الجديد من وحدة التحكم، ويفحصه، ويثبّته، ويعيد التشغيل عليه. ولا تفعل أنت شيئًا على الـ Node.

ما تراه

  • صفحة Nodes. الـ Node الذي تأخر وكيله يُوسَم بـ العميل قديم.
  • صفحة الـ Node. تعرض إصدار الوكيل ووقت بنائه، وما إذا كان محدَّثًا، وما آلت إليه آخر محاولة ترقية.
  • Dashboard. تحت حالة الأسطول، عدد وكلاء الـ Nodes المحدَّثين، وعدد القدامى منهم، وعدد الترقيات التي فشلت، وما إذا كانت الترقيات التلقائية مفعَّلة.

بدء ترقية بنفسك، من صفحة الـ Node، يتطلب nodes:manage على دور تتضمن مجموعات الـ Nodes الخاصة به ذلك الـ Node. أما الترقيات التي تبدؤها وحدة التحكم بنفسها فلا تقيّدها مجموعات الـ Nodes لأي أحد.

الـ Node الذي لم يتصل منذ ترقية وحدة التحكم يظهر على أنه لم يُبلّغ بعد، لا على أنه قديم. ويُبلّغ في المرة التالية التي يتصل فيها.

الـ Nodes المثبّتة قبل وجود الترقيات التلقائية

وكيل الـ Node الذي يسبق هذه الميزة لا يستطيع ترقية نفسه، لأنه لا يفهم الطلب. تعرض وحدة التحكم مثل هذا الـ Node على أنه قديم، مع ملاحظة بأن سكربت التثبيت يجب أن يُشغَّل مجددًا. شغّله على الـ Node مرة واحدة، تمامًا كما فعلت عند إضافة الـ Node:

Linuxcurl -fsSL https://console.example.com/packages/install.sh | sudo bash macOScurl -fsSL https://console.example.com/packages/install-macos.sh | sudo bash WindowsInvoke-WebRequest https://console.example.com/packages/install.ps1 -OutFile install.ps1 .\install.ps1

ومن ذلك الحين يُبقي الـ Node نفسه محدَّثًا. وتُحصي لوحة Dashboard الـ Nodes التي لا تزال تنتظر ذلك، فتعرف متى انتهيت منها كلها.

إذا كنت تدير حزمة Linux باستخدام Puppet بدلًا من ذلك، فإن ensure => latest على الحزمة node-agent-client من مستودع وحدة التحكم يؤدي المهمة نفسها.

ما تفعله الترقية وما لا تفعله

  • لا يقاطع العمل أبدًا. فالـ Node الذي يكون في منتصف تشغيل أو Task يُترك وشأنه ويُعاد المحاولة معه بعد دقيقة.
  • يُفحص قبل تثبيته. ترسل وحدة التحكم المجموع الاختباري المتوقع للملف المنزَّل عبر اتصال الـ Node المُصادَق عليه. ويرفض الـ Node أي شيء لا يطابقه، ويشغّل الوكيل الجديد مرة واحدة للتأكد من أنه يعمل قبل استبدال القديم. وإذا فشل أيٌّ من الفحصين، يحتفظ الـ Node بالوكيل الذي لديه.
  • يجري على بضعة Nodes في كل مرة. يُرقّى 20 Node على الأكثر في وقت واحد، مهما كان عدد المتأخرة.
  • لا يمضي إلا إلى الأمام. فالـ Node الذي يشغّل وكيلًا أحدث مما توزّعه وحدة التحكم يُترك وشأنه. وهذا ما تراه في منتصف ترقية عنقود من مثيلات وحدة التحكم، أو بعد إرجاع وحدة التحكم إلى إصدار سابق.
  • على Linux تمر عبر مدير الحزم. يثبّت الـ Node حزمة .deb أو .rpm الخاصة بوحدة التحكم، فيُظهر dpkg وrpm الإصدار المثبَّت فعليًا.

تغطي اختبارات المشروع الترقيات على macOS وWindows، لكنها لم تُشغَّل بعدُ من البداية إلى النهاية على مضيفي macOS وWindows حقيقيين. أبلِغ عن أي شيء لا يجري كما هو موصوف هنا.

حين تفشل ترقية

تعرض صفحة الـ Node السبب، بكلمات الـ Node نفسه: فشل التنزيل، أو لم يتطابق المجموع الاختباري، أو كان مدير الحزم مشغولًا. وتعيد وحدة التحكم المحاولة بعد خمس دقائق، ثم تنتظر ضعف المدة في كل مرة، وتتوقف بعد خمس حالات فشل على إصدار البناء نفسه.

السبب الأكثر شيوعًا Node لا يستطيع الوصول إلى عنوان URL الأساسي لوحدة التحكم (CONSOLE_BASE_URL)، وهو المكان الذي ينزّل منه الوكيل الجديد. وقد استخدم سكربت التثبيت العنوان نفسه، لذا تحقّق مما تغيّر منذ تثبيت الـ Node.

بعد أن تُصلح السبب، اختر ترقية العميل في صفحة الـ Node لإعادة المحاولة فورًا. يحتاج هذا إلى الإذن nodes:manage وإلى Node متصل. ويعمل سواء كانت الترقيات التلقائية مفعَّلة أم لا، وبعد توقف المحاولات التلقائية.

وتبدأ وحدة التحكم المحاولة مجددًا من تلقاء نفسها حين ترقّيها إلى إصدار يوزّع وكيل Node مختلفًا.

إيقاف الترقيات التلقائية

لمنع وحدة التحكم من ترقية وكلاء الـ Nodes بنفسها، اضبط هذا على كل مثيل من وحدة التحكم وأعِد تشغيله:

CONSOLE_AGENT_AUTO_UPGRADE=false

تظل وحدة التحكم تسجّل إصدار بناء الوكيل لكل Node وتظل تعرض الـ Nodes القديمة. ويظل ترقية العميل في صفحة الـ Node يعمل.

لاستثناء Node واحد بدلًا من ذلك، اضبط NODE_AGENT_ACCEPT_UPGRADES=false لوكيل الـ Node على ذلك الـ Node وأعِد تشغيله:

المنصة أين تضبطه
Linux أضف السطر إلى /etc/node-agent-client/local.env، ثم sudo systemctl restart node-agent-client
Windows اضبطه كمتغير بيئة على مستوى النظام، ثم أعِد تشغيل الخدمة node-agent-client
macOS أضفه إلى EnvironmentVariables في /Library/LaunchDaemons/org.voxpupuli.node-agent-client.plist، ثم أعِد تحميل المهمة (job)

تذكر صفحة الـ Node عندئذ أن الترقيات مرفوضة على ذلك الـ Node، ولا تحاول وحدة التحكم. وعلى macOS، يعيد تشغيل سكربت التثبيت مجددًا كتابة ذلك الملف، لذا اضبطه مجددًا بعد ذلك.

ما تراه الـ Nodes المثبّتة قبل وجود الترقيات التلقائية ما تفعله الترقية وما لا تفعله حين تفشل ترقية إيقاف الترقيات التلقائية

يُوزَّع OpenVox Console على هيئة صور حاويات تُبنى لمعماريتَي amd64 وarm64 مع كل push، وعلى هيئة ملف تنفيذي واحد. تأخذك أدلة التثبيت من مضيف فارغ إلى نشر عامل - openvoxserver وopenvoxdb وPostgres ووحدة التحكم - باستخدام الحاويات أو الحزم.
