التثبيت

التثبيت باستخدام الحاويات

شغّل openvoxserver وopenvoxdb وقاعدتَي البيانات ووحدة التحكم باستخدام Docker Compose، من مضيف فارغ إلى وحدة تحكم جاهزة لاستقبال الـ Nodes.

يشغّل هذا الدليل المنظومة كاملة من ملف compose الإنتاجي للمشروع وصوره المنشورة. لا يُبنى شيء على المضيف. حدّد الأسماء في خطّط للنشر قبل أن تبدأ.

تحتاج إلى مضيف Linux عليه Docker Engine والإضافة Compose، وإلى مستخدم يستطيع تشغيل docker دون sudo.

احصل على ملف compose

الملف docker-compose.yml في مستودع المشروع هو منظومة الإنتاج: وحدة التحكم وقاعدتا البيانات وopenvoxserver وopenvoxdb. انسخ هذا الملف وحده إلى المضيف، في مجلد خاص به يملكه مستخدمك:

sudo mkdir -p /opt/openvox-console sudo chown "$USER": /opt/openvox-console mkdir -p /opt/openvox-console/secrets /opt/openvox-console/certs cd /opt/openvox-console curl -fsSLO https://raw.githubusercontent.com/avitacco/openvox-console/main/docker-compose.yml

لا تنشر من نسخة checkout من المستودع. فنسخة الـ checkout تحمل أيضًا docker-compose.override.yml، وهو منظومة التطوير، الذي يحمّله الأمر docker compose up المجرّد بصمت: كلمات مرور مؤقتة، ومنافذ قواعد بيانات مفتوحة، وتوقيع تلقائي للشهادات. يمرّر كل أمر في هذا الدليل -f docker-compose.yml حتى لا يُقرأ إلا ملف الإنتاج.

اضبط القيم الخاصة بالنشر

أنشئ .env بجوار ملف compose. يرفض ملف compose البدء ما دام أيٌّ من المتغيرات الثلاثة الأولى غير مضبوط، فلا يمكن لنشرٍ أن يقلع بقيمة مؤقتة:

CONSOLE_BASE_URL=https://console.example.com CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 OPENVOXDB_POSTGRES_PASSWORD=<a strong password> # Every name nodes or the console use to reach openvoxserver, beyond its # own name "openvoxserver" - see Plan a deployment. OPENVOXSERVER_DNS_ALT_NAMES=puppet.example.com # The Puppet server a node should enroll against, written into the node # install script. Must be one of the names above. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # The first admin user, created only while there are no users. Its # password is a secret file, below. Without this name no admin is # created and nobody can log in. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin # The console's plain-HTTP port, published on loopback only, so the # TLS proxy in front of it is the only way in. See "Put TLS in front of # the console" below. CONSOLE_HTTP_PORT=127.0.0.1:8080

اختر صورة وحدة التحكم التي ستشغّلها. القيمة الافتراضية لـ CONSOLE_IMAGE_TAG هي main، التي تتبع أحدث commit. أما للنشر الذي تريده ثابتًا فثبّت بدلًا من ذلك الوسم غير القابل للتغيير الخاص بـ commit واحد:

CONSOLE_IMAGE_TAG=sha-a1b2c3d

وسوم الإصدارات مثل v1.2.3، وكذلك latest، لا تُنشر إلا عند إصدار نسخة رسمية. وحتى ذلك الحين يفشل طلب latest مع manifest unknown.

اكتب الأسرار

الأسرار ملفات في secrets/، قيمة واحدة لكل ملف، بدل متغيرات البيئة، فلا تظهر أبدًا في docker inspect:

printf '%s' '<console database password>' > secrets/console_postgres_password printf 'postgres://console:%s@console-postgres:5432/console?sslmode=disable' '<console database password>' \ > secrets/console_postgres_dsn printf '%s' '<a strong password, 12 characters or more>' > secrets/console_bootstrap_admin_password chmod 600 secrets/*

يجب أن تستخدم سلسلة اتصال قاعدة بيانات وحدة التحكم كلمة المرور نفسها الموجودة في console_postgres_password. والإعداد sslmode=disable مقصود: فحاوية Postgres تعمل دون TLS، والاتصال لا يغادر شبكة compose أبدًا، فطلب TLS لن يؤدي إلا إلى فشل وحدة التحكم في الاتصال.

يحتاج openvoxserver أيضًا إلى ملف رمز، enc_bridge_token، تملؤه بعد أن تعمل وحدة التحكم. أنشئه فارغًا الآن، لأن openvoxserver لن يبدأ من دونه:

: > secrets/enc_bridge_token

شغّل المرجع المُصدِر للشهادات

openvoxserver هو الـ CA التي تأتي منها شهادة كل جزء آخر، لذا يبدأ أولًا ووحده:

docker compose -f docker-compose.yml up -d openvoxserver

يُنشئ تشغيله الأول الـ CA، وهذا يستغرق دقيقة أو دقيقتين. انتظر حتى يبلّغ بأنه يعمل:

docker compose -f docker-compose.yml exec openvoxserver \ curl -ksS https://127.0.0.1:8140/status/v1/simple

الرد هو running.

وحدة التخزين openvoxserver-ca هي المرجع المُصدِر للشهادات لديك. وفقدانها يعني أن على كل Node أن يسجّل من جديد. احفظ نسخة احتياطية منها، ولا تُزِلها أبدًا باستخدام docker compose down -v.

أصدِر شهادات وحدة التحكم

تحتاج وحدة التحكم إلى شهادتين من الـ CA، واختياريًا إلى ثالثة. أصدِرها داخل حاوية openvoxserver العاملة وانسخها إلى certs/، حيث يركّبها ملف compose لوحدة التحكم.

شهادة عميل openvoxdb

بهذه الشهادة تصادق وحدة التحكم على نفسها لدى openvoxdb:

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname console docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console.pem certs/console-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console.pem certs/console-key.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/ca.pem certs/ca.pem

يبدأ puppetserver ca generate بطباعة Error: Signed certificate console could not be found on the CA. وهذا تحقّقه من أن الاسم غير مستخدم، لا فشلًا. المهم هو الأسطر التي تليه، المنتهية بـ Successfully saved certificate.

شهادة نقل الـ Nodes

تتحقق الـ Nodes من هذه الشهادة عند اتصالها بوحدة التحكم، لذا يجب أن تحمل الاسم الذي تتصل به بالضبط: جزء المضيف من CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR.

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/node-transport.pem certs/node-transport-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/node-transport.pem certs/node-transport-key.pem

تصادق الـ Nodes على نفسها في المقابل بشهاداتها الخاصة الصادرة من الـ CA نفسها، ولهذا لا تحتاج وحدة التحكم إلى أي ملف آخر من أجلها.

مفتاح توقيع الرموز

توقّع وحدة التحكم رموز تسجيل الدخول الخاصة بها بمفتاح ES256. وهذا المفتاح لا يأتي من الـ CA. ولّده على أي جهاز باستخدام OpenSSL:

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

احفظ نسخة احتياطية من هذا الملف. ففقدانه يُبطل كل رمز صادر، فيُخرج الجميع من حساباتهم؛ وتسرّبه يتيح لأي أحد سكّ الرموز. راجع تدوير مفتاح توقيع الرموز لاستبداله بأمان.

ولّدها مباشرة داخل certs/:

openssl ecparam -genkey -name prime256v1 -noout -out certs/rbac-signing-key.pem

بيانات اعتماد إدارة الشهادات (اختيارية)

بيانات الاعتماد هذه هي ما يتيح لصفحة Nodes عرض حالة الشهادات، وتوقيع الشهادات وإبطالها وتنظيفها. من دونها لا تسرد وحدة التحكم إلا الـ Nodes التي اتصلت أو أبلغت بالفعل. أما الـ Node الذي ينتظر توقيع شهادته فلا يظهر إطلاقًا، لأن الـ CA هي الجزء الوحيد الذي يعرف بوجوده.

بيانات الاعتماد هذه صلاحية إدارة كاملة على الـ CA. يحمي openvoxserver كل نقطة نهاية للـ CA خلف امتداد تفويض واحد، لذا فإن الشهادة التي تستطيع قراءة الحالات تستطيع أيضًا توقيع شهادة أي Node وإبطالها وتنظيفها. ولا توجد صيغة للقراءة فقط. احتفظ بها حيث تعمل وحدة التحكم فقط، واقرأ إدارة شهادات الـ Nodes قبل إصدارها.

إصدارها يكتب في حالة الـ CA التي يكتب فيها أيضًا openvoxserver أثناء عمله، لذا أوقف openvoxserver أولًا وأصدِرها من حاوية لمرة واحدة تستخدم وحدات التخزين نفسها. يسمّي Compose وحدات التخزين باسم مجلد المشروع، لذا تحقّق من الأسماء الدقيقة أولًا:

docker volume ls | grep openvoxserver

ثم، باستخدام الاسمين اللذين طبعهما:

docker compose -f docker-compose.yml stop openvoxserver docker run --rm --entrypoint "" \ -v openvox-console_openvoxserver-ssl:/etc/puppetlabs/puppet/ssl \ -v openvox-console_openvoxserver-ca:/etc/puppetlabs/puppetserver/ca \ ghcr.io/avitacco/openvox-console-server:main \ puppetserver ca generate --ca-client --force --certname console-ca-client docker compose -f docker-compose.yml start openvoxserver

الخيار --force مطلوب هنا. قبل التوقيع يتحقق الأمر من أن الخادم متوقف فعلًا، وداخل حاوية مجرّدة لا يستطيع معرفة ذلك، لذا فإنه من دون --force يطبع «Could not determine whether Puppet Server is online» ويخرج دون أن يُنشئ شيئًا. اقرأ مخرجاته بدل أن تفترض أنه نجح.

يُفيد بأنه كتب ملفاته تحت مسار .puppetlabs طويل. تجاهل ذلك: ففي وحدات التخزين تستقر الملفات في مكانها المعتاد. انسخها إلى الخارج:

docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem certs/ca-client-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem certs/ca-client-key.pem

ثم أخبر وحدة التحكم بمكان الـ CA، في .env. داخل شبكة compose تصل وحدة التحكم إلى openvoxserver باسم حاويته، وهو موجود دائمًا في شهادة openvoxserver:

CONSOLE_CA_CLIENT_URL=https://openvoxserver:8140

تأكّد من قبول بيانات الاعتماد، من داخل openvoxserver:

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://openvoxserver:8140/puppet-ca/v1/certificate_statuses/all

تعني HTTP 200 أن الـ CA تقبلها.

Tasks

لا يحتاج تشغيل Tasks الخاصة بـ Puppet إلى أي شيء إضافي. تسأل وحدة التحكم openvoxserver عن الـ Tasks التي يحتويها الكود الذي جرى له deploy، على https://openvoxserver:8140، باستخدام شهادة عميل openvoxdb التي أصدرتها بالفعل؛ إذ يسمح openvoxserver لأي شهادة من الـ CA الخاصة به بقراءة الـ Tasks. ولإيقاف الـ Tasks، اضبط العنوان على قيمة فارغة في .env:

CONSOLE_PUPPET_SERVER_URL=

راجع تشغيل الـ Jobs لمعرفة كيفية تشغيلها.

قائمة الفئات

تعرض صفحة مجموعة الـ Nodes الفئات التي يعرّفها الكود الذي جرى له deploy، مع معاملاتها، فتُختار بدل أن تُكتب. تقرؤها وحدة التحكم من openvoxserver عبر الاتصال نفسه المستخدم للـ Tasks.

لا يسمح openvoxserver افتراضيًا لأي شهادة بقراءة الفئات. وتضيف صورة الخادم في ملف compose القاعدة عند كل بدء، سامحةً للشهادة المسمّاة console - أي شهادة عميل openvoxdb التي أصدرتها أعلاه. وإذا أصدرتها باسم آخر، فاضبط ذلك الاسم في .env:

CLASS_DISCOVERY_CERTNAME=my-console-cert

تحقّق من ذلك من داخل openvoxserver، بشهادة وحدة التحكم. تعني HTTP 200 أن القائمة قابلة للقراءة:

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ 'https://openvoxserver:8140/puppet/v3/environment_classes?environment=production'

تعني HTTP 403 أن القاعدة لا تذكر هذه الشهادة. ولا شيء آخر يعتمد على ذلك: إذ تقول صفحة المجموعة عندئذ إن القائمة غير متاحة، وتُدخَل الفئات بالاسم، كما كانت قبل وجود القائمة. راجع تصنيف الـ Nodes.

شغّل كل ما تبقّى

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

يطلب openvoxdb شهادته الخاصة من الـ CA عند تشغيله الأول. ويوقّع ملف compose ذلك الطلب وحده تلقائيًا، عبر قائمة سماح لا تحوي إلا openvoxdb؛ ولا تُوقَّع الـ Nodes بهذه الطريقة أبدًا. ثم ينتظر openvoxdb قاعدة بياناته، وتنتظر وحدة التحكم كليهما. راقبها وهي تعمل:

docker compose -f docker-compose.yml ps

تبلغ كل خدمة الحالة healthy في غضون دقائق قليلة.

إذا لم يصبح openvoxdb سليمًا أبدًا

يستسلم openvoxdb إذا لم يُوقَّع طلب شهادته في غضون دقيقتين، وحين يفعل يكتب الفشل في ملف شهادته نفسه. فترى كل إعادة تشغيل بعد ذلك ملف شهادة، فتتخطى التسجيل، وتفشل مع No certs found in 'ssl-cert' file. ولا يتعافى من تلقاء نفسه. أعِد ضبط هويته بدل إعادة تشغيله:

docker compose -f docker-compose.yml rm -sf openvoxdb docker volume rm openvox-console_openvoxdb-ssl docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca clean --certname openvoxdb docker compose -f docker-compose.yml up -d openvoxdb

يتبع اسم وحدة التخزين اسم مجلد المشروع؛ تحقّق منه باستخدام docker volume ls. وتخطّي ca clean يترك الـ CA محتفظة بشهادة موقَّعة لـ openvoxdb بلا مفتاح مطابق لها، فيفشل التشغيل الجديد مع No keypair on disk and CA already has signed certificate.

ضع TLS أمام وحدة التحكم

تقدّم وحدة التحكم واجهة الويب والـ API الخاصين بها عبر HTTP عادي. ويُوصَل إلى عنوان URL الأساسي https:// عبر وكيل عكسي (reverse proxy) يُنهي TLS ويمرّر الطلبات إلى وحدة التحكم. أي وكيل عكسي يفي بالغرض. وهنا نستخدم Caddy، على مضيف وحدة التحكم:

Debian وUbuntusudo apt-get install -y caddy RHEL وRocky وAlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

وهذا هو عندئذ محتوى /etc/caddy/Caddyfile كاملًا:

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

إذا كانت وحدة التحكم تستمع على منفذ آخر، لأنها تتشارك المضيف مع openvoxdb، فضع ذلك المنفذ في reverse_proxy بدلًا من ذلك.

للاسم الذي يمكن تحليله عبر الإنترنت، يحصل Caddy على الشهادة ويجدّدها بنفسه. أما للاسم الداخلي، فأعطِه شهادة من الـ CA الخاصة بك بسطر tls <cert file> <key file> داخل الكتلة. وللتجربة، يجعل tls internal برنامج Caddy يُصدر شهادة من CA محلية خاصة به، تحذّر منها المتصفحات.

لا تمر عبر الوكيل الوسيط إلا واجهة الويب. أما نقل الـ Nodes، على المنفذ 8142، فيحمل TLS الخاص به ويتحقق من شهادة كل Node بنفسه، لذا يجب أن تصل إليه الـ Nodes مباشرة. لا تضعه أبدًا خلف الوكيل الوسيط.

سجّل الدخول لأول مرة

في تشغيلها الأول تُنشئ وحدة التحكم مخطط قاعدة بياناتها، ثم تُنشئ المسؤول التمهيدي ما دام جدول المستخدمين فارغًا. ويُظهر سجلها ثلاثة أسطر حين تصبح جاهزة:

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

تحقّق من أنها تبلّغ عن نفسها بأنها سليمة، أولًا مباشرة على مضيف وحدة التحكم، ثم عبر وكيل TLS الوسيط على عنوان URL الأساسي لها:

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

يسرد كل رد كل تبعية بالحالة ok. إذا فشل الثاني وحده، فوحدة التحكم سليمة والوكيل الوسيط ليس كذلك. استخدم في الأول منفذ وحدة التحكم الخاص بها إن نقلتها عن 8080. ثم افتح عنوان URL الأساسي لوحدة التحكم، وسجّل الدخول بصفتك المسؤول التمهيدي، وغيّر كلمة مروره فورًا.

يجب أن تتكون كلمة مرور المسؤول التمهيدي من 12 حرفًا على الأقل وألّا تطابق اسم المستخدم الخاص به. وإن لم تكن كذلك، فلا يُنشأ أي مسؤول ولا يستطيع أحد تسجيل الدخول. ويذكر السجل ذلك:

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

اضبط كلمة مرور أطول وشغّل وحدة التحكم مجددًا. راجع كلمات المرور والقفل.

بعد أن تسجّل الدخول وتغيّر كلمة المرور، أزِل إعدادات المسؤول التمهيدي من تهيئة وحدة التحكم. فهي لا تُقرأ إلا ما دام جدول المستخدمين فارغًا، لكن لا داعي لترك كلمة مرور ملقاة هنا وهناك.

اربط التصنيف

يسأل openvoxserver وحدة التحكم عن الفئات التي يحصل عليها كل Node، عبر الـ node terminus القياسي exec في Puppet. ويرسل برنامج صغير، enc-bridge، هذا الطلب نيابة عن openvoxserver، ويحتاج إلى رمز ليفعل ذلك.

أصدِر رمزًا لـ enc-bridge

يحمل رمز الخدمة مجموعة ثابتة من الأذونات تُختار عند إنشائه، دون أي دور. أنشئ رمزًا لا يُسمح له إلا بقراءة التصنيف:

  1. في وحدة التحكم، افتح الإدارة، ثم رموز الخدمة.
  2. تحت رمز خدمة جديد، سمّه enc-bridge وامنحه الإذن enc:read وحده.
  3. اختر إنشاء رمز خدمة.

يُعرض الرمز مرة واحدة. انسخه الآن.

والأمر نفسه عبر الـ API، برمز وصول من تسجيل دخول مسؤول: curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

أعطِ openvoxserver الرمز

تحتوي صورة openvoxserver بالفعل على enc-bridge، وتهيئة Puppet التي تستخدمه، ودالة Hiera التي تتيح للـ Nodes قراءة بيانات التكوين، فكل ما تحتاج إليه هو الرمز. اكتبه في ملف السر الذي أنشأته فارغًا من قبل:

printf '%s' '<the enc:read service token>' > secrets/enc_bridge_token

لا يعمل openvoxserver بصلاحيات root داخل حاويته، ويركّب Compose ملفات الأسرار بالملكية التي لها على المضيف. لذا فإن الملف الذي لا يقرؤه إلا مستخدمك يكون غير مقروء لـ openvoxserver، فيفشل التصنيف. امنح المجموعة 0 صلاحية القراءة واحمِ المجلد بدلًا من ذلك:

sudo chgrp 0 secrets/enc_bridge_token chmod 640 secrets/enc_bridge_token chmod 700 secrets

أعِد إنشاء openvoxserver حتى يقرأ الرمز الجديد:

docker compose -f docker-compose.yml up -d --force-recreate openvoxserver

تحقّق من التصنيف

اسأل enc-bridge مباشرة، بالطريقة التي يشغّله بها openvoxserver. يتحقق هذا من البرنامج والرمز وأذونات الملفات وإجابة وحدة التحكم بأمر واحد:

docker compose -f docker-compose.yml exec -u puppet:0 openvoxserver \ /usr/local/bin/enc-bridge <a certname>

تعني {} أن التصنيف يعمل وأن هذا الـ Node لا يطابق أي مجموعة بعد. أنشئ مجموعة Nodes في صفحة المجموعات في وحدة التحكم تثبّت هذا الـ certname، ثم شغّل الأمر نفسه مرة أخرى، فتعود فئاته:

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

الخطأ هنا هو الفشل الذي ينبغي اكتشافه. تعني permission denied أن الرمز غير قابل للقراءة من المستخدم الذي يعمل openvoxserver باسمه، وتعني الاستجابة 401 أن الرمز خاطئ أو يفتقر إلى enc:read.

إذا فشل تشغيل Puppet التالي لـ Node ما بالرسالة Could not find class <name>، فالتصنيف يعمل: لقد طلبت وحدة التحكم من openvoxserver تضمين فئة لا يعرّفها كود Puppet الخاص بك بعد.

يخزّن openvoxserver الـ Environments مؤقتًا، لذا بعد إضافة كود Puppet أفرغ ذاكرته المؤقتة وإلا استمر الخطأ نفسه:

docker compose -f docker-compose.yml exec openvoxserver sh -c \ 'curl -ksS -X DELETE \ --cert /etc/puppetlabs/puppet/ssl/certs/openvoxserver.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/openvoxserver.pem \ https://127.0.0.1:8140/puppet-admin-api/v1/environment-cache'

الترقية لاحقًا

للانتقال إلى إصدار أحدث من وحدة التحكم، غيّر CONSOLE_IMAGE_TAG (أو اسحب الصورة مجددًا إن كنت تتبع main) ثم شغّل المنظومة مرة أخرى. يعيد Compose إنشاء ما تغيّر فقط:

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

لا ينشر ملف compose منفذ openvoxdb، لذا للفحص أدناه، اسأله من داخل حاويته: docker compose -f docker-compose.yml exec openvoxdb curl -ksS https://127.0.0.1:8081/status/v1/simple

تحقّق من النشر بأكمله

الفحص المتوقَّع
curl -ksS https://<openvoxserver>:8140/status/v1/simple running
curl -ksS https://<openvoxdb>:8081/status/v1/simple، من مكان يستطيع الوصول إليه running
curl -fsS https://console.example.com/health كل تبعية ok
سجل وحدة التحكم عند البدء عمليات الترحيل، ونقل الـ Nodes، وجاهزية وحدة التحكم
تسجيل الدخول بصفتك المسؤول التمهيدي ينجح، وقد تغيّرت كلمة المرور
صفحة المجموعات تطابق مجموعةٌ الـ Nodes التي تتوقعها

وحدة التحكم لديك جاهزة لاستقبال الـ Nodes. تابع مع إضافة Nodes لتسجيل أول Node.

احصل على ملف compose اضبط القيم الخاصة بالنشر اكتب الأسرار شغّل المرجع المُصدِر للشهادات أصدِر شهادات وحدة التحكم شهادة عميل openvoxdb شهادة نقل الـ Nodes مفتاح توقيع الرموز بيانات اعتماد إدارة الشهادات (اختيارية) Tasks قائمة الفئات شغّل كل ما تبقّى إذا لم يصبح openvoxdb سليمًا أبدًا ضع TLS أمام وحدة التحكم سجّل الدخول لأول مرة اربط التصنيف أصدِر رمزًا لـ enc-bridge أعطِ openvoxserver الرمز تحقّق من التصنيف الترقية لاحقًا تحقّق من النشر بأكمله

يُوزَّع OpenVox Console على هيئة صور حاويات تُبنى لمعماريتَي amd64 وarm64 مع كل push، وعلى هيئة ملف تنفيذي واحد. تأخذك أدلة التثبيت من مضيف فارغ إلى نشر عامل - openvoxserver وopenvoxdb وPostgres ووحدة التحكم - باستخدام الحاويات أو الحزم.
