التثبيت

التثبيت من الحزم والملفات التنفيذية

ثبّت openvoxserver وopenvoxdb وPostgres من الحزم، وابنِ وحدة التحكم، وشغّلها كخدمة systemd.

يثبّت هذا الدليل openvoxserver وopenvoxdb وPostgres من حزم OpenVox وحزم التوزيعة، ويشغّل وحدة التحكم كملف تنفيذي واحد تحت systemd. حدّد الأسماء في خطّط للنشر قبل أن تبدأ.

الأوامر مخصصة لـ Debian وUbuntu، مع ما يقابلها في RHEL وRocky Linux وAlmaLinux إلى جانبها حيث تختلف. يمكن أن تقيم الأجزاء على مضيف واحد أو أكثر؛ وحيث تخص خطوةٌ مضيفًا بعينه، فإنها تذكر ذلك.

ثبّت openvoxserver

openvoxserver هو المرجع المُصدِر للشهادات الذي تأتي منه شهادة كل جزء آخر، لذا يأتي أولًا. أضف مستودع OpenVox 8 وثبّته:

Debian وUbuntu. /etc/os-release curl -fsSL -o /tmp/openvox8-release.deb \ "https://apt.voxpupuli.org/openvox8-release-${ID}${VERSION_ID}.deb" sudo apt-get install -y /tmp/openvox8-release.deb sudo apt-get update && sudo apt-get install -y openvox-server RHEL وRocky وAlmaLinuxsudo dnf install -y https://yum.voxpupuli.org/openvox8-release-el-9.noarch.rpm sudo dnf install -y openvox-server

لا تُنشئ الحزمة الـ CA بنفسها. بل يُنشئ تشغيلها الأول الـ CA وشهادة هذا الخادم، الصادرة للـ certname الخاص بالمضيف، وهو عادةً اسمه المؤهَّل بالكامل. وفي الحالة الشائعة لا يبقى ما تفعله سوى تشغيله:

sudo systemctl enable --now puppetserver

لا تشغّل puppetserver ca setup على مضيف لديه CA بالفعل. فهو لا يُنشئ إلا CA غير موجودة بعد، وعلى CA موجودة يتوقف بالرسالة «Existing file at .../ca_crt.pem». وحذف تلك الملفات كما تقترح الرسالة يدمّر الـ CA لديك وكل شهادة أصدرتها على الإطلاق، بما في ذلك شهادة كل Node مسجَّل.

اسمح للـ CA بتوقيع الأسماء البديلة

تحمل شهادة نقل الـ Nodes الخاصة بوحدة التحكم، وشهادة هذا الخادم إن أعدت إصدارها أدناه، أكثر من اسم واحد. وافتراضيًا ترفض الـ CA توقيع مثل هذا الطلب وتتركه قيد الانتظار، لذا اسمح بذلك مرة واحدة. في /etc/puppetlabs/puppetserver/conf.d/ca.conf، أضف الإعداد داخل الكتلة certificate-authority:

certificate-authority: { allow-subject-alt-names: true ... } sudo systemctl restart puppetserver

تحقّق من الأسماء في شهادته

الشهادة صالحة دائمًا للـ certname الخاص بها. إذا كانت الـ Nodes ووحدة التحكم تصل كلتاهما إلى هذا الخادم بالـ certname الخاص به، فلا شيء يحتاج إلى تغيير. وإلا فتحقّق من الأسماء التي تغطيها الشهادة بالفعل:

sudo openssl x509 -in /etc/puppetlabs/puppet/ssl/certs/$(hostname -f).pem \ -noout -subject -ext subjectAltName

إذا كان اسم من خطتك مفقودًا، فأعِد إصدار شهادة هذا الخادم وحدها، لا الـ CA أبدًا. ضبط dns_alt_names بعد ذلك لا يغيّر شهادة موجودة بالفعل، لذا نظّفها وأعِد توليدها والخادم يعمل:

sudo /opt/puppetlabs/bin/puppetserver ca clean --certname $(hostname -f) sudo /opt/puppetlabs/bin/puppetserver ca generate --certname $(hostname -f) \ --subject-alt-names puppet.example.com,openvoxserver sudo systemctl restart puppetserver

على مضيف جديد، يمكنك بدلًا من ذلك ضبط الأسماء قبل التشغيل الأول، وترك ذلك التشغيل يُنشئ الشهادة بها: sudo /opt/puppetlabs/bin/puppet config set --section server dns_alt_names puppet.example.com,openvoxserver

تحقّق من أنه يعمل

curl -ksS https://puppet.example.com:8140/status/v1/simple

الرد هو running.

ثبّت openvoxdb وقاعدة بياناته

سجّل مضيف openvoxdb

لا يطلب openvoxdb شهادة بنفسه: إذ ينسخ إعداده الشهادة التي يملكها مضيفه بالفعل. إذا كان لـ openvoxdb مضيف خاص به، فسجّل ذلك المضيف لدى الـ CA أولًا، ثم وقّع طلبه على الـ CA إن لم تكن الـ CA توقّع تلقائيًا:

sudo /opt/puppetlabs/bin/puppet ssl bootstrap --server puppet.example.com # on the CA host: sudo /opt/puppetlabs/bin/puppetserver ca sign --certname <openvoxdb host>

تخطَّ هذه الخطوة حين يتشارك openvoxdb المضيف مع openvoxserver، الذي لديه شهادة بالفعل.

أنشئ قاعدة بياناته

يحتاج openvoxdb إلى قاعدة بيانات Postgres خاصة به، لا تُنشئها الحزمة:

Debian وUbuntusudo apt-get install -y postgresql sudo systemctl enable --now postgresql RHEL وRocky وAlmaLinuxsudo dnf install -y postgresql-server postgresql-contrib sudo postgresql-setup --initdb # Accept passwords over local connections, which are refused by the # default "ident" rules, and store passwords to match. sudo sed -i -E 's/^(host .*)(ident)$/\1scram-sha-256/' /var/lib/pgsql/data/pg_hba.conf echo "password_encryption = 'scram-sha-256'" | sudo tee -a /var/lib/pgsql/data/postgresql.conf sudo systemctl enable --now postgresql

على RHEL والتوزيعات المعاد بناؤها منها، يأتي pg_trgm أدناه من postgresql-contrib، ويجب أن يسبق تغيير كلمة المرور إنشاء المستخدمين: فكلمة المرور المخزَّنة قبله لا يمكن التحقق منها بالقواعد الجديدة.

sudo -u postgres createuser --pwprompt puppetdb sudo -u postgres createdb --owner=puppetdb puppetdb # openvoxdb refuses to start without this extension, and creating it # needs superuser rights - so it is run as postgres, not as puppetdb. sudo -u postgres psql -d puppetdb -c 'CREATE EXTENSION IF NOT EXISTS pg_trgm;'

تحقّق من أن Postgres يقبل الاتصالات:

pg_isready

ينتهي الرد بـ accepting connections.

على Debian وUbuntu، يُظهر systemctl status postgresql الحالة active (exited)، وهذا طبيعي: فتلك الوحدة لا تفعل سوى تشغيل الوحدة الحقيقية الخاصة بكل عنقود. ويُظهر pg_lsclusters العنقود نفسه بالحالة online.

ثبّت openvoxdb وشغّله

Debian وUbuntusudo apt-get install -y openvoxdb RHEL وRocky وAlmaLinuxsudo dnf install -y openvoxdb

أخبره بمكان قاعدة بياناته. من دون هذا الملف لن يبدأ، وسيخرج مع No subname set in the "database" config.:

[database] subname = //localhost:5432/puppetdb username = puppetdb password = <the password you set above>

احفظ ذلك باسم /etc/puppetlabs/puppetdb/conf.d/database.ini، مستخدمًا اسم مضيف قاعدة البيانات بدل localhost إن كانت في مكان آخر، وقيّد الوصول إليه:

sudo chown puppetdb:puppetdb /etc/puppetlabs/puppetdb/conf.d/database.ini sudo chmod 640 /etc/puppetlabs/puppetdb/conf.d/database.ini

ثم انسخ شهادات المضيف إلى مكانها وشغّله:

sudo /opt/puppetlabs/bin/puppetdb ssl-setup sudo systemctl enable --now puppetdb

إذا فشل في البدء، فالسبب الحقيقي موجود في /var/log/puppetlabs/puppetdb/puppetdb.log؛ أما خطأ systemd نفسه فعادةً ما يكون مجرد نتيجة.

أرسل إليه الـ catalogs والـ Reports

على مضيف openvoxserver، ثبّت الـ terminus الذي يرسل الـ catalogs والـ Reports إلى openvoxdb:

Debian وUbuntusudo apt-get install -y openvoxdb-termini RHEL وRocky وAlmaLinuxsudo dnf install -y openvoxdb-termini

تحقّق من أنه يعمل

يُصرّ منفذ HTTPS الخاص بـ openvoxdb على شهادة عميل، لذا اسأله بشهادة المضيف نفسه. ومن دونها يكون الرد certificate required:

H=$(hostname -f) sudo curl -sS --cert /etc/puppetlabs/puppet/ssl/certs/$H.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/$H.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://$H:8081/status/v1/simple

الرد هو running. قد يُفيد السجل بأن «the read-database user is not configured properly». وهذا يتعلق بمستخدم منفصل للقراءة فقط لا يُعدّه هذا الدليل، ويعمل openvoxdb من دونه.

أنشئ قاعدة بيانات وحدة التحكم

تحتفظ وحدة التحكم ببياناتها في قاعدة بيانات منفصلة عن قاعدة بيانات openvoxdb. وتُنشئ مخططها بنفسها عند التشغيل الأول؛ وكل ما تحتاج إليه قاعدة بيانات فارغة ودور يملكها. على مضيف Postgres:

sudo -u postgres createuser --pwprompt console sudo -u postgres createdb --owner=console console

إذا كانت وحدة التحكم ستعمل على مضيف مختلف، فيجب أن يستمع Postgres أيضًا على الشبكة. فهو يستمع افتراضيًا على localhost فقط، لذا يُرفض الاتصال البعيد حتى لو نجح pg_isready محليًا. اسمح لمضيف وحدة التحكم أو لشبكتها الفرعية، مع تعديل نطاق العناوين:

Debian وUbuntusudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /etc/postgresql/*/main/pg_hba.conf sudo systemctl restart postgresql@*-main.service RHEL وRocky وAlmaLinuxsudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /var/lib/pgsql/data/pg_hba.conf sudo systemctl restart postgresql

تحقّق من أن دور وحدة التحكم يستطيع الاتصال، من مضيف وحدة التحكم (يأتي psql هناك مع الحزمة postgresql-client):

PGPASSWORD='<password>' psql -h <postgres host> -U console -d console -c 'select 1;'

أبقِ علامات الاقتباس المفردة. وإلا فإن الصدفة (shell) توسّع كلمة المرور التي تحتوي على $ قبل أن يراها psql.

أصدِر شهادات وحدة التحكم

تحتاج وحدة التحكم إلى شهادتين من الـ CA، واختياريًا إلى ثالثة. ولّدها على مضيف openvoxserver، ثم انسخها إلى مضيف وحدة التحكم، داخل /etc/openvox-console/. أنشئ ذلك المجلد أولًا، على مضيف وحدة التحكم، مع المستخدم الذي ستعمل وحدة التحكم باسمه:

sudo useradd --system --home-dir /nonexistent --shell /usr/sbin/nologin openvox-console sudo install -d -m 0750 -o root -g openvox-console /etc/openvox-console

شهادة عميل openvoxdb

بهذه الشهادة تصادق وحدة التحكم على نفسها لدى openvoxdb:

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname console

يبدأ puppetserver ca generate بطباعة Error: Signed certificate console could not be found on the CA. وهذا تحقّقه من أن الاسم غير مستخدم، لا فشلًا. المهم هو الأسطر التي تليه، المنتهية بـ Successfully saved certificate.

يكتب ثلاثة ملفات تحتاج إليها وحدة التحكم. انسخها بهذه الأسماء:

على مضيف openvoxserver على مضيف وحدة التحكم
/etc/puppetlabs/puppet/ssl/certs/console.pem /etc/openvox-console/console-cert.pem
/etc/puppetlabs/puppet/ssl/private_keys/console.pem /etc/openvox-console/console-key.pem
/etc/puppetlabs/puppet/ssl/certs/ca.pem /etc/openvox-console/ca.pem

شهادة نقل الـ Nodes

تتحقق الـ Nodes من هذه الشهادة عند اتصالها بوحدة التحكم، لذا يجب أن تحمل الاسم الذي تتصل به بالضبط: جزء المضيف من CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR.

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport

انسخ certs/node-transport.pem وprivate_keys/node-transport.pem بالطريقة نفسها، باسمَي node-transport-cert.pem وnode-transport-key.pem. تصادق الـ Nodes على نفسها في المقابل بشهاداتها الخاصة من الـ CA نفسها، فلا تحتاج وحدة التحكم إلى شيء آخر من أجلها.

مفتاح توقيع الرموز

توقّع وحدة التحكم رموز تسجيل الدخول الخاصة بها بمفتاح ES256. وهذا المفتاح لا يأتي من الـ CA. ولّده على أي جهاز باستخدام OpenSSL:

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

احفظ نسخة احتياطية من هذا الملف. ففقدانه يُبطل كل رمز صادر، فيُخرج الجميع من حساباتهم؛ وتسرّبه يتيح لأي أحد سكّ الرموز. راجع تدوير مفتاح توقيع الرموز لاستبداله بأمان.

ولّده على مضيف وحدة التحكم، داخل /etc/openvox-console/.

بيانات اعتماد إدارة الشهادات (اختيارية)

بيانات الاعتماد هذه هي ما يتيح لصفحة Nodes عرض حالة الشهادات، وتوقيع الشهادات وإبطالها وتنظيفها. من دونها لا تسرد وحدة التحكم إلا الـ Nodes التي اتصلت أو أبلغت بالفعل. أما الـ Node الذي ينتظر توقيع شهادته فلا يظهر إطلاقًا، لأن الـ CA هي الجزء الوحيد الذي يعرف بوجوده.

بيانات الاعتماد هذه صلاحية إدارة كاملة على الـ CA. يحمي openvoxserver كل نقطة نهاية للـ CA خلف امتداد تفويض واحد، لذا فإن الشهادة التي تستطيع قراءة الحالات تستطيع أيضًا توقيع شهادة أي Node وإبطالها وتنظيفها. ولا توجد صيغة للقراءة فقط. احتفظ بها حيث تعمل وحدة التحكم فقط، واقرأ إدارة شهادات الـ Nodes قبل إصدارها.

إصدارها يكتب في حالة الـ CA التي يكتب فيها الخادم العامل أيضًا، لذا أوقف openvoxserver أثناء إصدارها:

sudo systemctl stop puppetserver sudo /opt/puppetlabs/bin/puppetserver ca generate --ca-client --certname console-ca-client sudo systemctl start puppetserver

انسخ certs/console-ca-client.pem وprivate_keys/console-ca-client.pem باسمَي ca-client-cert.pem وca-client-key.pem. ثم تأكّد من أن الـ CA تقبلها، من مضيف وحدة التحكم:

curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/ca-client-cert.pem \ --key /etc/openvox-console/ca-client-key.pem \ --cacert /etc/openvox-console/ca.pem \ https://puppet.example.com:8140/puppet-ca/v1/certificate_statuses/all

تعني HTTP 200 أنه يعمل.

ابنِ وحدة التحكم

وحدة التحكم ملف تنفيذي واحد مدمجة فيه واجهة الويب. لا توجد حزمة لها؛ ابنِها من مستودع الشيفرة المصدرية. تحتاج إلى Go بالإصدار المذكور في go.mod، وإلى git.

git clone https://github.com/avitacco/openvox-console.git cd openvox-console

تقدّم وحدة التحكم أيضًا وكيل الـ Node الذي تثبّته الـ Nodes، من مستودع الحزم الخاص بها، وهؤلاء الوكلاء مدمجون في الملف التنفيذي لوحدة التحكم. ابنِهم أولًا، وإلا فشل كل تثبيت على الـ Nodes مع 404:

make agent-binaries make agent-packages make build

ينتج عن ذلك bin/console وbin/enc-bridge. ثبّت وحدة التحكم على مضيفها:

sudo install -m 0755 bin/console /usr/local/bin/console

هيّئ وحدة التحكم

تُهيَّأ وحدة التحكم بمتغيرات البيئة فقط، في ملف داخل المجلد /etc/openvox-console/ الذي أنشأته لشهاداتها.

ستة إعدادات مطلوبة، وترفض وحدة التحكم البدء من دونها، مع ذكر اسم الإعداد المفقود. ضعها في /etc/openvox-console/console.env:

CONSOLE_POSTGRES_DSN=postgres://console:<password>@<postgres host>:5432/console?sslmode=require CONSOLE_OPENVOXDB_URL=https://<openvoxdb host>:8081 CONSOLE_OPENVOXDB_CERT_FILE=/etc/openvox-console/console-cert.pem CONSOLE_OPENVOXDB_KEY_FILE=/etc/openvox-console/console-key.pem CONSOLE_OPENVOXDB_CA_FILE=/etc/openvox-console/ca.pem CONSOLE_RBAC_SIGNING_KEY_FILE=/etc/openvox-console/rbac-signing-key.pem

يفترض sslmode=require أن Postgres لديك يقدّم TLS، وهذا ما ينبغي أن يكون حين يغادر الاتصال المضيف. إذا كانت وحدة التحكم وPostgres على المضيف نفسه ولم يكن لدى Postgres شهادة، فاستخدم sslmode=disable.

البقية اختيارية، وكل ميزة اختيارية تعطّل نفسها بدل أن تعيق البدء. أما للنشر الفعلي فأضف:

# Where the console listens, and how the outside world reaches it. It # listens on loopback only: the TLS proxy in front of it is the way in. # On a host shared with openvoxdb, which holds 8080, use 127.0.0.1:8088. CONSOLE_HTTP_ADDR=127.0.0.1:8080 CONSOLE_BASE_URL=https://console.example.com # The first admin user, created only while there are no users. The # password needs at least 12 characters. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin CONSOLE_BOOTSTRAP_ADMIN_PASSWORD=<a strong password> # The node transport. ADDR is what the console binds; PUBLIC_ADDR is what # a node dials, and its host must be in the node transport certificate. CONSOLE_NODE_TRANSPORT_ADDR=:8142 CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 CONSOLE_NODE_TRANSPORT_CERT_FILE=/etc/openvox-console/node-transport-cert.pem CONSOLE_NODE_TRANSPORT_KEY_FILE=/etc/openvox-console/node-transport-key.pem CONSOLE_NODE_TRANSPORT_CA_FILE=/etc/openvox-console/ca.pem # The Puppet server a node should enroll against, written into the node # install script. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # Certificate management from the Nodes page (the optional credential). CONSOLE_CA_CLIENT_URL=https://puppet.example.com:8140 CONSOLE_CA_CLIENT_CERT_FILE=/etc/openvox-console/ca-client-cert.pem CONSOLE_CA_CLIENT_KEY_FILE=/etc/openvox-console/ca-client-key.pem CONSOLE_CA_CLIENT_CA_FILE=/etc/openvox-console/ca.pem # Puppet tasks: where the console asks which tasks your deployed code # contains. Uses the openvoxdb client certificate above unless you name # another with CONSOLE_PUPPET_SERVER_CERT_FILE, _KEY_FILE and _CA_FILE. CONSOLE_PUPPET_SERVER_URL=https://puppet.example.com:8140

لا تحتاج الـ Tasks إلى شهادة خاصة بها: إذ يسمح openvoxserver لأي شهادة من الـ CA الخاصة به بقراءة الـ Tasks، فتؤدي شهادة عميل openvoxdb الغرض. لا توجّهها إلى بيانات اعتماد إدارة الشهادات، التي تستطيع فعل ما هو أكثر بكثير مما تحتاج إليه قراءة الـ Tasks. راجع تشغيل الـ Jobs لمعرفة كيفية تشغيلها.

اسمح لوحدة التحكم بقراءة قائمة الفئات

تعرض صفحة مجموعة الـ Nodes الفئات التي يعرّفها الكود الذي جرى له deploy، مع معاملاتها، فتُختار بدل أن تُكتب. تقرؤها وحدة التحكم من openvoxserver عبر الاتصال نفسه المستخدم للـ Tasks، لكن openvoxserver لا يسمح لأي شهادة بقراءة الفئات حتى تقول قاعدة ذلك.

على مضيف openvoxserver، أضف هذه القاعدة إلى القائمة rules في /etc/puppetlabs/puppetserver/conf.d/auth.conf، فوق القاعدة الأخيرة puppetlabs deny all. وconsole هو اسم شهادة عميل openvoxdb التي أصدرتها أعلاه:

{ match-request: { path: "/puppet/v3/environment_classes" type: path method: get } allow: "console" sort-order: 500 name: "openvox console class discovery" },

ثم أعِد تحميل openvoxserver:

sudo systemctl reload puppetserver

تحقّق من ذلك من مضيف وحدة التحكم. تعني HTTP 200 أن القائمة قابلة للقراءة:

sudo curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/console-cert.pem \ --key /etc/openvox-console/console-key.pem \ --cacert /etc/openvox-console/ca.pem \ 'https://puppet.example.com:8140/puppet/v3/environment_classes?environment=production'

تعني HTTP 403 أن القاعدة مفقودة أو تذكر شهادة أخرى. ولا شيء آخر يعتمد على هذه الخطوة: فمن دونها تقول صفحة المجموعة إن القائمة غير متاحة، وتُدخَل الفئات بالاسم. راجع تصنيف الـ Nodes.

احتفظ بالأسرار في ملفات

يمكن قراءة أي إعداد من ملف بدلًا من ذلك: حدّد الملف في اسم الإعداد متبوعًا بـ _FILE. وهذا يُبقي كلمات المرور خارج بيئة العملية:

CONSOLE_POSTGRES_DSN_FILE=/etc/openvox-console/postgres-dsn CONSOLE_BOOTSTRAP_ADMIN_PASSWORD_FILE=/etc/openvox-console/bootstrap-admin-password

يُتجاهَل سطر جديد في نهاية الملف. والملف المحدَّد الذي تتعذّر قراءته يمنع وحدة التحكم من البدء، بدل أن يتركها تبدأ والقيمة فارغة بصمت.

أخيرًا، اجعل كل ملف قابلًا للقراءة من مستخدم وحدة التحكم ولا أحد غيره:

sudo sh -c 'chown root:openvox-console /etc/openvox-console/* && chmod 0640 /etc/openvox-console/*'

الأمر sh -c مهم: فالصدفة (shell) الخاصة بك لا تستطيع سرد ذلك المجلد، لذا يفشل الأمر المجرّد sudo chown ... /etc/openvox-console/* بالرسالة «No such file or directory».

شغّلها تحت systemd

أنشئ /etc/systemd/system/openvox-console.service:

[Unit] Description=OpenVox Console After=network-online.target Wants=network-online.target [Service] EnvironmentFile=/etc/openvox-console/console.env ExecStart=/usr/local/bin/console Restart=on-failure User=openvox-console Group=openvox-console [Install] WantedBy=multi-user.target

ثم شغّلها:

sudo systemctl daemon-reload sudo systemctl enable --now openvox-console journalctl -u openvox-console -f

ضع TLS أمام وحدة التحكم

تقدّم وحدة التحكم واجهة الويب والـ API الخاصين بها عبر HTTP عادي. ويُوصَل إلى عنوان URL الأساسي https:// عبر وكيل عكسي (reverse proxy) يُنهي TLS ويمرّر الطلبات إلى وحدة التحكم. أي وكيل عكسي يفي بالغرض. وهنا نستخدم Caddy، على مضيف وحدة التحكم:

Debian وUbuntusudo apt-get install -y caddy RHEL وRocky وAlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

وهذا هو عندئذ محتوى /etc/caddy/Caddyfile كاملًا:

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

إذا كانت وحدة التحكم تستمع على منفذ آخر، لأنها تتشارك المضيف مع openvoxdb، فضع ذلك المنفذ في reverse_proxy بدلًا من ذلك.

للاسم الذي يمكن تحليله عبر الإنترنت، يحصل Caddy على الشهادة ويجدّدها بنفسه. أما للاسم الداخلي، فأعطِه شهادة من الـ CA الخاصة بك بسطر tls <cert file> <key file> داخل الكتلة. وللتجربة، يجعل tls internal برنامج Caddy يُصدر شهادة من CA محلية خاصة به، تحذّر منها المتصفحات.

لا تمر عبر الوكيل الوسيط إلا واجهة الويب. أما نقل الـ Nodes، على المنفذ 8142، فيحمل TLS الخاص به ويتحقق من شهادة كل Node بنفسه، لذا يجب أن تصل إليه الـ Nodes مباشرة. لا تضعه أبدًا خلف الوكيل الوسيط.

سجّل الدخول لأول مرة

في تشغيلها الأول تُنشئ وحدة التحكم مخطط قاعدة بياناتها، ثم تُنشئ المسؤول التمهيدي ما دام جدول المستخدمين فارغًا. ويُظهر سجلها ثلاثة أسطر حين تصبح جاهزة:

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

تحقّق من أنها تبلّغ عن نفسها بأنها سليمة، أولًا مباشرة على مضيف وحدة التحكم، ثم عبر وكيل TLS الوسيط على عنوان URL الأساسي لها:

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

يسرد كل رد كل تبعية بالحالة ok. إذا فشل الثاني وحده، فوحدة التحكم سليمة والوكيل الوسيط ليس كذلك. استخدم في الأول منفذ وحدة التحكم الخاص بها إن نقلتها عن 8080. ثم افتح عنوان URL الأساسي لوحدة التحكم، وسجّل الدخول بصفتك المسؤول التمهيدي، وغيّر كلمة مروره فورًا.

يجب أن تتكون كلمة مرور المسؤول التمهيدي من 12 حرفًا على الأقل وألّا تطابق اسم المستخدم الخاص به. وإن لم تكن كذلك، فلا يُنشأ أي مسؤول ولا يستطيع أحد تسجيل الدخول. ويذكر السجل ذلك:

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

اضبط كلمة مرور أطول وشغّل وحدة التحكم مجددًا. راجع كلمات المرور والقفل.

بعد أن تسجّل الدخول وتغيّر كلمة المرور، أزِل إعدادات المسؤول التمهيدي من تهيئة وحدة التحكم. فهي لا تُقرأ إلا ما دام جدول المستخدمين فارغًا، لكن لا داعي لترك كلمة مرور ملقاة هنا وهناك.

اربط التصنيف

يسأل openvoxserver وحدة التحكم عن الفئات التي يحصل عليها كل Node، عبر الـ node terminus القياسي exec في Puppet. ويرسل برنامج صغير، enc-bridge، هذا الطلب نيابة عن openvoxserver، ويحتاج إلى رمز ليفعل ذلك.

أصدِر رمزًا لـ enc-bridge

يحمل رمز الخدمة مجموعة ثابتة من الأذونات تُختار عند إنشائه، دون أي دور. أنشئ رمزًا لا يُسمح له إلا بقراءة التصنيف:

  1. في وحدة التحكم، افتح الإدارة، ثم رموز الخدمة.
  2. تحت رمز خدمة جديد، سمّه enc-bridge وامنحه الإذن enc:read وحده.
  3. اختر إنشاء رمز خدمة.

يُعرض الرمز مرة واحدة. انسخه الآن.

والأمر نفسه عبر الـ API، برمز وصول من تسجيل دخول مسؤول: curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

ثبّت enc-bridge على مضيف openvoxserver

انسخ bin/enc-bridge من ناتج البناء لديك إلى مضيف openvoxserver وثبّته:

sudo install -m 0755 enc-bridge /usr/local/bin/enc-bridge

احفظ الرمز حيث لا يستطيع قراءته إلا مستخدم openvoxserver:

printf '%s' '<the enc:read service token>' | sudo tee /etc/puppetlabs/enc-bridge-token >/dev/null sudo chown root:puppet /etc/puppetlabs/enc-bridge-token sudo chmod 0640 /etc/puppetlabs/enc-bridge-token

يقرأ enc-bridge مكان وحدة التحكم، ورمزه، من بيئته، التي يرثها من openvoxserver. أعطِ openvoxserver الاثنين، باستخدام sudo systemctl edit puppetserver:

[Service] Environment=ENC_BRIDGE_URL=https://console.example.com Environment=ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token

يتحقق enc-bridge من شهادة وحدة التحكم مقابل مخزن شهادات النظام على مضيف openvoxserver. إذا كانت شهادة الوكيل الوسيط من الـ CA الخاصة بك، فأضف تلك الـ CA إلى المخزن، وإلا فشل التصنيف مع certificate signed by unknown authority:

Debian وUbuntusudo cp <your CA>.crt /usr/local/share/ca-certificates/ sudo update-ca-certificates RHEL وRocky وAlmaLinuxsudo cp <your CA>.crt /etc/pki/ca-trust/source/anchors/ sudo update-ca-trust

ثم وجّه Puppet إليه، في القسم [server] من /etc/puppetlabs/puppet/puppet.conf، وأعِد تشغيل openvoxserver:

[server] node_terminus = exec external_nodes = /usr/local/bin/enc-bridge sudo systemctl restart puppetserver

اسمح للـ Nodes بقراءة بيانات التكوين

اختياري. يتيح هذا للـ Nodes قراءة بيانات التكوين المضبوطة على مجموعات الـ Nodes باستخدام lookup()، قبل بيانات Hiera في مستودع التحكم لديك. تشغّل الدالة enc-bridge --data، فتستخدم عنوان وحدة التحكم والرمز نفسيهما المستخدمين في التصنيف ولا تحتاج إلى أي تهيئة إضافية. وتحتاج إلى enc-bridge مبنيّ من هذا الإصدار.

يجب تثبيت الدالة في مجلد الدوال الخاص بـ Puppet نفسه، وهو المكان الوحيد الذي يحمّل منه openvoxserver دالة Hiera عامة. من نسخة الـ checkout التي بنيت منها:

sudo install -m 0644 openvoxserver-init/console_config_data.rb \ /opt/puppetlabs/puppet/lib/ruby/vendor_ruby/puppet/functions/console_config_data.rb

ثم أضفها إلى تهيئة Hiera العامة، /etc/puppetlabs/puppet/hiera.yaml، أولًا في التسلسل الهرمي حتى تفوز بيانات وحدة التحكم. تثبّت الحزمة ملفًا مؤقتًا هناك؛ وإن لم تكن قد غيّرته، فاستبدله بهذا:

--- version: 5 hierarchy: - name: "Console configuration data" data_hash: console_config_data

إذا كان لديك بالفعل ملف hiera.yaml عام، فأضف الإدخال إليه وأبقِ إدخالاتك الخاصة بعده.

sudo systemctl restart puppetserver

بعد ترقية الحزمة openvox-agent، تحقّق من أن الملف لا يزال موجودًا، وثبّته مجددًا إن لم يكن كذلك. إذا فشل تشغيل Node بالرسالة «Unable to find 'data_hash' function named 'console_config_data'»، فالدالة ليست في ذلك المجلد. وصورة الحاوية تفعل كل هذا بنفسها عند كل بدء.

تحقّق من التصنيف

شغّل enc-bridge بالطريقة التي يشغّله بها openvoxserver: باسم مستخدمه، وبالإعدادات نفسها. يتحقق هذا من البرنامج والرمز وأذونات الملفات وإجابة وحدة التحكم بأمر واحد:

sudo -u puppet env ENC_BRIDGE_URL=https://console.example.com \ ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token \ /usr/local/bin/enc-bridge <a certname>

تعني {} أن التصنيف يعمل وأن هذا الـ Node لا يطابق أي مجموعة بعد. أنشئ مجموعة Nodes في صفحة المجموعات في وحدة التحكم تثبّت هذا الـ certname، ثم شغّل الأمر نفسه مرة أخرى، فتعود فئاته:

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

الخطأ هنا هو الفشل الذي ينبغي اكتشافه. تعني permission denied أن الرمز غير قابل للقراءة من المستخدم الذي يعمل openvoxserver باسمه، وتعني الاستجابة 401 أن الرمز خاطئ أو يفتقر إلى enc:read.

إذا فشل تشغيل Puppet التالي لـ Node ما بالرسالة Could not find class <name>، فالتصنيف يعمل: لقد طلبت وحدة التحكم من openvoxserver تضمين فئة لا يعرّفها كود Puppet الخاص بك بعد.

الترقية لاحقًا

للانتقال إلى إصدار أحدث من وحدة التحكم، اسحب الشيفرة المصدرية، وأعِد البناء بالترتيب نفسه، وثبّت الملف التنفيذي الجديد وأعِد التشغيل:

git pull make agent-binaries make agent-packages make build sudo install -m 0755 bin/console /usr/local/bin/console sudo systemctl restart openvox-console

تحقّق من النشر بأكمله

الفحص المتوقَّع
curl -ksS https://<openvoxserver>:8140/status/v1/simple running
curl -ksS https://<openvoxdb>:8081/status/v1/simple، من مكان يستطيع الوصول إليه running
curl -fsS https://console.example.com/health كل تبعية ok
سجل وحدة التحكم عند البدء عمليات الترحيل، ونقل الـ Nodes، وجاهزية وحدة التحكم
تسجيل الدخول بصفتك المسؤول التمهيدي ينجح، وقد تغيّرت كلمة المرور
صفحة المجموعات تطابق مجموعةٌ الـ Nodes التي تتوقعها

وحدة التحكم لديك جاهزة لاستقبال الـ Nodes. تابع مع إضافة Nodes لتسجيل أول Node.

ثبّت openvoxserver اسمح للـ CA بتوقيع الأسماء البديلة تحقّق من الأسماء في شهادته تحقّق من أنه يعمل ثبّت openvoxdb وقاعدة بياناته سجّل مضيف openvoxdb أنشئ قاعدة بياناته ثبّت openvoxdb وشغّله أرسل إليه الـ catalogs والـ Reports تحقّق من أنه يعمل أنشئ قاعدة بيانات وحدة التحكم أصدِر شهادات وحدة التحكم شهادة عميل openvoxdb شهادة نقل الـ Nodes مفتاح توقيع الرموز بيانات اعتماد إدارة الشهادات (اختيارية) ابنِ وحدة التحكم هيّئ وحدة التحكم اسمح لوحدة التحكم بقراءة قائمة الفئات احتفظ بالأسرار في ملفات شغّلها تحت systemd ضع TLS أمام وحدة التحكم سجّل الدخول لأول مرة اربط التصنيف أصدِر رمزًا لـ enc-bridge ثبّت enc-bridge على مضيف openvoxserver اسمح للـ Nodes بقراءة بيانات التكوين تحقّق من التصنيف الترقية لاحقًا تحقّق من النشر بأكمله

يُوزَّع OpenVox Console على هيئة صور حاويات تُبنى لمعماريتَي amd64 وarm64 مع كل push، وعلى هيئة ملف تنفيذي واحد. تأخذك أدلة التثبيت من مضيف فارغ إلى نشر عامل - openvoxserver وopenvoxdb وPostgres ووحدة التحكم - باستخدام الحاويات أو الحزم.
