परिनियोजन की योजना बनाएँ कंटेनरों से इंस्टॉल करें पैकेजों और बाइनरी से इंस्टॉल करें Nodes जोड़ें Node प्रमाणपत्र प्रबंधित करें किसी Node को हटाएँ Node एजेंटों को नवीनतम रखें Run modes अधिक इंस्टेंस चलाएँ Nodes का वर्गीकरण करें कोड deploy करें Jobs चलाएँ Plans चलाएँ Jobs शेड्यूल करें उपयोगकर्ता, भूमिकाएँ और टोकन कमज़ोरियों पर नज़र रखें छूटे हुए अपडेट खोजें और लागू करें बिना एजेंट वाले होस्टों पर Tasks चलाएँ अपने कोड से Plans चलाएँ AI एजेंटों को कंसोल का उपयोग करने दें standby डेटाबेस पर failover करें टोकन हस्ताक्षर कुंजी बदलें कंटेनर डेटाबेस को Postgres 18 पर अपग्रेड करें

इंस्टॉल

कंटेनरों से इंस्टॉल करें

openvoxserver, openvoxdb, दोनों डेटाबेस और कंसोल को Docker Compose से चलाइए — खाली होस्ट से Nodes के लिए तैयार कंसोल तक।

यह गाइड पूरे स्टैक को प्रोजेक्ट की प्रोडक्शन compose फ़ाइल और प्रकाशित इमेजों से चलाता है। होस्ट पर कुछ भी build नहीं होता। शुरू करने से पहले परिनियोजन की योजना बनाएँ में नाम तय कर लीजिए।

आपको Docker Engine और Compose plugin वाला एक Linux होस्ट चाहिए, और एक ऐसा उपयोगकर्ता जो sudo के बिना docker चला सके।

compose फ़ाइल प्राप्त करें

प्रोजेक्ट रिपॉज़िटरी में मौजूद docker-compose.yml प्रोडक्शन स्टैक है: कंसोल, दोनों डेटाबेस, openvoxserver और openvoxdb। वह एक फ़ाइल होस्ट पर, उसकी अपनी अलग डायरेक्टरी में कॉपी कीजिए, जिसका स्वामी आपका उपयोगकर्ता हो:

sudo mkdir -p /opt/openvox-console sudo chown "$USER": /opt/openvox-console mkdir -p /opt/openvox-console/secrets /opt/openvox-console/certs cd /opt/openvox-console curl -fsSLO https://raw.githubusercontent.com/avitacco/openvox-console/main/docker-compose.yml

रिपॉज़िटरी के checkout से परिनियोजन न करें। checkout में docker-compose.override.yml भी होती है — यानी डेवलपमेंट स्टैक — जिसे साधारण docker compose up चुपचाप लोड कर लेता है: अस्थायी पासवर्ड, खुले डेटाबेस पोर्ट और स्वचालित प्रमाणपत्र हस्ताक्षर। इस गाइड की हर कमांड -f docker-compose.yml देती है, ताकि केवल प्रोडक्शन फ़ाइल ही पढ़ी जाए।

परिनियोजन के अपने मान सेट करें

compose फ़ाइल के बगल में .env बनाइए। पहले तीन में से कोई भी सेट न होने पर compose फ़ाइल शुरू होने से मना कर देती है, ताकि कोई परिनियोजन प्लेसहोल्डर मान पर चालू न हो सके:

CONSOLE_BASE_URL=https://console.example.com CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 OPENVOXDB_POSTGRES_PASSWORD=<a strong password> # Every name nodes or the console use to reach openvoxserver, beyond its # own name "openvoxserver" - see Plan a deployment. OPENVOXSERVER_DNS_ALT_NAMES=puppet.example.com # The Puppet server a node should enroll against, written into the node # install script. Must be one of the names above. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # The first admin user, created only while there are no users. Its # password is a secret file, below. Without this name no admin is # created and nobody can log in. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin # The console's plain-HTTP port, published on loopback only, so the # TLS proxy in front of it is the only way in. See "Put TLS in front of # the console" below. CONSOLE_HTTP_PORT=127.0.0.1:8080

चुनिए कि कंसोल की कौन-सी इमेज चलानी है। CONSOLE_IMAGE_TAG का डिफ़ॉल्ट main है, जो नवीनतम commit के साथ चलता है। जिस परिनियोजन को आप स्थिर रखना चाहते हैं, उसके लिए इसके बजाय किसी एक commit का अपरिवर्तनीय टैग पिन कीजिए:

CONSOLE_IMAGE_TAG=sha-a1b2c3d

v1.2.3 जैसे संस्करण टैग, और latest, केवल release जारी होने के बाद ही प्रकाशित होते हैं। तब तक latest माँगना manifest unknown के साथ विफल होता है।

गोपनीय मान लिखें

गोपनीय मान environment variables नहीं, बल्कि secrets/ में फ़ाइलें होते हैं, हर फ़ाइल में एक मान, ताकि वे कभी docker inspect में न दिखें:

printf '%s' '<console database password>' > secrets/console_postgres_password printf 'postgres://console:%s@console-postgres:5432/console?sslmode=disable' '<console database password>' \ > secrets/console_postgres_dsn printf '%s' '<a strong password, 12 characters or more>' > secrets/console_bootstrap_admin_password chmod 600 secrets/*

कंसोल की डेटाबेस connection string में वही पासवर्ड होना चाहिए जो console_postgres_password में है। sslmode=disable जानबूझकर रखा गया है: Postgres कंटेनर TLS के बिना चलता है, और कनेक्शन कभी compose नेटवर्क से बाहर नहीं जाता, इसलिए TLS माँगने से कंसोल बस कनेक्ट होने में विफल हो जाएगा।

openvoxserver को एक टोकन फ़ाइल, enc_bridge_token, की भी ज़रूरत है, जिसे आप कंसोल चालू होने के बाद भरते हैं। अभी इसे खाली बना दीजिए, क्योंकि इसके बिना openvoxserver शुरू नहीं होगा:

: > secrets/enc_bridge_token

प्रमाणपत्र प्राधिकरण शुरू करें

openvoxserver ही वह CA है जिससे बाक़ी हर हिस्से का प्रमाणपत्र आता है, इसलिए यह सबसे पहले और अकेले शुरू होता है:

docker compose -f docker-compose.yml up -d openvoxserver

इसकी पहली शुरुआत CA बनाती है, जिसमें एक-दो मिनट लगते हैं। तब तक प्रतीक्षा कीजिए जब तक यह स्वयं को चालू न बताए:

docker compose -f docker-compose.yml exec openvoxserver \ curl -ksS https://127.0.0.1:8140/status/v1/simple

उत्तर running होता है।

openvoxserver-ca volume ही आपका प्रमाणपत्र प्राधिकरण है। इसके खोने का अर्थ है कि हर Node को फिर से नामांकित होना पड़ेगा। इसका बैकअप लीजिए, और इसे कभी docker compose down -v से न हटाइए।

कंसोल के प्रमाणपत्र जारी करें

कंसोल को CA से दो प्रमाणपत्र चाहिए, और वैकल्पिक रूप से एक तीसरा। उन्हें चालू openvoxserver कंटेनर के भीतर जारी कीजिए और certs/ में कॉपी कीजिए, जहाँ से compose फ़ाइल उन्हें कंसोल के लिए माउंट करती है।

openvoxdb क्लाइंट प्रमाणपत्र

इसी से कंसोल openvoxdb के समक्ष प्रमाणित होता है:

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname console docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console.pem certs/console-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console.pem certs/console-key.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/ca.pem certs/ca.pem

puppetserver ca generate शुरुआत में Error: Signed certificate console could not be found on the CA छापता है। यह विफलता नहीं, बल्कि इस बात की जाँच है कि नाम उपलब्ध है। महत्वपूर्ण वे पंक्तियाँ हैं जो इसके बाद आती हैं और Successfully saved certificate पर समाप्त होती हैं।

Node ट्रांसपोर्ट प्रमाणपत्र

Nodes कंसोल से जुड़ते समय इस प्रमाणपत्र की जाँच करते हैं, इसलिए इसमें ठीक वही नाम होना चाहिए जिस पर वे कनेक्ट करते हैं: CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR का होस्ट वाला हिस्सा।

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/node-transport.pem certs/node-transport-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/node-transport.pem certs/node-transport-key.pem

Nodes बदले में उसी CA से मिले अपने प्रमाणपत्रों से प्रमाणित होते हैं, इसीलिए कंसोल को उनके लिए किसी और फ़ाइल की ज़रूरत नहीं होती।

टोकन हस्ताक्षर कुंजी

कंसोल अपने लॉगिन टोकनों पर एक ES256 कुंजी से हस्ताक्षर करता है। यह कुंजी CA से नहीं आती। इसे किसी भी मशीन पर OpenSSL से बनाइए:

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

इस फ़ाइल का बैकअप लीजिए। इसके खोने से हर जारी टोकन अमान्य हो जाता है, जिससे सभी लॉग आउट हो जाते हैं; इसके लीक होने से कोई भी टोकन गढ़ सकता है। इसे सुरक्षित रूप से बदलने के लिए देखें टोकन हस्ताक्षर कुंजी बदलें।

इसे सीधे certs/ में बनाइए:

openssl ecparam -genkey -name prime256v1 -noout -out certs/rbac-signing-key.pem

certificate-admin क्रेडेंशियल (वैकल्पिक)

यही क्रेडेंशियल Nodes पृष्ठ को प्रमाणपत्र की स्थिति दिखाने, और प्रमाणपत्रों पर हस्ताक्षर करने, उन्हें निरस्त करने और साफ़ करने देता है। इसके बिना कंसोल केवल वही Nodes सूचीबद्ध करता है जो पहले ही कनेक्ट हो चुके हैं या रिपोर्ट कर चुके हैं। जो Node अपने प्रमाणपत्र पर हस्ताक्षर की प्रतीक्षा कर रहा है, वह दिखता ही नहीं, क्योंकि केवल CA ही जानता है कि वह मौजूद है।

यह क्रेडेंशियल पूर्ण CA admin है। openvoxserver हर CA endpoint को एक ही authorization extension के पीछे रखता है, इसलिए जो प्रमाणपत्र स्थितियाँ पढ़ सकता है, वह किसी भी Node के प्रमाणपत्र पर हस्ताक्षर कर सकता है, उसे निरस्त और साफ़ भी कर सकता है। इसका कोई केवल-पढ़ने वाला रूप नहीं है। इसे केवल वहीं रखिए जहाँ कंसोल चलता है, और जारी करने से पहले Node प्रमाणपत्र प्रबंधित करें पढ़िए।

इसे जारी करना उस CA स्थिति में लिखता है जिसमें चालू openvoxserver भी लिखता है, इसलिए पहले openvoxserver को रोकिए और उन्हीं volumes का उपयोग करने वाले एक बार के कंटेनर से इसे जारी कीजिए। Compose volumes के नाम प्रोजेक्ट डायरेक्टरी के नाम पर रखता है, इसलिए पहले सटीक नाम जाँच लीजिए:

docker volume ls | grep openvoxserver

फिर, उसके द्वारा छापे गए दोनों नामों का उपयोग करते हुए:

docker compose -f docker-compose.yml stop openvoxserver docker run --rm --entrypoint "" \ -v openvox-console_openvoxserver-ssl:/etc/puppetlabs/puppet/ssl \ -v openvox-console_openvoxserver-ca:/etc/puppetlabs/puppetserver/ca \ ghcr.io/avitacco/openvox-console-server:main \ puppetserver ca generate --ca-client --force --certname console-ca-client docker compose -f docker-compose.yml start openvoxserver

यहाँ --force आवश्यक है। हस्ताक्षर करने से पहले कमांड जाँचती है कि सर्वर सचमुच बंद है, और एक साधारण कंटेनर के भीतर वह यह पता नहीं लगा पाती, इसलिए --force के बिना वह "Could not determine whether Puppet Server is online" छापकर कुछ भी बनाए बिना बाहर निकल जाती है। यह मान लेने के बजाय कि काम हो गया, उसका आउटपुट पढ़िए।

यह बताता है कि इसने अपनी फ़ाइलें एक लंबे .puppetlabs पथ के अंतर्गत लिखी हैं। इसे अनदेखा कीजिए: volumes में वे सामान्य स्थान पर ही पहुँचती हैं। उन्हें बाहर कॉपी कीजिए:

docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem certs/ca-client-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem certs/ca-client-key.pem

फिर .env में कंसोल को बताइए कि CA कहाँ है। compose नेटवर्क के भीतर कंसोल openvoxserver तक उसके कंटेनर नाम से पहुँचता है, जो openvoxserver के प्रमाणपत्र में हमेशा होता है:

CONSOLE_CA_CLIENT_URL=https://openvoxserver:8140

openvoxserver के भीतर से पुष्टि कीजिए कि क्रेडेंशियल स्वीकार किया जाता है:

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://openvoxserver:8140/puppet-ca/v1/certificate_statuses/all

HTTP 200 का अर्थ है कि CA उसे स्वीकार करता है।

Tasks

Puppet Tasks चलाने के लिए और कुछ नहीं चाहिए। कंसोल, आपके पहले से जारी openvoxdb क्लाइंट प्रमाणपत्र का उपयोग करते हुए, https://openvoxserver:8140 पर openvoxserver से पूछता है कि आपके deploy किए गए कोड में कौन-से Tasks हैं; openvoxserver अपने CA के किसी भी प्रमाणपत्र को Tasks पढ़ने देता है। Tasks बंद करने के लिए .env में पता खाली सेट कीजिए:

CONSOLE_PUPPET_SERVER_URL=

इन्हें चलाने के लिए देखें Jobs चलाएँ।

क्लास सूची

Node समूह का पृष्ठ आपके deploy किए गए कोड द्वारा परिभाषित क्लासें, उनके पैरामीटरों के साथ, प्रस्तुत करता है, ताकि उन्हें टाइप करने के बजाय चुना जा सके। कंसोल उन्हें openvoxserver से उसी कनेक्शन पर पढ़ता है जिस पर Tasks।

openvoxserver डिफ़ॉल्ट रूप से किसी भी प्रमाणपत्र को क्लासें पढ़ने नहीं देता। compose फ़ाइल की server इमेज हर शुरुआत पर यह नियम जोड़ती है, जो console नाम वाले प्रमाणपत्र को अनुमति देता है - यानी ऊपर आपके द्वारा जारी openvoxdb क्लाइंट प्रमाणपत्र को। यदि आपने उसे किसी और नाम से जारी किया है, तो वह नाम .env में सेट कीजिए:

CLASS_DISCOVERY_CERTNAME=my-console-cert

इसे openvoxserver के भीतर से, कंसोल के प्रमाणपत्र के साथ जाँचिए। HTTP 200 का अर्थ है कि सूची पढ़ी जा सकती है:

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ 'https://openvoxserver:8140/puppet/v3/environment_classes?environment=production'

HTTP 403 का अर्थ है कि नियम में इस प्रमाणपत्र का नाम नहीं है। और कुछ इस पर निर्भर नहीं है: तब समूह पृष्ठ बताता है कि सूची उपलब्ध नहीं है, और क्लासें नाम से दर्ज की जाती हैं, जैसे सूची के आने से पहले होती थीं। देखें Nodes का वर्गीकरण करें।

बाक़ी सब कुछ शुरू करें

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

openvoxdb पहली शुरुआत पर CA से अपना प्रमाणपत्र माँगता है। compose फ़ाइल ठीक उसी एक अनुरोध पर स्वचालित रूप से हस्ताक्षर करती है, एक allow list के ज़रिये जिसमें केवल openvoxdb है; Nodes पर कभी इस तरह हस्ताक्षर नहीं होते। फिर openvoxdb अपने डेटाबेस की प्रतीक्षा करता है, और कंसोल दोनों की। उन्हें चालू होते देखिए:

docker compose -f docker-compose.yml ps

हर सेवा कुछ ही मिनटों में healthy तक पहुँच जाती है।

यदि openvoxdb कभी स्वस्थ न हो

यदि openvoxdb के प्रमाणपत्र अनुरोध पर दो मिनट के भीतर हस्ताक्षर नहीं होते, तो वह हार मान लेता है, और ऐसा होने पर विफलता को अपनी ही प्रमाणपत्र फ़ाइल में लिख देता है। उसके बाद हर पुनः आरंभ को एक प्रमाणपत्र फ़ाइल दिखती है, वह नामांकन छोड़ देता है, और No certs found in 'ssl-cert' file के साथ विफल होता है। यह अपने-आप ठीक नहीं होता। इसे पुनः आरंभ करने के बजाय इसकी पहचान रीसेट कीजिए:

docker compose -f docker-compose.yml rm -sf openvoxdb docker volume rm openvox-console_openvoxdb-ssl docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca clean --certname openvoxdb docker compose -f docker-compose.yml up -d openvoxdb

volume का नाम प्रोजेक्ट डायरेक्टरी के नाम पर होता है; इसे docker volume ls से जाँचिए। ca clean छोड़ देने से CA के पास openvoxdb का एक हस्ताक्षरित प्रमाणपत्र रह जाता है जिससे मेल खाने वाली कोई कुंजी नहीं होती, और नई शुरुआत No keypair on disk and CA already has signed certificate के साथ विफल होती है।

कंसोल के आगे TLS लगाएँ

कंसोल अपना वेब इंटरफ़ेस और API सादे HTTP पर देता है। https:// base URL तक एक reverse proxy के ज़रिये पहुँचा जाता है जो TLS समाप्त करके अनुरोध कंसोल तक पहुँचाता है। कोई भी reverse proxy काम करता है। यहाँ कंसोल के होस्ट पर Caddy का उपयोग किया गया है:

Debian और Ubuntusudo apt-get install -y caddy RHEL, Rocky और AlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

तब पूरी /etc/caddy/Caddyfile बस इतनी है:

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

यदि कंसोल openvoxdb के साथ होस्ट साझा करने के कारण किसी दूसरे पोर्ट पर सुनता है, तो reverse_proxy में वही पोर्ट डालिए।

इंटरनेट पर resolve हो सकने वाले नाम के लिए Caddy प्रमाणपत्र स्वयं प्राप्त और नवीनीकृत करता है। आंतरिक नाम के लिए, block के भीतर tls <cert file> <key file> पंक्ति से उसे अपने CA का प्रमाणपत्र दीजिए। परीक्षण के लिए, tls internal से Caddy अपने स्थानीय CA से प्रमाणपत्र जारी करता है, जिस पर browsers चेतावनी देते हैं।

केवल वेब इंटरफ़ेस proxy से होकर जाता है। Node ट्रांसपोर्ट, पोर्ट 8142, अपना TLS स्वयं रखता है और हर Node का प्रमाणपत्र स्वयं जाँचता है, इसलिए Nodes को उस तक सीधे पहुँचना चाहिए। इसे कभी proxy के पीछे न रखें।

पहली बार लॉग इन करें

पहली शुरुआत पर कंसोल अपना डेटाबेस schema बनाता है, फिर users तालिका के खाली रहते ही bootstrap admin बनाता है। चालू होने पर उसके लॉग में तीन पंक्तियाँ दिखती हैं:

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

जाँचिए कि यह स्वयं को स्वस्थ बताता है, पहले सीधे कंसोल के होस्ट पर, फिर उसके base URL पर TLS proxy के ज़रिये:

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

हर उत्तर हर निर्भरता को ok के रूप में सूचीबद्ध करता है। यदि केवल दूसरा विफल हो, तो कंसोल ठीक है और proxy नहीं। यदि आपने कंसोल को 8080 से हटाया है, तो पहले में कंसोल का अपना पोर्ट उपयोग कीजिए। फिर कंसोल का base URL खोलिए, bootstrap admin के रूप में लॉग इन कीजिए, और उसका पासवर्ड तुरंत बदल दीजिए।

bootstrap admin के पासवर्ड में कम से कम 12 अक्षर होने चाहिए और वह उसके username जैसा नहीं होना चाहिए। अन्यथा कोई admin नहीं बनता और कोई लॉग इन नहीं कर सकता। लॉग यह बताता है:

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

लंबा पासवर्ड सेट कीजिए और कंसोल फिर से शुरू कीजिए। देखें पासवर्ड और लॉकआउट।

लॉग इन करके पासवर्ड बदल लेने के बाद, कंसोल के कॉन्फ़िगरेशन से bootstrap admin सेटिंग्स हटा दीजिए। वे केवल तभी पढ़ी जाती हैं जब users तालिका खाली हो, फिर भी किसी पासवर्ड को यूँ ही पड़ा रहने देने का कोई कारण नहीं है।

वर्गीकरण जोड़ें

openvoxserver, Puppet के मानक exec node terminus के ज़रिये, कंसोल से पूछता है कि हर Node को कौन-सी क्लासें मिलेंगी। एक छोटा प्रोग्राम, enc-bridge, openvoxserver की ओर से यह अनुरोध करता है, और इसके लिए उसे एक टोकन चाहिए।

enc-bridge के लिए टोकन जारी करें

सेवा टोकन में अनुमतियों का एक निश्चित समुच्चय होता है जो उसे बनाते समय चुना जाता है, बिना किसी भूमिका के। ऐसा एक टोकन बनाइए जिसे केवल वर्गीकरण पढ़ने की अनुमति हो:

  1. कंसोल में प्रशासन खोलिए, फिर सेवा टोकन।
  2. नया सेवा टोकन के अंतर्गत इसका नाम enc-bridge रखिए और इसे केवल enc:read अनुमति दीजिए।
  3. सेवा टोकन बनाएँ चुनिए।

टोकन केवल एक बार दिखाया जाता है। इसे अभी कॉपी कर लीजिए।

यही काम API से, admin लॉगिन के access token के साथ: curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

openvoxserver को टोकन दें

openvoxserver इमेज में enc-bridge, उसका उपयोग करने वाला Puppet कॉन्फ़िगरेशन, और Nodes को कॉन्फ़िगरेशन डेटा पढ़ने देने वाला Hiera function पहले से है, इसलिए इसे केवल टोकन चाहिए। इसे उस secret फ़ाइल में लिखिए जिसे आपने पहले खाली बनाया था:

printf '%s' '<the enc:read service token>' > secrets/enc_bridge_token

openvoxserver अपने कंटेनर के भीतर root के रूप में नहीं चलता, और Compose गोपनीय फ़ाइलों को होस्ट पर उनके स्वामित्व के साथ ही माउंट करता है। इसलिए जो फ़ाइल केवल आपके अपने उपयोगकर्ता द्वारा पढ़ी जा सकती है, उसे openvoxserver नहीं पढ़ सकता, और वर्गीकरण विफल हो जाता है। इसके बजाय group 0 को पढ़ने की अनुमति दीजिए और डायरेक्टरी को सुरक्षित कीजिए:

sudo chgrp 0 secrets/enc_bridge_token chmod 640 secrets/enc_bridge_token chmod 700 secrets

openvoxserver को दोबारा बनाइए ताकि वह नया टोकन पढ़े:

docker compose -f docker-compose.yml up -d --force-recreate openvoxserver

वर्गीकरण जाँचें

enc-bridge से सीधे पूछिए, ठीक वैसे जैसे openvoxserver उसे चलाता है। यह एक ही कमांड में प्रोग्राम, टोकन, फ़ाइल अनुमतियाँ और कंसोल का उत्तर जाँच लेता है:

docker compose -f docker-compose.yml exec -u puppet:0 openvoxserver \ /usr/local/bin/enc-bridge <a certname>

{} का अर्थ है कि वर्गीकरण काम कर रहा है और वह Node अभी किसी समूह से मेल नहीं खाता। कंसोल के समूह पृष्ठ पर एक Node समूह बनाइए जो उस certname को पिन करे, वही कमांड फिर चलाइए, और उसकी क्लासें लौट आती हैं:

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

यहाँ आने वाली त्रुटि ही वह विफलता है जिसे पकड़ना है। permission denied का अर्थ है कि openvoxserver जिस उपयोगकर्ता के रूप में चलता है, वह टोकन को पढ़ नहीं सकता, और 401 का अर्थ है कि टोकन गलत है या उसमें enc:read नहीं है।

यदि किसी Node का अगला Puppet रन Could not find class <name> के साथ विफल होता है, तो वर्गीकरण काम कर रहा है: कंसोल ने openvoxserver से एक ऐसी क्लास शामिल करने को कहा है जिसे आपका Puppet कोड अभी परिभाषित नहीं करता।

openvoxserver Environments को कैश करता है, इसलिए Puppet कोड जोड़ने के बाद उसका कैश साफ़ कीजिए, वरना वही त्रुटि बनी रहती है:

docker compose -f docker-compose.yml exec openvoxserver sh -c \ 'curl -ksS -X DELETE \ --cert /etc/puppetlabs/puppet/ssl/certs/openvoxserver.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/openvoxserver.pem \ https://127.0.0.1:8140/puppet-admin-api/v1/environment-cache'

बाद में अपग्रेड करें

नए कंसोल पर जाने के लिए CONSOLE_IMAGE_TAG बदलिए (या यदि आप main का अनुसरण करते हैं तो फिर से pull कीजिए) और स्टैक को दोबारा चालू कीजिए। Compose केवल वही दोबारा बनाता है जो बदला है:

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

compose फ़ाइल openvoxdb का पोर्ट प्रकाशित नहीं करती, इसलिए नीचे की जाँच के लिए उससे उसके कंटेनर के भीतर से पूछिए: docker compose -f docker-compose.yml exec openvoxdb curl -ksS https://127.0.0.1:8081/status/v1/simple

पूरे परिनियोजन की जाँच करें

जाँच अपेक्षित परिणाम
curl -ksS https://<openvoxserver>:8140/status/v1/simple running
curl -ksS https://<openvoxdb>:8081/status/v1/simple, किसी ऐसी जगह से जो उस तक पहुँच सके running
curl -fsS https://console.example.com/health हर निर्भरता ok
शुरू होने पर कंसोल का लॉग migrations, Node ट्रांसपोर्ट, कंसोल तैयार
bootstrap admin के रूप में लॉग इन करना सफल होता है, और पासवर्ड बदल दिया गया है
समूह पृष्ठ कोई समूह उन्हीं Nodes से मेल खाता है जिनकी आप अपेक्षा करते हैं

आपका कंसोल Nodes के लिए तैयार है। पहला Node नामांकित करने के लिए Nodes जोड़ें पर आगे बढ़िए।

compose फ़ाइल प्राप्त करें परिनियोजन के अपने मान सेट करें गोपनीय मान लिखें प्रमाणपत्र प्राधिकरण शुरू करें कंसोल के प्रमाणपत्र जारी करें openvoxdb क्लाइंट प्रमाणपत्र Node ट्रांसपोर्ट प्रमाणपत्र टोकन हस्ताक्षर कुंजी certificate-admin क्रेडेंशियल (वैकल्पिक) Tasks क्लास सूची बाक़ी सब कुछ शुरू करें यदि openvoxdb कभी स्वस्थ न हो कंसोल के आगे TLS लगाएँ पहली बार लॉग इन करें वर्गीकरण जोड़ें enc-bridge के लिए टोकन जारी करें openvoxserver को टोकन दें वर्गीकरण जाँचें बाद में अपग्रेड करें पूरे परिनियोजन की जाँच करें

OpenVox Console कंटेनर इमेजों के रूप में आता है, जो हर push पर amd64 और arm64 के लिए बनती हैं, और एक अकेली बाइनरी के रूप में भी। इंस्टॉल गाइड आपको खाली होस्ट से एक चालू परिनियोजन तक ले जाते हैं - openvoxserver, openvoxdb, Postgres और कंसोल - कंटेनरों से या पैकेजों से।
