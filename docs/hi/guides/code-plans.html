परिनियोजन की योजना बनाएँ कंटेनरों से इंस्टॉल करें पैकेजों और बाइनरी से इंस्टॉल करें Nodes जोड़ें Node प्रमाणपत्र प्रबंधित करें किसी Node को हटाएँ Node एजेंटों को नवीनतम रखें Run modes अधिक इंस्टेंस चलाएँ Nodes का वर्गीकरण करें कोड deploy करें Jobs चलाएँ Plans चलाएँ Jobs शेड्यूल करें उपयोगकर्ता, भूमिकाएँ और टोकन कमज़ोरियों पर नज़र रखें छूटे हुए अपडेट खोजें और लागू करें बिना एजेंट वाले होस्टों पर Tasks चलाएँ अपने कोड से Plans चलाएँ AI एजेंटों को कंसोल का उपयोग करने दें standby डेटाबेस पर failover करें टोकन हस्ताक्षर कुंजी बदलें कंटेनर डेटाबेस को Postgres 18 पर अपग्रेड करें

उपयोग

अपने कोड से Plans चलाएँ

अपने modules में रखे YAML Plans चलाइए, typed पैरामीटरों के साथ, चरणों के बीच पहुँचाए गए परिणामों के साथ, और हर Task को आपके Node समूहों के विरुद्ध जाँचते हुए।

code plan किसी module की plans डायरेक्टरी में एक YAML फ़ाइल है, उसी प्रारूप में जिसका उपयोग Bolt और Puppet Enterprise करते हैं। कंसोल इसे अपने deploy किए गए कोड से पढ़ता है और स्वयं चलाता है: एक के बाद एक चरण, एक चरण से दूसरे चरण तक परिणाम पहुँचाते हुए। इसके लिए Bolt या Puppet language की ज़रूरत नहीं है।

यह सहेजे गए Plan से अलग है, जो Puppet रनों और Tasks की एक निश्चित सूची है जिसे आप कंसोल में बनाते हैं और जो Nodes के एक समुच्चय पर चलती है। code plan आपके कोड के साथ रहता है, अपने पैरामीटर लेता है, और हर चरण के लक्ष्य पिछले चरणों से तय करता है।

Plans की सूची पढ़ने के लिए orchestrator:read चाहिए। किसी Plan को चलाने के लिए orchestrator:run। कोई नई अनुमति शामिल नहीं है।

Plans कहाँ से आते हैं

कंसोल हर Environment के modules में, environment.conf में modulepath के क्रम में (न हो तो modules), <module>/plans/<name>.yaml खोजता है। Plan का नाम module::name होता है, या init.yaml के लिए केवल module। यदि कोई नाम दो डायरेक्टरी में आए, तो Puppet की तरह पहला जीतता है।

फ़ाइलें आपका कोड deploy करने वाले कंसोल इंस्टेंस की code डायरेक्टरी (CONSOLE_CODE_DIR_PATH) से पढ़ी जाती हैं। जिस इंस्टेंस के पास deploy किया गया कोड नहीं है, वह Plans सूचीबद्ध नहीं कर सकता और न चला सकता है, और खाली सूची दिखाने के बजाय यह बताता है। Plans उसी इंस्टेंस से चलाइए जो deploy करता है।

Jobs खोलिए, फिर Plans: कोड में प्लान खंड किसी Environment के Plans सूचीबद्ध करता है। जिस Plan को कंसोल नहीं चला सकता, वह चरण का नाम बताते हुए कारण सहित सूचीबद्ध होता है।

Plan क्या कर सकता है

Plan में एक description, parameters, steps और एक return होता है:

description: Restart a service, then check it parameters: targets: type: TargetSpec description: Where to restart it service: type: String[1] default: nginx token: type: Optional[Sensitive[String]] steps: - name: restart description: Restart the service task: service::restart targets: $targets parameters: name: $service - name: status task: service::status targets: $restart.ok_targets parameters: name: $service - message: "checked ${status.targets}" return: restarted: $restart.ok_targets healthy: $status.ok

पैरामीटर एक type, एक वैकल्पिक default और एक description घोषित करते हैं। types वही हैं जो Tasks उपयोग करते हैं (String, Integer[1, 10], Boolean, Array[String], Enum['a','b'], Optional[...], ...) और साथ में TargetSpec (Nodes) और Sensitive[...]। जिस पैरामीटर का कोई default नहीं है और जो Optional नहीं है, वह आवश्यक है। अनुपस्थित, अज्ञात या गलत type वाले पैरामीटर वाले रन को कंसोल कुछ भी शुरू होने से पहले ही, पैरामीटर का नाम बताते हुए, अस्वीकार कर देता है।

चरण इनमें से ठीक एक काम करते हैं:

  • task: module::task, targets और parameters के साथ। Task चलाता है।
  • plan: module::plan, parameters के साथ। इस Plan के हिस्से के रूप में दूसरा Plan चलाता है। कोई Plan पाँच स्तर की गहराई तक Plans को कॉल कर सकता है, और स्वयं को कभी नहीं।
  • message: text। रन के रिकॉर्ड में पाठ छापता है।

किसी चरण का एक name हो सकता है, जिससे उसका परिणाम बाद के चरणों को $name के रूप में उपलब्ध होता है, और एक description।

References $name, $name.field, $name[0] और $name['field'] हैं, किसी पैरामीटर या पिछले चरण के लिए। जो string केवल एक reference है, वह मान का type बनाए रखती है (सूची सूची ही रहती है)। पाठ में ${name.field} लिखिए; डॉलर चिह्न के लिए $$ लिखिए। बस इतना ही syntax है: कोई operators नहीं, कोई conditionals नहीं, कोई functions नहीं। एक पंक्ति में लिखी YAML सूची या mapping के भीतर, [ या , वाले reference को quotes में रखिए।

चरण के परिणाम में होता है:

फ़ील्ड इसमें होता है
ok हर लक्ष्य सफल रहा
results हर लक्ष्य का target, ok, value और error
targets, ok_targets, error_targets Node नाम
value Task का परिणाम, किसी एक Node पर चलने वाले चरण के लिए

किसी Task का value वह है जो उसने JSON के रूप में छापा, या उसका पाठ _output के रूप में।

यदि कोई Task चरण किसी भी लक्ष्य पर विफल होता है, तो Plan वहीं विफल हो जाता है: उसके बाद के चरण नहीं चले के रूप में दर्ज होते हैं और आगे कुछ नहीं भेजा जाता। जिस चरण के लक्ष्य खाली हों (मान लीजिए पिछले चरण की कोई सफलता नहीं थी), वह कुछ नहीं चलाता और सफल गिना जाता है।

समर्थित नहीं: command, script, upload, download, resources और eval चरण, Puppet-language expressions, चरणों को समानांतर चलाना, पुनः प्रयास और त्रुटियाँ पकड़ना, और code plan को शेड्यूल करना। इनमें से किसी का उपयोग करने वाला Plan कारण सहित अनुपयोगी के रूप में सूचीबद्ध होता है। Bolt के Puppet-language Plans (.pp) नहीं चलाए जाते।

किसी Plan को चलाएँ

किसी Plan के बगल में चलाएँ चुनिए। फ़ॉर्म उसके पैरामीटरों से बनता है; डिफ़ॉल्ट उपयोग करने के लिए फ़ील्ड खाली छोड़ दीजिए। Nodes (TargetSpec) नामों की सूची, किसी क्वेरी या किसी Node समूह के रूप में दिए जाते हैं, Plan शुरू होने पर एक बार हल किए जाते हैं, और पहले उनका पूर्वावलोकन होता है। रन एक Job के रूप में खुलता है; उसका पृष्ठ हर चरण को होते समय दिखाता है: उसकी स्थिति, उसके द्वारा शुरू किया गया Job, किसी message ने क्या छापा, और कोई चरण क्यों विफल हुआ, साथ ही Plan द्वारा लौटाया गया मान और उसे दिए गए पैरामीटर।

दायरा और अनुमतियाँ

Plan ऐसा कुछ नहीं कर सकता जो आप हाथ से न कर सकें। जब आप इसे शुरू करते हैं:

  • हर चरण में नामित Task मौजूद होना चाहिए और ऐसा होना चाहिए जिसकी आपकी भूमिकाएँ अनुमति देती हों, वरना अनुरोध चरण का नाम बताते हुए अस्वीकार होता है;
  • आपके द्वारा नामित Nodes आपके Node समूहों में होने चाहिए, वरना पूरा अनुरोध अस्वीकार होता है;
  • हर चरण पर पहुँचते समय, उसके लक्ष्य आपके Node समूहों से और Task आपकी allowlist से जाँचे जाते हैं, ठीक वैसे ही जैसे आपके स्वयं शुरू किए Task को। जो चरण अस्वीकार होने वाला हो, वह कारण सहित Plan को वहीं विफल कर देता है।

Task चरणों में agentless लक्ष्यों का उपयोग किया जा सकता है।

कुछ Node समूहों तक सीमित पाठक को Plan रन तभी दिखता है जब वह उसके Nodes पर चला हो, और यदि वह दूसरों पर भी चला हो, तो उसे यह नहीं दिखता कि उसने क्या छापा, क्या लौटाया या उसे क्या दिया गया।

संवेदनशील मान

Sensitive[...] type वाला पैरामीटर कभी कहीं लिखा नहीं जाता: संग्रहीत पैरामीटरों, trace, संदेशों, लौटाए गए मान, लॉग और ऑडिट प्रविष्टियों में यह [redacted] होता है, और केवल उसी Task पैरामीटर तक पहुँचता है जिसे यह दिया गया है। संवेदनशील मान केवल ऐसे पैरामीटर को आगे दिया जा सकता है जो स्वयं Sensitive हो।

लंबे रन

Plan घंटों तक चल सकता है, अधिकतम 24 घंटे। चलते समय कंसोल Job को बताता रहता है कि वह जीवित है। यदि उस पर नज़र रखने वाला कंसोल इंस्टेंस रुक जाए, तो उससे अंतिम बार सूचना मिलने के दस मिनट बाद Plan विफल हो जाता है; पहले से शुरू हो चुके चरण अपने Nodes पर चलते रहते हैं। एक रन अधिकतम 200 चरणों तक और एक चरण अधिकतम 1000 लक्ष्यों तक सीमित है; कोई सीमा पार होने पर Plan उस सीमा का नाम बताते हुए विफल हो जाता है।

Plan की शुरुआत और उसका अंत ऑडिट प्रविष्टियाँ हैं, जिनमें किसने, कौन-सा Plan और Environment, और दिए गए पैरामीटरों के नाम होते हैं, उनके मान कभी नहीं।

Plans कहाँ से आते हैं Plan क्या कर सकता है किसी Plan को चलाएँ दायरा और अनुमतियाँ संवेदनशील मान लंबे रन
