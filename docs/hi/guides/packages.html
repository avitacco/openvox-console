इंस्टॉल

पैकेजों और बाइनरी से इंस्टॉल करें

openvoxserver, openvoxdb और Postgres को पैकेजों से इंस्टॉल कीजिए, कंसोल build कीजिए, और उसे systemd सेवा के रूप में चलाइए।

यह गाइड openvoxserver, openvoxdb और Postgres को OpenVox और डिस्ट्रीब्यूशन पैकेजों से इंस्टॉल करता है, और कंसोल को systemd के अंतर्गत एक अकेली बाइनरी के रूप में चलाता है। शुरू करने से पहले परिनियोजन की योजना बनाएँ में नाम तय कर लीजिए।

कमांड Debian और Ubuntu के लिए हैं, और जहाँ अंतर है वहाँ RHEL, Rocky Linux और AlmaLinux का समकक्ष साथ में दिया गया है। हिस्से एक होस्ट पर भी रह सकते हैं और कई पर भी; जहाँ कोई क़दम किसी विशेष होस्ट पर करना है, वहाँ यह बताया गया है।

openvoxserver इंस्टॉल करें

openvoxserver वह प्रमाणपत्र प्राधिकरण है जिससे बाक़ी हर हिस्से का प्रमाणपत्र आता है, इसलिए यह सबसे पहले आता है। OpenVox 8 रिपॉज़िटरी जोड़िए और इसे इंस्टॉल कीजिए:

Debian और Ubuntu. /etc/os-release curl -fsSL -o /tmp/openvox8-release.deb \ "https://apt.voxpupuli.org/openvox8-release-${ID}${VERSION_ID}.deb" sudo apt-get install -y /tmp/openvox8-release.deb sudo apt-get update && sudo apt-get install -y openvox-server RHEL, Rocky और AlmaLinuxsudo dnf install -y https://yum.voxpupuli.org/openvox8-release-el-9.noarch.rpm sudo dnf install -y openvox-server

पैकेज स्वयं CA नहीं बनाता। इसकी पहली शुरुआत CA और इस सर्वर का अपना प्रमाणपत्र बनाती है, जो होस्ट के certname, सामान्यतः उसके पूर्ण योग्य नाम, के लिए जारी होता है। सामान्य स्थिति में इसे शुरू करने के अलावा और कुछ नहीं करना होता:

sudo systemctl enable --now puppetserver

जिस होस्ट पर पहले से CA है, उस पर puppetserver ca setup न चलाएँ। यह केवल वही CA बनाता है जो अभी मौजूद नहीं है, और मौजूदा CA पर यह "Existing file at .../ca_crt.pem" के साथ रुक जाता है। संदेश के सुझाव के अनुसार उन फ़ाइलों को हटाने से आपका CA और उसके द्वारा कभी जारी किया गया हर प्रमाणपत्र नष्ट हो जाता है, जिसमें हर नामांकित Node का प्रमाणपत्र भी शामिल है।

CA को वैकल्पिक नामों पर हस्ताक्षर करने दें

कंसोल के Node ट्रांसपोर्ट प्रमाणपत्र में, और यदि आप नीचे इस सर्वर का अपना प्रमाणपत्र दोबारा जारी करते हैं तो उसमें भी, एक से अधिक नाम होते हैं। डिफ़ॉल्ट रूप से CA ऐसे अनुरोध पर हस्ताक्षर करने से मना करता है और उसे प्रतीक्षा में छोड़ देता है, इसलिए एक बार इसकी अनुमति दीजिए। /etc/puppetlabs/puppetserver/conf.d/ca.conf में, certificate-authority block के भीतर यह सेटिंग जोड़िए:

certificate-authority: { allow-subject-alt-names: true ... } sudo systemctl restart puppetserver

इसके प्रमाणपत्र के नाम जाँचें

कोई प्रमाणपत्र अपने certname के लिए हमेशा मान्य होता है। यदि Nodes और कंसोल दोनों इस सर्वर तक उसके certname से पहुँचते हैं, तो कुछ बदलने की ज़रूरत नहीं। अन्यथा जाँचिए कि प्रमाणपत्र पहले से किन नामों को कवर करता है:

sudo openssl x509 -in /etc/puppetlabs/puppet/ssl/certs/$(hostname -f).pem \ -noout -subject -ext subjectAltName

यदि आपकी योजना का कोई नाम छूट गया है, तो केवल इस सर्वर का अपना प्रमाणपत्र दोबारा जारी कीजिए, CA कभी नहीं। बाद में dns_alt_names सेट करने से पहले से मौजूद प्रमाणपत्र नहीं बदलता, इसलिए सर्वर के चलते रहते ही उसे साफ़ करके फिर से बनाइए:

sudo /opt/puppetlabs/bin/puppetserver ca clean --certname $(hostname -f) sudo /opt/puppetlabs/bin/puppetserver ca generate --certname $(hostname -f) \ --subject-alt-names puppet.example.com,openvoxserver sudo systemctl restart puppetserver

नए होस्ट पर, आप इसके बजाय पहली शुरुआत से पहले नाम सेट कर सकते हैं, और उसी शुरुआत को उन नामों के साथ प्रमाणपत्र बनाने दे सकते हैं: sudo /opt/puppetlabs/bin/puppet config set --section server dns_alt_names puppet.example.com,openvoxserver

जाँचें कि यह चल रहा है

curl -ksS https://puppet.example.com:8140/status/v1/simple

उत्तर running होता है।

openvoxdb और उसका डेटाबेस इंस्टॉल करें

openvoxdb के होस्ट को नामांकित करें

openvoxdb स्वयं प्रमाणपत्र का अनुरोध नहीं करता: उसका setup वही प्रमाणपत्र कॉपी कर लेता है जो उसके होस्ट के पास पहले से है। यदि openvoxdb का अपना अलग होस्ट है, तो पहले उस होस्ट को CA के साथ नामांकित कीजिए, फिर यदि CA स्वचालित रूप से हस्ताक्षर नहीं करता, तो CA पर उसके अनुरोध पर हस्ताक्षर कीजिए:

sudo /opt/puppetlabs/bin/puppet ssl bootstrap --server puppet.example.com # on the CA host: sudo /opt/puppetlabs/bin/puppetserver ca sign --certname <openvoxdb host>

जब openvoxdb, openvoxserver के साथ एक ही होस्ट पर हो, तो इसे छोड़ दीजिए, क्योंकि उसके पास पहले से एक प्रमाणपत्र है।

इसका डेटाबेस बनाएँ

openvoxdb को अपना एक Postgres डेटाबेस चाहिए, जिसे पैकेज नहीं बनाता:

Debian और Ubuntusudo apt-get install -y postgresql sudo systemctl enable --now postgresql RHEL, Rocky और AlmaLinuxsudo dnf install -y postgresql-server postgresql-contrib sudo postgresql-setup --initdb # Accept passwords over local connections, which are refused by the # default "ident" rules, and store passwords to match. sudo sed -i -E 's/^(host .*)(ident)$/\1scram-sha-256/' /var/lib/pgsql/data/pg_hba.conf echo "password_encryption = 'scram-sha-256'" | sudo tee -a /var/lib/pgsql/data/postgresql.conf sudo systemctl enable --now postgresql

RHEL और उसके rebuilds पर, नीचे वाला pg_trgm postgresql-contrib से आता है, और पासवर्ड वाला बदलाव उपयोगकर्ता बनाने से पहले करना होगा: उससे पहले संग्रहीत पासवर्ड नए नियमों से जाँचा नहीं जा सकता।

sudo -u postgres createuser --pwprompt puppetdb sudo -u postgres createdb --owner=puppetdb puppetdb # openvoxdb refuses to start without this extension, and creating it # needs superuser rights - so it is run as postgres, not as puppetdb. sudo -u postgres psql -d puppetdb -c 'CREATE EXTENSION IF NOT EXISTS pg_trgm;'

जाँचिए कि Postgres कनेक्शन स्वीकार कर रहा है:

pg_isready

उत्तर accepting connections पर समाप्त होता है।

Debian और Ubuntu पर systemctl status postgresql में active (exited) दिखता है, और यह सामान्य है: वह unit केवल असली प्रति-cluster unit को शुरू करती है। pg_lsclusters स्वयं cluster को online दिखाता है।

openvoxdb इंस्टॉल करें और शुरू करें

Debian और Ubuntusudo apt-get install -y openvoxdb RHEL, Rocky और AlmaLinuxsudo dnf install -y openvoxdb

इसे बताइए कि इसका डेटाबेस कहाँ है। इस फ़ाइल के बिना यह शुरू नहीं होगा, और No subname set in the "database" config. के साथ बाहर निकल जाएगा:

[database] subname = //localhost:5432/puppetdb username = puppetdb password = <the password you set above>

इसे /etc/puppetlabs/puppetdb/conf.d/database.ini के रूप में सहेजिए — यदि डेटाबेस कहीं और है तो localhost के बजाय डेटाबेस होस्ट का नाम उपयोग करते हुए — और इसकी पहुँच सीमित कीजिए:

sudo chown puppetdb:puppetdb /etc/puppetlabs/puppetdb/conf.d/database.ini sudo chmod 640 /etc/puppetlabs/puppetdb/conf.d/database.ini

फिर होस्ट के प्रमाणपत्रों को उनकी जगह कॉपी कीजिए और इसे शुरू कीजिए:

sudo /opt/puppetlabs/bin/puppetdb ssl-setup sudo systemctl enable --now puppetdb

यदि यह शुरू होने में विफल हो, तो असली कारण /var/log/puppetlabs/puppetdb/puppetdb.log में होता है; systemd की अपनी त्रुटि आमतौर पर केवल उसका परिणाम होती है।

catalogs और Reports इसे भेजें

openvoxserver होस्ट पर वह terminus इंस्टॉल कीजिए जो catalogs और Reports को openvoxdb तक भेजता है:

Debian और Ubuntusudo apt-get install -y openvoxdb-termini RHEL, Rocky और AlmaLinuxsudo dnf install -y openvoxdb-termini

जाँचें कि यह चल रहा है

openvoxdb का HTTPS पोर्ट क्लाइंट प्रमाणपत्र माँगता है, इसलिए होस्ट के अपने प्रमाणपत्र के साथ पूछिए। इसके बिना उत्तर certificate required होता है:

H=$(hostname -f) sudo curl -sS --cert /etc/puppetlabs/puppet/ssl/certs/$H.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/$H.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://$H:8081/status/v1/simple

उत्तर running होता है। लॉग में यह आ सकता है कि "the read-database user is not configured properly"। इसका संबंध एक अलग केवल-पढ़ने वाले उपयोगकर्ता से है जिसे यह गाइड सेट अप नहीं करता, और openvoxdb उसके बिना चलता है।

कंसोल का डेटाबेस बनाएँ

कंसोल अपना डेटा openvoxdb के डेटाबेस से अलग एक डेटाबेस में रखता है। यह पहली शुरुआत पर अपना schema स्वयं बनाता है; इसे केवल एक खाली डेटाबेस और उसका स्वामी एक role चाहिए। Postgres होस्ट पर:

sudo -u postgres createuser --pwprompt console sudo -u postgres createdb --owner=console console

यदि कंसोल किसी दूसरे होस्ट पर चलेगा, तो Postgres को नेटवर्क पर भी सुनना होगा। यह डिफ़ॉल्ट रूप से केवल localhost पर सुनता है, इसलिए स्थानीय रूप से pg_isready सफल होने के बावजूद दूरस्थ कनेक्शन अस्वीकार हो जाता है। पता-सीमा को अपने अनुसार बदलते हुए, कंसोल के होस्ट या subnet को अनुमति दीजिए:

Debian और Ubuntusudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /etc/postgresql/*/main/pg_hba.conf sudo systemctl restart postgresql@*-main.service RHEL, Rocky और AlmaLinuxsudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /var/lib/pgsql/data/pg_hba.conf sudo systemctl restart postgresql

कंसोल के होस्ट से जाँचिए कि कंसोल का role कनेक्ट कर सकता है (वहाँ psql postgresql-client पैकेज के साथ आता है):

PGPASSWORD='<password>' psql -h <postgres host> -U console -d console -c 'select 1;'

single quotes बनाए रखिए। अन्यथा $ वाले पासवर्ड को psql के देखने से पहले ही shell विस्तारित कर देता है।

कंसोल के प्रमाणपत्र जारी करें

कंसोल को CA से दो प्रमाणपत्र चाहिए, और वैकल्पिक रूप से एक तीसरा। उन्हें openvoxserver होस्ट पर बनाइए, फिर कंसोल के होस्ट पर /etc/openvox-console/ में कॉपी कीजिए। पहले कंसोल के होस्ट पर वह डायरेक्टरी बनाइए, उस उपयोगकर्ता के साथ जिसके रूप में कंसोल चलेगा:

sudo useradd --system --home-dir /nonexistent --shell /usr/sbin/nologin openvox-console sudo install -d -m 0750 -o root -g openvox-console /etc/openvox-console

openvoxdb क्लाइंट प्रमाणपत्र

इसी से कंसोल openvoxdb के समक्ष प्रमाणित होता है:

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname console

puppetserver ca generate शुरुआत में Error: Signed certificate console could not be found on the CA छापता है। यह विफलता नहीं, बल्कि इस बात की जाँच है कि नाम उपलब्ध है। महत्वपूर्ण वे पंक्तियाँ हैं जो इसके बाद आती हैं और Successfully saved certificate पर समाप्त होती हैं।

यह तीन फ़ाइलें लिखता है जिनकी कंसोल को ज़रूरत है। उन्हें इन नामों से कॉपी कीजिए:

openvoxserver होस्ट पर कंसोल होस्ट पर
/etc/puppetlabs/puppet/ssl/certs/console.pem /etc/openvox-console/console-cert.pem
/etc/puppetlabs/puppet/ssl/private_keys/console.pem /etc/openvox-console/console-key.pem
/etc/puppetlabs/puppet/ssl/certs/ca.pem /etc/openvox-console/ca.pem

Node ट्रांसपोर्ट प्रमाणपत्र

Nodes कंसोल से जुड़ते समय इस प्रमाणपत्र की जाँच करते हैं, इसलिए इसमें ठीक वही नाम होना चाहिए जिस पर वे कनेक्ट करते हैं: CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR का होस्ट वाला हिस्सा।

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport

certs/node-transport.pem और private_keys/node-transport.pem को भी इसी तरह node-transport-cert.pem और node-transport-key.pem के रूप में कॉपी कीजिए। Nodes बदले में उसी CA से मिले अपने प्रमाणपत्रों से प्रमाणित होते हैं, इसलिए कंसोल को उनके लिए और कुछ नहीं चाहिए।

टोकन हस्ताक्षर कुंजी

कंसोल अपने लॉगिन टोकनों पर एक ES256 कुंजी से हस्ताक्षर करता है। यह कुंजी CA से नहीं आती। इसे किसी भी मशीन पर OpenSSL से बनाइए:

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

इस फ़ाइल का बैकअप लीजिए। इसके खोने से हर जारी टोकन अमान्य हो जाता है, जिससे सभी लॉग आउट हो जाते हैं; इसके लीक होने से कोई भी टोकन गढ़ सकता है। इसे सुरक्षित रूप से बदलने के लिए देखें टोकन हस्ताक्षर कुंजी बदलें।

इसे कंसोल के होस्ट पर, /etc/openvox-console/ में बनाइए।

certificate-admin क्रेडेंशियल (वैकल्पिक)

यही क्रेडेंशियल Nodes पृष्ठ को प्रमाणपत्र की स्थिति दिखाने, और प्रमाणपत्रों पर हस्ताक्षर करने, उन्हें निरस्त करने और साफ़ करने देता है। इसके बिना कंसोल केवल वही Nodes सूचीबद्ध करता है जो पहले ही कनेक्ट हो चुके हैं या रिपोर्ट कर चुके हैं। जो Node अपने प्रमाणपत्र पर हस्ताक्षर की प्रतीक्षा कर रहा है, वह दिखता ही नहीं, क्योंकि केवल CA ही जानता है कि वह मौजूद है।

यह क्रेडेंशियल पूर्ण CA admin है। openvoxserver हर CA endpoint को एक ही authorization extension के पीछे रखता है, इसलिए जो प्रमाणपत्र स्थितियाँ पढ़ सकता है, वह किसी भी Node के प्रमाणपत्र पर हस्ताक्षर कर सकता है, उसे निरस्त और साफ़ भी कर सकता है। इसका कोई केवल-पढ़ने वाला रूप नहीं है। इसे केवल वहीं रखिए जहाँ कंसोल चलता है, और जारी करने से पहले Node प्रमाणपत्र प्रबंधित करें पढ़िए।

इसे जारी करना उस CA स्थिति में लिखता है जिसमें चालू सर्वर भी लिखता है, इसलिए इसे जारी करते समय openvoxserver रोक दीजिए:

sudo systemctl stop puppetserver sudo /opt/puppetlabs/bin/puppetserver ca generate --ca-client --certname console-ca-client sudo systemctl start puppetserver

certs/console-ca-client.pem और private_keys/console-ca-client.pem को ca-client-cert.pem और ca-client-key.pem के रूप में कॉपी कीजिए। फिर कंसोल के होस्ट से पुष्टि कीजिए कि CA इसे स्वीकार करता है:

curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/ca-client-cert.pem \ --key /etc/openvox-console/ca-client-key.pem \ --cacert /etc/openvox-console/ca.pem \ https://puppet.example.com:8140/puppet-ca/v1/certificate_statuses/all

HTTP 200 का अर्थ है कि यह काम करता है।

कंसोल build करें

कंसोल एक अकेली बाइनरी है जिसमें उसका वेब इंटरफ़ेस अंतर्निहित है। इसका कोई पैकेज नहीं है; इसे स्रोत रिपॉज़िटरी से build कीजिए। आपको go.mod में बताए गए संस्करण का Go, और git चाहिए।

git clone https://github.com/avitacco/openvox-console.git cd openvox-console

कंसोल वह node agent भी अपनी पैकेज रिपॉज़िटरी से देता है जिसे Nodes इंस्टॉल करते हैं, और वे agents कंसोल बाइनरी में ही build होते हैं। पहले उन्हें build कीजिए, वरना हर Node इंस्टॉल 404 के साथ विफल होगा:

make agent-binaries make agent-packages make build

इससे bin/console और bin/enc-bridge बनते हैं। कंसोल को उसके होस्ट पर इंस्टॉल कीजिए:

sudo install -m 0755 bin/console /usr/local/bin/console

कंसोल कॉन्फ़िगर करें

कंसोल केवल environment variables से कॉन्फ़िगर होता है, जो उस /etc/openvox-console/ डायरेक्टरी की एक फ़ाइल में होते हैं जिसे आपने उसके प्रमाणपत्रों के लिए बनाया था।

छह सेटिंग्स आवश्यक हैं, और उनके बिना कंसोल, अनुपस्थित सेटिंग का नाम बताते हुए, शुरू होने से मना कर देता है। उन्हें /etc/openvox-console/console.env में रखिए:

CONSOLE_POSTGRES_DSN=postgres://console:<password>@<postgres host>:5432/console?sslmode=require CONSOLE_OPENVOXDB_URL=https://<openvoxdb host>:8081 CONSOLE_OPENVOXDB_CERT_FILE=/etc/openvox-console/console-cert.pem CONSOLE_OPENVOXDB_KEY_FILE=/etc/openvox-console/console-key.pem CONSOLE_OPENVOXDB_CA_FILE=/etc/openvox-console/ca.pem CONSOLE_RBAC_SIGNING_KEY_FILE=/etc/openvox-console/rbac-signing-key.pem

sslmode=require मानता है कि आपका Postgres TLS देता है, और कनेक्शन होस्ट से बाहर जाते ही उसे देना चाहिए। यदि कंसोल और Postgres एक ही होस्ट पर हैं और Postgres के पास कोई प्रमाणपत्र नहीं है, तो sslmode=disable का उपयोग कीजिए।

बाक़ी वैकल्पिक है, और हर वैकल्पिक सुविधा शुरुआत को रोकने के बजाय स्वयं को बंद कर लेती है। असली परिनियोजन के लिए ये जोड़िए:

# Where the console listens, and how the outside world reaches it. It # listens on loopback only: the TLS proxy in front of it is the way in. # On a host shared with openvoxdb, which holds 8080, use 127.0.0.1:8088. CONSOLE_HTTP_ADDR=127.0.0.1:8080 CONSOLE_BASE_URL=https://console.example.com # The first admin user, created only while there are no users. The # password needs at least 12 characters. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin CONSOLE_BOOTSTRAP_ADMIN_PASSWORD=<a strong password> # The node transport. ADDR is what the console binds; PUBLIC_ADDR is what # a node dials, and its host must be in the node transport certificate. CONSOLE_NODE_TRANSPORT_ADDR=:8142 CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 CONSOLE_NODE_TRANSPORT_CERT_FILE=/etc/openvox-console/node-transport-cert.pem CONSOLE_NODE_TRANSPORT_KEY_FILE=/etc/openvox-console/node-transport-key.pem CONSOLE_NODE_TRANSPORT_CA_FILE=/etc/openvox-console/ca.pem # The Puppet server a node should enroll against, written into the node # install script. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # Certificate management from the Nodes page (the optional credential). CONSOLE_CA_CLIENT_URL=https://puppet.example.com:8140 CONSOLE_CA_CLIENT_CERT_FILE=/etc/openvox-console/ca-client-cert.pem CONSOLE_CA_CLIENT_KEY_FILE=/etc/openvox-console/ca-client-key.pem CONSOLE_CA_CLIENT_CA_FILE=/etc/openvox-console/ca.pem # Puppet tasks: where the console asks which tasks your deployed code # contains. Uses the openvoxdb client certificate above unless you name # another with CONSOLE_PUPPET_SERVER_CERT_FILE, _KEY_FILE and _CA_FILE. CONSOLE_PUPPET_SERVER_URL=https://puppet.example.com:8140

Tasks को अपना कोई प्रमाणपत्र नहीं चाहिए: openvoxserver अपने CA के किसी भी प्रमाणपत्र को Tasks पढ़ने देता है, इसलिए openvoxdb क्लाइंट प्रमाणपत्र काम कर जाता है। इन्हें certificate-admin क्रेडेंशियल पर न लगाइए, जो Tasks पढ़ने की ज़रूरत से कहीं अधिक कर सकता है। इन्हें चलाने के लिए देखें Jobs चलाएँ।

कंसोल को क्लास सूची पढ़ने दें

Node समूह का पृष्ठ आपके deploy किए गए कोड द्वारा परिभाषित क्लासें, उनके पैरामीटरों के साथ, प्रस्तुत करता है, ताकि उन्हें टाइप करने के बजाय चुना जा सके। कंसोल उन्हें openvoxserver से उसी कनेक्शन पर पढ़ता है जिस पर Tasks, लेकिन openvoxserver किसी भी प्रमाणपत्र को तब तक क्लासें पढ़ने नहीं देता जब तक कोई नियम ऐसा न कहे।

openvoxserver के होस्ट पर, यह नियम /etc/puppetlabs/puppetserver/conf.d/auth.conf की rules सूची में, अंतिम puppetlabs deny all नियम के ऊपर जोड़िए। console उस openvoxdb क्लाइंट प्रमाणपत्र का नाम है जिसे आपने ऊपर जारी किया:

{ match-request: { path: "/puppet/v3/environment_classes" type: path method: get } allow: "console" sort-order: 500 name: "openvox console class discovery" },

फिर openvoxserver को reload कीजिए:

sudo systemctl reload puppetserver

इसे कंसोल के होस्ट से जाँचिए। HTTP 200 का अर्थ है कि सूची पढ़ी जा सकती है:

sudo curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/console-cert.pem \ --key /etc/openvox-console/console-key.pem \ --cacert /etc/openvox-console/ca.pem \ 'https://puppet.example.com:8140/puppet/v3/environment_classes?environment=production'

HTTP 403 का अर्थ है कि नियम मौजूद नहीं है या उसमें किसी दूसरे प्रमाणपत्र का नाम है। और कुछ इस क़दम पर निर्भर नहीं है: इसके बिना समूह पृष्ठ बताता है कि सूची उपलब्ध नहीं है, और क्लासें नाम से दर्ज की जाती हैं। देखें Nodes का वर्गीकरण करें।

गोपनीय मान फ़ाइलों में रखें

कोई भी सेटिंग इसके बजाय किसी फ़ाइल से पढ़ी जा सकती है: सेटिंग के नाम के बाद _FILE लगाकर उसमें फ़ाइल का नाम दीजिए। इससे पासवर्ड प्रोसेस environment से बाहर रहते हैं:

CONSOLE_POSTGRES_DSN_FILE=/etc/openvox-console/postgres-dsn CONSOLE_BOOTSTRAP_ADMIN_PASSWORD_FILE=/etc/openvox-console/bootstrap-admin-password

फ़ाइल के अंत की newline को अनदेखा किया जाता है। जो फ़ाइल नामित है पर पढ़ी नहीं जा सकती, वह कंसोल को चुपचाप खाली मान के साथ शुरू होने देने के बजाय उसे शुरू होने से रोक देती है।

अंत में, हर फ़ाइल को केवल कंसोल के उपयोगकर्ता द्वारा पठनीय बनाइए, और किसी के द्वारा नहीं:

sudo sh -c 'chown root:openvox-console /etc/openvox-console/* && chmod 0640 /etc/openvox-console/*'

sh -c ज़रूरी है: आपका अपना shell उस डायरेक्टरी को सूचीबद्ध नहीं कर सकता, इसलिए साधारण sudo chown ... /etc/openvox-console/* "No such file or directory" के साथ विफल होता है।

इसे systemd के अंतर्गत चलाएँ

/etc/systemd/system/openvox-console.service बनाइए:

[Unit] Description=OpenVox Console After=network-online.target Wants=network-online.target [Service] EnvironmentFile=/etc/openvox-console/console.env ExecStart=/usr/local/bin/console Restart=on-failure User=openvox-console Group=openvox-console [Install] WantedBy=multi-user.target

फिर इसे शुरू कीजिए:

sudo systemctl daemon-reload sudo systemctl enable --now openvox-console journalctl -u openvox-console -f

कंसोल के आगे TLS लगाएँ

कंसोल अपना वेब इंटरफ़ेस और API सादे HTTP पर देता है। https:// base URL तक एक reverse proxy के ज़रिये पहुँचा जाता है जो TLS समाप्त करके अनुरोध कंसोल तक पहुँचाता है। कोई भी reverse proxy काम करता है। यहाँ कंसोल के होस्ट पर Caddy का उपयोग किया गया है:

Debian और Ubuntusudo apt-get install -y caddy RHEL, Rocky और AlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

तब पूरी /etc/caddy/Caddyfile बस इतनी है:

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

यदि कंसोल openvoxdb के साथ होस्ट साझा करने के कारण किसी दूसरे पोर्ट पर सुनता है, तो reverse_proxy में वही पोर्ट डालिए।

इंटरनेट पर resolve हो सकने वाले नाम के लिए Caddy प्रमाणपत्र स्वयं प्राप्त और नवीनीकृत करता है। आंतरिक नाम के लिए, block के भीतर tls <cert file> <key file> पंक्ति से उसे अपने CA का प्रमाणपत्र दीजिए। परीक्षण के लिए, tls internal से Caddy अपने स्थानीय CA से प्रमाणपत्र जारी करता है, जिस पर browsers चेतावनी देते हैं।

केवल वेब इंटरफ़ेस proxy से होकर जाता है। Node ट्रांसपोर्ट, पोर्ट 8142, अपना TLS स्वयं रखता है और हर Node का प्रमाणपत्र स्वयं जाँचता है, इसलिए Nodes को उस तक सीधे पहुँचना चाहिए। इसे कभी proxy के पीछे न रखें।

पहली बार लॉग इन करें

पहली शुरुआत पर कंसोल अपना डेटाबेस schema बनाता है, फिर users तालिका के खाली रहते ही bootstrap admin बनाता है। चालू होने पर उसके लॉग में तीन पंक्तियाँ दिखती हैं:

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

जाँचिए कि यह स्वयं को स्वस्थ बताता है, पहले सीधे कंसोल के होस्ट पर, फिर उसके base URL पर TLS proxy के ज़रिये:

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

हर उत्तर हर निर्भरता को ok के रूप में सूचीबद्ध करता है। यदि केवल दूसरा विफल हो, तो कंसोल ठीक है और proxy नहीं। यदि आपने कंसोल को 8080 से हटाया है, तो पहले में कंसोल का अपना पोर्ट उपयोग कीजिए। फिर कंसोल का base URL खोलिए, bootstrap admin के रूप में लॉग इन कीजिए, और उसका पासवर्ड तुरंत बदल दीजिए।

bootstrap admin के पासवर्ड में कम से कम 12 अक्षर होने चाहिए और वह उसके username जैसा नहीं होना चाहिए। अन्यथा कोई admin नहीं बनता और कोई लॉग इन नहीं कर सकता। लॉग यह बताता है:

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

लंबा पासवर्ड सेट कीजिए और कंसोल फिर से शुरू कीजिए। देखें पासवर्ड और लॉकआउट।

लॉग इन करके पासवर्ड बदल लेने के बाद, कंसोल के कॉन्फ़िगरेशन से bootstrap admin सेटिंग्स हटा दीजिए। वे केवल तभी पढ़ी जाती हैं जब users तालिका खाली हो, फिर भी किसी पासवर्ड को यूँ ही पड़ा रहने देने का कोई कारण नहीं है।

वर्गीकरण जोड़ें

openvoxserver, Puppet के मानक exec node terminus के ज़रिये, कंसोल से पूछता है कि हर Node को कौन-सी क्लासें मिलेंगी। एक छोटा प्रोग्राम, enc-bridge, openvoxserver की ओर से यह अनुरोध करता है, और इसके लिए उसे एक टोकन चाहिए।

enc-bridge के लिए टोकन जारी करें

सेवा टोकन में अनुमतियों का एक निश्चित समुच्चय होता है जो उसे बनाते समय चुना जाता है, बिना किसी भूमिका के। ऐसा एक टोकन बनाइए जिसे केवल वर्गीकरण पढ़ने की अनुमति हो:

  1. कंसोल में प्रशासन खोलिए, फिर सेवा टोकन।
  2. नया सेवा टोकन के अंतर्गत इसका नाम enc-bridge रखिए और इसे केवल enc:read अनुमति दीजिए।
  3. सेवा टोकन बनाएँ चुनिए।

टोकन केवल एक बार दिखाया जाता है। इसे अभी कॉपी कर लीजिए।

यही काम API से, admin लॉगिन के access token के साथ: curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

openvoxserver के होस्ट पर enc-bridge इंस्टॉल करें

अपने build से bin/enc-bridge को openvoxserver होस्ट पर कॉपी कीजिए और इंस्टॉल कीजिए:

sudo install -m 0755 enc-bridge /usr/local/bin/enc-bridge

टोकन ऐसी जगह सहेजिए जहाँ केवल openvoxserver का उपयोगकर्ता उसे पढ़ सके:

printf '%s' '<the enc:read service token>' | sudo tee /etc/puppetlabs/enc-bridge-token >/dev/null sudo chown root:puppet /etc/puppetlabs/enc-bridge-token sudo chmod 0640 /etc/puppetlabs/enc-bridge-token

enc-bridge कंसोल का पता और अपना टोकन अपने environment से पढ़ता है, जो उसे openvoxserver से विरासत में मिलता है। sudo systemctl edit puppetserver से openvoxserver को दोनों दीजिए:

[Service] Environment=ENC_BRIDGE_URL=https://console.example.com Environment=ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token

enc-bridge कंसोल के प्रमाणपत्र को openvoxserver होस्ट के system certificate store से जाँचता है। यदि proxy का प्रमाणपत्र आपके अपने CA से आता है, तो उस CA को store में जोड़िए, वरना वर्गीकरण certificate signed by unknown authority के साथ विफल होता है:

Debian और Ubuntusudo cp <your CA>.crt /usr/local/share/ca-certificates/ sudo update-ca-certificates RHEL, Rocky और AlmaLinuxsudo cp <your CA>.crt /etc/pki/ca-trust/source/anchors/ sudo update-ca-trust

फिर /etc/puppetlabs/puppet/puppet.conf के [server] खंड में Puppet को इस पर लगाइए, और openvoxserver पुनः आरंभ कीजिए:

[server] node_terminus = exec external_nodes = /usr/local/bin/enc-bridge sudo systemctl restart puppetserver

Nodes को कॉन्फ़िगरेशन डेटा पढ़ने दें

वैकल्पिक। इससे Nodes, Node समूहों पर सेट किया गया कॉन्फ़िगरेशन डेटा lookup() से, आपके control repo के Hiera डेटा से पहले, पढ़ पाते हैं। function enc-bridge --data चलाता है, इसलिए यह वर्गीकरण वाला ही कंसोल पता और टोकन उपयोग करता है और इसके लिए और कुछ कॉन्फ़िगर नहीं करना पड़ता। इसके लिए इसी संस्करण से build हुआ enc-bridge चाहिए।

function को Puppet की अपनी function डायरेक्टरी में इंस्टॉल करना होगा, यही एकमात्र जगह है जहाँ से openvoxserver कोई global Hiera function लोड करता है। अपने build के checkout से:

sudo install -m 0644 openvoxserver-init/console_config_data.rb \ /opt/puppetlabs/puppet/lib/ruby/vendor_ruby/puppet/functions/console_config_data.rb

फिर इसे global Hiera कॉन्फ़िगरेशन, /etc/puppetlabs/puppet/hiera.yaml, में hierarchy में सबसे पहले जोड़िए ताकि कंसोल डेटा जीते। पैकेज वहाँ एक प्लेसहोल्डर फ़ाइल इंस्टॉल करता है; यदि आपने उसे नहीं बदला है, तो उसे इससे बदल दीजिए:

--- version: 5 hierarchy: - name: "Console configuration data" data_hash: console_config_data

यदि आपके पास पहले से एक global hiera.yaml है, तो उसमें यह प्रविष्टि जोड़िए और अपनी प्रविष्टियाँ इसके बाद रखिए।

sudo systemctl restart puppetserver

openvox-agent पैकेज अपग्रेड करने के बाद जाँचिए कि फ़ाइल अब भी मौजूद है, और न हो तो उसे फिर से इंस्टॉल कीजिए। यदि किसी Node का रन "Unable to find 'data_hash' function named 'console_config_data'" के साथ विफल हो, तो function उस डायरेक्टरी में नहीं है। कंटेनर इमेज हर शुरुआत पर यह सब स्वयं करती है।

वर्गीकरण जाँचें

enc-bridge को वैसे ही चलाइए जैसे openvoxserver चलाता है: उसके उपयोगकर्ता के रूप में, उन्हीं सेटिंग्स के साथ। यह एक ही कमांड में प्रोग्राम, टोकन, फ़ाइल अनुमतियाँ और कंसोल का उत्तर जाँच लेता है:

sudo -u puppet env ENC_BRIDGE_URL=https://console.example.com \ ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token \ /usr/local/bin/enc-bridge <a certname>

{} का अर्थ है कि वर्गीकरण काम कर रहा है और वह Node अभी किसी समूह से मेल नहीं खाता। कंसोल के समूह पृष्ठ पर एक Node समूह बनाइए जो उस certname को पिन करे, वही कमांड फिर चलाइए, और उसकी क्लासें लौट आती हैं:

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

यहाँ आने वाली त्रुटि ही वह विफलता है जिसे पकड़ना है। permission denied का अर्थ है कि openvoxserver जिस उपयोगकर्ता के रूप में चलता है, वह टोकन को पढ़ नहीं सकता, और 401 का अर्थ है कि टोकन गलत है या उसमें enc:read नहीं है।

यदि किसी Node का अगला Puppet रन Could not find class <name> के साथ विफल होता है, तो वर्गीकरण काम कर रहा है: कंसोल ने openvoxserver से एक ऐसी क्लास शामिल करने को कहा है जिसे आपका Puppet कोड अभी परिभाषित नहीं करता।

बाद में अपग्रेड करें

नए कंसोल पर जाने के लिए, स्रोत pull कीजिए, उसी क्रम में दोबारा build कीजिए, नई बाइनरी इंस्टॉल कीजिए और पुनः आरंभ कीजिए:

git pull make agent-binaries make agent-packages make build sudo install -m 0755 bin/console /usr/local/bin/console sudo systemctl restart openvox-console

पूरे परिनियोजन की जाँच करें

जाँच अपेक्षित परिणाम
curl -ksS https://<openvoxserver>:8140/status/v1/simple running
curl -ksS https://<openvoxdb>:8081/status/v1/simple, किसी ऐसी जगह से जो उस तक पहुँच सके running
curl -fsS https://console.example.com/health हर निर्भरता ok
शुरू होने पर कंसोल का लॉग migrations, Node ट्रांसपोर्ट, कंसोल तैयार
bootstrap admin के रूप में लॉग इन करना सफल होता है, और पासवर्ड बदल दिया गया है
समूह पृष्ठ कोई समूह उन्हीं Nodes से मेल खाता है जिनकी आप अपेक्षा करते हैं

आपका कंसोल Nodes के लिए तैयार है। पहला Node नामांकित करने के लिए Nodes जोड़ें पर आगे बढ़िए।

openvoxserver इंस्टॉल करें CA को वैकल्पिक नामों पर हस्ताक्षर करने दें इसके प्रमाणपत्र के नाम जाँचें जाँचें कि यह चल रहा है openvoxdb और उसका डेटाबेस इंस्टॉल करें openvoxdb के होस्ट को नामांकित करें इसका डेटाबेस बनाएँ openvoxdb इंस्टॉल करें और शुरू करें catalogs और Reports इसे भेजें जाँचें कि यह चल रहा है कंसोल का डेटाबेस बनाएँ कंसोल के प्रमाणपत्र जारी करें openvoxdb क्लाइंट प्रमाणपत्र Node ट्रांसपोर्ट प्रमाणपत्र टोकन हस्ताक्षर कुंजी certificate-admin क्रेडेंशियल (वैकल्पिक) कंसोल build करें कंसोल कॉन्फ़िगर करें कंसोल को क्लास सूची पढ़ने दें गोपनीय मान फ़ाइलों में रखें इसे systemd के अंतर्गत चलाएँ कंसोल के आगे TLS लगाएँ पहली बार लॉग इन करें वर्गीकरण जोड़ें enc-bridge के लिए टोकन जारी करें openvoxserver के होस्ट पर enc-bridge इंस्टॉल करें Nodes को कॉन्फ़िगरेशन डेटा पढ़ने दें वर्गीकरण जाँचें बाद में अपग्रेड करें पूरे परिनियोजन की जाँच करें

OpenVox Console कंटेनर इमेजों के रूप में आता है, जो हर push पर amd64 और arm64 के लिए बनती हैं, और एक अकेली बाइनरी के रूप में भी। इंस्टॉल गाइड आपको खाली होस्ट से एक चालू परिनियोजन तक ले जाते हैं - openvoxserver, openvoxdb, Postgres और कंसोल - कंटेनरों से या पैकेजों से।
