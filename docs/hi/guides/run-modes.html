परिनियोजन की योजना बनाएँ कंटेनरों से इंस्टॉल करें पैकेजों और बाइनरी से इंस्टॉल करें Nodes जोड़ें Node प्रमाणपत्र प्रबंधित करें किसी Node को हटाएँ Node एजेंटों को नवीनतम रखें Run modes अधिक इंस्टेंस चलाएँ Nodes का वर्गीकरण करें कोड deploy करें Jobs चलाएँ Plans चलाएँ Jobs शेड्यूल करें उपयोगकर्ता, भूमिकाएँ और टोकन कमज़ोरियों पर नज़र रखें छूटे हुए अपडेट खोजें और लागू करें बिना एजेंट वाले होस्टों पर Tasks चलाएँ अपने कोड से Plans चलाएँ AI एजेंटों को कंसोल का उपयोग करने दें standby डेटाबेस पर failover करें टोकन हस्ताक्षर कुंजी बदलें कंटेनर डेटाबेस को Postgres 18 पर अपग्रेड करें

विस्तार

Run modes

कंसोल का हर run mode क्या देता है और क्या चलाता है, और हर एक के लिए क्या कॉन्फ़िगर करना ज़रूरी है।

एक इमेज, एक बाइनरी। CONSOLE_RUN_MODE चुनता है कि कोई इंस्टेंस कंसोल के कौन-से हिस्से चलाए, ताकि बहुत अलग-अलग भार वाले हिस्सों का अलग से विस्तार किया और उन्हें अलग जगह रखा जा सके। सेट न होने पर यह all होता है: सब कुछ एक इंस्टेंस में, जो एकल-इंस्टेंस परिनियोजन हमेशा चलाता है।

हर मोड क्या चलाता है

मोड क्या देता है सुनता है पृष्ठभूमि में चलाता है
all (डिफ़ॉल्ट) सब कुछ HTTP, Node ट्रांसपोर्ट हर पृष्ठभूमि कार्य
web कंसोल, उसका API, code-deploy webhooks और वर्गीकरण HTTP इसके ज़रिये शुरू किए गए Jobs पर नज़र रखना
enc केवल वर्गीकरण HTTP कुछ नहीं
orchestrator health और metrics के अलावा कुछ नहीं HTTP, Node ट्रांसपोर्ट Job भेजना, शेड्यूल किए गए Jobs, नए Nodes का पहला रन, और Node एजेंट अपग्रेड
worker health और metrics के अलावा कुछ नहीं HTTP कमज़ोरी sync, और छोड़े गए Jobs की सफ़ाई

हर मोड /health और /metrics देता है, इसलिए किसी भी इंस्टेंस को उसका मोड जाने बिना जाँचा जा सकता है, और /health बताता है कि वह किस मोड में चल रहा है।

उस तालिका में दो चुनाव जानबूझकर किए गए हैं:

  • web भी वर्गीकरण का उत्तर देता है। enc इसलिए है कि वर्गीकरण compilers के पास अलग से चल सके, इसलिए नहीं कि वह बाक़ी हर जगह से ग़ायब हो जाए। जो विभाजन चुपचाप Nodes का वर्गीकरण बंद कर दे, वह web के उस भार का कुछ हिस्सा उठाने से कहीं बदतर होगा।
  • orchestrator कोई API नहीं देता। यह Node कनेक्शन सँभालता है और उन्हीं के ज़रिये Jobs भेजता है। Job शुरू करना web का काम है, और web उन कनेक्शनों तक cluster के ज़रिये पहुँचता है।
  • किसी Job पर वही इंस्टेंस नज़र रखता है जिसने उसे शुरू किया। कंसोल में शुरू किया गया रन, Task या Plan उसी web इंस्टेंस द्वारा भेजा और ट्रैक किया जाता है जिसने अनुरोध लिया, इसलिए किसी भी Node तक पहुँचने के लिए web इंस्टेंसों का orchestrator इंस्टेंसों के साथ cluster में होना ज़रूरी है। यदि वह web इंस्टेंस Job समाप्त होने से पहले रुक जाए, तो कोई worker इंस्टेंस Job को विफल चिह्नित कर देता है।

हर मोड को क्या चाहिए

हर मोड केवल वही माँगता है जिसका वह उपयोग करता है, और उसके बिना, अनुपस्थित सेटिंग का नाम बताते हुए, शुरू होने से मना कर देता है:

मोड आवश्यकता
हर मोड CONSOLE_POSTGRES_DSN और चारों CONSOLE_OPENVOXDB_* सेटिंग्स
all, web CONSOLE_RBAC_SIGNING_KEY_FILE: केवल यही मोड लॉगिन टोकन जारी करते हैं
enc, orchestrator, worker CONSOLE_RBAC_VERIFICATION_KEYS_DIR: ये टोकन जाँचते हैं, पर कभी जारी नहीं करते
orchestrator CONSOLE_NODE_TRANSPORT_ADDR: Node listener के बिना, स्वस्थ दिखने वाले इंस्टेंस पर हर Job "not connected" के साथ विफल होता

शेड्यूलर को वह दें जिसका शेड्यूल किए गए Jobs उपयोग करते हैं

शेड्यूल किए गए Jobs all और orchestrator इंस्टेंस शुरू करते हैं, web नहीं। orchestrator इंस्टेंस इनके बिना भी शुरू हो जाता है, लेकिन जिस शेड्यूल को इनमें से किसी की ज़रूरत है, वह कारण बताते हुए तब तक छोड़ दिया जाता है जब तक इंस्टेंस को वह न मिल जाए:

  • CONSOLE_PUPPET_SERVER_URL, शेड्यूल किया गया Task शुरू करने के लिए: शेड्यूल शुरू होने पर Task को deploy किए गए कोड में खोजा जाता है।
  • CONSOLE_SECRETS_KEY_FILE, वही कुंजी जो web पर है, ऐसा शेड्यूल किया गया Task शुरू करने के लिए जिसमें कोई संवेदनशील पैरामीटर हो।

जब कई इंस्टेंस शेड्यूलर चलाते हैं, तो हर देय समय को उनमें से ठीक एक शुरू करता है। यदि शेड्यूल देय होने पर कोई नहीं चल रहा, तो वह तब शुरू होता है जब कोई चलने लगे - जब तक इसमें 15 मिनट से अधिक की देरी न हो, जिस स्थिति में वह समय छूटा हुआ दर्ज होता है।

टोकन जारी न करने वाले मोड को verification कुंजियाँ दें

जो इंस्टेंस केवल टोकन जाँचता है, वह जाँच के लिए कुंजियाँ एक डायरेक्टरी से पढ़ता है, हर कुंजी के लिए एक फ़ाइल, जिसका नाम कुंजी की ID पर होता है। जिस परिनियोजन ने कभी अपनी कुंजी नहीं बदली, वह ID default का उपयोग करता है, इसलिए डायरेक्टरी में एक ही फ़ाइल होती है, default.pem, जो स्वयं हस्ताक्षर कुंजी फ़ाइल है:

sudo install -d -m 0750 -o root -g openvox-console /etc/openvox-console/rbac-verification-keys sudo install -m 0640 -o root -g openvox-console \ rbac-signing-key.pem /etc/openvox-console/rbac-verification-keys/default.pem CONSOLE_RUN_MODE=enc CONSOLE_RBAC_VERIFICATION_KEYS_DIR=/etc/openvox-console/rbac-verification-keys

verification डायरेक्टरी फ़िलहाल केवल उसी प्रारूप की कुंजियाँ स्वीकार करती है जो हस्ताक्षर कुंजी का है: private key, जिसका कंसोल केवल public हिस्सा उपयोग करता है। इसलिए जिस इंस्टेंस को यह डायरेक्टरी दी जाती है, उसके पास ऐसी कुंजी भी होती है जो टोकनों पर हस्ताक्षर कर सकती है। हर होस्ट पर इसे ठीक वैसे ही सुरक्षित रखिए जैसे हस्ताक्षर कुंजी को, compilers के पास वाले enc इंस्टेंसों सहित।

जब आप हस्ताक्षर कुंजी बदलते हैं, तो हर इंस्टेंस की verification डायरेक्टरी में भी नई कुंजी चाहिए; क्रम टोकन हस्ताक्षर कुंजी बदलें में बताया गया है।

किसी इंस्टेंस का मोड बदलना

CONSOLE_RUN_MODE सेट कीजिए और इंस्टेंस को पुनः आरंभ कीजिए। कोई डेटा कहीं नहीं जाता: हर मोड उसी डेटाबेस को पढ़ता और उसमें लिखता है। इसे वापस all पर सेट करने से बदलाव पलट जाता है।

अकेला इंस्टेंस मोड बदल सकता है, लेकिन all के अलावा कोई मोड केवल उन clustered इंस्टेंसों के बीच समझ में आता है जो मिलकर हर मोड चलाते हैं। देखें अधिक इंस्टेंस चलाएँ।

हर मोड क्या चलाता है हर मोड को क्या चाहिए शेड्यूलर को वह दें जिसका शेड्यूल किए गए Jobs उपयोग करते हैं टोकन जारी न करने वाले मोड को verification कुंजियाँ दें किसी इंस्टेंस का मोड बदलना

OpenVox Console कंटेनर इमेजों के रूप में आता है, जो हर push पर amd64 और arm64 के लिए बनती हैं, और एक अकेली बाइनरी के रूप में भी। इंस्टॉल गाइड आपको खाली होस्ट से एक चालू परिनियोजन तक ले जाते हैं - openvoxserver, openvoxdb, Postgres और कंसोल - कंटेनरों से या पैकेजों से।
