Nodes

Node एजेंटों को नवीनतम रखें

कंसोल आपके Nodes पर Node एजेंट को स्वयं कैसे अपग्रेड करता है, कैसे देखें कि कौन-से Nodes पीछे हैं, और इस सुविधा से पहले इंस्टॉल हुए Nodes के लिए एक बार का क़दम।

Node एजेंट वह छोटी सेवा है जिसे इंस्टॉल स्क्रिप्ट हर Node पर रखती है। यह कंसोल से Node का कनेक्शन सँभालता है और आपके शुरू किए गए रन और Tasks पूरे करता है। यह कंसोल के साथ build होता है और उसी के भीतर आता है, इसलिए नया कंसोल आमतौर पर नया Node एजेंट लाता है।

कंसोल आपके Nodes पर Node एजेंट को आपके लिए अपग्रेड करता है। जब कोई Node कनेक्ट होता है, तो कंसोल पूछता है कि वह एजेंट का कौन-सा build चलाता है। यदि वह build कंसोल के साथ आने वाले build से पुराना है, तो कंसोल Node को अपग्रेड करने को कहता है, और Node कंसोल से नया build डाउनलोड करता है, उसे जाँचता है, इंस्टॉल करता है और उस पर पुनः आरंभ होता है। आपको Node पर कुछ नहीं करना पड़ता।

आपको क्या दिखता है

  • Nodes पृष्ठ। जिस Node का agent पीछे है, उसे क्लाइंट पुराना है चिह्नित किया जाता है।
  • किसी Node का पृष्ठ। agent का संस्करण और वह कब build हुआ, वह नवीनतम है या नहीं, और पिछले अपग्रेड प्रयास का क्या हुआ, यह दिखाता है।
  • Dashboard। फ़्लीट स्थिति के अंतर्गत, कितने node agents नवीनतम हैं, कितने पुराने हैं, कितने अपग्रेड विफल हुए हैं, और स्वचालित अपग्रेड चालू हैं या नहीं।

Node के पृष्ठ से स्वयं अपग्रेड शुरू करने के लिए ऐसी भूमिका पर nodes:manage चाहिए जिसके Node समूहों में वह Node शामिल हो। कंसोल द्वारा अपने-आप शुरू किए गए अपग्रेड किसी के Node समूहों से सीमित नहीं होते।

जो Node कंसोल के अपग्रेड होने के बाद से कनेक्ट नहीं हुआ, वह पुराना नहीं, बल्कि अभी रिपोर्ट नहीं हुआ के रूप में दिखता है। वह अगली बार कनेक्ट होने पर रिपोर्ट करता है।

स्वचालित अपग्रेड आने से पहले इंस्टॉल हुए Nodes

इस सुविधा से पहले का node agent स्वयं को अपग्रेड नहीं कर सकता, क्योंकि वह अनुरोध को नहीं समझता। कंसोल ऐसे Node को पुराना दिखाता है, इस टिप्पणी के साथ कि इंस्टॉल स्क्रिप्ट फिर से चलानी होगी। इसे Node पर एक बार चलाइए, ठीक वैसे ही जैसे आपने Node जोड़ने के लिए चलाया था:

Linuxcurl -fsSL https://console.example.com/packages/install.sh | sudo bash macOScurl -fsSL https://console.example.com/packages/install-macos.sh | sudo bash WindowsInvoke-WebRequest https://console.example.com/packages/install.ps1 -OutFile install.ps1 .\install.ps1

उसके बाद Node स्वयं को नवीनतम रखता है। Dashboard उन Nodes को गिनता है जो अभी इसकी प्रतीक्षा कर रहे हैं, ताकि आप जान सकें कि आपने सब कर लिए हैं।

यदि आप इसके बजाय Linux पैकेज को Puppet से प्रबंधित करते हैं, तो कंसोल की रिपॉज़िटरी के node-agent-client पैकेज पर ensure => latest वही काम करता है।

अपग्रेड क्या करता है और क्या नहीं

  • यह कभी काम में बाधा नहीं डालता। जो Node किसी रन या Task के बीच में है, उसे छोड़ दिया जाता है और एक मिनट बाद फिर प्रयास किया जाता है।
  • इंस्टॉल होने से पहले इसकी जाँच होती है। कंसोल Node के प्रमाणित कनेक्शन पर डाउनलोड का अपेक्षित checksum भेजता है। Node मेल न खाने वाली हर चीज़ को अस्वीकार कर देता है, और पुराने agent को बदलने से पहले नए agent को एक बार शुरू करके पुष्टि करता है कि वह काम करता है। यदि कोई भी जाँच विफल हो, तो Node अपना मौजूदा agent बनाए रखता है।
  • यह एक बार में कुछ ही Nodes पर होता है। एक साथ अधिकतम 20 Nodes अपग्रेड होते हैं, चाहे कितने भी पीछे हों।
  • यह केवल आगे बढ़ता है। जो Node कंसोल के साथ आने वाले agent से नया agent चला रहा है, उसे छोड़ दिया जाता है। कंसोल इंस्टेंसों के cluster के अपग्रेड के बीच में, या कंसोल को पिछले संस्करण पर लौटाने के बाद, आपको यही दिखता है।
  • Linux पर यह package manager के ज़रिये होता है। Node कंसोल का .deb या .rpm इंस्टॉल करता है, इसलिए dpkg और rpm वही संस्करण दिखाते हैं जो वास्तव में इंस्टॉल है।

macOS और Windows पर अपग्रेड प्रोजेक्ट के tests से कवर हैं, लेकिन अभी तक असली macOS और Windows होस्ट पर शुरू से अंत तक नहीं चलाए गए हैं। जो कुछ भी यहाँ बताए अनुसार न हो, उसकी रिपोर्ट कीजिए।

जब अपग्रेड विफल होता है

Node का पृष्ठ कारण, Node के अपने शब्दों में, दिखाता है: डाउनलोड विफल हुआ, checksum मेल नहीं खाया, package manager व्यस्त था। कंसोल पाँच मिनट बाद फिर प्रयास करता है, फिर हर बार दोगुनी देर प्रतीक्षा करता है, और एक ही build पर पाँच विफलताओं के बाद रुक जाता है।

सबसे आम कारण है Node का कंसोल के base URL (CONSOLE_BASE_URL) तक न पहुँच पाना, जहाँ से वह नया एजेंट डाउनलोड करता है। इंस्टॉल स्क्रिप्ट ने यही पता उपयोग किया था, इसलिए जाँचिए कि Node के इंस्टॉल होने के बाद से क्या बदला है।

कारण ठीक कर लेने के बाद, तुरंत फिर से प्रयास करने के लिए Node के पृष्ठ पर क्लाइंट अपग्रेड करें चुनिए। इसके लिए nodes:manage अनुमति और एक कनेक्टेड Node चाहिए। यह स्वचालित अपग्रेड चालू हों या न हों, दोनों स्थितियों में काम करता है, और स्वचालित प्रयास रुक जाने के बाद भी।

जब आप कंसोल को किसी अलग Node एजेंट वाले संस्करण पर अपग्रेड करते हैं, तब भी कंसोल अपने-आप फिर से शुरू कर देता है।

स्वचालित अपग्रेड बंद करना

कंसोल को Node एजेंट अपने-आप अपग्रेड करने से रोकने के लिए, हर कंसोल इंस्टेंस पर यह सेट कीजिए और उसे पुनः आरंभ कीजिए:

CONSOLE_AGENT_AUTO_UPGRADE=false

कंसोल अब भी हर Node का एजेंट build दर्ज करता है और अब भी दिखाता है कि कौन-से Nodes पुराने हैं। Node के पृष्ठ पर क्लाइंट अपग्रेड करें अब भी काम करता है।

इसके बजाय किसी एक Node को छूट देने के लिए, उस Node पर Node एजेंट के लिए NODE_AGENT_ACCEPT_UPGRADES=false सेट कीजिए और उसे पुनः आरंभ कीजिए:

प्लेटफ़ॉर्म इसे कहाँ सेट करें
Linux यह पंक्ति /etc/node-agent-client/local.env में जोड़िए, फिर sudo systemctl restart node-agent-client
Windows इसे system environment variable के रूप में सेट कीजिए, फिर node-agent-client सेवा पुनः आरंभ कीजिए
macOS इसे /Library/LaunchDaemons/org.voxpupuli.node-agent-client.plist में EnvironmentVariables में जोड़िए, फिर job को दोबारा लोड कीजिए

तब Node का पृष्ठ बताता है कि उस Node पर अपग्रेड अस्वीकार किए जाते हैं, और कंसोल प्रयास नहीं करता। macOS पर इंस्टॉल स्क्रिप्ट फिर से चलाने से वह फ़ाइल दोबारा लिखी जाती है, इसलिए बाद में इसे फिर से सेट कीजिए।

आपको क्या दिखता है स्वचालित अपग्रेड आने से पहले इंस्टॉल हुए Nodes अपग्रेड क्या करता है और क्या नहीं जब अपग्रेड विफल होता है स्वचालित अपग्रेड बंद करना

OpenVox Console कंटेनर इमेजों के रूप में आता है, जो हर push पर amd64 और arm64 के लिए बनती हैं, और एक अकेली बाइनरी के रूप में भी। इंस्टॉल गाइड आपको खाली होस्ट से एक चालू परिनियोजन तक ले जाते हैं - openvoxserver, openvoxdb, Postgres और कंसोल - कंटेनरों से या पैकेजों से।
