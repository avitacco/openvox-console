Installer

Installer à partir de paquets et de binaires

Installez openvoxserver, openvoxdb et Postgres à partir de paquets, construisez la console et faites-la tourner comme service systemd.

Ce guide installe openvoxserver, openvoxdb et Postgres à partir des paquets OpenVox et de la distribution, et fait tourner la console sous forme de binaire unique sous systemd. Fixez les noms dans Planifier un déploiement avant de commencer.

Les commandes sont données pour Debian et Ubuntu, avec l'équivalent RHEL, Rocky Linux et AlmaLinux à côté lorsqu'il diffère. Les composants peuvent résider sur un seul hôte ou sur plusieurs ; lorsqu'une étape concerne un hôte particulier, c'est précisé.

Installer openvoxserver

openvoxserver est l'autorité de certification dont proviennent les certificats de tous les autres composants ; il vient donc en premier. Ajoutez le dépôt OpenVox 8 et installez-le :

Debian et Ubuntu. /etc/os-release curl -fsSL -o /tmp/openvox8-release.deb \ "https://apt.voxpupuli.org/openvox8-release-${ID}${VERSION_ID}.deb" sudo apt-get install -y /tmp/openvox8-release.deb sudo apt-get update && sudo apt-get install -y openvox-server RHEL, Rocky et AlmaLinuxsudo dnf install -y https://yum.voxpupuli.org/openvox8-release-el-9.noarch.rpm sudo dnf install -y openvox-server

Le paquet ne crée pas lui-même la CA. C'est son premier démarrage qui crée la CA et le propre certificat de ce serveur, émis pour le certname de l'hôte, normalement son nom pleinement qualifié. Dans le cas courant, il n'y a plus qu'à le démarrer :

sudo systemctl enable --now puppetserver

N'exécutez pas puppetserver ca setup sur un hôte qui possède déjà une CA. La commande ne crée qu'une CA qui n'existe pas encore ; face à une CA existante, elle s'arrête avec « Existing file at .../ca_crt.pem ». Supprimer ces fichiers comme le suggère le message détruit votre CA et tous les certificats qu'elle a jamais émis, y compris ceux de tous les Nodes enrôlés.

Autoriser la CA à signer des noms alternatifs

Le certificat du transport vers les Nodes de la console, ainsi que celui de ce serveur si vous le réémettez ci-dessous, portent plusieurs noms. Par défaut, la CA refuse de signer une telle demande et la laisse en attente ; autorisez-le donc une fois pour toutes. Dans /etc/puppetlabs/puppetserver/conf.d/ca.conf, ajoutez le paramètre à l'intérieur du bloc certificate-authority :

certificate-authority: { allow-subject-alt-names: true ... } sudo systemctl restart puppetserver

Vérifier les noms de son certificat

Un certificat est toujours valable pour son propre certname. Si les Nodes et la console joignent tous deux ce serveur par son certname, il n'y a rien à changer. Sinon, vérifiez quels noms le certificat couvre déjà :

sudo openssl x509 -in /etc/puppetlabs/puppet/ssl/certs/$(hostname -f).pem \ -noout -subject -ext subjectAltName

S'il manque un nom de votre plan, réémettez uniquement le propre certificat de ce serveur, jamais la CA. Définir dns_alt_names après coup ne modifie pas un certificat existant ; nettoyez-le donc et régénérez-le pendant que le serveur tourne :

sudo /opt/puppetlabs/bin/puppetserver ca clean --certname $(hostname -f) sudo /opt/puppetlabs/bin/puppetserver ca generate --certname $(hostname -f) \ --subject-alt-names puppet.example.com,openvoxserver sudo systemctl restart puppetserver

Sur un hôte neuf, vous pouvez plutôt définir les noms avant le premier démarrage, et laisser ce démarrage créer le certificat avec eux : sudo /opt/puppetlabs/bin/puppet config set --section server dns_alt_names puppet.example.com,openvoxserver

Vérifier qu'il est en marche

curl -ksS https://puppet.example.com:8140/status/v1/simple

La réponse est running.

Installer openvoxdb et sa base de données

Enrôler l'hôte d'openvoxdb

openvoxdb ne demande pas lui-même de certificat : son installation copie celui que possède déjà son hôte. Si openvoxdb dispose de son propre hôte, enrôlez d'abord cet hôte auprès de la CA, puis signez sa demande sur la CA si celle-ci ne signe pas automatiquement :

sudo /opt/puppetlabs/bin/puppet ssl bootstrap --server puppet.example.com # on the CA host: sudo /opt/puppetlabs/bin/puppetserver ca sign --certname <openvoxdb host>

Sautez cette étape si openvoxdb partage l'hôte d'openvoxserver, qui a déjà un certificat.

Créer sa base de données

openvoxdb a besoin de sa propre base de données Postgres, que le paquet ne crée pas :

Debian et Ubuntusudo apt-get install -y postgresql sudo systemctl enable --now postgresql RHEL, Rocky et AlmaLinuxsudo dnf install -y postgresql-server postgresql-contrib sudo postgresql-setup --initdb # Accept passwords over local connections, which are refused by the # default "ident" rules, and store passwords to match. sudo sed -i -E 's/^(host .*)(ident)$/\1scram-sha-256/' /var/lib/pgsql/data/pg_hba.conf echo "password_encryption = 'scram-sha-256'" | sudo tee -a /var/lib/pgsql/data/postgresql.conf sudo systemctl enable --now postgresql

Sur RHEL et ses recompilations, pg_trgm ci-dessous provient de postgresql-contrib, et le changement de mot de passe doit précéder la création des utilisateurs : un mot de passe enregistré avant ne peut pas être vérifié par les nouvelles règles.

sudo -u postgres createuser --pwprompt puppetdb sudo -u postgres createdb --owner=puppetdb puppetdb # openvoxdb refuses to start without this extension, and creating it # needs superuser rights - so it is run as postgres, not as puppetdb. sudo -u postgres psql -d puppetdb -c 'CREATE EXTENSION IF NOT EXISTS pg_trgm;'

Vérifiez que Postgres accepte les connexions :

pg_isready

La réponse se termine par accepting connections.

Sur Debian et Ubuntu, systemctl status postgresql affiche active (exited), et c'est normal : cette unité ne fait que démarrer l'unité réelle propre à chaque cluster. pg_lsclusters montre le cluster lui-même à l'état online.

Installer et démarrer openvoxdb

Debian et Ubuntusudo apt-get install -y openvoxdb RHEL, Rocky et AlmaLinuxsudo dnf install -y openvoxdb

Indiquez-lui où se trouve sa base de données. Sans ce fichier, il ne démarre pas et s'arrête avec No subname set in the "database" config. :

[database] subname = //localhost:5432/puppetdb username = puppetdb password = <the password you set above>

Enregistrez cela sous /etc/puppetlabs/puppetdb/conf.d/database.ini, en remplaçant localhost par le nom de l'hôte de la base de données si elle se trouve ailleurs, et restreignez-en l'accès :

sudo chown puppetdb:puppetdb /etc/puppetlabs/puppetdb/conf.d/database.ini sudo chmod 640 /etc/puppetlabs/puppetdb/conf.d/database.ini

Copiez ensuite les certificats de l'hôte à leur place et démarrez-le :

sudo /opt/puppetlabs/bin/puppetdb ssl-setup sudo systemctl enable --now puppetdb

S'il ne démarre pas, /var/log/puppetlabs/puppetdb/puppetdb.log contient la vraie raison ; l'erreur de systemd n'en est généralement que la conséquence.

Lui envoyer les catalogues et les Reports

Sur l'hôte openvoxserver, installez le terminus qui envoie les catalogues et les Reports à openvoxdb :

Debian et Ubuntusudo apt-get install -y openvoxdb-termini RHEL, Rocky et AlmaLinuxsudo dnf install -y openvoxdb-termini

Vérifier qu'il est en marche

Le port HTTPS d'openvoxdb exige un certificat client : interrogez-le donc avec celui de l'hôte. Sans certificat, la réponse est certificate required :

H=$(hostname -f) sudo curl -sS --cert /etc/puppetlabs/puppet/ssl/certs/$H.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/$H.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://$H:8081/status/v1/simple

La réponse est running. Le journal peut signaler que « the read-database user is not configured properly ». Cela concerne un utilisateur distinct en lecture seule que ce guide ne configure pas, et openvoxdb fonctionne sans lui.

Créer la base de données de la console

La console conserve ses propres données dans une base distincte de celle d'openvoxdb. Elle crée elle-même son schéma au premier démarrage ; il lui faut seulement une base vide et un rôle qui en est propriétaire. Sur l'hôte Postgres :

sudo -u postgres createuser --pwprompt console sudo -u postgres createdb --owner=console console

Si la console doit tourner sur un autre hôte, Postgres doit aussi écouter sur le réseau. Par défaut, il n'écoute que sur localhost : une connexion distante est donc refusée alors même que pg_isready réussit en local. Autorisez l'hôte ou le sous-réseau de la console, en adaptant la plage d'adresses :

Debian et Ubuntusudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /etc/postgresql/*/main/pg_hba.conf sudo systemctl restart postgresql@*-main.service RHEL, Rocky et AlmaLinuxsudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /var/lib/pgsql/data/pg_hba.conf sudo systemctl restart postgresql

Vérifiez, depuis l'hôte de la console, que le rôle de la console peut se connecter (psql y est fourni par le paquet postgresql-client) :

PGPASSWORD='<password>' psql -h <postgres host> -U console -d console -c 'select 1;'

Conservez les apostrophes simples. Sinon, un mot de passe contenant $ est développé par le shell avant que psql ne le voie.

Émettre les certificats de la console

La console a besoin de deux certificats issus de la CA, et éventuellement d'un troisième. Générez-les sur l'hôte openvoxserver, puis copiez-les sur l'hôte de la console, dans /etc/openvox-console/. Créez d'abord ce répertoire sur l'hôte de la console, avec l'utilisateur sous lequel tournera la console :

sudo useradd --system --home-dir /nonexistent --shell /usr/sbin/nologin openvox-console sudo install -d -m 0750 -o root -g openvox-console /etc/openvox-console

Le certificat client openvoxdb

C'est ainsi que la console s'authentifie auprès d'openvoxdb :

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname console

puppetserver ca generate commence par afficher Error: Signed certificate console could not be found on the CA. C'est la commande qui vérifie que le nom est libre, et non un échec. Ce qui compte, ce sont les lignes suivantes, qui se terminent par Successfully saved certificate.

La commande écrit trois fichiers dont la console a besoin. Copiez-les sous ces noms :

Sur l'hôte openvoxserver Sur l'hôte de la console
/etc/puppetlabs/puppet/ssl/certs/console.pem /etc/openvox-console/console-cert.pem
/etc/puppetlabs/puppet/ssl/private_keys/console.pem /etc/openvox-console/console-key.pem
/etc/puppetlabs/puppet/ssl/certs/ca.pem /etc/openvox-console/ca.pem

Le certificat du transport vers les Nodes

Les Nodes vérifient ce certificat lorsqu'ils se connectent à la console ; il doit donc porter exactement le nom qu'ils composent : la partie hôte de CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR.

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport

Copiez de la même façon certs/node-transport.pem et private_keys/node-transport.pem sous les noms node-transport-cert.pem et node-transport-key.pem. Les Nodes s'authentifient en retour avec leurs propres certificats issus de la même CA ; la console n'a donc besoin de rien d'autre pour eux.

La clé de signature des jetons

La console signe ses propres jetons de connexion avec une clé ES256. Celle-ci ne provient pas de la CA. Générez-la sur n'importe quelle machine avec OpenSSL :

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

Sauvegardez ce fichier. Le perdre invalide tous les jetons émis, ce qui déconnecte tout le monde ; le laisser fuiter permet à n'importe qui de fabriquer des jetons. Voir Renouveler la clé de signature des jetons pour le remplacer en toute sécurité.

Générez-la sur l'hôte de la console, dans /etc/openvox-console/.

L'identifiant d'administration des certificats (facultatif)

C'est cet identifiant qui permet à la page Nodes d'afficher l'état des certificats, et de signer, révoquer et nettoyer des certificats. Sans lui, la console ne liste que les Nodes qui se sont déjà connectés ou ont déjà envoyé un Report. Un Node dont le certificat attend d'être signé n'apparaît pas du tout, car la CA est le seul composant à connaître son existence.

Cet identifiant donne un accès administrateur complet à la CA. openvoxserver protège chaque point d'accès de la CA derrière une seule extension d'autorisation : un certificat capable de lire les états peut donc aussi signer, révoquer et nettoyer le certificat de n'importe quel Node. Il n'existe pas de variante en lecture seule. Ne le conservez que là où tourne la console, et lisez Gérer les certificats des Nodes avant de l'émettre.

Son émission écrit dans l'état de la CA, que le serveur en marche écrit lui aussi ; arrêtez donc openvoxserver pendant l'émission :

sudo systemctl stop puppetserver sudo /opt/puppetlabs/bin/puppetserver ca generate --ca-client --certname console-ca-client sudo systemctl start puppetserver

Copiez certs/console-ca-client.pem et private_keys/console-ca-client.pem sous les noms ca-client-cert.pem et ca-client-key.pem. Confirmez ensuite, depuis l'hôte de la console, que la CA l'accepte :

curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/ca-client-cert.pem \ --key /etc/openvox-console/ca-client-key.pem \ --cacert /etc/openvox-console/ca.pem \ https://puppet.example.com:8140/puppet-ca/v1/certificate_statuses/all

HTTP 200 signifie que cela fonctionne.

Construire la console

La console est un binaire unique qui intègre son interface web. Il n'en existe pas de paquet ; construisez-la depuis le dépôt source. Il vous faut Go dans la version indiquée dans go.mod, ainsi que git.

git clone https://github.com/avitacco/openvox-console.git cd openvox-console

La console sert aussi l'agent de Node que les Nodes installent, depuis son propre dépôt de paquets, et ces agents sont intégrés au binaire de la console. Construisez-les d'abord, sinon chaque installation de Node échoue avec une 404 :

make agent-binaries make agent-packages make build

Vous obtenez bin/console et bin/enc-bridge. Installez la console sur son hôte :

sudo install -m 0755 bin/console /usr/local/bin/console

Configurer la console

La console se configure uniquement par des variables d'environnement, dans un fichier placé dans le répertoire /etc/openvox-console/ que vous avez créé pour ses certificats.

Six paramètres sont obligatoires, et la console refuse de démarrer sans eux, en nommant celui qui manque. Placez-les dans /etc/openvox-console/console.env :

CONSOLE_POSTGRES_DSN=postgres://console:<password>@<postgres host>:5432/console?sslmode=require CONSOLE_OPENVOXDB_URL=https://<openvoxdb host>:8081 CONSOLE_OPENVOXDB_CERT_FILE=/etc/openvox-console/console-cert.pem CONSOLE_OPENVOXDB_KEY_FILE=/etc/openvox-console/console-key.pem CONSOLE_OPENVOXDB_CA_FILE=/etc/openvox-console/ca.pem CONSOLE_RBAC_SIGNING_KEY_FILE=/etc/openvox-console/rbac-signing-key.pem

sslmode=require suppose que votre Postgres sert du TLS, ce qui devrait être le cas dès que la connexion quitte l'hôte. Si la console et Postgres partagent un hôte et que Postgres n'a pas de certificat, utilisez sslmode=disable.

Le reste est facultatif, et chaque fonctionnalité facultative se désactive d'elle-même plutôt que de bloquer le démarrage. Pour un vrai déploiement, ajoutez :

# Where the console listens, and how the outside world reaches it. It # listens on loopback only: the TLS proxy in front of it is the way in. # On a host shared with openvoxdb, which holds 8080, use 127.0.0.1:8088. CONSOLE_HTTP_ADDR=127.0.0.1:8080 CONSOLE_BASE_URL=https://console.example.com # The first admin user, created only while there are no users. The # password needs at least 12 characters. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin CONSOLE_BOOTSTRAP_ADMIN_PASSWORD=<a strong password> # The node transport. ADDR is what the console binds; PUBLIC_ADDR is what # a node dials, and its host must be in the node transport certificate. CONSOLE_NODE_TRANSPORT_ADDR=:8142 CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 CONSOLE_NODE_TRANSPORT_CERT_FILE=/etc/openvox-console/node-transport-cert.pem CONSOLE_NODE_TRANSPORT_KEY_FILE=/etc/openvox-console/node-transport-key.pem CONSOLE_NODE_TRANSPORT_CA_FILE=/etc/openvox-console/ca.pem # The Puppet server a node should enroll against, written into the node # install script. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # Certificate management from the Nodes page (the optional credential). CONSOLE_CA_CLIENT_URL=https://puppet.example.com:8140 CONSOLE_CA_CLIENT_CERT_FILE=/etc/openvox-console/ca-client-cert.pem CONSOLE_CA_CLIENT_KEY_FILE=/etc/openvox-console/ca-client-key.pem CONSOLE_CA_CLIENT_CA_FILE=/etc/openvox-console/ca.pem # Puppet tasks: where the console asks which tasks your deployed code # contains. Uses the openvoxdb client certificate above unless you name # another with CONSOLE_PUPPET_SERVER_CERT_FILE, _KEY_FILE and _CA_FILE. CONSOLE_PUPPET_SERVER_URL=https://puppet.example.com:8140

Les Tasks n'ont pas besoin de leur propre certificat : openvoxserver permet à tout certificat de sa CA de lire les Tasks, et le certificat client openvoxdb fait donc l'affaire. Ne les pointez pas vers l'identifiant d'administration des certificats, qui peut faire bien plus que ce qu'exige la lecture des Tasks. Voir Lancer des Jobs pour les exécuter.

Permettre à la console de lire la liste des classes

La page d'un groupe de Nodes propose les classes que définit votre code déployé, avec leurs paramètres, pour qu'elles soient choisies plutôt que tapées. La console les lit depuis openvoxserver par la même connexion que les Tasks, mais openvoxserver ne laisse aucun certificat lire les classes tant qu'une règle ne l'autorise pas.

Sur l'hôte d'openvoxserver, ajoutez cette règle à la liste rules de /etc/puppetlabs/puppetserver/conf.d/auth.conf, au-dessus de la règle finale puppetlabs deny all. console est le nom du certificat client openvoxdb que vous avez émis plus haut :

{ match-request: { path: "/puppet/v3/environment_classes" type: path method: get } allow: "console" sort-order: 500 name: "openvox console class discovery" },

Rechargez ensuite openvoxserver :

sudo systemctl reload puppetserver

Vérifiez-le depuis l'hôte de la console. HTTP 200 signifie que la liste peut être lue :

sudo curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/console-cert.pem \ --key /etc/openvox-console/console-key.pem \ --cacert /etc/openvox-console/ca.pem \ 'https://puppet.example.com:8140/puppet/v3/environment_classes?environment=production'

HTTP 403 signifie que la règle est absente ou nomme un autre certificat. Rien d'autre ne dépend de cette étape : sans elle, la page du groupe indique que la liste n'est pas disponible, et les classes se saisissent par leur nom. Voir Classifier les Nodes.

Garder les secrets dans des fichiers

Tout paramètre peut aussi être lu depuis un fichier : indiquez le fichier dans le nom du paramètre suivi de _FILE. Cela garde les mots de passe hors de l'environnement du processus :

CONSOLE_POSTGRES_DSN_FILE=/etc/openvox-console/postgres-dsn CONSOLE_BOOTSTRAP_ADMIN_PASSWORD_FILE=/etc/openvox-console/bootstrap-admin-password

Un saut de ligne final dans le fichier est ignoré. Un fichier indiqué mais illisible empêche la console de démarrer, plutôt que de la laisser démarrer avec une valeur vide sans rien dire.

Enfin, rendez chaque fichier lisible par l'utilisateur de la console et par personne d'autre :

sudo sh -c 'chown root:openvox-console /etc/openvox-console/* && chmod 0640 /etc/openvox-console/*'

Le sh -c est important : votre propre shell ne peut pas lister ce répertoire, si bien qu'un simple sudo chown ... /etc/openvox-console/* échoue avec « No such file or directory ».

La faire tourner sous systemd

Créez /etc/systemd/system/openvox-console.service :

[Unit] Description=OpenVox Console After=network-online.target Wants=network-online.target [Service] EnvironmentFile=/etc/openvox-console/console.env ExecStart=/usr/local/bin/console Restart=on-failure User=openvox-console Group=openvox-console [Install] WantedBy=multi-user.target

Démarrez-la ensuite :

sudo systemctl daemon-reload sudo systemctl enable --now openvox-console journalctl -u openvox-console -f

Placer TLS devant la console

La console sert son interface web et son API en HTTP simple. L'URL de base en https:// est atteinte via un reverse proxy qui termine le TLS et transmet les requêtes à la console. N'importe quel reverse proxy convient. Cet exemple utilise Caddy, sur l'hôte de la console :

Debian et Ubuntusudo apt-get install -y caddy RHEL, Rocky et AlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

Voici alors l'intégralité de /etc/caddy/Caddyfile :

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

Si la console écoute sur un autre port, parce qu'elle partage un hôte avec openvoxdb, indiquez plutôt ce port dans reverse_proxy.

Pour un nom résolvable sur Internet, Caddy obtient et renouvelle lui-même le certificat. Pour un nom interne, donnez-lui un certificat issu de votre propre CA avec une ligne tls <cert file> <key file> à l'intérieur du bloc. Pour un essai, tls internal fait émettre par Caddy un certificat issu de sa propre CA locale, ce que les navigateurs signalent par un avertissement.

Seule l'interface web passe par le proxy. Le transport vers les Nodes, sur le port 8142, porte son propre TLS et vérifie lui-même le certificat de chaque Node : les Nodes doivent donc le joindre directement. Ne le placez jamais derrière le proxy.

Se connecter pour la première fois

À son premier démarrage, la console crée le schéma de sa base de données, puis l'administrateur initial tant que la table des utilisateurs est encore vide. Une fois démarrée, son journal affiche trois lignes :

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

Vérifiez qu'elle se déclare en bonne santé, d'abord directement sur l'hôte de la console, puis via le proxy TLS à son URL de base :

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

Chaque réponse indique ok pour chaque dépendance. Si seule la seconde échoue, la console va bien et c'est le proxy qui pose problème. Utilisez le port propre de la console dans la première si vous l'avez déplacée hors du port 8080. Ouvrez ensuite l'URL de base de la console, connectez-vous en tant qu'administrateur initial et changez immédiatement son mot de passe.

Le mot de passe de l'administrateur initial doit compter au moins 12 caractères et ne doit pas être identique à son nom d'utilisateur. Sinon, aucun administrateur n'est créé et personne ne peut se connecter. Le journal l'indique :

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

Définissez un mot de passe plus long et redémarrez la console. Voir Mots de passe et verrouillage.

Une fois connecté et le mot de passe changé, retirez de la configuration de la console les paramètres de l'administrateur initial. Ils ne sont lus que tant que la table des utilisateurs est vide, mais rien ne justifie de laisser traîner un mot de passe.

Connecter la classification

openvoxserver demande à la console quelles classes attribuer à chaque Node, via le node terminus exec standard de Puppet. Un petit programme, enc-bridge, effectue cette requête pour le compte d'openvoxserver, et il lui faut un jeton pour cela.

Émettre un jeton pour enc-bridge

Un jeton de service porte un ensemble fixe de permissions choisies à sa création, sans aucun rôle. Créez-en un autorisé uniquement à lire la classification :

  1. Dans la console, ouvrez Administration, puis Jetons de service.
  2. Sous Nouveau jeton de service, nommez-le enc-bridge et donnez-lui uniquement la permission enc:read.
  3. Choisissez Créer un jeton de service.

Le jeton n'est affiché qu'une fois. Copiez-le maintenant.

La même chose via l'API, avec un jeton d'accès issu d'une connexion administrateur : curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

Installer enc-bridge sur l'hôte d'openvoxserver

Copiez bin/enc-bridge de votre build vers l'hôte openvoxserver et installez-le :

sudo install -m 0755 enc-bridge /usr/local/bin/enc-bridge

Enregistrez le jeton à un endroit où seul l'utilisateur d'openvoxserver peut le lire :

printf '%s' '<the enc:read service token>' | sudo tee /etc/puppetlabs/enc-bridge-token >/dev/null sudo chown root:puppet /etc/puppetlabs/enc-bridge-token sudo chmod 0640 /etc/puppetlabs/enc-bridge-token

enc-bridge lit l'emplacement de la console et son jeton dans son environnement, qu'il hérite d'openvoxserver. Donnez les deux à openvoxserver, avec sudo systemctl edit puppetserver :

[Service] Environment=ENC_BRIDGE_URL=https://console.example.com Environment=ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token

enc-bridge vérifie le certificat de la console à l'aide du magasin de certificats système de l'hôte openvoxserver. Si le certificat du proxy provient de votre propre CA, ajoutez cette CA au magasin, sinon la classification échoue avec certificate signed by unknown authority :

Debian et Ubuntusudo cp <your CA>.crt /usr/local/share/ca-certificates/ sudo update-ca-certificates RHEL, Rocky et AlmaLinuxsudo cp <your CA>.crt /etc/pki/ca-trust/source/anchors/ sudo update-ca-trust

Pointez ensuite Puppet vers lui, dans la section [server] de /etc/puppetlabs/puppet/puppet.conf, et redémarrez openvoxserver :

[server] node_terminus = exec external_nodes = /usr/local/bin/enc-bridge sudo systemctl restart puppetserver

Permettre aux Nodes de lire les données de configuration

Facultatif. Cela permet aux Nodes de lire avec lookup() les données de configuration définies sur les groupes de Nodes, avant les données Hiera de votre dépôt de contrôle. La fonction exécute enc-bridge --data : elle utilise donc la même adresse de console et le même jeton que la classification, et ne nécessite aucune autre configuration. Elle nécessite un enc-bridge construit à partir de cette version.

La fonction doit être installée dans le répertoire de fonctions de Puppet lui-même, le seul endroit d'où openvoxserver charge une fonction Hiera globale. Depuis le clone utilisé pour votre build :

sudo install -m 0644 openvoxserver-init/console_config_data.rb \ /opt/puppetlabs/puppet/lib/ruby/vendor_ruby/puppet/functions/console_config_data.rb

Ajoutez-la ensuite à la configuration Hiera globale, /etc/puppetlabs/puppet/hiera.yaml, en premier dans la hiérarchie pour que les données de la console l'emportent. Le paquet y installe un fichier provisoire ; si vous ne l'avez pas modifié, remplacez-le par ceci :

--- version: 5 hierarchy: - name: "Console configuration data" data_hash: console_config_data

Si vous avez déjà un hiera.yaml global, ajoutez-y l'entrée et conservez vos propres entrées après elle.

sudo systemctl restart puppetserver

Après chaque mise à jour du paquet openvox-agent, vérifiez que le fichier est toujours présent, et réinstallez-le sinon. Si l'exécution d'un Node échoue avec « Unable to find 'data_hash' function named 'console_config_data' », la fonction ne se trouve pas dans ce répertoire. L'image de conteneur fait tout cela elle-même à chaque démarrage.

Vérifier la classification

Exécutez enc-bridge comme le fait openvoxserver : sous son utilisateur, avec les mêmes paramètres. Cela vérifie en une seule commande le programme, le jeton, les permissions des fichiers et la réponse de la console :

sudo -u puppet env ENC_BRIDGE_URL=https://console.example.com \ ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token \ /usr/local/bin/enc-bridge <a certname>

{} signifie que la classification fonctionne et que ce Node ne correspond encore à aucun groupe. Créez sur la page Groupes de la console un groupe de Nodes qui épingle ce certname, relancez la même commande, et ses classes apparaissent :

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

Une erreur ici, c'est justement la panne à détecter. permission denied signifie que le jeton n'est pas lisible par l'utilisateur sous lequel tourne openvoxserver, et une 401 que le jeton est incorrect ou ne dispose pas de enc:read.

Si la prochaine exécution Puppet d'un Node échoue avec Could not find class <name>, c'est que la classification fonctionne : la console a demandé à openvoxserver d'inclure une classe que votre code Puppet ne définit pas encore.

Mettre à jour plus tard

Pour passer à une console plus récente, récupérez les sources, reconstruisez dans le même ordre, installez le nouveau binaire et redémarrez :

git pull make agent-binaries make agent-packages make build sudo install -m 0755 bin/console /usr/local/bin/console sudo systemctl restart openvox-console
