Passer à l'échelle

Faire tourner plus d'instances

Mettez en cluster une deuxième instance de la console, répartissez les instances en modes d'exécution et placez la classification à côté des compilateurs.

Plusieurs instances de la console partagent une base de données et rejoignent un même cluster. C'est par le cluster qu'elles se signalent ce qui doit atteindre toutes les instances à la fois - une connexion révoquée, un certificat de Node révoqué - et qu'un Job lancé sur une instance atteint un Node connecté à une autre.

Tout ce qui est durable réside dans Postgres : une fois les instances en cluster, n'importe laquelle peut donc servir n'importe quelle requête, et un répartiteur de charge peut envoyer les requêtes à celle qui est en bonne santé.

Des instances qui partagent une base de données doivent être en cluster. Une instance qui ne l'est pas n'apprend la révocation d'une connexion que lorsqu'elle relit les révocations dans la base, jusqu'à 30 secondes plus tard, et ne peut pas atteindre les Nodes connectés à une autre instance.

Comment les instances se trouvent

Chaque instance fait tourner un serveur NATS intégré. Les modes centraux (all, web, orchestrator et worker) se connectent directement les uns aux autres, en pairs routés. Les instances enc se rattachent quant à elles en tant que feuilles : la connexion ne va que vers l'extérieur, de l'instance enc vers une instance centrale, si bien que le cœur n'a jamais besoin d'accéder au réseau où se trouvent les compilateurs.

web-1 --+ web-2 --+-- routed peers (:6222) orch-1 -+ worker -+ ^ | leaf connections, outbound only | (to a core instance's leaf listener, :6223) | enc-1, enc-2 (beside the compilers)

Une feuille transporte entre les instances les messages propres à la console, comme les révocations et l'état, et jamais le trafic des Nodes : une instance enc ne peut jamais atteindre un Node géré.

Avant de commencer

Chaque connexion entre pairs est chiffrée et authentifiée de deux façons :

  • TLS mutuel, avec le certificat de chaque instance issu de la CA. Par défaut, une instance utilise le même certificat que pour openvoxdb, celui de CONSOLE_OPENVOXDB_CERT_FILE : il n'y a donc rien de nouveau à émettre. Un pair qui contacte une instance vérifie que son certificat est valable pour le nom qu'il a composé ; chaque instance doit donc être jointe par un nom que porte son certificat.
  • un secret partagé, identique sur chaque instance centrale. Un Node géré détient lui aussi un certificat de la CA, et c'est le secret qui empêche ce certificat de suffire pour rejoindre le cluster.

Si vous donnez à une instance son propre certificat plutôt que le certificat partagé, openvoxserver doit aussi l'autoriser à lire la liste des classes : sa règle nomme le certificat qu'elle autorise, console par défaut, et refuse tout autre avec HTTP 403. Ajoutez à cette règle le certname de chaque instance web et all, sinon la page des groupes de ces instances indique que la liste n'est pas disponible. Voir Installer à partir de paquets et de binaires.

Les feuilles utilisent un second secret qui leur est propre et qui doit différer du secret du cluster : un hôte enc est l'endroit le moins sûr où tourne une console, et il ne doit pas pouvoir rejoindre le cluster en tant que pair à part entière.

Générez les deux secrets et gardez-les hors de l'environnement du processus grâce à la forme _FILE de chaque paramètre :

openssl rand -base64 32 > cluster-secret openssl rand -base64 32 > cluster-leaf-secret

Ajouter une deuxième instance

Commencez avec deux instances all. Cela met le cluster à l'épreuve avant toute séparation des rôles.

Sur la première instance, ouvrez une écoute pour les pairs et redémarrez-la :

CONSOLE_CLUSTER_ADDR=:6222 CONSOLE_CLUSTER_SECRET_FILE=/etc/openvox-console/cluster-secret

Sur la deuxième, donnez-lui la même base de données, la même clé de signature des jetons et les mêmes secrets, sa propre écoute pour les pairs, et la première instance comme pair, sous un nom figurant dans le certificat de la première instance :

CONSOLE_CLUSTER_ADDR=:6222 CONSOLE_CLUSTER_PEERS=console-1.example.com:6222 CONSOLE_CLUSTER_SECRET_FILE=/etc/openvox-console/cluster-secret

Un seul côté a besoin de nommer l'autre. Chaque instance qui rejoint ensuite le cluster en nomme une existante, et le cluster connecte le reste.

La deuxième instance a aussi besoin de sa propre écoute pour les Nodes et de son propre certificat de transport vers les Nodes si des Nodes doivent s'y connecter, et toutes les instances ont besoin du même CONSOLE_BASE_URL, pour que les liens et les scripts d'installation passent par le répartiteur de charge.

Les instances apprennent les adresses des autres par le cluster lui-même, et ce sont par défaut des adresses IP, qu'un certificat porte rarement. Avec trois instances routées ou plus, chacune dotée de son propre certificat, définissez sur chacune CONSOLE_CLUSTER_ADVERTISE avec un nom figurant dans son propre certificat, comme console-2.example.com:6222.

Vérifier que le cluster s'est formé

Chaque instance journalise cluster joined au démarrage, avec les pairs qui lui ont été donnés. Ensuite, en tant qu'utilisateur disposant de la permission status:read, ouvrez Système dans la console. L'onglet État du parc liste chaque instance qui a répondu, regroupée par mode ; les deux instances y figurent.

status:read n'est pas ajoutée automatiquement aux rôles existants. Accordez-la aux rôles qui doivent voir la page, sur la page Rôles.

Répartir les instances en modes

Une fois deux instances all en marche ensemble, séparez les rôles selon la charge : le travail en arrière-plan vers worker, les connexions des Nodes vers orchestrator, tout ce qu'utilise une personne vers web. Définissez CONSOLE_RUN_MODE sur chaque instance et redémarrez-la ; voir Modes d'exécution pour ce dont chaque mode a besoin, y compris les clés de vérification des modes qui n'émettent pas de jetons.

Chaque mode peut tourner sur plusieurs instances :

  • le travail qui ne doit avoir lieu qu'une fois, comme une synchronisation de vulnérabilités, le déploiement de code d'un Environment ou le nettoyage des Jobs abandonnés, est coordonné par la base de données, si bien que deux instances worker ne le font jamais toutes les deux ;
  • les révocations atteignent chaque instance, si bien que la vue de chacune reste à jour ;
  • l'activité est consignée une seule fois, par l'instance où elle a eu lieu.

Pointez le répartiteur de charge vers les instances web pour la console et son API, et pointez les Nodes vers le transport des instances orchestrator via CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR.

Placer la classification à côté des compilateurs

Les instances enc répondent aux requêtes de classification des compilateurs auprès desquels elles se trouvent, et se rattachent au cluster en tant que feuilles.

Sur une ou plusieurs instances centrales, ouvrez une écoute pour les feuilles, protégée par le secret des feuilles :

CONSOLE_CLUSTER_LEAF_ADDR=:6223 CONSOLE_CLUSTER_LEAF_SECRET_FILE=/etc/openvox-console/cluster-leaf-secret

Sur chaque instance enc, rattachez-vous à l'écoute des feuilles d'une instance centrale. Elle ne détient que le secret des feuilles, jamais le secret du cluster :

CONSOLE_RUN_MODE=enc CONSOLE_CLUSTER_MODE=leaf CONSOLE_CLUSTER_PEERS=console-1.example.com:6223 CONSOLE_CLUSTER_LEAF_SECRET_FILE=/etc/openvox-console/cluster-leaf-secret CONSOLE_RBAC_VERIFICATION_KEYS_DIR=/etc/openvox-console/rbac-verification-keys

Pointez ensuite l'enc-bridge de chaque compilateur vers l'instance enc placée à côté, avec ENC_BRIDGE_URL.

Vérifier l'ensemble du parc

L'onglet État du parc établit son tableau en direct, en interrogeant chaque instance et en recueillant les réponses reçues en moins d'une seconde. Deux points méritent d'être connus :

  • Si moins d'instances que prévu ont répondu, c'est indiqué au-dessus de la liste, par exemple « 1 of 4 instances did not reply within 1s ». Prenez-le au sérieux : une instance qui tourne mais ne peut pas joindre les autres est généralement bloquée.
  • Chaque dépendance, comme openvoxdb ou la CA, est affichée telle que la voit l'instance qui répond. Une dépendance sur laquelle les instances ne s'accordent pas est marquée diffère selon l'instance : certaines instances peuvent la joindre et d'autres non.

La page ne se rafraîchit pas d'elle-même ; rechargez-la pour obtenir un état à jour.

Surveiller les messages perdus

console_nats_async_errors_total, sur le /metrics de chaque instance, compte les problèmes survenus sur ses connexions au cluster. Celui qui compte est un abonné qui prend du retard, ce qui fait perdre des messages ; chaque occurrence est aussi journalisée au niveau error sous la forme « NATS subscriber fell behind; messages were dropped ». Un compteur qui augmente mérite qu'on s'y intéresse.

Revenir en arrière

Chaque étape est réversible : définissez CONSOLE_RUN_MODE=all et retirez les paramètres du cluster. Rien dans la base de données ne dépend de la séparation.
