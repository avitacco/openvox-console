Utiliser

Exécuter des Plans

Construisez un Plan - une liste d'exécutions Puppet et de Tasks effectués dans l'ordre -, conservez-le, exécutez-le sur les Nodes de votre choix, et suivez chaque étape.

Un Plan est une liste d'étapes effectuées dans l'ordre sur les mêmes Nodes. Chaque étape est une exécution Puppet ou un Task, exactement comme vous en lanceriez un à la main - voir Lancer des Jobs. Un Plan est conservé dans la console pour pouvoir être réexécuté, sur des Nodes différents à chaque fois.

Voir les Plans nécessite orchestrator:read. Les créer, les modifier, les supprimer et les exécuter nécessite orchestrator:run.

Un Plan désigne ici une liste d'étapes construite dans la console. Ce n'est pas un Plan écrit en langage Puppet, que la console n'exécute pas. Un Plan écrit en YAML dans vos propres modules s'exécute depuis la même page : voir Exécuter des Plans issus de votre code.

Construire un Plan

Ouvrez Jobs, puis Plans, puis Nouveau Plan.

  1. Donnez-lui un Nom et, si vous le souhaitez, une description. Un nom ne peut être utilisé que par un seul Plan.
  2. Ajoutez des étapes avec Ajouter une étape d'exécution Puppet et Ajouter une étape de Task. Un Plan compte entre 1 et 20 étapes.
    • Une étape d'exécution Puppet accepte les options d'exécution : no-op, débogage et un Environment.
    • Une étape de Task accepte un Environment, un Task, ses paramètres et un délai d'expiration, comme dans Exécuter un Task.
  3. Ordonnez les étapes avec Monter et Descendre. Ce que vous avez saisi dans une étape se déplace avec elle.
  4. Enregistrer le Plan.

La console vérifie chaque étape à l'enregistrement, comme elle vérifierait l'exécution ou le Task si vous le lanciez maintenant. Une étape refusée est marquée avec la raison, et rien de ce que vous avez saisi n'est perdu.

Un Plan n'indique pas sur quels Nodes il s'exécute. Cela se choisit à chaque exécution.

Valeurs de Task sensibles

Un paramètre de Task marqué sensitive - un mot de passe, un jeton - n'est jamais conservé dans un Plan. Son champ est absent de l'éditeur, et la valeur est demandée à chaque exécution du Plan. En effet, un Plan est partagé : toute personne qui peut lancer des Jobs peut l'ouvrir.

Qui peut modifier un Plan

Toute personne dotée de orchestrator:run peut modifier ou supprimer n'importe quel Plan, quels que soient les groupes de Nodes sur lesquels son rôle est accordé. Un Plan ne nomme aucun Node : les groupes de Nodes n'y trouvent donc rien à limiter. Ce sur quoi une personne peut exécuter un Plan est limité comme pour tout Job. Une personne dont le rôle est limité à certains Tasks ne peut enregistrer un Plan qu'avec des Tasks qu'elle a le droit d'exécuter.

Exécuter un Plan

Sur la page Plans, choisissez Exécuter à côté d'un Plan, ou ouvrez le Plan et choisissez Exécuter.

  1. Choisissez les Nodes : une liste, une requête ou un groupe de Nodes, comme dans Choisir les Nodes. Aperçu des Nodes montre sur quoi il s'exécuterait.
  2. Saisissez les valeurs sensibles que demandent les étapes. Chacune est étiquetée avec son étape.
  3. Exécuter le Plan. La page du Job du Plan s'ouvre.

Les Nodes sont déterminés une seule fois, au lancement du Plan, et chaque étape s'exécute sur ces Nodes. Si votre rôle est accordé sur certains groupes de Nodes, une requête ou un groupe est restreint à vos Nodes, et une liste qui nomme un Node hors de ces groupes est refusée en bloc, comme pour tout Job.

Chaque étape est vérifiée avant que quoi que ce soit ne démarre. Si l'une d'elles devait être refusée - un Task retiré du code entre-temps, par exemple -, le Plan est refusé en nommant l'étape, et rien ne s'exécute.

Un Plan dont une étape ne peut plus s'exécuter affiche un avertissement sur cette étape. Modifiez le Plan avant de l'exécuter.

Tasks que vos rôles n'autorisent pas

Si votre rôle est limité à certains Tasks - voir Limiter un rôle à certains Tasks -, un Plan enregistré par quelqu'un d'autre peut contenir un Task que vous n'avez pas le droit d'exécuter. Vous voyez toujours chaque étape, et celles que vous ne pouvez pas exécuter sont marquées Vos rôles n'autorisent pas le Task .... Exécuter est désactivé pour ce Plan, et l'API le refuse avec 403, en nommant l'étape et le Task. Modifier le Plan n'y changera rien à moins de retirer ces étapes ; l'enregistrer avec elles est refusé de la même façon.

Lorsque la cible est une requête ou un groupe de Nodes, le Plan s'exécute sur les Nodes sur lesquels vous pouvez exécuter chacune de ses étapes de Task, si bien que toutes ses étapes partagent toujours un même ensemble de Nodes. Les étapes d'exécution Puppet ne sont pas limitées.

Suivre un Plan

La page du Job d'un Plan liste ses étapes dans l'ordre. Chacune indique ce qu'elle fait, son état, ses heures de début et de fin, et le résultat de chaque Node. La page se met à jour d'elle-même pendant l'exécution du Plan.

État Signification
En attente une étape précédente n'est pas encore terminée
En cours envoyée aux Nodes, qui n'ont pas tous répondu
Réussi terminée sur chaque Node
Échoué a échoué sur au moins un Node
Non exécutée une étape précédente a échoué, si bien que celle-ci n'a été envoyée à aucun Node

Le numéro d'une étape renvoie vers la page du Job propre à cette étape, qui renvoie elle-même au Plan. La liste Jobs affiche un Plan sur une seule ligne, et non une par étape.

Quand une étape échoue

Une étape échoue si elle échoue sur l'un quelconque de ses Nodes, y compris un Node qui n'était pas connecté. Le Plan s'arrête là : les étapes suivantes sont marquées Non exécutée, et rien n'est envoyé à aucun Node pour elles. Le Job du Plan est en échec.

Il n'existe aucune option pour continuer après une étape en échec, ignorer les Nodes en échec ou retenter une étape. Corrigez ce qui a échoué et relancez le Plan ; un Plan qui ne doit pas répéter ses premières étapes peut être scindé en deux.

Planifier un Plan

Dans la boîte de dialogue Exécuter le Plan, choisissez Planifier plutôt, ou créez une planification et choisissez Exécuter un Plan - voir Planifier des Jobs.

Une planification conserve sa propre copie des étapes du Plan, prise lors de son enregistrement. Si le Plan est modifié ou supprimé par la suite, la planification continue d'exécuter les étapes avec lesquelles elle a été enregistrée. Pour prendre en compte un changement, modifiez la planification, choisissez de nouveau le Plan et enregistrez.

C'est délibéré. Une planification s'exécute avec l'accès de son propriétaire, et toute personne qui peut lancer des Jobs peut modifier un Plan. Si une planification suivait le Plan, une personne limitée à quelques Nodes pourrait modifier ce que la planification d'un administrateur exécute sur tous les Nodes.

Via l'API

Plans enregistrés :

Requête Effet
GET /api/v1/orchestrator/saved-plans liste les Plans, sans leurs étapes
GET /api/v1/orchestrator/saved-plans/<id> un Plan avec ses étapes
POST /api/v1/orchestrator/saved-plans crée un Plan
PUT /api/v1/orchestrator/saved-plans/<id> remplace un Plan
DELETE /api/v1/orchestrator/saved-plans/<id> supprime un Plan
curl -X POST https://console.example.com/api/v1/orchestrator/saved-plans \ -H "Authorization: Bearer <access token>" \ -H 'Content-Type: application/json' \ -d '{"name":"Restart web tier", "description":"Check first, then restart", "steps":[ {"kind":"run","options":{"noop":true}}, {"kind":"task","taskName":"service","environment":"production", "params":{"name":"nginx","action":"restart"},"timeoutSeconds":300} ]}'

Un Plan, tel qu'il est lu, indique pour chaque étape de Task les paramètres sensibles à fournir lors de son exécution (needs), ainsi qu'un problem si son Task est introuvable.

Aucune requête n'exécute un Plan par son id. Pour en exécuter un, envoyez ses étapes - avec les valeurs sensibles ajoutées aux params de chaque étape - et les Nodes :

curl -X POST https://console.example.com/api/v1/orchestrator/plans \ -H "Authorization: Bearer <access token>" \ -H 'Content-Type: application/json' \ -d '{"name":"Restart web tier", "group":12, "steps":[ {"kind":"run","options":{"noop":true}}, {"kind":"task","taskName":"service", "params":{"name":"nginx","action":"restart"}} ]}'

Les Nodes sont désignés par targets, query ou group. La réponse est le Job du Plan. Lisez-le avec GET /api/v1/orchestrator/jobs/<id>, qui renvoie ses steps, chacune avec un state valant waiting, running, succeeded, failed ou not_run.

Une requête refusée répond 400 (ou 403 pour un Node hors de vos groupes de Nodes) avec une error. Lorsqu'une étape en est la cause, elle porte aussi step, numérotée à partir de 1, et, pour les paramètres d'un Task, fields.

GET /api/v1/orchestrator/jobs ne liste plus les étapes d'un Plan comme des Jobs à part entière. Ajoutez ?parent=<plan job id> pour les lister.

Dans un déploiement séparé

Un Plan lancé dans la console est envoyé et suivi, étape par étape, par l'instance qui a reçu la requête : une instance web dans un déploiement séparé (voir modes d'exécution). Si cette instance s'arrête avant la fin du Plan, les étapes encore en cours sont marquées en échec et les autres sont closes comme non exécutées ; relancez le Plan. Un Plan planifié est lancé et suivi de la même façon par une instance orchestrator.
