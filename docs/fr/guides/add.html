Nodes

Ajouter des Nodes

Enrôlez un Node avec un seul script sous Linux, macOS ou Windows, signez son certificat, et voyez-le se connecter et s'exécuter.

Ajouter un Node tient en un script, exécuté une fois sur le Node. Il installe l'agent OpenVox, enrôle le Node auprès de la CA s'il n'a pas encore de certificat, installe l'agent de Node de la console depuis le dépôt de paquets de la console, et le démarre en tant que service. Il peut être relancé sans risque.

Avant de commencer

La console doit connaître deux adresses qu'un Node utilisera, toutes deux définies lors de l'installation :

  • CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR, l'adresse que les Nodes composent pour maintenir leur connexion à la console ouverte. Son hôte doit figurer dans le certificat du transport vers les Nodes.
  • CONSOLE_PUPPET_SERVER_PUBLIC_ADDR, le serveur Puppet auprès duquel un Node s'enrôle. Ce doit être un nom figurant dans le certificat d'openvoxserver. S'il n'est pas défini, le script ne touche pas à la configuration du serveur Puppet du Node, ce qui convient aux Nodes déjà pointés vers un serveur par un autre moyen.

Chaque Node doit pouvoir joindre l'URL de base de la console, openvoxserver sur le port 8140, et l'adresse du transport vers les Nodes.

L'image publiée de la console contient déjà les paquets de l'agent de Node que le script installe. Si vous avez construit la console vous-même, construisez-les avant la console, comme le décrit le guide d'installation par paquets, sinon chaque installation de Node échoue avec une 404.

Lancer le script d'installation

Sur le Node, en tant qu'administrateur :

Linuxcurl -fsSL https://console.example.com/packages/install.sh | sudo bash macOScurl -fsSL https://console.example.com/packages/install-macos.sh | sudo bash WindowsInvoke-WebRequest https://console.example.com/packages/install.ps1 -OutFile install.ps1 .\install.ps1

Sous Windows, lancez PowerShell en tant qu'administrateur.

Les scripts macOS et Windows sont vérifiés par les tests du projet, mais n'ont pas encore été exécutés de bout en bout sur de vrais hôtes macOS et Windows, comme l'a été le script Linux. Signalez tout ce qui ne se déroule pas comme décrit ici.

Signer le certificat du Node

Si la CA signe les demandes automatiquement, le script se termine de lui-même. Sinon, il attend jusqu'à cinq minutes, en vérifiant toutes les 15 secondes. Signez la demande pendant qu'il attend, et la même exécution se poursuit jusqu'au bout :

  1. Ouvrez la page Nodes de la console. Le Node y figure avec une demande de certificat en attente.
  2. Choisissez Signer.

Signer depuis la console nécessite l'identifiant d'administration des certificats, et un utilisateur disposant de la permission nodes:certs:manage ; voir Gérer les certificats des Nodes. Vous pouvez aussi signer sur l'hôte de la CA lui-même :

sudo /opt/puppetlabs/bin/puppetserver ca sign --certname <node certname>

Le script se termine de l'une de ces trois façons :

Ce qui s'est passé Ce que vous voyez
La demande a été signée pendant l'attente Il poursuit et termine l'installation
L'attente a expiré sans que la demande soit signée Il s'arrête en indiquant la page Nodes où la signer ; signez-la, puis relancez le script
Il n'a pas pu joindre la CA Il s'arrête en signalant un problème de connexion ou de TLS - et non une demande en attente

Une CA injoignable n'est signalée qu'une fois toute l'attente écoulée, car l'agent continue de réessayer au cas où le problème serait passager. Si vous voyez une erreur de connexion, vérifiez la résolution de noms et le port 8140 plutôt que de chercher une demande à signer.

Voir le Node se connecter

Sur la page Nodes, le Node apparaît comme connecté, avec un certificat signé.

Un Node qui se connecte avant d'avoir jamais envoyé de Report à openvoxdb resterait sinon vide jusqu'à sa prochaine exécution Puppet planifiée ; la console lance donc immédiatement sa première exécution. Celle-ci apparaît sur la page Jobs comme n'importe quelle autre, enregistrée comme lancée par system:initial-run. Une fois terminée, la page du Node affiche ses Facts, ses Reports et les classes qui lui sont appliquées.

Ensuite, l'agent de Node se gère lui-même

Vous n'avez pas à relancer le script pour mettre à jour l'agent de Node. Lorsque vous mettez à jour la console, elle met à jour pour vous l'agent de Node sur chaque Node connecté ; voir Tenir les agents de Node à jour.

Remonter les paquets du Node (facultatif)

L'inventaire des paquets est désactivé pour chaque Node jusqu'à ce que vous l'activiez. Sur la page du Node, dans sa section Paquets, activez la remontée. La console demande au Node d'ajouter le Fact des paquets et exécute Puppet immédiatement : l'inventaire apparaît donc dès cette exécution plutôt qu'à la prochaine exécution planifiée. La désactivation retire le Fact de la même façon.

L'interrupteur nécessite la permission orchestrator:run, et ne fonctionne que si le Node est connecté : il agit sur le Node sur-le-champ, au lieu de mettre un changement en file d'attente.

OpenVox Console est distribué sous forme d'images de conteneur, construites pour amd64 et arm64 à chaque push, et d'un binaire unique. Les guides d'installation vous mènent d'un hôte vide à un déploiement fonctionnel - openvoxserver, openvoxdb, Postgres et la console - avec des conteneurs ou avec des paquets.
