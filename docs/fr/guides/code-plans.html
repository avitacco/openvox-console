Utiliser

Exécuter des Plans issus de votre code

Exécutez les Plans YAML de vos modules, avec des paramètres typés, des résultats transmis entre étapes, et chaque Task vérifié au regard de vos groupes de Nodes.

Un Plan de code est un fichier YAML placé dans le répertoire plans d'un module, au format qu'utilisent Bolt et Puppet Enterprise. La console le lit dans le code qu'elle a déployé et l'exécute elle-même : une étape après l'autre, en transmettant les résultats d'étape en étape. Elle n'a besoin ni de Bolt ni du langage Puppet.

Il diffère d'un Plan enregistré, qui est une liste fixe d'exécutions Puppet et de Tasks construite dans la console et exécutée sur un seul ensemble de Nodes. Un Plan de code vit avec votre code, prend ses propres paramètres, et détermine les cibles de chaque étape à partir des étapes précédentes.

Lire la liste des Plans nécessite orchestrator:read. En exécuter un nécessite orchestrator:run. Aucune nouvelle permission n'entre en jeu.

D'où viennent les Plans

La console cherche <module>/plans/<name>.yaml dans les modules de chaque Environment, dans l'ordre du modulepath de environment.conf (modules s'il n'y en a pas). Un Plan est nommé module::name, ou simplement module pour init.yaml. Si un nom apparaît dans deux répertoires, le premier l'emporte, comme dans Puppet.

Les fichiers sont lus dans le répertoire de code de l'instance de la console qui déploie votre code (CONSOLE_CODE_DIR_PATH). Une instance qui ne détient pas le code déployé ne peut ni lister ni exécuter de Plans, et l'indique plutôt que d'afficher une liste vide. Exécutez les Plans depuis l'instance qui déploie.

Ouvrez Jobs, puis Plans : la section Plans dans le code liste les Plans d'un Environment. Un Plan que la console ne peut pas exécuter est listé avec la raison, en nommant l'étape.

Ce que peut faire un Plan

Un Plan comporte une description, des parameters, des steps et un return :

description: Restart a service, then check it parameters: targets: type: TargetSpec description: Where to restart it service: type: String[1] default: nginx token: type: Optional[Sensitive[String]] steps: - name: restart description: Restart the service task: service::restart targets: $targets parameters: name: $service - name: status task: service::status targets: $restart.ok_targets parameters: name: $service - message: "checked ${status.targets}" return: restarted: $restart.ok_targets healthy: $status.ok

Les paramètres déclarent un type, un default facultatif et une description. Les types sont ceux qu'utilisent les Tasks (String, Integer[1, 10], Boolean, Array[String], Enum['a','b'], Optional[...], ...) ainsi que TargetSpec (des Nodes) et Sensitive[...]. Un paramètre sans valeur par défaut qui n'est pas Optional est obligatoire. La console refuse une exécution dont un paramètre est manquant, inconnu ou mal typé avant que quoi que ce soit ne démarre, en le nommant.

Les étapes font exactement l'une des choses suivantes :

  • task: module::task, avec targets et parameters. Exécute le Task.
  • plan: module::plan, avec parameters. Exécute un autre Plan au sein de celui-ci. Un Plan peut appeler des Plans jusqu'à cinq niveaux de profondeur, et jamais lui-même.
  • message: text. Inscrit du texte dans le compte rendu de l'exécution.

Une étape peut avoir un name, qui rend son résultat disponible sous la forme $name pour les étapes suivantes, ainsi qu'une description.

Les références s'écrivent $name, $name.field, $name[0] et $name['field'], vers un paramètre ou une étape précédente. Une chaîne constituée uniquement d'une référence conserve le type de la valeur (une liste reste une liste). Dans du texte, écrivez ${name.field} ; écrivez $$ pour un signe dollar. C'est toute la syntaxe : pas d'opérateurs, pas de conditions, pas de fonctions. Dans une liste ou un mapping YAML écrit sur une ligne, mettez entre guillemets une référence qui contient [ ou ,.

Le résultat d'une étape comporte :

Champ Contient
ok chaque cible a réussi
results les target, ok, value et error de chaque cible
targets, ok_targets, error_targets noms des Nodes
value le résultat du Task, pour une étape portant sur un seul Node

La value d'un Task est ce qu'il a affiché en JSON, ou son texte sous la forme _output.

Si une étape de Task échoue sur l'une quelconque de ses cibles, le Plan échoue à ce point : les étapes suivantes sont consignées comme non exécutées et plus rien n'est envoyé. Une étape sans cible (par exemple parce qu'une étape précédente n'a réussi nulle part) n'exécute rien et compte comme réussie.

Non pris en charge : les étapes command, script, upload, download, resources et eval, les expressions en langage Puppet, l'exécution d'étapes en parallèle, les nouvelles tentatives et la capture d'erreurs, ainsi que la planification d'un Plan issu du code. Un Plan qui utilise l'un de ces éléments est listé comme inutilisable, avec la raison. Les Plans Bolt en langage Puppet (.pp) ne sont pas exécutés.

En exécuter un

Choisissez Exécuter à côté d'un Plan. Le formulaire est construit à partir de ses paramètres ; laissez un champ vide pour utiliser la valeur par défaut. Les Nodes (TargetSpec) sont indiqués par une liste de noms, une requête ou un groupe de Nodes, résolus une fois au lancement du Plan, et prévisualisés d'abord. L'exécution s'ouvre comme un Job ; sa page montre chaque étape au fur et à mesure : son statut, le Job qu'elle a lancé, ce qu'un message a affiché et la raison de l'échec d'une étape, avec la valeur renvoyée par le Plan et les paramètres qu'il a reçus.

Portée et permissions

Un Plan ne peut rien faire que vous ne pourriez faire à la main. Lorsque vous le lancez :

  • le Task que nomme chaque étape doit exister et être autorisé par vos rôles, sinon la requête est refusée en nommant l'étape ;
  • les Nodes que vous nommez doivent faire partie de vos groupes de Nodes, sinon toute la requête est refusée ;
  • à chaque étape atteinte, ses cibles sont vérifiées au regard de vos groupes de Nodes et le Task au regard de votre liste d'autorisation, exactement comme pour un Task que vous lancez vous-même. Une étape qui serait refusée fait échouer le Plan à ce point, avec la raison.

Les cibles sans agent peuvent être utilisées dans les étapes de Task.

Un lecteur limité à certains groupes de Nodes ne voit l'exécution d'un Plan que si elle a porté sur ses Nodes, et ne voit pas ce qu'elle a affiché, renvoyé ou reçu lorsqu'elle a aussi porté sur d'autres Nodes.

Valeurs sensibles

Un paramètre de type Sensitive[...] n'est jamais consigné : il apparaît comme [redacted] dans les paramètres enregistrés, la trace, les messages, la valeur renvoyée, les journaux et les entrées d'audit, et n'atteint que le paramètre de Task auquel il est transmis. Une valeur sensible ne peut être transmise qu'à un paramètre lui-même Sensitive.

Exécutions longues

Un Plan peut tourner pendant des heures, jusqu'à 24. La console signale au Job qu'il est en vie au fil de l'exécution. Si l'instance de la console qui le suit s'arrête, le Plan est mis en échec dix minutes après le dernier signe de vie ; les étapes déjà lancées se poursuivent sur leurs Nodes. Une exécution est limitée à 200 étapes et une étape à 1000 cibles ; une limite atteinte fait échouer le Plan, en la nommant.

Le lancement d'un Plan, et sa fin, donnent lieu à des entrées d'audit indiquant qui, quel Plan et quel Environment, ainsi que les noms des paramètres fournis, jamais leurs valeurs.
