Modes d'exécution

Ce que sert et fait tourner chacun des modes d'exécution de la console, et ce que chacun nécessite comme configuration.

Une seule image, un seul binaire. CONSOLE_RUN_MODE choisit les parties de la console qu'une instance fait tourner, afin que des parties aux charges très différentes puissent être dimensionnées et placées séparément. Non défini, il vaut all : tout dans une seule instance, ce que fait toujours tourner un déploiement à instance unique.

Ce que fait tourner chaque mode

Mode Sert Écoute Tâches en arrière-plan
all (par défaut) tout HTTP, transport vers les Nodes toutes les tâches en arrière-plan
web la console, son API, les webhooks de déploiement de code et la classification HTTP le suivi des Jobs lancés par son intermédiaire
enc la classification uniquement HTTP rien
orchestrator rien d'autre que la santé et les métriques HTTP, transport vers les Nodes l'envoi des Jobs, les Jobs planifiés, la première exécution des nouveaux Nodes et les mises à jour de l'agent de Node
worker rien d'autre que la santé et les métriques HTTP les synchronisations de vulnérabilités et le nettoyage des Jobs abandonnés

Chaque mode sert /health et /metrics : toute instance peut donc être vérifiée sans connaître son mode, et /health indique le mode dans lequel elle tourne.

Deux choix de ce tableau sont délibérés :

  • web répond aussi à la classification. enc existe pour que la classification puisse tourner seule, à côté des compilateurs, et non pour qu'elle manque partout ailleurs. Une séparation qui cesserait discrètement de classifier les Nodes serait bien pire que de laisser web porter une partie de cette charge.
  • orchestrator ne sert aucune API. Il détient les connexions des Nodes et y envoie les Jobs. Lancer un Job est le rôle de web, et web atteint ces connexions à travers le cluster.
  • Un Job est suivi par l'instance qui l'a lancé. Une exécution, un Task ou un Plan lancé dans la console est envoyé et suivi par l'instance web qui a reçu la requête ; les instances web doivent donc être en cluster avec les instances orchestrator pour atteindre le moindre Node. Si cette instance web s'arrête avant la fin du Job, celui-ci est marqué en échec par une instance worker.

Ce dont chaque mode a besoin

Chaque mode n'exige que ce qu'il utilise, et refuse de démarrer sans, en nommant le paramètre manquant :

Mode Nécessite
tous les modes CONSOLE_POSTGRES_DSN et les quatre paramètres CONSOLE_OPENVOXDB_*
all, web CONSOLE_RBAC_SIGNING_KEY_FILE : ce sont les seuls modes qui émettent des jetons de connexion
enc, orchestrator, worker CONSOLE_RBAC_VERIFICATION_KEYS_DIR : ils vérifient les jetons, mais n'en émettent jamais
orchestrator CONSOLE_NODE_TRANSPORT_ADDR : sans écoute pour les Nodes, chaque Job échouerait avec « not connected » sur une instance en apparence saine

Donner au planificateur ce qu'utilisent les Jobs planifiés

Les Jobs planifiés sont lancés par les instances all et orchestrator, et non par web. Une instance orchestrator démarre sans ces paramètres, mais une planification qui en a besoin est ignorée, avec la raison, tant que l'instance ne l'a pas :

  • CONSOLE_PUPPET_SERVER_URL, pour lancer un Task planifié : le Task est recherché dans le code déployé au déclenchement de la planification.
  • CONSOLE_SECRETS_KEY_FILE, la même clé que sur web, pour lancer un Task planifié doté d'un paramètre sensible.

Lorsque plusieurs instances font tourner le planificateur, chaque échéance est déclenchée par une seule d'entre elles. Si aucune ne tourne à l'échéance d'une planification, celle-ci démarre dès qu'une instance tourne - sauf si le retard dépasse 15 minutes, auquel cas cette échéance est consignée comme manquée.

Donner les clés de vérification aux modes qui n'émettent pas de jetons

Une instance qui se contente de vérifier les jetons lit les clés de vérification dans un répertoire, un fichier par clé, nommé d'après l'ID de la clé. Un déploiement qui n'a jamais renouvelé sa clé utilise l'ID default ; le répertoire contient donc un seul fichier, default.pem, qui est le fichier de la clé de signature lui-même :

sudo install -d -m 0750 -o root -g openvox-console /etc/openvox-console/rbac-verification-keys sudo install -m 0640 -o root -g openvox-console \ rbac-signing-key.pem /etc/openvox-console/rbac-verification-keys/default.pem CONSOLE_RUN_MODE=enc CONSOLE_RBAC_VERIFICATION_KEYS_DIR=/etc/openvox-console/rbac-verification-keys

Le répertoire de vérification n'accepte pour l'instant que des clés au même format que la clé de signature : la clé privée, dont la console n'utilise que la moitié publique. Une instance qui reçoit ce répertoire détient donc aussi une clé capable de signer des jetons. Protégez-le sur chaque hôte exactement comme la clé de signature, y compris sur les instances enc placées à côté des compilateurs.

Lorsque vous renouvelez la clé de signature, le répertoire de vérification de chaque instance doit lui aussi recevoir la nouvelle clé ; Renouveler la clé de signature des jetons détaille l'ordre à suivre.

Changer le mode d'une instance

Définissez CONSOLE_RUN_MODE et redémarrez l'instance. Aucune donnée ne bouge : tous les modes lisent et écrivent la même base de données. Le remettre à all annule le changement.

Une instance isolée peut changer de mode, mais un mode autre que all n'a de sens qu'au sein d'instances en cluster qui, ensemble, couvrent tous les modes. Voir Faire tourner plus d'instances.
