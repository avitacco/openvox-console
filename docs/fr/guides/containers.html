Installer

Installer avec des conteneurs

Faites tourner openvoxserver, openvoxdb, les deux bases de données et la console avec Docker Compose, d'un hôte vide jusqu'à une console prête à accueillir des Nodes.

Ce guide fait tourner toute la pile à partir du fichier compose de production du projet et de ses images publiées. Rien n'est construit sur l'hôte. Fixez les noms dans Planifier un déploiement avant de commencer.

Il vous faut un hôte Linux avec Docker Engine et le plugin Compose, ainsi qu'un utilisateur capable d'exécuter docker sans sudo.

Récupérer le fichier compose

Le fichier docker-compose.yml du dépôt du projet décrit la pile de production : la console, les deux bases de données, openvoxserver et openvoxdb. Copiez ce seul fichier sur l'hôte, dans un répertoire dédié appartenant à votre utilisateur :

sudo mkdir -p /opt/openvox-console sudo chown "$USER": /opt/openvox-console mkdir -p /opt/openvox-console/secrets /opt/openvox-console/certs cd /opt/openvox-console curl -fsSLO https://raw.githubusercontent.com/avitacco/openvox-console/main/docker-compose.yml

Ne déployez pas depuis un clone du dépôt. Un clone contient aussi docker-compose.override.yml, la pile de développement, qu'un simple docker compose up charge sans rien dire : mots de passe jetables, ports de base de données ouverts et signature automatique des certificats. Chaque commande de ce guide passe -f docker-compose.yml pour que seul le fichier de production soit lu.

Définir les valeurs propres au déploiement

Créez .env à côté du fichier compose. Celui-ci refuse de démarrer tant que l'une des trois premières variables n'est pas définie, si bien qu'un déploiement ne peut pas démarrer avec une valeur fictive :

CONSOLE_BASE_URL=https://console.example.com CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 OPENVOXDB_POSTGRES_PASSWORD=<a strong password> # Every name nodes or the console use to reach openvoxserver, beyond its # own name "openvoxserver" - see Plan a deployment. OPENVOXSERVER_DNS_ALT_NAMES=puppet.example.com # The Puppet server a node should enroll against, written into the node # install script. Must be one of the names above. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # The first admin user, created only while there are no users. Its # password is a secret file, below. Without this name no admin is # created and nobody can log in. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin # The console's plain-HTTP port, published on loopback only, so the # TLS proxy in front of it is the only way in. See "Put TLS in front of # the console" below. CONSOLE_HTTP_PORT=127.0.0.1:8080

Choisissez l'image de la console à exécuter. CONSOLE_IMAGE_TAG vaut par défaut main, qui suit le dernier commit. Pour un déploiement que vous voulez figer, épinglez plutôt le tag immuable d'un commit précis :

CONSOLE_IMAGE_TAG=sha-a1b2c3d

Les tags de version tels que v1.2.3, ainsi que latest, ne sont publiés qu'une fois une version officielle sortie. D'ici là, demander latest échoue avec manifest unknown.

Écrire les secrets

Les secrets sont des fichiers dans secrets/, une valeur par fichier, plutôt que des variables d'environnement, afin de ne jamais apparaître dans docker inspect :

printf '%s' '<console database password>' > secrets/console_postgres_password printf 'postgres://console:%s@console-postgres:5432/console?sslmode=disable' '<console database password>' \ > secrets/console_postgres_dsn printf '%s' '<a strong password, 12 characters or more>' > secrets/console_bootstrap_admin_password chmod 600 secrets/*

La chaîne de connexion à la base de données de la console doit utiliser le même mot de passe que console_postgres_password. sslmode=disable est voulu : le conteneur Postgres tourne sans TLS et la connexion ne quitte jamais le réseau compose, si bien qu'exiger TLS ne ferait qu'empêcher la console de se connecter.

openvoxserver a aussi besoin d'un fichier de jeton, enc_bridge_token, que vous remplirez une fois la console en marche. Créez-le vide pour l'instant, car openvoxserver ne démarre pas sans lui :

: > secrets/enc_bridge_token

Démarrer l'autorité de certification

openvoxserver est la CA dont proviennent les certificats de tous les autres composants ; il démarre donc en premier, et seul :

docker compose -f docker-compose.yml up -d openvoxserver

Son premier démarrage crée la CA, ce qui prend une minute ou deux. Attendez qu'il se déclare en marche :

docker compose -f docker-compose.yml exec openvoxserver \ curl -ksS https://127.0.0.1:8140/status/v1/simple

La réponse est running.

Le volume openvoxserver-ca est votre autorité de certification. Le perdre oblige chaque Node à s'enrôler de nouveau. Sauvegardez-le, et ne le supprimez jamais avec docker compose down -v.

Émettre les certificats de la console

La console a besoin de deux certificats issus de la CA, et éventuellement d'un troisième. Émettez-les dans le conteneur openvoxserver en marche et copiez-les dans certs/, où le fichier compose les monte pour la console.

Le certificat client openvoxdb

C'est ainsi que la console s'authentifie auprès d'openvoxdb :

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname console docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console.pem certs/console-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console.pem certs/console-key.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/ca.pem certs/ca.pem

puppetserver ca generate commence par afficher Error: Signed certificate console could not be found on the CA. C'est la commande qui vérifie que le nom est libre, et non un échec. Ce qui compte, ce sont les lignes suivantes, qui se terminent par Successfully saved certificate.

Le certificat du transport vers les Nodes

Les Nodes vérifient ce certificat lorsqu'ils se connectent à la console ; il doit donc porter exactement le nom qu'ils composent : la partie hôte de CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR.

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/node-transport.pem certs/node-transport-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/node-transport.pem certs/node-transport-key.pem

Les Nodes s'authentifient en retour avec leurs propres certificats, issus de la même CA ; c'est pourquoi la console n'a besoin d'aucun autre fichier pour eux.

La clé de signature des jetons

La console signe ses propres jetons de connexion avec une clé ES256. Celle-ci ne provient pas de la CA. Générez-la sur n'importe quelle machine avec OpenSSL :

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

Sauvegardez ce fichier. Le perdre invalide tous les jetons émis, ce qui déconnecte tout le monde ; le laisser fuiter permet à n'importe qui de fabriquer des jetons. Voir Renouveler la clé de signature des jetons pour le remplacer en toute sécurité.

Générez-la directement dans certs/ :

openssl ecparam -genkey -name prime256v1 -noout -out certs/rbac-signing-key.pem

L'identifiant d'administration des certificats (facultatif)

C'est cet identifiant qui permet à la page Nodes d'afficher l'état des certificats, et de signer, révoquer et nettoyer des certificats. Sans lui, la console ne liste que les Nodes qui se sont déjà connectés ou ont déjà envoyé un Report. Un Node dont le certificat attend d'être signé n'apparaît pas du tout, car la CA est le seul composant à connaître son existence.

Cet identifiant donne un accès administrateur complet à la CA. openvoxserver protège chaque point d'accès de la CA derrière une seule extension d'autorisation : un certificat capable de lire les états peut donc aussi signer, révoquer et nettoyer le certificat de n'importe quel Node. Il n'existe pas de variante en lecture seule. Ne le conservez que là où tourne la console, et lisez Gérer les certificats des Nodes avant de l'émettre.

Son émission écrit dans l'état de la CA, qu'un openvoxserver en marche écrit lui aussi : arrêtez donc d'abord openvoxserver et émettez-le depuis un conteneur ponctuel utilisant les mêmes volumes. Compose nomme les volumes d'après le répertoire du projet ; vérifiez donc d'abord leurs noms exacts :

docker volume ls | grep openvoxserver

Puis, avec les deux noms affichés :

docker compose -f docker-compose.yml stop openvoxserver docker run --rm --entrypoint "" \ -v openvox-console_openvoxserver-ssl:/etc/puppetlabs/puppet/ssl \ -v openvox-console_openvoxserver-ca:/etc/puppetlabs/puppetserver/ca \ ghcr.io/avitacco/openvox-console-server:main \ puppetserver ca generate --ca-client --force --certname console-ca-client docker compose -f docker-compose.yml start openvoxserver

--force est obligatoire ici. Avant de signer, la commande vérifie que le serveur est bien arrêté ; dans un simple conteneur, elle ne peut pas le savoir, si bien que sans --force elle affiche « Could not determine whether Puppet Server is online » et se termine sans rien avoir créé. Lisez sa sortie plutôt que de supposer qu'elle a fonctionné.

La commande indique écrire ses fichiers sous un long chemin .puppetlabs. Ignorez-le : dans les volumes, ils arrivent à l'emplacement habituel. Copiez-les à l'extérieur :

docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem certs/ca-client-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem certs/ca-client-key.pem

Indiquez ensuite à la console où se trouve la CA, dans .env. Au sein du réseau compose, la console joint openvoxserver par son nom de conteneur, qui figure toujours dans le certificat d'openvoxserver :

CONSOLE_CA_CLIENT_URL=https://openvoxserver:8140

Confirmez, depuis l'intérieur d'openvoxserver, que l'identifiant est accepté :

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://openvoxserver:8140/puppet-ca/v1/certificate_statuses/all

HTTP 200 signifie que la CA l'accepte.

Tasks

L'exécution de Tasks Puppet ne nécessite rien de plus. La console demande à openvoxserver, à l'adresse https://openvoxserver:8140, quels Tasks contient votre code déployé, en utilisant le certificat client openvoxdb déjà émis ; openvoxserver permet à tout certificat de sa CA de lire les Tasks. Pour désactiver les Tasks, définissez une adresse vide dans .env :

CONSOLE_PUPPET_SERVER_URL=

Voir Lancer des Jobs pour les exécuter.

La liste des classes

La page d'un groupe de Nodes propose les classes que définit votre code déployé, avec leurs paramètres, pour qu'elles soient choisies plutôt que tapées. La console les lit depuis openvoxserver par la même connexion que les Tasks.

Par défaut, openvoxserver ne laisse aucun certificat lire les classes. L'image du serveur dans le fichier compose ajoute la règle à chaque démarrage, en autorisant le certificat nommé console - le certificat client openvoxdb émis plus haut. Si vous l'avez émis sous un autre nom, indiquez ce nom dans .env :

CLASS_DISCOVERY_CERTNAME=my-console-cert

Vérifiez-le depuis l'intérieur d'openvoxserver, avec le certificat de la console. HTTP 200 signifie que la liste peut être lue :

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ 'https://openvoxserver:8140/puppet/v3/environment_classes?environment=production'

HTTP 403 signifie que la règle ne nomme pas ce certificat. Rien d'autre n'en dépend : la page du groupe indique alors que la liste n'est pas disponible, et les classes se saisissent par leur nom, comme avant l'existence de la liste. Voir Classifier les Nodes.

Démarrer tout le reste

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

openvoxdb demande son propre certificat à la CA lors de son premier démarrage. Le fichier compose signe automatiquement cette seule demande, via une liste d'autorisation qui ne contient que openvoxdb ; les Nodes ne sont jamais signés ainsi. openvoxdb attend ensuite sa base de données, et la console attend les deux. Suivez leur démarrage :

docker compose -f docker-compose.yml ps

Chaque service atteint l'état healthy en quelques minutes.

Si openvoxdb n'atteint jamais l'état sain

openvoxdb abandonne si sa demande de certificat n'est pas signée dans les deux minutes, et il inscrit alors l'échec dans son propre fichier de certificat. Chaque redémarrage ultérieur trouve un fichier de certificat, saute l'enrôlement et échoue avec No certs found in 'ssl-cert' file. Il ne se rétablit pas de lui-même. Réinitialisez son identité plutôt que de le redémarrer :

docker compose -f docker-compose.yml rm -sf openvoxdb docker volume rm openvox-console_openvoxdb-ssl docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca clean --certname openvoxdb docker compose -f docker-compose.yml up -d openvoxdb

Le nom du volume suit celui du répertoire du projet ; vérifiez-le avec docker volume ls. Omettre le ca clean laisse la CA avec un certificat signé pour openvoxdb sans clé correspondante, et le nouveau démarrage échoue avec No keypair on disk and CA already has signed certificate.

Placer TLS devant la console

La console sert son interface web et son API en HTTP simple. L'URL de base en https:// est atteinte via un reverse proxy qui termine le TLS et transmet les requêtes à la console. N'importe quel reverse proxy convient. Cet exemple utilise Caddy, sur l'hôte de la console :

Debian et Ubuntusudo apt-get install -y caddy RHEL, Rocky et AlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

Voici alors l'intégralité de /etc/caddy/Caddyfile :

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

Si la console écoute sur un autre port, parce qu'elle partage un hôte avec openvoxdb, indiquez plutôt ce port dans reverse_proxy.

Pour un nom résolvable sur Internet, Caddy obtient et renouvelle lui-même le certificat. Pour un nom interne, donnez-lui un certificat issu de votre propre CA avec une ligne tls <cert file> <key file> à l'intérieur du bloc. Pour un essai, tls internal fait émettre par Caddy un certificat issu de sa propre CA locale, ce que les navigateurs signalent par un avertissement.

Seule l'interface web passe par le proxy. Le transport vers les Nodes, sur le port 8142, porte son propre TLS et vérifie lui-même le certificat de chaque Node : les Nodes doivent donc le joindre directement. Ne le placez jamais derrière le proxy.

Se connecter pour la première fois

À son premier démarrage, la console crée le schéma de sa base de données, puis l'administrateur initial tant que la table des utilisateurs est encore vide. Une fois démarrée, son journal affiche trois lignes :

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

Vérifiez qu'elle se déclare en bonne santé, d'abord directement sur l'hôte de la console, puis via le proxy TLS à son URL de base :

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

Chaque réponse indique ok pour chaque dépendance. Si seule la seconde échoue, la console va bien et c'est le proxy qui pose problème. Utilisez le port propre de la console dans la première si vous l'avez déplacée hors du port 8080. Ouvrez ensuite l'URL de base de la console, connectez-vous en tant qu'administrateur initial et changez immédiatement son mot de passe.

Le mot de passe de l'administrateur initial doit compter au moins 12 caractères et ne doit pas être identique à son nom d'utilisateur. Sinon, aucun administrateur n'est créé et personne ne peut se connecter. Le journal l'indique :

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

Définissez un mot de passe plus long et redémarrez la console. Voir Mots de passe et verrouillage.

Une fois connecté et le mot de passe changé, retirez de la configuration de la console les paramètres de l'administrateur initial. Ils ne sont lus que tant que la table des utilisateurs est vide, mais rien ne justifie de laisser traîner un mot de passe.

Connecter la classification

openvoxserver demande à la console quelles classes attribuer à chaque Node, via le node terminus exec standard de Puppet. Un petit programme, enc-bridge, effectue cette requête pour le compte d'openvoxserver, et il lui faut un jeton pour cela.

Émettre un jeton pour enc-bridge

Un jeton de service porte un ensemble fixe de permissions choisies à sa création, sans aucun rôle. Créez-en un autorisé uniquement à lire la classification :

  1. Dans la console, ouvrez Administration, puis Jetons de service.
  2. Sous Nouveau jeton de service, nommez-le enc-bridge et donnez-lui uniquement la permission enc:read.
  3. Choisissez Créer un jeton de service.

Le jeton n'est affiché qu'une fois. Copiez-le maintenant.

La même chose via l'API, avec un jeton d'accès issu d'une connexion administrateur : curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

Donner le jeton à openvoxserver

L'image openvoxserver contient déjà enc-bridge, la configuration Puppet qui l'utilise et la fonction Hiera qui permet aux Nodes de lire les données de configuration : il ne lui faut donc que le jeton. Écrivez-le dans le fichier secret créé vide plus tôt :

printf '%s' '<the enc:read service token>' > secrets/enc_bridge_token

openvoxserver ne tourne pas en root dans son conteneur, et Compose monte les fichiers secrets avec leur propriétaire sur l'hôte. Un fichier lisible uniquement par votre propre utilisateur est donc illisible pour openvoxserver, et la classification échoue. Donnez plutôt l'accès en lecture au groupe 0 et protégez le répertoire :

sudo chgrp 0 secrets/enc_bridge_token chmod 640 secrets/enc_bridge_token chmod 700 secrets

Recréez openvoxserver pour qu'il lise le nouveau jeton :

docker compose -f docker-compose.yml up -d --force-recreate openvoxserver

Vérifier la classification

Interrogez enc-bridge directement, comme openvoxserver l'exécute. Cela vérifie en une seule commande le programme, le jeton, les permissions des fichiers et la réponse de la console :

docker compose -f docker-compose.yml exec -u puppet:0 openvoxserver \ /usr/local/bin/enc-bridge <a certname>

{} signifie que la classification fonctionne et que ce Node ne correspond encore à aucun groupe. Créez sur la page Groupes de la console un groupe de Nodes qui épingle ce certname, relancez la même commande, et ses classes apparaissent :

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

Une erreur ici, c'est justement la panne à détecter. permission denied signifie que le jeton n'est pas lisible par l'utilisateur sous lequel tourne openvoxserver, et une 401 que le jeton est incorrect ou ne dispose pas de enc:read.

Si la prochaine exécution Puppet d'un Node échoue avec Could not find class <name>, c'est que la classification fonctionne : la console a demandé à openvoxserver d'inclure une classe que votre code Puppet ne définit pas encore.

openvoxserver met les Environments en cache : après avoir ajouté du code Puppet, videz son cache, sinon la même erreur persiste :

docker compose -f docker-compose.yml exec openvoxserver sh -c \ 'curl -ksS -X DELETE \ --cert /etc/puppetlabs/puppet/ssl/certs/openvoxserver.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/openvoxserver.pem \ https://127.0.0.1:8140/puppet-admin-api/v1/environment-cache'

Mettre à jour plus tard

Pour passer à une console plus récente, modifiez CONSOLE_IMAGE_TAG (ou refaites un pull si vous suivez main) et relancez la pile. Compose ne recrée que ce qui a changé :

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

Le fichier compose ne publie pas le port d'openvoxdb ; pour la vérification ci-dessous, interrogez-le donc depuis l'intérieur de son conteneur : docker compose -f docker-compose.yml exec openvoxdb curl -ksS https://127.0.0.1:8081/status/v1/simple
