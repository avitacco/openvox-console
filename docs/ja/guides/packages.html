インストール

パッケージとバイナリからインストールする

openvoxserver、openvoxdb、Postgres をパッケージからインストールし、コンソールをビルドして systemd サービスとして動かします。

このガイドでは、openvoxserver、openvoxdb、Postgres を OpenVox とディストリビューションのパッケージからインストールし、コンソールを単一のバイナリとして systemd のもとで動かします。始める前に、デプロイを計画するで名前を決めておいてください。

コマンドは Debian と Ubuntu 向けで、異なる箇所には RHEL、Rocky Linux、AlmaLinux の同等のコマンドを併記しています。構成要素は 1 台のホストにも複数のホストにも置けます。特定のホストで行う手順には、その旨を記しています。

openvoxserver をインストールする

openvoxserver は他のすべての構成要素の証明書の発行元となる認証局なので、最初にインストールします。OpenVox 8 リポジトリを追加してインストールします:

Debian と Ubuntu. /etc/os-release curl -fsSL -o /tmp/openvox8-release.deb \ "https://apt.voxpupuli.org/openvox8-release-${ID}${VERSION_ID}.deb" sudo apt-get install -y /tmp/openvox8-release.deb sudo apt-get update && sudo apt-get install -y openvox-server RHEL、Rocky、AlmaLinuxsudo dnf install -y https://yum.voxpupuli.org/openvox8-release-el-9.noarch.rpm sudo dnf install -y openvox-server

パッケージ自体は CA を作成しません。初回起動時に CA とこのサーバー自身の証明書が作成されます。証明書はホストの certname (通常は完全修飾名) に対して発行されます。一般的なケースでは、起動する以外にすることはありません:

sudo systemctl enable --now puppetserver

すでに CA があるホストで puppetserver ca setup を実行しないでください。このコマンドはまだ存在しない CA を作成するだけで、既存の CA に対しては「Existing file at .../ca_crt.pem」で停止します。メッセージが示すとおりにそれらのファイルを削除すると、CA と、それがこれまでに発行したすべての証明書 (登録済みのすべての Node の証明書を含む) が破壊されます。

CA に別名の署名を許可する

コンソールの Node トランスポート証明書と、下で再発行する場合はこのサーバー自身の証明書は、複数の名前を持ちます。初期状態の CA はそのような要求への署名を拒否して保留のままにするため、一度だけ許可しておきます。/etc/puppetlabs/puppetserver/conf.d/ca.conf の certificate-authority ブロック内に次の設定を追加します:

certificate-authority: { allow-subject-alt-names: true ... } sudo systemctl restart puppetserver

証明書の名前を確認する

証明書は常に自身の certname に対して有効です。Node とコンソールの両方がこのサーバーに certname で到達するなら、変更するものはありません。そうでない場合は、証明書がすでにどの名前をカバーしているかを確認します:

sudo openssl x509 -in /etc/puppetlabs/puppet/ssl/certs/$(hostname -f).pem \ -noout -subject -ext subjectAltName

計画した名前が欠けている場合は、このサーバー自身の証明書だけを再発行し、CA は決して再発行しないでください。後から dns_alt_names を設定しても既存の証明書は変わらないため、サーバーを稼働させたままクリーンアップして再生成します:

sudo /opt/puppetlabs/bin/puppetserver ca clean --certname $(hostname -f) sudo /opt/puppetlabs/bin/puppetserver ca generate --certname $(hostname -f) \ --subject-alt-names puppet.example.com,openvoxserver sudo systemctl restart puppetserver

新しいホストでは、代わりに初回起動の前に名前を設定し、初回起動時にその名前で証明書を作成させることもできます: sudo /opt/puppetlabs/bin/puppet config set --section server dns_alt_names puppet.example.com,openvoxserver

稼働していることを確認する

curl -ksS https://puppet.example.com:8140/status/v1/simple

応答は running です。

openvoxdb とそのデータベースをインストールする

openvoxdb のホストを登録する

openvoxdb は自分で証明書を要求しません: セットアップ時に、ホストがすでに持っている証明書をコピーします。openvoxdb が専用のホストを持つ場合は、まずそのホストを CA に登録し、CA が自動的に署名しないなら CA 上でその要求に署名します:

sudo /opt/puppetlabs/bin/puppet ssl bootstrap --server puppet.example.com # on the CA host: sudo /opt/puppetlabs/bin/puppetserver ca sign --certname <openvoxdb host>

openvoxdb が openvoxserver とホストを共有している場合は、すでに証明書があるため、この手順は飛ばしてください。

データベースを作成する

openvoxdb には専用の Postgres データベースが必要ですが、パッケージはこれを作成しません:

Debian と Ubuntusudo apt-get install -y postgresql sudo systemctl enable --now postgresql RHEL、Rocky、AlmaLinuxsudo dnf install -y postgresql-server postgresql-contrib sudo postgresql-setup --initdb # Accept passwords over local connections, which are refused by the # default "ident" rules, and store passwords to match. sudo sed -i -E 's/^(host .*)(ident)$/\1scram-sha-256/' /var/lib/pgsql/data/pg_hba.conf echo "password_encryption = 'scram-sha-256'" | sudo tee -a /var/lib/pgsql/data/postgresql.conf sudo systemctl enable --now postgresql

RHEL とそのリビルド版では、下の pg_trgm は postgresql-contrib から提供されます。また、パスワードの変更はユーザーを作成する前に行う必要があります: それより前に保存されたパスワードは、新しいルールでは検証できないためです。

sudo -u postgres createuser --pwprompt puppetdb sudo -u postgres createdb --owner=puppetdb puppetdb # openvoxdb refuses to start without this extension, and creating it # needs superuser rights - so it is run as postgres, not as puppetdb. sudo -u postgres psql -d puppetdb -c 'CREATE EXTENSION IF NOT EXISTS pg_trgm;'

Postgres が接続を受け付けていることを確認します:

pg_isready

応答は accepting connections で終わります。

Debian と Ubuntu では、systemctl status postgresql は active (exited) と表示されますが、これは正常です: このユニットは実際のクラスターごとのユニットを起動するだけです。pg_lsclusters はクラスター自体を online と表示します。

openvoxdb をインストールして起動する

Debian と Ubuntusudo apt-get install -y openvoxdb RHEL、Rocky、AlmaLinuxsudo dnf install -y openvoxdb

データベースの場所を伝えます。このファイルがないと起動せず、No subname set in the "database" config. で終了します:

[database] subname = //localhost:5432/puppetdb username = puppetdb password = <the password you set above>

これを /etc/puppetlabs/puppetdb/conf.d/database.ini として保存し (データベースが別のホストにある場合は localhost の代わりにそのホスト名を使い)、アクセスを制限します:

sudo chown puppetdb:puppetdb /etc/puppetlabs/puppetdb/conf.d/database.ini sudo chmod 640 /etc/puppetlabs/puppetdb/conf.d/database.ini

次に、ホストの証明書を所定の場所にコピーして起動します:

sudo /opt/puppetlabs/bin/puppetdb ssl-setup sudo systemctl enable --now puppetdb

起動に失敗した場合、本当の原因は /var/log/puppetlabs/puppetdb/puppetdb.log にあります。systemd 自身のエラーはたいてい結果にすぎません。

カタログと Reports をそこへ送る

openvoxserver のホスト上で、カタログと Reports を openvoxdb に送る terminus をインストールします:

Debian と Ubuntusudo apt-get install -y openvoxdb-termini RHEL、Rocky、AlmaLinuxsudo dnf install -y openvoxdb-termini

稼働していることを確認する

openvoxdb の HTTPS ポートはクライアント証明書を必須とするため、ホスト自身の証明書を使って問い合わせます。証明書がないと、応答は certificate required になります:

H=$(hostname -f) sudo curl -sS --cert /etc/puppetlabs/puppet/ssl/certs/$H.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/$H.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://$H:8081/status/v1/simple

応答は running です。ログに「the read-database user is not configured properly」と報告されることがあります。これはこのガイドでは設定しない別の読み取り専用ユーザーに関するもので、openvoxdb はそれがなくても動作します。

コンソールのデータベースを作成する

コンソールは自身のデータを openvoxdb とは別のデータベースに保持します。スキーマは初回起動時にコンソール自身が作成するため、必要なのは空のデータベースとそれを所有するロールだけです。Postgres のホスト上で:

sudo -u postgres createuser --pwprompt console sudo -u postgres createdb --owner=console console

コンソールを別のホストで動かす場合は、Postgres がネットワーク上でも待ち受ける必要があります。既定では localhost でのみ待ち受けるため、ローカルでは pg_isready が成功しても、リモートからの接続は拒否されます。アドレス範囲を調整して、コンソールのホストまたはサブネットを許可します:

Debian と Ubuntusudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /etc/postgresql/*/main/pg_hba.conf sudo systemctl restart postgresql@*-main.service RHEL、Rocky、AlmaLinuxsudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /var/lib/pgsql/data/pg_hba.conf sudo systemctl restart postgresql

コンソールのホストから、コンソールのロールで接続できることを確認します (そのホストでは psql は postgresql-client パッケージに含まれています):

PGPASSWORD='<password>' psql -h <postgres host> -U console -d console -c 'select 1;'

シングルクォートは残してください。そうしないと、$ を含むパスワードは psql に渡る前にシェルによって展開されます。

コンソールの証明書を発行する

コンソールには CA から 2 つの証明書と、任意で 3 つ目の証明書が必要です。openvoxserver のホスト上で生成し、コンソールのホストの /etc/openvox-console/ にコピーします。まずコンソールのホスト上で、コンソールを実行するユーザーでそのディレクトリを作成します:

sudo useradd --system --home-dir /nonexistent --shell /usr/sbin/nologin openvox-console sudo install -d -m 0750 -o root -g openvox-console /etc/openvox-console

openvoxdb のクライアント証明書

コンソールはこれを使って openvoxdb に認証します:

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname console

puppetserver ca generate は、最初に Error: Signed certificate console could not be found on the CA と出力します。これは名前が空いているかを確認しているだけで、失敗ではありません。重要なのはその後に続く行で、最後が Successfully saved certificate で終わっていれば成功です。

コンソールが必要とする 3 つのファイルが書き出されます。次の名前でコピーします:

openvoxserver のホスト上で コンソールのホスト上で
/etc/puppetlabs/puppet/ssl/certs/console.pem /etc/openvox-console/console-cert.pem
/etc/puppetlabs/puppet/ssl/private_keys/console.pem /etc/openvox-console/console-key.pem
/etc/puppetlabs/puppet/ssl/certs/ca.pem /etc/openvox-console/ca.pem

Node トランスポートの証明書

Node はコンソールへの接続時にこの証明書を検証するため、証明書には Node が接続に使う名前そのもの、つまり CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR のホスト部分が含まれている必要があります。

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport

certs/node-transport.pem と private_keys/node-transport.pem も同じように node-transport-cert.pem と node-transport-key.pem としてコピーします。Node は同じ CA から発行された自身の証明書で認証し返すため、コンソールは Node 用に他に何も必要としません。

トークン署名鍵

コンソールは自身のログイントークンに ES256 鍵で署名します。この鍵は CA からではありません。任意のマシンで OpenSSL を使って生成します:

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

このファイルはバックアップしてください。失うと発行済みのトークンがすべて無効になり、全員がログアウトされます。漏れると誰でもトークンを発行できてしまいます。安全に置き換えるにはトークン署名鍵をローテーションするを参照してください。

コンソールのホスト上で、/etc/openvox-console/ に生成します。

証明書管理者の認証情報 (任意)

この認証情報があることで、Nodes ページに証明書のステータスが表示され、証明書の署名、失効、削除ができるようになります。これがない場合、コンソールが一覧表示するのはすでに接続または報告した Node だけです。証明書の署名を待っている Node はまったく表示されません。その存在を知っているのは CA だけだからです。

この認証情報は CA の完全な管理権限です。openvoxserver はすべての CA エンドポイントを 1 つの認可拡張で保護しているため、ステータスを読める証明書は、どの Node の証明書でも署名、失効、クリーンアップができます。読み取り専用の種類はありません。コンソールが動作する場所にだけ置き、発行する前にNode の証明書を管理するを読んでください。

発行の際には稼働中のサーバーも書き込む CA の状態に書き込みが行われるため、発行中は openvoxserver を停止してください:

sudo systemctl stop puppetserver sudo /opt/puppetlabs/bin/puppetserver ca generate --ca-client --certname console-ca-client sudo systemctl start puppetserver

certs/console-ca-client.pem と private_keys/console-ca-client.pem を ca-client-cert.pem と ca-client-key.pem としてコピーします。次に、コンソールのホストから CA がそれを受け入れることを確認します:

curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/ca-client-cert.pem \ --key /etc/openvox-console/ca-client-key.pem \ --cacert /etc/openvox-console/ca.pem \ https://puppet.example.com:8140/puppet-ca/v1/certificate_statuses/all

HTTP 200 は正常に機能していることを意味します。

コンソールをビルドする

コンソールは Web インターフェースを組み込んだ 1 つのバイナリです。パッケージは提供されていないため、ソースリポジトリからビルドします。go.mod に記載されたバージョンの Go と git が必要です。

git clone https://github.com/avitacco/openvox-console.git cd openvox-console

コンソールは、Node がインストールする Node エージェントも独自のパッケージリポジトリから提供しており、それらのエージェントはコンソールのバイナリに組み込まれます。先にそれらをビルドしてください。そうしないと、すべての Node のインストールが 404 で失敗します:

make agent-binaries make agent-packages make build

これで bin/console と bin/enc-bridge が残ります。コンソールをそのホストにインストールします:

sudo install -m 0755 bin/console /usr/local/bin/console

コンソールを設定する

コンソールの設定は環境変数だけで行い、証明書用に作成した /etc/openvox-console/ ディレクトリ内のファイルに記述します。

6 つの設定が必須で、これらがないとコンソールは不足しているものを示して起動を拒否します。/etc/openvox-console/console.env に記述します:

CONSOLE_POSTGRES_DSN=postgres://console:<password>@<postgres host>:5432/console?sslmode=require CONSOLE_OPENVOXDB_URL=https://<openvoxdb host>:8081 CONSOLE_OPENVOXDB_CERT_FILE=/etc/openvox-console/console-cert.pem CONSOLE_OPENVOXDB_KEY_FILE=/etc/openvox-console/console-key.pem CONSOLE_OPENVOXDB_CA_FILE=/etc/openvox-console/ca.pem CONSOLE_RBAC_SIGNING_KEY_FILE=/etc/openvox-console/rbac-signing-key.pem

sslmode=require は Postgres が TLS を提供していることを前提としており、接続がホストの外に出るならそうあるべきです。コンソールと Postgres が同じホストにあり、Postgres に証明書がない場合は sslmode=disable を使ってください。

残りは任意で、各任意機能は起動を妨げるのではなく自動的に無効になります。実際のデプロイでは、次を追加してください:

# Where the console listens, and how the outside world reaches it. It # listens on loopback only: the TLS proxy in front of it is the way in. # On a host shared with openvoxdb, which holds 8080, use 127.0.0.1:8088. CONSOLE_HTTP_ADDR=127.0.0.1:8080 CONSOLE_BASE_URL=https://console.example.com # The first admin user, created only while there are no users. The # password needs at least 12 characters. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin CONSOLE_BOOTSTRAP_ADMIN_PASSWORD=<a strong password> # The node transport. ADDR is what the console binds; PUBLIC_ADDR is what # a node dials, and its host must be in the node transport certificate. CONSOLE_NODE_TRANSPORT_ADDR=:8142 CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 CONSOLE_NODE_TRANSPORT_CERT_FILE=/etc/openvox-console/node-transport-cert.pem CONSOLE_NODE_TRANSPORT_KEY_FILE=/etc/openvox-console/node-transport-key.pem CONSOLE_NODE_TRANSPORT_CA_FILE=/etc/openvox-console/ca.pem # The Puppet server a node should enroll against, written into the node # install script. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # Certificate management from the Nodes page (the optional credential). CONSOLE_CA_CLIENT_URL=https://puppet.example.com:8140 CONSOLE_CA_CLIENT_CERT_FILE=/etc/openvox-console/ca-client-cert.pem CONSOLE_CA_CLIENT_KEY_FILE=/etc/openvox-console/ca-client-key.pem CONSOLE_CA_CLIENT_CA_FILE=/etc/openvox-console/ca.pem # Puppet tasks: where the console asks which tasks your deployed code # contains. Uses the openvoxdb client certificate above unless you name # another with CONSOLE_PUPPET_SERVER_CERT_FILE, _KEY_FILE and _CA_FILE. CONSOLE_PUPPET_SERVER_URL=https://puppet.example.com:8140

Task には独自の証明書は必要ありません: openvoxserver はその CA が発行したどの証明書にも Task の読み取りを許可しているため、openvoxdb クライアント証明書で十分です。Task の読み取りに必要な範囲をはるかに超える権限を持つ証明書管理者の認証情報を使わないでください。実行方法についてはJobs を実行するを参照してください。

コンソールにクラス一覧を読み込ませる

Node グループのページでは、deploy したコードが定義するクラスがパラメーターとともに提示されるため、入力するのではなく選択できます。コンソールは Tasks と同じ接続を通じて openvoxserver からそれらを読み込みますが、openvoxserver はルールで許可されるまでどの証明書にもクラスの読み取りを許しません。

openvoxserver のホスト上で、/etc/puppetlabs/puppetserver/conf.d/auth.conf の rules リストの、最後の puppetlabs deny all ルールより上に次のルールを追加します。console は、上で発行した openvoxdb クライアント証明書の名前です:

{ match-request: { path: "/puppet/v3/environment_classes" type: path method: get } allow: "console" sort-order: 500 name: "openvox console class discovery" },

次に、openvoxserver を再読み込みします:

sudo systemctl reload puppetserver

コンソールのホストから確認します。HTTP 200 は一覧を読み取れることを意味します:

sudo curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/console-cert.pem \ --key /etc/openvox-console/console-key.pem \ --cacert /etc/openvox-console/ca.pem \ 'https://puppet.example.com:8140/puppet/v3/environment_classes?environment=production'

HTTP 403 は、ルールがないか、別の証明書を指定していることを意味します。他にこの手順に依存するものはありません: これがない場合、グループページには一覧を利用できないと表示され、クラスは名前で入力します。Node を分類するを参照してください。

シークレットをファイルに保管する

どの設定も、代わりにファイルから読み込めます: 設定名の後ろに _FILE を付けた設定でファイルを指定します。これでパスワードをプロセスの環境変数に置かずに済みます:

CONSOLE_POSTGRES_DSN_FILE=/etc/openvox-console/postgres-dsn CONSOLE_BOOTSTRAP_ADMIN_PASSWORD_FILE=/etc/openvox-console/bootstrap-admin-password

ファイル末尾の改行は無視されます。指定されたファイルが読めない場合、値が黙って空のまま起動するのではなく、コンソールは起動しません。

最後に、すべてのファイルをコンソールのユーザーだけが読めるようにします:

sudo sh -c 'chown root:openvox-console /etc/openvox-console/* && chmod 0640 /etc/openvox-console/*'

sh -c が重要です: 自分のシェルではそのディレクトリを一覧表示できないため、単純な sudo chown ... /etc/openvox-console/* は「No such file or directory」で失敗します。

systemd で動かす

/etc/systemd/system/openvox-console.service を作成します:

[Unit] Description=OpenVox Console After=network-online.target Wants=network-online.target [Service] EnvironmentFile=/etc/openvox-console/console.env ExecStart=/usr/local/bin/console Restart=on-failure User=openvox-console Group=openvox-console [Install] WantedBy=multi-user.target

次に起動します:

sudo systemctl daemon-reload sudo systemctl enable --now openvox-console journalctl -u openvox-console -f

コンソールの前段に TLS を置く

コンソールは Web インターフェースと API を平文の HTTP で提供します。https:// のベース URL には、TLS を終端してリクエストをコンソールに渡すリバースプロキシを通じて到達します。どのリバースプロキシでも機能します。ここではコンソールのホスト上で Caddy を使います:

Debian と Ubuntusudo apt-get install -y caddy RHEL、Rocky、AlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

これで /etc/caddy/Caddyfile の全体は次のとおりです:

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

openvoxdb とホストを共有しているなどの理由でコンソールが別のポートで待ち受けている場合は、代わりにそのポートを reverse_proxy に指定します。

インターネットで名前解決できる名前なら、Caddy が自ら証明書を取得・更新します。内部名の場合は、ブロック内に tls <cert file> <key file> の行を置き、独自の CA の証明書を与えます。試用には、tls internal で Caddy 自身のローカル CA から証明書を発行させることもできますが、ブラウザーは警告を表示します。

プロキシを経由するのは Web インターフェースだけです。Node トランスポート (ポート 8142) は独自の TLS を持ち、各 Node の証明書を自ら検証するため、Node は直接到達する必要があります。決してプロキシの背後に置かないでください。

初めてログインする

初回起動時、コンソールはデータベーススキーマを作成し、続いてユーザーテーブルがまだ空のうちにブートストラップ管理者を作成します。起動が完了すると、ログに次の 3 行が表示されます:

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

正常であると報告されることを、まずコンソールのホスト上で直接、次にベース URL の TLS プロキシ経由で確認します:

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

どちらの応答でも各依存先が ok と表示されます。2 つ目だけが失敗する場合、コンソールは正常で、問題はプロキシにあります。コンソールのポートを 8080 から変更した場合は、1 つ目でそのポートを使ってください。次にコンソールのベース URL を開き、ブートストラップ管理者としてログインし、すぐにパスワードを変更してください。

ブートストラップ管理者のパスワードは 12 文字以上で、ユーザー名と同じであってはなりません。そうでない場合、管理者は作成されず、誰もログインできません。ログにはその旨が記録されます:

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

より長いパスワードを設定し、コンソールを再び起動してください。パスワードとロックアウトを参照してください。

ログインしてパスワードを変更したら、コンソールの設定からブートストラップ管理者の設定を削除してください。これらはユーザーテーブルが空の間しか読み込まれませんが、パスワードを放置しておく理由はありません。

分類を接続する

openvoxserver は、Puppet 標準の exec node terminus を通じて、各 Node にどのクラスを割り当てるかをコンソールに問い合わせます。小さなプログラム enc-bridge が openvoxserver に代わってこの要求を行い、そのためにトークンを必要とします。

enc-bridge にトークンを発行する

サービストークンは作成時に選んだ固定の権限セットを持ち、ロールは関係しません。分類の読み取りだけが許可されたトークンを作成します:

  1. コンソールで管理を開き、サービストークンを開きます。
  2. 新しいサービストークンで、名前を enc-bridge とし、enc:read 権限だけを与えます。
  3. サービストークンを作成を選びます。

トークンは一度しか表示されません。今すぐコピーしてください。

API でも同じことができます。管理者ログインのアクセストークンを使います: curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

openvoxserver のホストに enc-bridge をインストールする

ビルドした bin/enc-bridge を openvoxserver のホストにコピーし、インストールします:

sudo install -m 0755 enc-bridge /usr/local/bin/enc-bridge

openvoxserver のユーザーだけが読める場所にトークンを保存します:

printf '%s' '<the enc:read service token>' | sudo tee /etc/puppetlabs/enc-bridge-token >/dev/null sudo chown root:puppet /etc/puppetlabs/enc-bridge-token sudo chmod 0640 /etc/puppetlabs/enc-bridge-token

enc-bridge はコンソールの場所とトークンを環境変数から読み込み、これらは openvoxserver から継承されます。sudo systemctl edit puppetserver で openvoxserver に両方を与えます:

[Service] Environment=ENC_BRIDGE_URL=https://console.example.com Environment=ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token

enc-bridge は、openvoxserver のホストのシステム証明書ストアに照らしてコンソールの証明書を検証します。プロキシの証明書が独自の CA から発行されている場合は、その CA をストアに追加してください。そうしないと、分類は certificate signed by unknown authority で失敗します:

Debian と Ubuntusudo cp <your CA>.crt /usr/local/share/ca-certificates/ sudo update-ca-certificates RHEL、Rocky、AlmaLinuxsudo cp <your CA>.crt /etc/pki/ca-trust/source/anchors/ sudo update-ca-trust

次に、/etc/puppetlabs/puppet/puppet.conf の [server] セクションで Puppet をそれに向け、openvoxserver を再起動します:

[server] node_terminus = exec external_nodes = /usr/local/bin/enc-bridge sudo systemctl restart puppetserver

Node に設定データを読み込ませる

任意です。これにより、Node は Node グループに設定された設定データを、control リポジトリの Hiera データより先に lookup() で読み込めるようになります。この関数は enc-bridge --data を実行するため、分類と同じコンソールのアドレスとトークンを使い、追加の設定は必要ありません。このバージョンからビルドされた enc-bridge が必要です。

この関数は、Puppet 自身の関数ディレクトリにインストールする必要があります。openvoxserver がグローバルな Hiera 関数を読み込むのはそこだけです。ビルドしたチェックアウトから:

sudo install -m 0644 openvoxserver-init/console_config_data.rb \ /opt/puppetlabs/puppet/lib/ruby/vendor_ruby/puppet/functions/console_config_data.rb

次に、コンソールのデータが優先されるよう、グローバルな Hiera 設定 /etc/puppetlabs/puppet/hiera.yaml の階層の先頭に追加します。パッケージはそこにプレースホルダーのファイルをインストールします。変更していなければ、次の内容で置き換えます:

--- version: 5 hierarchy: - name: "Console configuration data" data_hash: console_config_data

すでにグローバルな hiera.yaml がある場合は、そこにエントリを追加し、独自のエントリはその後ろに置いてください。

sudo systemctl restart puppetserver

openvox-agent パッケージをアップグレードした後は、ファイルがまだ存在することを確認し、なければ再度インストールしてください。Node の実行が「Unable to find 'data_hash' function named 'console_config_data'」で失敗する場合、関数がそのディレクトリにありません。コンテナイメージは、起動のたびにこれらすべてを自動で行います。

分類を確認する

openvoxserver と同じ方法で enc-bridge を実行します: openvoxserver のユーザーとして、同じ設定で。これでプログラム、トークン、ファイルのパーミッション、コンソールの応答を 1 つのコマンドで確認できます:

sudo -u puppet env ENC_BRIDGE_URL=https://console.example.com \ ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token \ /usr/local/bin/enc-bridge <a certname>

{} は、分類が機能していて、その Node がまだどのグループにも一致していないことを意味します。コンソールのグループページでその certname を固定する Node グループを作成し、同じコマンドをもう一度実行すると、クラスが返ってきます:

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

ここで見逃してはならないのがエラーです。permission denied は openvoxserver の実行ユーザーがトークンを読めないことを意味し、401 はトークンが誤っているか enc:read を持っていないことを意味します。

Node の次の Puppet run が Could not find class <name> で失敗する場合、分類は機能しています: コンソールが openvoxserver に、Puppet コードでまだ定義されていないクラスを含めるよう指示したということです。

後でアップグレードする

新しいコンソールに移行するには、ソースを pull し、同じ順序で再ビルドし、新しいバイナリをインストールして再起動します:

git pull make agent-binaries make agent-packages make build sudo install -m 0755 bin/console /usr/local/bin/console sudo systemctl restart openvox-console
