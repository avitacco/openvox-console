使う

Plans を実行する

Plan (順番に実行される Puppet run と Task の一覧) を組み立てて保存し、選んだ Node で実行して、各ステップを見守ります。

Plan は、同じ Node に対して順番に実行されるステップの一覧です。各ステップは Puppet run または Task で、手動で開始する場合とまったく同じです。Jobs を実行するを参照してください。Plan はコンソールに保存されるため、毎回異なる Node に対して再実行できます。

Plans の閲覧には orchestrator:read が、作成、変更、削除、実行には orchestrator:run が必要です。

ここでいう Plan は、コンソールで組み立てたステップの一覧です。Puppet 言語で書かれた Plan ではなく、コンソールはそれを実行しません。独自のモジュール内に YAML で書かれた Plan は同じページから実行できます: コード内の Plan を実行するを参照してください。

Plan を組み立てる

Jobs、Plans、新しい Plan の順に開きます。

  1. 名前を付け、必要なら説明も付けます。1 つの名前は 1 つの Plan にしか使えません。
  2. Puppet 実行ステップを追加と Task ステップを追加でステップを追加します。Plan のステップ数は 1～20 です。
    • Puppet run のステップには実行オプションを指定できます: no-op、デバッグ、Environment。
    • Task ステップには、Task を実行すると同様に、Environment、Task、そのパラメーター、タイムアウトを指定します。
  3. 上へ移動と下へ移動でステップを並べ替えます。ステップに入力した内容は一緒に移動します。
  4. Plan を保存。

コンソールは保存時に、今すぐ実行や Task を開始した場合と同じようにすべてのステップを検査します。拒否されたステップには理由の印が付き、入力した内容は何も失われません。

Plan には、どの Node で実行するかが記されていません。それは実行のたびに選びます。

機密の Task の値

sensitive とマークされた Task パラメーター (パスワードやトークン) が Plan に保存されることはありません。そのフィールドはエディターから除外され、値は Plan を実行するたびに入力を求められます。Plan は共有されるもので、Jobs を実行できる全員が開けるためです。

Plan を変更できる人

orchestrator:run を持つ全員が、ロールがどの Node グループに付与されているかに関係なく、どの Plan でも変更・削除できます。Plan は Node を指定しないため、Node グループで制限すべきものが含まれていないのです。Plan をどの Node で実行できるかは、他の Job と同様に制限されます。ロールが一部の Task に限定されている人は、実行できる Task だけを含む Plan しか保存できません。

Plan を実行する

Plans ページで Plan の横にある実行を選ぶか、Plan を開いて実行を選びます。

  1. Node を選びます: Node を選ぶと同様に、一覧、クエリ、または Node グループ。Nodes をプレビューで、何に対して実行されるかを確認できます。
  2. ステップが求める機密の値を入力します。それぞれにステップ名のラベルが付いています。
  3. Plan を実行。Plan の Job ページが開きます。

Node は Plan の開始時に一度だけ割り出され、すべてのステップがそれらの Node で実行されます。ロールが特定の Node グループに対して付与されている場合、他の Job と同様に、クエリやグループは自分の Node に絞り込まれ、グループ外の Node を指定した一覧は全体が拒否されます。

何かが始まる前に、すべてのステップが検査されます。拒否されるステップがある場合 (たとえば、その後コードから削除された Task)、Plan はそのステップを示して拒否され、何も実行されません。

実行できなくなったステップを含む Plan では、そのステップに警告が表示されます。実行する前に Plan を編集してください。

ロールで許可されていない Task

ロールが一部の Task に限定されている場合 (ロールを一部の Task に限定するを参照)、他の人が保存した Plan に実行できない Task が含まれていることがあります。その場合もすべてのステップが表示され、実行できないものにはあなたのロールでは Task ... が許可されていませんと表示されます。その Plan では実行が無効になり、API はステップと Task を示して 403 で拒否します。それらのステップを削除しない限り、Plan を編集しても解決しません。それらを含んだまま保存しようとしても同様に拒否されます。

対象がクエリや Node グループの場合、Plan は、あなたがすべての Task ステップを実行できる Node で実行されるため、すべてのステップは引き続き 1 組の Node を共有します。Puppet run のステップは制限されません。

Plan を見守る

Plan の Job ページには、ステップが順番に一覧表示されます。それぞれに、何を行うか、状態、開始・終了日時、各 Node の結果が表示されます。Plan の実行中、ページは自動的に更新されます。

状態 意味
待機中 前のステップがまだ完了していない
実行中 Node に送信され、まだすべてが応答していない
成功 すべての Node で完了した
失敗 少なくとも 1 つの Node で失敗した
未実行 前のステップが失敗したため、このステップはどの Node にも送られなかった

ステップの番号はそのステップ自身の Job ページにリンクしており、そこから Plan に戻れます。Jobs の一覧では、Plan はステップごとではなく 1 行で表示されます。

ステップが失敗した場合

ステップは、未接続の Node を含め、いずれかの Node で失敗すると失敗となります。Plan はそこで停止します: それ以降のステップは未実行とマークされ、それらについてはどの Node にも何も送られません。Plan の Job は失敗となります。

失敗したステップを越えて続行したり、失敗した Node をスキップしたり、ステップを再試行したりするオプションはありません。失敗したものを修正して Plan を再度実行してください。最初のステップを繰り返すべきでない Plan は、2 つに分割できます。

Plan をスケジュールする

Plan の実行ダイアログで代わりにスケジュールを選ぶか、スケジュールを作成して Plan を実行を選びます。Jobs をスケジュールするを参照してください。

スケジュールは、保存時点の Plan のステップの独自のコピーを保持します。その後 Plan が変更または削除されても、スケジュールは保存時のステップを実行し続けます。変更を反映するには、スケジュールを編集し、Plan を選び直して保存します。

これは意図的なものです。スケジュールは所有者のアクセス権で実行され、Jobs を実行できる全員が Plan を変更できます。スケジュールが Plan に追従すると、少数の Node に限定された人が、管理者のスケジュールがすべての Node で実行する内容を変更できてしまいます。

API から

保存された Plans:

リクエスト 内容
GET /api/v1/orchestrator/saved-plans Plans を一覧表示する (ステップは含まない)
GET /api/v1/orchestrator/saved-plans/<id> ステップを含む 1 つの Plan を返す
POST /api/v1/orchestrator/saved-plans Plan を作成する
PUT /api/v1/orchestrator/saved-plans/<id> Plan を置き換える
DELETE /api/v1/orchestrator/saved-plans/<id> Plan を削除する
curl -X POST https://console.example.com/api/v1/orchestrator/saved-plans \ -H "Authorization: Bearer <access token>" \ -H 'Content-Type: application/json' \ -d '{"name":"Restart web tier", "description":"Check first, then restart", "steps":[ {"kind":"run","options":{"noop":true}}, {"kind":"task","taskName":"service","environment":"production", "params":{"name":"nginx","action":"restart"},"timeoutSeconds":300} ]}'

読み込まれた Plan では、各 Task ステップについて、実行時に指定すべき機密パラメーター (needs) が列挙され、Task が見つからなくなった場合は problem が示されます。

ID で Plan を実行するリクエストはありません。実行するには、そのステップ (各ステップの params に機密の値を追加したもの) と Node を送ります:

curl -X POST https://console.example.com/api/v1/orchestrator/plans \ -H "Authorization: Bearer <access token>" \ -H 'Content-Type: application/json' \ -d '{"name":"Restart web tier", "group":12, "steps":[ {"kind":"run","options":{"noop":true}}, {"kind":"task","taskName":"service", "params":{"name":"nginx","action":"restart"}} ]}'

Node は targets、query、group で指定します。応答は Plan の Job です。GET /api/v1/orchestrator/jobs/<id> で読み取ると、その steps が返され、それぞれの state は waiting、running、succeeded、failed、not_run のいずれかです。

拒否されたリクエストは 400 (自分の Node グループ外の Node の場合は 403) で error とともに応答します。1 つのステップが原因の場合は 1 から数えた step も含まれ、Task のパラメーターについては fields も含まれます。

GET /api/v1/orchestrator/jobs は、Plan のステップを独立した Jobs として一覧表示しなくなりました。それらを一覧表示するには ?parent=<plan job id> を追加します。

分割されたデプロイの場合

コンソールで開始された Plan は、リクエストを受けたインスタンス (分割されたデプロイでは web インスタンス。実行モードを参照) によって、ステップごとに送信・追跡されます。Plan が終わる前にそのインスタンスが停止すると、実行中のステップは失敗としてマークされ、残りは未実行として閉じられます。Plan を再度開始してください。スケジュールされた Plan は、同様に orchestrator インスタンスによって開始・追跡されます。
