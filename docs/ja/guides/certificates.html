Nodes

Node の証明書を管理する

コンソールから Node の証明書に署名、失効、クリーンアップを行う方法と、それぞれが接続中の Node に何をもたらすか。

すべての Node の ID は openvoxserver の CA が発行した証明書です。証明書管理者の認証情報が設定されていれば、コンソールの Nodes ページに各証明書の状態が表示され、操作できるようになります。

証明書管理を有効にする

証明書管理には、インストール時に発行する証明書管理者の認証情報が必要です。どちらのインストールガイドでもその発行方法を説明しています。コンソールは 4 つの設定がすべて揃っているときにこれを使用します:

設定 説明
CONSOLE_CA_CLIENT_URL openvoxserver のアドレス (コンソールから到達するアドレス)
CONSOLE_CA_CLIENT_CERT_FILE 認証情報の証明書
CONSOLE_CA_CLIENT_KEY_FILE その秘密鍵
CONSOLE_CA_CLIENT_CA_FILE openvoxserver を検証するための CA バンドル

いずれか 1 つでも未設定の場合、すべての Node の証明書の状態は unknown と表示され、コンソールの他の部分は通常どおり機能します。

この認証情報は CA の完全な管理権限です: これを使えるものは、どの Node の証明書でも署名、失効、クリーンアップができます。openvoxserver にはより限定的な種類はありません。その鍵はコンソールだけが読めるようにしてください。

証明書を操作できるユーザーを決める

関係する権限は 2 つで、これらは意図的に大きく分けられています:

権限 許可する操作
nodes:read 各 Node とその証明書の状態の閲覧
nodes:certs:manage 証明書の署名、失効、クリーンアップ

nodes:certs:manage を付与することは、CA へのシェルアクセスを与えることに等しいものです: 署名は許可して失効は許可しない、ある Node は許可して別の Node は許可しない、といったことはできません。Node のステータスを見る必要がある全員ではなく、信頼できる特定のオペレーターに付与してください。

チームに自分たちの Node への署名を任せる

特定の Node グループに対して付与されたロールは、それらのグループ内の Node の証明書しか操作できません。ユーザー、ロール、トークンを参照してください。署名を待っている新しい Node は一度も Puppet を実行していないため、Facts がなく、どのグループのルールにも含まれません。チームがそれに署名するには、先にその名前をチームのグループに固定します:

  1. グループを開き、チームのグループを開きます。そのグループは All Nodes の直下になければなりません。より深い階層のグループへの固定は、その上位の各グループにも Node が固定されている場合にだけ有効です。
  2. 固定された Nodes に、Node が登録するときの名前を正確に追加して保存します。これには classifier:write が必要です。
  3. これで、チームの nodes:certs:manage の保持者には Nodes ページにその要求が表示され、署名できるようになります。

Node が Puppet を実行した後は、その Facts によって通常どおりグループに振り分けられるため、固定は削除できます。All Nodes に対してロールが付与されている人は、これまでどおりどの要求にも署名できます。

署名、失効、クリーンアップ

Nodes ページでは、各 Node の証明書の状態は requested、signed、revoked、unknown のいずれかで、提供される操作はそれによって決まります:

操作 利用できる条件 何ができるか
署名 requested Node の証明書を発行し、Node が認証できるようにします
失効させる signed その証明書がどこでも二度と受け入れられないようにします
クリーンアップ 既知のすべての状態 必要に応じて証明書を失効させ、その後 certname に関する CA の記録を完全に削除します

同じ名前で Node を再登録する前に使うのがクリーンアップです: 記録が消えれば、その certname で新しい要求を送信できます。

CA が拒否する操作 (署名待ちでない証明書への署名など) は、理由とともに失敗し、何も変更しません。完了した操作はそれぞれ node.certificate.signed、node.certificate.revoked、node.certificate.cleaned として監査ログに書き込まれます。

失効が接続中の Node に何をもたらすか

コンソールから失効またはクリーンアップされた Node は、ただちに切断されます。すべてのコンソールインスタンスに通知され、その Node の接続を保持しているインスタンスが接続を閉じます。各インスタンスはまず CA の最新の失効リストを取得するため、その Node が単純に再接続することはできません。

コンソールの外で、CA ホスト上の puppetserver ca revoke によって失効させた証明書も検出されます: 各インスタンスは 1 分ごとに失効リストを読み直し、新たに失効した接続が生きていれば切断します。

失効リストは次の 2 か所のいずれかから取得されます:

  • CONSOLE_NODE_TRANSPORT_CRL_FILE で指定されたファイル。通常は、コンソールホスト自身の Puppet エージェントの crl.pem で、エージェントが最新の状態に保ちます。これが設定されているのに読めない場合、コンソールは起動を拒否します。
  • それ以外の場合は、証明書管理者の認証情報を通じて CA 自体から。

どちらもない場合、コンソールは起動時に警告をログに記録します: その場合、失効した Node 証明書でも接続できてしまいます。

インフラストラクチャの証明書

Nodes ページには CA が知っているすべての certname が一覧表示され、そこにはコンソール自身の証明書と、コンソールが通信するサーバーの証明書も含まれます: 既定のインストールでは console、node-transport、console-ca-client、openvoxdb、openvoxserver です。これらは自動的に認識され、既定では非表示になります。インフラ証明書を表示で印付きで表示され、それらを失効またはクリーンアップしようとすると、何が壊れるかを示して確認を求められます。

証明書管理者の認証情報を廃止する

これは CA の完全な管理権限であるため、不要になったらすぐに (たとえばコンソールインスタンスを廃止するときに) この認証情報をクリーンアップしてください。CA ホスト上で:

sudo /opt/puppetlabs/bin/puppetserver ca clean --certname console-ca-client

次に、この認証情報が設定されたままのすべてのコンソールから、4 つの CONSOLE_CA_CLIENT_* 設定を削除します。クリーンアップ済みの認証情報を保持したままのコンソールは、すべての証明書を unknown と報告するだけで、他に機能しなくなるものはありません。
