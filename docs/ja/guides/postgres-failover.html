スタンバイデータベースにフェイルオーバーする

ストリーミングレプリケーションのスタンバイを昇格させて、コンソールのデータベースの喪失から復旧します。

コンソールは永続的なものをすべて Postgres データベースに保持しており、コンソール自体に復旧が必要なものはありません。そのため、プライマリデータベースの喪失からは、スタンバイを昇格させてコンソールをそちらに向けることで復旧します。この手順書は、Postgres 自身のストリーミングレプリケーションで最新の状態に保たれたスタンバイがあることを前提としています。

必要になる前にスタンバイを確認する

スタンバイ上で:

psql -U console -d console -c "SELECT pg_is_in_recovery();"

応答は t です: まだレプリカです。書き込みは cannot execute INSERT in a read-only transaction で拒否されますが、これは正常なレプリカの挙動でもあります。

スタンバイを昇格する

psql -U console -d console -c "SELECT pg_promote();"

数秒以内に pg_is_in_recovery() は f を返します: スタンバイは独立した書き込み可能なデータベースになりました。

昇格したデータベースは、古いプライマリが復帰してもそこからのレプリケーションを再開しません。この時点以降、古いプライマリは廃止されたものとして扱ってください。再びスタンバイを持つには、pg_basebackup -R を使って古いプライマリを昇格したデータベースの新しいスタンバイとして再構築します。

コンソールをそちらに向ける

CONSOLE_POSTGRES_DSN を昇格したデータベースのアドレスに変更し、コンソールを再起動します。コンソールは起動時に一度だけ接続を開くため、再起動が必要です。インスタンスが複数ある場合は、すべてを再起動してください。

データベースの前に置いたコネクションプーラーやプロキシは、フェイルオーバー後も変わらない 1 つのアドレスをコンソールに提供します。そうすれば向け直すのはプロキシだけで、コンソール自身の設定は一切変わりません。

コンソールが復旧したことを確認する

/health が再び Postgres を ok と報告します。次にログインしてください: ログインはデータベースに書き込むため、読み取りだけでなく書き込みも機能することの証明になります。
