スケール

実行モード

コンソールの各実行モードが何を提供・実行し、それぞれにどの設定が必要か。

1 つのイメージ、1 つのバイナリ。CONSOLE_RUN_MODE はインスタンスがコンソールのどの部分を動かすかを選択するため、負荷が大きく異なる部分を別々にスケールし、配置できます。未設定の場合は all で、すべてを 1 つのインスタンスで動かします。単一インスタンスのデプロイでは常にこれが使われます。

各モードが実行するもの

モード 提供するもの 待ち受け バックグラウンドで実行
all (既定値) すべて HTTP、Node トランスポート すべてのバックグラウンドタスク
web コンソール、その API、コード deploy の webhook、分類 HTTP それを通じて開始された Jobs の追跡
enc 分類のみ HTTP なし
orchestrator ヘルスとメトリクス以外なし HTTP、Node トランスポート Job の送信、スケジュールされた Jobs、新しい Node の初回実行、Node エージェントのアップグレード
worker ヘルスとメトリクス以外なし HTTP 脆弱性の同期と、放棄された Jobs のクリーンアップ

すべてのモードが /health と /metrics を提供するため、モードを知らなくてもどのインスタンスでも確認でき、/health は実行中のモードを報告します。

この表の 2 つの選択は意図的なものです:

  • web も分類に応答します。enc は、分類をコンパイラーの隣で単独で動かすことができるように存在するのであって、他の場所で分類をなくすためではありません。知らないうちに Node の分類が止まってしまうような分割は、web がその負荷の一部を担うよりはるかに悪い結果になります。
  • orchestrator は API を提供しません。Node の接続を保持し、その接続を通じて Jobs を送信します。Job の開始は web の役割で、web はクラスターを通じてそれらの接続に到達します。
  • Job はそれを開始したインスタンスが追跡します。コンソールで開始された実行、Task、Plan は、リクエストを受けた web インスタンスが送信・追跡します。そのため、web インスタンスがどの Node にも到達できるよう、orchestrator インスタンスとクラスター化されている必要があります。Job が終わる前にその web インスタンスが停止した場合、Job は worker インスタンスによって失敗としてマークされます。

各モードに必要なもの

各モードは使用するものだけを必要とし、それがない場合は不足している設定名を示して起動を拒否します:

モード 必要な設定
すべてのモード CONSOLE_POSTGRES_DSN と 4 つの CONSOLE_OPENVOXDB_* 設定
all, web CONSOLE_RBAC_SIGNING_KEY_FILE: ログイントークンを発行するのはこれらのモードだけです
enc, orchestrator, worker CONSOLE_RBAC_VERIFICATION_KEYS_DIR: これらはトークンを検証しますが、発行はしません
orchestrator CONSOLE_NODE_TRANSPORT_ADDR: Node リスナーがなければ、正常に見えるインスタンス上ですべての Job が「not connected」で失敗します

スケジューラーに、スケジュールされた Jobs が使うものを与える

スケジュールされた Jobs は、web ではなく all と orchestrator のインスタンスによって開始されます。orchestrator インスタンスはこれらがなくても起動しますが、それを必要とするスケジュールは、インスタンスがそれを持つまで理由を示してスキップされます:

  • CONSOLE_PUPPET_SERVER_URL。スケジュールされた Task を開始するために必要です: スケジュールの開始時に、deploy されたコードから Task が検索されます。
  • CONSOLE_SECRETS_KEY_FILE。web と同じ鍵で、機密パラメーターを持つスケジュールされた Task を開始するために必要です。

複数のインスタンスがスケジューラーを実行している場合、各予定時刻はそのうちのちょうど 1 つによって開始されます。予定時刻にどれも動いていない場合は、いずれかが動き出した時点で開始されます — ただし 15 分以上遅れている場合は、その時刻は未実行として記録されます。

トークンを発行しないモードに検証鍵を渡す

トークンの検証だけを行うインスタンスは、検証に使う鍵をディレクトリから読み込みます。1 つの鍵につき 1 ファイルで、ファイル名は鍵の ID です。一度も鍵をローテーションしていないデプロイでは ID default を使うため、ディレクトリには 1 つのファイル default.pem が置かれ、これは署名鍵ファイルそのものです:

sudo install -d -m 0750 -o root -g openvox-console /etc/openvox-console/rbac-verification-keys sudo install -m 0640 -o root -g openvox-console \ rbac-signing-key.pem /etc/openvox-console/rbac-verification-keys/default.pem CONSOLE_RUN_MODE=enc CONSOLE_RBAC_VERIFICATION_KEYS_DIR=/etc/openvox-console/rbac-verification-keys

検証用ディレクトリは現在、署名鍵と同じ形式の鍵、つまり秘密鍵しか受け付けません (コンソールが使うのはその公開部分だけです)。そのため、ディレクトリを与えられたインスタンスは、トークンに署名できる鍵も保持することになります。コンパイラーの隣の enc インスタンスも含め、すべてのホストで署名鍵とまったく同じように保護してください。

署名鍵をローテーションするときは、すべてのインスタンスの検証用ディレクトリにも新しい鍵が必要です。手順の順序についてはトークン署名鍵をローテーションするを参照してください。

インスタンスのモードを変更する

CONSOLE_RUN_MODE を設定し、インスタンスを再起動します。データは移動しません: どのモードも同じデータベースを読み書きします。all に戻せば変更は元に戻ります。

単独のインスタンスでもモードを変更できますが、all 以外のモードが意味を持つのは、全体ですべてのモードを動かしているクラスター化されたインスタンス群の中だけです。インスタンスを増やすを参照してください。

各モードが実行するもの 各モードに必要なもの スケジューラーに、スケジュールされた Jobs が使うものを与える トークンを発行しないモードに検証鍵を渡す インスタンスのモードを変更する

OpenVox Console は、push のたびに amd64 と arm64 向けにビルドされるコンテナイメージと、単一のバイナリとして提供されます。インストールガイドでは、コンテナまたはパッケージを使って、空のホストから openvoxserver、openvoxdb、Postgres、コンソールからなる稼働するデプロイまでを案内します。
