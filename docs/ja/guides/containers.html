インストール

コンテナでインストールする

openvoxserver、openvoxdb、2 つのデータベース、コンソールを Docker Compose で動かし、空のホストから Node を迎える準備ができたコンソールまでを構築します。

このガイドでは、プロジェクトの本番用 compose ファイルと公開イメージからスタック全体を動かします。ホスト上では何もビルドしません。始める前に、デプロイを計画するで名前を決めておいてください。

Docker Engine と Compose プラグインを備えた Linux ホストと、sudo なしで docker を実行できるユーザーが必要です。

compose ファイルを取得する

プロジェクトリポジトリの docker-compose.yml が本番用のスタックです: コンソール、2 つのデータベース、openvoxserver、openvoxdb。このファイル 1 つだけを、ホスト上の自分のユーザーが所有する専用ディレクトリにコピーします:

sudo mkdir -p /opt/openvox-console sudo chown "$USER": /opt/openvox-console mkdir -p /opt/openvox-console/secrets /opt/openvox-console/certs cd /opt/openvox-console curl -fsSLO https://raw.githubusercontent.com/avitacco/openvox-console/main/docker-compose.yml

リポジトリのチェックアウトからデプロイしないでください。チェックアウトには開発用スタックである docker-compose.override.yml も含まれており、素の docker compose up はこれを黙って読み込みます: 使い捨てのパスワード、公開されたデータベースポート、証明書の自動署名。このガイドのすべてのコマンドは -f docker-compose.yml を指定しているため、読み込まれるのは常に本番用のファイルだけです。

デプロイ固有の値を設定する

compose ファイルと同じ場所に .env を作成します。compose ファイルは最初の 3 つのいずれかが未設定のままだと起動を拒否するため、プレースホルダーのままデプロイが立ち上がることはありません:

CONSOLE_BASE_URL=https://console.example.com CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 OPENVOXDB_POSTGRES_PASSWORD=<a strong password> # Every name nodes or the console use to reach openvoxserver, beyond its # own name "openvoxserver" - see Plan a deployment. OPENVOXSERVER_DNS_ALT_NAMES=puppet.example.com # The Puppet server a node should enroll against, written into the node # install script. Must be one of the names above. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # The first admin user, created only while there are no users. Its # password is a secret file, below. Without this name no admin is # created and nobody can log in. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin # The console's plain-HTTP port, published on loopback only, so the # TLS proxy in front of it is the only way in. See "Put TLS in front of # the console" below. CONSOLE_HTTP_PORT=127.0.0.1:8080

実行するコンソールイメージを選びます。CONSOLE_IMAGE_TAG の既定値は main で、最新のコミットに追従します。固定しておきたいデプロイでは、代わりに特定のコミットの不変タグを指定してください:

CONSOLE_IMAGE_TAG=sha-a1b2c3d

v1.2.3 のようなバージョンタグと latest は、リリースが作成されて初めて公開されます。それまでは、latest を指定すると manifest unknown で失敗します。

シークレットを書き込む

シークレットは環境変数ではなく secrets/ 内のファイル (1 ファイルにつき 1 つの値) として置くため、docker inspect に表示されることはありません:

printf '%s' '<console database password>' > secrets/console_postgres_password printf 'postgres://console:%s@console-postgres:5432/console?sslmode=disable' '<console database password>' \ > secrets/console_postgres_dsn printf '%s' '<a strong password, 12 characters or more>' > secrets/console_bootstrap_admin_password chmod 600 secrets/*

コンソールのデータベース接続文字列には、console_postgres_password と同じパスワードを使う必要があります。sslmode=disable は意図的なものです: Postgres コンテナは TLS なしで動作し、接続が compose ネットワークの外に出ることはないため、TLS を要求するとコンソールが接続に失敗するだけです。

openvoxserver にはトークンファイル enc_bridge_token も必要で、これはコンソールが起動してから記入します。openvoxserver はこれがないと起動しないため、今は空のまま作成しておきます:

: > secrets/enc_bridge_token

認証局を起動する

openvoxserver は他のすべての構成要素の証明書の発行元となる CA なので、最初に単独で起動します:

docker compose -f docker-compose.yml up -d openvoxserver

初回起動時に CA が作成され、これには 1～2 分かかります。実行中であると報告されるまで待ちます:

docker compose -f docker-compose.yml exec openvoxserver \ curl -ksS https://127.0.0.1:8140/status/v1/simple

応答は running です。

openvoxserver-ca ボリュームこそが認証局そのものです。失うと、すべての Node を登録し直す必要があります。バックアップを取り、docker compose down -v で削除することは決してしないでください。

コンソールの証明書を発行する

コンソールには CA から 2 つの証明書と、任意で 3 つ目の証明書が必要です。稼働中の openvoxserver コンテナ内で発行し、compose ファイルがコンソール用にマウントする certs/ にコピーします。

openvoxdb のクライアント証明書

コンソールはこれを使って openvoxdb に認証します:

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname console docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console.pem certs/console-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console.pem certs/console-key.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/ca.pem certs/ca.pem

puppetserver ca generate は、最初に Error: Signed certificate console could not be found on the CA と出力します。これは名前が空いているかを確認しているだけで、失敗ではありません。重要なのはその後に続く行で、最後が Successfully saved certificate で終わっていれば成功です。

Node トランスポートの証明書

Node はコンソールへの接続時にこの証明書を検証するため、証明書には Node が接続に使う名前そのもの、つまり CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR のホスト部分が含まれている必要があります。

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/node-transport.pem certs/node-transport-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/node-transport.pem certs/node-transport-key.pem

Node は同じ CA から発行された自身の証明書で認証し返すため、コンソールは Node 用に他のファイルを必要としません。

トークン署名鍵

コンソールは自身のログイントークンに ES256 鍵で署名します。この鍵は CA からではありません。任意のマシンで OpenSSL を使って生成します:

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

このファイルはバックアップしてください。失うと発行済みのトークンがすべて無効になり、全員がログアウトされます。漏れると誰でもトークンを発行できてしまいます。安全に置き換えるにはトークン署名鍵をローテーションするを参照してください。

certs/ に直接生成します:

openssl ecparam -genkey -name prime256v1 -noout -out certs/rbac-signing-key.pem

証明書管理者の認証情報 (任意)

この認証情報があることで、Nodes ページに証明書のステータスが表示され、証明書の署名、失効、削除ができるようになります。これがない場合、コンソールが一覧表示するのはすでに接続または報告した Node だけです。証明書の署名を待っている Node はまったく表示されません。その存在を知っているのは CA だけだからです。

この認証情報は CA の完全な管理権限です。openvoxserver はすべての CA エンドポイントを 1 つの認可拡張で保護しているため、ステータスを読める証明書は、どの Node の証明書でも署名、失効、クリーンアップができます。読み取り専用の種類はありません。コンソールが動作する場所にだけ置き、発行する前にNode の証明書を管理するを読んでください。

発行の際には、稼働中の openvoxserver も書き込む CA の状態に書き込みが行われます。そのため、まず openvoxserver を停止し、同じボリュームを使う使い捨てのコンテナから発行してください。Compose はプロジェクトディレクトリにちなんでボリューム名を付けるので、まず正確な名前を確認します:

docker volume ls | grep openvoxserver

次に、表示された 2 つの名前を使って:

docker compose -f docker-compose.yml stop openvoxserver docker run --rm --entrypoint "" \ -v openvox-console_openvoxserver-ssl:/etc/puppetlabs/puppet/ssl \ -v openvox-console_openvoxserver-ca:/etc/puppetlabs/puppetserver/ca \ ghcr.io/avitacco/openvox-console-server:main \ puppetserver ca generate --ca-client --force --certname console-ca-client docker compose -f docker-compose.yml start openvoxserver

ここでは --force が必須です。このコマンドは署名の前にサーバーが本当に停止しているかを確認しますが、素のコンテナの中ではそれを判別できないため、--force がないと「Could not determine whether Puppet Server is online」と表示し、何も作成せずに終了します。うまくいったと思い込まず、出力を読んでください。

ファイルは長い .puppetlabs パスの下に書き込んだと報告されますが、無視してかまいません: ボリューム内では通常の場所に置かれます。それらをコピーして取り出します:

docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem certs/ca-client-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem certs/ca-client-key.pem

次に、コンソールに CA の場所を .env で伝えます。compose ネットワーク内では、コンソールは openvoxserver にコンテナ名で到達し、この名前は常に openvoxserver の証明書に含まれています:

CONSOLE_CA_CLIENT_URL=https://openvoxserver:8140

認証情報が受け入れられることを、openvoxserver の内部から確認します:

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://openvoxserver:8140/puppet-ca/v1/certificate_statuses/all

HTTP 200 は CA がそれを受け入れたことを意味します。

Tasks

Puppet の Task の実行には、これ以上何も必要ありません。コンソールは、すでに発行した openvoxdb クライアント証明書を使って、https://openvoxserver:8140 で、deploy したコードにどの Task が含まれているかを openvoxserver に問い合わせます。openvoxserver は、その CA が発行したどの証明書にも Task の読み取りを許可しています。Task を無効にするには、.env でアドレスを空に設定します:

CONSOLE_PUPPET_SERVER_URL=

実行方法についてはJobs を実行するを参照してください。

クラス一覧

Node グループのページでは、deploy したコードが定義するクラスがパラメーターとともに提示されるため、入力するのではなく選択できます。コンソールは Tasks と同じ接続を通じて openvoxserver からそれらを読み込みます。

openvoxserver は既定ではどの証明書にもクラスの読み取りを許可しません。compose ファイルのサーバーイメージは、起動のたびにルールを追加し、console という名前の証明書 (上で発行した openvoxdb クライアント証明書) を許可します。別の名前で発行した場合は、.env でその名前を設定します:

CLASS_DISCOVERY_CERTNAME=my-console-cert

openvoxserver の内部から、コンソールの証明書を使って確認します。HTTP 200 は一覧を読み取れることを意味します:

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ 'https://openvoxserver:8140/puppet/v3/environment_classes?environment=production'

HTTP 403 は、ルールがこの証明書を指定していないことを意味します。他にこれに依存するものはありません: その場合、グループページには一覧を利用できないと表示され、クラスは一覧が存在する前と同様に名前で入力します。Node を分類するを参照してください。

残りをすべて起動する

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

openvoxdb は初回起動時に自身の証明書を CA に要求します。compose ファイルは、openvoxdb だけを含む許可リストを通じて、まさにその 1 件の要求だけを自動的に署名します。Node がこの方法で署名されることはありません。その後 openvoxdb はデータベースを待ち、コンソールはその両方を待ちます。起動の様子を見守ります:

docker compose -f docker-compose.yml ps

数分以内にすべてのサービスが healthy になります。

openvoxdb が healthy にならない場合

openvoxdb は、証明書要求が 2 分以内に署名されないと諦め、その際に失敗を自身の証明書ファイルに書き込みます。それ以降の再起動では証明書ファイルが存在するため登録を飛ばし、No certs found in 'ssl-cert' file で失敗します。自然には回復しません。再起動するのではなく、ID をリセットしてください:

docker compose -f docker-compose.yml rm -sf openvoxdb docker volume rm openvox-console_openvoxdb-ssl docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca clean --certname openvoxdb docker compose -f docker-compose.yml up -d openvoxdb

ボリューム名はプロジェクトディレクトリの名前に従います。docker volume ls で確認してください。ca clean を省略すると、CA は対応する鍵のない openvoxdb の署名済み証明書を保持したままになり、新たな起動は No keypair on disk and CA already has signed certificate で失敗します。

コンソールの前段に TLS を置く

コンソールは Web インターフェースと API を平文の HTTP で提供します。https:// のベース URL には、TLS を終端してリクエストをコンソールに渡すリバースプロキシを通じて到達します。どのリバースプロキシでも機能します。ここではコンソールのホスト上で Caddy を使います:

Debian と Ubuntusudo apt-get install -y caddy RHEL、Rocky、AlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

これで /etc/caddy/Caddyfile の全体は次のとおりです:

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

openvoxdb とホストを共有しているなどの理由でコンソールが別のポートで待ち受けている場合は、代わりにそのポートを reverse_proxy に指定します。

インターネットで名前解決できる名前なら、Caddy が自ら証明書を取得・更新します。内部名の場合は、ブロック内に tls <cert file> <key file> の行を置き、独自の CA の証明書を与えます。試用には、tls internal で Caddy 自身のローカル CA から証明書を発行させることもできますが、ブラウザーは警告を表示します。

プロキシを経由するのは Web インターフェースだけです。Node トランスポート (ポート 8142) は独自の TLS を持ち、各 Node の証明書を自ら検証するため、Node は直接到達する必要があります。決してプロキシの背後に置かないでください。

初めてログインする

初回起動時、コンソールはデータベーススキーマを作成し、続いてユーザーテーブルがまだ空のうちにブートストラップ管理者を作成します。起動が完了すると、ログに次の 3 行が表示されます:

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

正常であると報告されることを、まずコンソールのホスト上で直接、次にベース URL の TLS プロキシ経由で確認します:

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

どちらの応答でも各依存先が ok と表示されます。2 つ目だけが失敗する場合、コンソールは正常で、問題はプロキシにあります。コンソールのポートを 8080 から変更した場合は、1 つ目でそのポートを使ってください。次にコンソールのベース URL を開き、ブートストラップ管理者としてログインし、すぐにパスワードを変更してください。

ブートストラップ管理者のパスワードは 12 文字以上で、ユーザー名と同じであってはなりません。そうでない場合、管理者は作成されず、誰もログインできません。ログにはその旨が記録されます:

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

より長いパスワードを設定し、コンソールを再び起動してください。パスワードとロックアウトを参照してください。

ログインしてパスワードを変更したら、コンソールの設定からブートストラップ管理者の設定を削除してください。これらはユーザーテーブルが空の間しか読み込まれませんが、パスワードを放置しておく理由はありません。

分類を接続する

openvoxserver は、Puppet 標準の exec node terminus を通じて、各 Node にどのクラスを割り当てるかをコンソールに問い合わせます。小さなプログラム enc-bridge が openvoxserver に代わってこの要求を行い、そのためにトークンを必要とします。

enc-bridge にトークンを発行する

サービストークンは作成時に選んだ固定の権限セットを持ち、ロールは関係しません。分類の読み取りだけが許可されたトークンを作成します:

  1. コンソールで管理を開き、サービストークンを開きます。
  2. 新しいサービストークンで、名前を enc-bridge とし、enc:read 権限だけを与えます。
  3. サービストークンを作成を選びます。

トークンは一度しか表示されません。今すぐコピーしてください。

API でも同じことができます。管理者ログインのアクセストークンを使います: curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

openvoxserver にトークンを渡す

openvoxserver のイメージには、enc-bridge、それを使う Puppet の設定、そして Node が設定データを読み込むための Hiera 関数がすでに含まれているため、必要なのはトークンだけです。先ほど空で作成したシークレットファイルに書き込みます:

printf '%s' '<the enc:read service token>' > secrets/enc_bridge_token

openvoxserver はコンテナ内で root として動作せず、Compose はシークレットファイルをホスト上の所有権のままマウントします。そのため、自分のユーザーだけが読めるファイルは openvoxserver からは読めず、分類が失敗します。代わりにグループ 0 に読み取り権限を与え、ディレクトリのほうを保護します:

sudo chgrp 0 secrets/enc_bridge_token chmod 640 secrets/enc_bridge_token chmod 700 secrets

新しいトークンを読み込ませるため、openvoxserver を再作成します:

docker compose -f docker-compose.yml up -d --force-recreate openvoxserver

分類を確認する

openvoxserver が実行するのと同じ方法で、enc-bridge に直接問い合わせます。これでプログラム、トークン、ファイルのパーミッション、コンソールの応答を 1 つのコマンドで確認できます:

docker compose -f docker-compose.yml exec -u puppet:0 openvoxserver \ /usr/local/bin/enc-bridge <a certname>

{} は、分類が機能していて、その Node がまだどのグループにも一致していないことを意味します。コンソールのグループページでその certname を固定する Node グループを作成し、同じコマンドをもう一度実行すると、クラスが返ってきます:

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

ここで見逃してはならないのがエラーです。permission denied は openvoxserver の実行ユーザーがトークンを読めないことを意味し、401 はトークンが誤っているか enc:read を持っていないことを意味します。

Node の次の Puppet run が Could not find class <name> で失敗する場合、分類は機能しています: コンソールが openvoxserver に、Puppet コードでまだ定義されていないクラスを含めるよう指示したということです。

openvoxserver は Environments をキャッシュするため、Puppet コードを追加した後はキャッシュを破棄してください。そうしないと同じエラーが続きます:

docker compose -f docker-compose.yml exec openvoxserver sh -c \ 'curl -ksS -X DELETE \ --cert /etc/puppetlabs/puppet/ssl/certs/openvoxserver.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/openvoxserver.pem \ https://127.0.0.1:8140/puppet-admin-api/v1/environment-cache'

後でアップグレードする

新しいコンソールに移行するには、CONSOLE_IMAGE_TAG を変更し (main に追従している場合は再度 pull し)、スタックをもう一度起動します。Compose は変更されたものだけを再作成します:

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

compose ファイルは openvoxdb のポートを公開していないため、以下の確認ではコンテナの内部から問い合わせます: docker compose -f docker-compose.yml exec openvoxdb curl -ksS https://127.0.0.1:8081/status/v1/simple
