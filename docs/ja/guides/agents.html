AI エージェントにコンソールを使わせる

AI エージェントに独自の限定されたトークンを与え、フリートを読み取らせて変更を依頼させ、何かが実行される前に各変更を自分で承認します。

コンソールには、MCP (Model Context Protocol) に基づく AI エージェント向けのエンドポイントが /mcp にあります。これに接続したエージェントは、Node、Node グループ、Tasks、Jobs を閲覧できます。何かを変更したいとき — Task の実行、Puppet の実行、Plan の実行、Node へのパッチ適用 — エージェントは何も開始しません。依頼し、そのリクエストは人が承認するまで承認ページで待機します。

エージェントが閲覧・要求できるものはすべて、エージェント自身のトークンによって制限されます: どの権限を持つか、どの Node グループに到達できるか、どの Task の実行を依頼できるか。エージェントが行うことはすべて、エージェント自身の名前で監査ログに記録されます。

エンドポイントを有効にする

エンドポイントはオフになっています。コンソールに CONSOLE_MCP_ENABLED=true を設定して再起動してください。それまでは /mcp は存在せず、未知のパスと同じ応答を返します。

設定 意味 既定値
CONSOLE_MCP_ENABLED /mcp を提供する オフ
CONSOLE_MCP_RATE_LIMIT 1 つのトークンが 1 分間に行える呼び出しの回数 60
CONSOLE_AGENT_REQUEST_TTL リクエストが判断を待つ時間 (30m など) 1h
CONSOLE_AGENT_TOKEN_MAX_DAYS エージェントトークンの最長有効期間 90

レート制限はコンソールインスタンスごとに管理されるため、トークンは各インスタンスで 1 分あたりその回数まで呼び出せます。コンソールの他の部分と同様に、エンドポイントは TLS の背後に置いてください: トークンはベアラー認証情報です。

エージェント用のトークンを発行する

エージェントトークンは独自の種類のトークンです。サービストークンではありません: 有効期限があり、Node グループに限定され、/mcp でのみ機能します。漏えいしても、コンソールの API の他の部分に対して使うことはできません。

  1. 管理、エージェントトークンの順に開きます。
  2. トークンには、用途となるエージェントにちなんだ名前を付けます (ops-assistant など)。
  3. 権限を選びます。エージェントトークンが持てるのは nodes:read、classifier:read、orchestrator:read、orchestrator:run、vulnerabilities:read だけです。orchestrator:run はエージェントに何かを実行させるものではありません: 依頼できるようにするものです。
  4. 到達を許可する Node グループを選びます。グループがないトークンはどの Node にも到達しません。エージェントが読み取るもの、要求するものはすべて、それらのグループとその配下のグループに限定されます。
  5. 必要なら、実行を依頼できる Task に、依頼を許可する Task を ロールと同様に 1 行に 1 パターンずつ列挙します。すべての Task を許可するには空のままにします。Node グループと Task はどちらもトークンの作成時に固定されます。
  6. 有効期間の日数を設定します。トークンには必ず有効期限があり、CONSOLE_AGENT_TOKEN_MAX_DAYS より長くすることはできません。30 日から始めるのがよいでしょう。
  7. エージェントトークンを作成を選び、トークンをコピーします: トークンは一度しか表示されません。

同じページの失効させるは、すべてのコンソールインスタンスで直ちにトークンを終了させます。そのリクエストは記録として承認ページに残り、待機中だったものは失敗としてマークされます。

エージェントを接続する

エージェントに、末尾に /mcp を付けたコンソールのアドレスと、ベアラートークンとしてのトークンを与えます。エンドポイントは streamable HTTP を話し、POST された各メッセージに直接応答します。たとえば Claude Code の場合:

claude mcp add --transport http openvox https://console.example.com/mcp \ --header "Authorization: Bearer <the token>"

エージェントに提供されるのは、そのトークンが許可するツールだけです。

ツール 必要なもの 何ができるか
list_nodes, get_node, get_node_reports nodes:read Node とその Facts、Reports の閲覧
get_node_patches, get_patch_inventory nodes:read 保留中の OS 更新
list_groups, get_group, get_group_nodes classifier:read Node グループ
list_tasks, get_task, list_code_plans, get_code_plan orchestrator:read deploy されたコードが提供するものと、それぞれのパラメーター
list_jobs, get_job orchestrator:read Jobs とその結果
resolve_targets orchestrator:run 対象の指定がどの Node を示すか
request_task, request_puppet_run, request_plan, request_patch_run, request_code_plan orchestrator:run 何かの実行を依頼する (後述)
get_request, list_requests orchestrator:run エージェント自身のリクエストと、それがどう判断されたか

エージェントが読み取るものはすべて、そのトークンを使ってコンソール自身のエンドポイントを通じて取得されるため、そのトークンの権限と Node グループを持つ人が見るものとまったく同じものが見え、機密の値は他の場所と同様にマスクされます。長い結果は切り詰められ、より少なく要求する方法をエージェントに伝える注記が付きます。

エージェントが求めるものを承認する

エージェントが request_ ツールのいずれかを呼び出すと、コンソールはあなたのリクエストとまったく同じように検査し (Task とそのパラメーター、Node、エージェントの Node グループと Task リスト)、通過すれば保存して、承認待ちであることをエージェントに伝えます。何も実行されません。検査に失敗したリクエストは理由とともに拒否されるため、エージェントはそれを修正できます。

Jobs、承認の順に開きます (タブには待機中の件数が表示され、ナビゲーションにも表示されます)。リクエストを確認すると、次の内容が表示されます:

  • どのエージェントがいつ依頼したか、そしてリクエストの有効期限
  • Task、Plan、または実行の種類と、その Environment
  • 正確な Node。エージェントが要求した時点で解決されたもの
  • パラメーター (機密の値はマスクされます)

承認して実行を選ぶと Job が開始され、却下を選ぶと (必要ならメモを添えて) エージェントにその旨が伝えられます。承認すると、表示された内容そのもの (パラメーターと Node はリクエスト時点で固定されています) がエージェントのトークンとして開始されます。Job には AI エージェントが要求したことと誰が承認したかが表示され、Jobs はその方法で開始された Jobs に絞り込めます。

誰も判断しなかったリクエストは、CONSOLE_AGENT_REQUEST_TTL を設定しない限り 1 時間後に期限切れとなり、承認できなくなります。エージェントが同時に保持できる待機中のリクエストの数には上限があります。

承認できる人

人のロールに付与するもので、エージェントトークンには与えられない 2 つの権限:

権限 できること
agent-requests:read 承認ページでリクエストを閲覧する
agent-requests:approve それらの承認と却下

承認者には、リクエストが操作するすべての Node に対する orchestrator:run も必要で、その Task を実行できなければなりません。自分では Task を実行できない Node へのリクエストは承認できません。一部の Node グループしか見られない人には、それらのグループ内の Node を指定したリクエストだけが表示されます。

エージェントのトークンを発行した人は、そのリクエストを承認できませんが、却下はできます。管理者が 1 人しかいない場合は、承認用に 2 つ目のアカウントを作成してください。

新しいバージョンのコンソールで追加された権限が、既存のロールに自動的に追加されることはありません。アップグレード後は、ロールページで agent-requests:read と agent-requests:approve を、それを持たせるべきロールに付与してください。新規インストールのブートストラップ管理者は両方を持っています。

承認する時点でエージェントのトークンが失効または期限切れになっていた場合、何も開始されず、リクエストにその理由が示されます。

コード内の Plans

request_code_plan は、コード内の Plan の実行を要求します。このような Plan は実行中に、エージェントのトークンが届く範囲内で自ら Node を選ぶため、承認するにはそのトークンが届くすべてに対する orchestrator:run が必要です。Plan はコードを deploy するコンソールインスタンス上でのみ実行されるため、そのインスタンスで承認してください。そうしないと、要求はその理由で失敗します。

記録されるもの

監査ログには、オーケストレーターのカテゴリーのレベルで、各リクエスト、各承認、却下、期限切れが、エージェントを agent:<token name> として、判断した人とリクエスト番号とともに記録されます。エージェントによる読み取りは、他の読み取りと同様に同じ名前で監査されます。機密の値は、監査ログ、アクティビティログ、リクエスト自体のいずれにも現れません: それらはコンソールのシークレット鍵 (CONSOLE_SECRETS_KEY) で暗号化して保持され、これがない場合、機密の値を含むリクエストは拒否されます。

API の記述

/api/v1/openapi.json は、自分で書くプログラム向けに REST API を記述したもので、サインインしている人なら誰でも参照できます。エージェントトークンはこの API を呼び出せず、サービストークンを使うプログラムには承認待ちが求められません。人による承認を挟んでエージェントに操作させるには、エージェントを /mcp に接続してください。
