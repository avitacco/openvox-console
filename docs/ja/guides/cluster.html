スケール

インスタンスを増やす

2 台目のコンソールインスタンスをクラスター化し、インスタンスを実行モードに分割し、分類をコンパイラーの隣に配置します。

複数のコンソールインスタンスが 1 つのデータベースを共有し、1 つのクラスターに参加します。クラスターは、すべてのインスタンスに同時に届けるべき事柄 (失効したログイン、失効した Node 証明書) を互いに伝える手段であり、あるインスタンスで開始された Job が別のインスタンスに接続している Node に届く手段でもあります。

永続的なものはすべて Postgres にあるため、クラスター化すればどのインスタンスもあらゆるリクエストに応答でき、ロードバランサーは正常なインスタンスのどれにでもリクエストを送れます。

データベースを共有するインスタンスはクラスター化する必要があります。クラスター化されていないインスタンスは、次にデータベースから失効情報を読み直すとき (最大 30 秒後) まで失効したログインを知ることができず、他のインスタンスに接続している Node にも到達できません。

インスタンスが互いを見つける仕組み

各インスタンスは組み込みの NATS サーバーを実行します。コアモード (all、web、orchestrator、worker) は、ルーティングされたピアとして互いに直接接続します。一方、enc インスタンスはリーフとして接続します: 接続は enc インスタンスからコアへの外向きにのみ張られるため、コア側がコンパイラーのあるネットワークに入る手段を持つ必要はありません。

web-1 --+ web-2 --+-- routed peers (:6222) orch-1 -+ worker -+ ^ | leaf connections, outbound only | (to a core instance's leaf listener, :6223) | enc-1, enc-2 (beside the compilers)

リーフはインスタンス間でコンソール自身のメッセージ (失効やステータスなど) を運び、Node のトラフィックは決して運びません: enc インスタンスが管理対象 Node に到達することはありません。

始める前に

すべてのピア接続は、2 つの方法で暗号化・認証されます:

  • 相互 TLS。各インスタンスの CA 発行の証明書を使います。既定では、インスタンスは openvoxdb 用と同じ証明書 (CONSOLE_OPENVOXDB_CERT_FILE の証明書) を使うため、新たに発行するものはありません。インスタンスに接続するピアは、その証明書が接続先の名前に対して有効であることを確認するため、各インスタンスには証明書に含まれる名前で到達する必要があります。
  • 共有シークレット。すべてのコアインスタンスで同じものです。管理対象 Node も CA からの証明書を持っているため、証明書だけでは参加できないようにしているのがこのシークレットです。

共有の証明書ではなく独自の証明書をインスタンスに与える場合は、openvoxserver がそのインスタンスにもクラス一覧の読み取りを許可する必要があります: そのルールは許可する証明書 (既定では console) を指定しており、それ以外は HTTP 403 で拒否します。すべての web と all インスタンスの certname をそのルールに追加してください。そうしないと、それらのインスタンスのグループページには一覧を利用できないと表示されます。パッケージとバイナリからインストールするを参照してください。

リーフは独自の 2 つ目のシークレットを使い、これはクラスターのシークレットとは異なるものでなければなりません: enc ホストはコンソールが動作する場所の中で最も信頼度が低く、完全なピアとして参加できてはなりません。

両方のシークレットを生成し、各設定の _FILE 形式を使ってプロセスの環境変数に置かないようにします:

openssl rand -base64 32 > cluster-secret openssl rand -base64 32 > cluster-leaf-secret

2 台目のインスタンスを追加する

まず 2 つの all インスタンスから始めます。そうすることで、役割を分割する前にクラスター化を試せます。

1 台目のインスタンスで、ピアリスナーを開いて再起動します:

CONSOLE_CLUSTER_ADDR=:6222 CONSOLE_CLUSTER_SECRET_FILE=/etc/openvox-console/cluster-secret

2 台目には、同じデータベース、同じトークン署名鍵、同じシークレットを与え、独自のピアリスナーを設定し、1 台目のインスタンスを、その証明書にある名前でピアとして指定します:

CONSOLE_CLUSTER_ADDR=:6222 CONSOLE_CLUSTER_PEERS=console-1.example.com:6222 CONSOLE_CLUSTER_SECRET_FILE=/etc/openvox-console/cluster-secret

相手を指定する必要があるのは片側だけです。後から参加するインスタンスはどれも既存のいずれかを指定し、残りはクラスターが接続します。

Node が 2 台目のインスタンスにも接続する場合は、そのインスタンスにも独自の Node リスナーと Node トランスポート証明書が必要です。また、リンクやインストールスクリプトがロードバランサーを経由するよう、すべてのインスタンスに同じ CONSOLE_BASE_URL が必要です。

インスタンスは互いのアドレスをクラスター自体から知りますが、既定ではそれは IP アドレスであり、証明書に IP アドレスが含まれていることはめったにありません。それぞれ独自の証明書を持つルーティングされたインスタンスが 3 つ以上ある場合は、各インスタンスの CONSOLE_CLUSTER_ADVERTISE に、そのインスタンス自身の証明書にある名前 (console-2.example.com:6222 など) を設定してください。

クラスターが形成されたことを確認する

各インスタンスは起動時に、与えられたピアとともに cluster joined をログに記録します。次に、status:read 権限を持つユーザーとして、コンソールのシステムを開きます。フリートの状態タブには応答したすべてのインスタンスがモードごとに一覧表示され、両方のインスタンスがそこに表示されます。

status:read は既存のロールに自動的には追加されません。ロールページで、このページを閲覧させたいロールに付与してください。

インスタンスをモードに分割する

2 つの all インスタンスが連携して動くようになったら、負荷に応じて役割を分割します: バックグラウンド処理は worker に、Node の接続は orchestrator に、利用者が使うものはすべて web に。各インスタンスで CONSOLE_RUN_MODE を設定して再起動します。各モードに必要なもの (トークンを発行しないモード用の検証鍵を含む) については実行モードを参照してください。

どのモードも複数のインスタンスとして動かせます:

  • 脆弱性の同期、1 つの Environment のコード deploy、放棄された Jobs のクリーンアップなど、一度だけ行うべき作業はデータベースを通じて調整されるため、2 つの worker インスタンスが両方で実行することはありません。
  • 失効情報はすべてのインスタンスに届くため、各インスタンスの表示は常に最新に保たれます。
  • アクティビティは、それが発生したインスタンスによって一度だけ記録されます。

コンソールとその API にはロードバランサーを web インスタンスに向け、Node は CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR を通じて orchestrator インスタンスの Node トランスポートに向けます。

分類をコンパイラーの隣に置く

enc インスタンスは隣接するコンパイラーに対して分類の応答を返し、リーフとしてクラスターに接続します。

1 つ以上のコアインスタンスで、リーフのシークレットで保護されたリーフリスナーを開きます:

CONSOLE_CLUSTER_LEAF_ADDR=:6223 CONSOLE_CLUSTER_LEAF_SECRET_FILE=/etc/openvox-console/cluster-leaf-secret

各 enc インスタンスで、コアインスタンスのリーフリスナーに接続します。保持するのはリーフのシークレットだけで、クラスターのシークレットは決して持ちません:

CONSOLE_RUN_MODE=enc CONSOLE_CLUSTER_MODE=leaf CONSOLE_CLUSTER_PEERS=console-1.example.com:6223 CONSOLE_CLUSTER_LEAF_SECRET_FILE=/etc/openvox-console/cluster-leaf-secret CONSOLE_RBAC_VERIFICATION_KEYS_DIR=/etc/openvox-console/rbac-verification-keys

次に、ENC_BRIDGE_URL を使って、各コンパイラーの enc-bridge をその隣の enc インスタンスに向けます。

フリート全体を確認する

フリートの状態タブは、すべてのインスタンスに問い合わせ、1 秒以内に応答したものを集めて、その場で全体像を組み立てます。知っておくべき点が 2 つあります:

  • 応答したインスタンスが本来の数より少ない場合は、一覧の上にその旨が表示されます (例:「1 of 4 instances did not reply within 1s」)。これは深刻に受け止めてください: 稼働しているのに他のインスタンスに到達できないインスタンスは、たいてい固まっています。
  • openvoxdb や CA などの各依存先は、応答したインスタンスから見た状態で表示されます。インスタンス間で見え方が異なるものはインスタンスごとに異なると表示され、一部のインスタンスからは到達でき、他のインスタンスからは到達できないことを意味します。

このページは自動では更新されません。最新の状態を見るには再読み込みしてください。

破棄されたメッセージに注意する

各インスタンスの /metrics にある console_nats_async_errors_total は、クラスター接続上の問題を数えます。重要なのはサブスクライバーの遅延で、これが起きるとメッセージが破棄されます。それぞれはエラーレベルで「NATS subscriber fell behind; messages were dropped」としてもログに記録されます。カウントが増えている場合は調べる価値があります。

元に戻す

どの手順も元に戻せます: CONSOLE_RUN_MODE=all を設定し、クラスターの設定を削除するだけです。データベース内に分割に依存するものはありません。

インスタンスが互いを見つける仕組み 始める前に 2 台目のインスタンスを追加する クラスターが形成されたことを確認する インスタンスをモードに分割する 分類をコンパイラーの隣に置く フリート全体を確認する 破棄されたメッセージに注意する 元に戻す

OpenVox Console は、push のたびに amd64 と arm64 向けにビルドされるコンテナイメージと、単一のバイナリとして提供されます。インストールガイドでは、コンテナまたはパッケージを使って、空のホストから openvoxserver、openvoxdb、Postgres、コンソールからなる稼働するデプロイまでを案内します。
