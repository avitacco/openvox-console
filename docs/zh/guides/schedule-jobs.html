使用

计划 Jobs

保存一次 Puppet 运行、一个 Task 或一个 Plan，以便稍后启动——一次或重复启动——其 Nodes 会在每次启动时重新确定。

计划是一个被保存下来、会自行启动的 Puppet 运行、Task 或 Plan：可以在你选定的时间启动一次，也可以重复启动。它所做的与你在那一刻手动启动同一个 Job 完全相同——参见运行 Jobs——而且每次启动时，都会像其他 Job 一样被记录下来。

创建和更改计划需要 orchestrator:run；查看计划需要 orchestrator:read。

创建计划

打开 Jobs，然后打开计划的 Jobs，再选择新建计划。或者在任意位置填写运行 Puppet、运行 Task 或运行 Plan，然后选择改为计划，这会打开同一个表单，并带上你已填写的内容。如果是从 Node 组的页面操作，计划的对象是该组，而不是该组当前包含的 Nodes。

  1. 为它设置名称。它启动的 Jobs 都会标上这个名称。
  2. 选择运行内容：Puppet（可带任意运行选项）；Task（带上其参数）；或者从已保存的 Plans 中选择一个 Plan。
  3. 选择哪些 Nodes：列表、查询或 Node 组，与选择 Nodes 中相同。预览 Nodes 会显示它此刻将在哪些 Nodes 上运行。
  4. 选择时间：开始时间，以及如需重复，重复的频率。
  5. 保存计划。

保存计划时，控制台会像你此刻启动该 Job 那样对它进行完全相同的检查，并在出错的部分旁边给出拒绝原因。只有一点不同：尚未匹配任何 Node 的查询或组也可以保存。

每次都会重新确定 Nodes

每次计划启动时，查询或 Node 组都会被重新计算。下周加入该组的 Node 会在下周被包括进来；不再匹配查询的 Node 会被排除在外。

时间与重复

时间按你浏览器的时区输入和显示，表单会注明该时区。处于其他时区的人看到的是同一时刻在其时区中的时间。

不重复的计划只启动一次，之后显示为完成。重复计划在其开始时间启动，之后每隔若干分钟、小时、天或周启动一次。最短的重复间隔为 5 分钟。

重复间隔是一段固定的时长：一天是 24 小时，一周是七个这样的一天。在实行夏令时调整时钟的地方，每日计划会按 UTC 保持其时间，因此在本地时钟上会移动一小时。没有诸如「第一个星期一」之类的日历规则。

重复计划可以设置一个过去的开始时间。它下一次会在仍在未来的第一个重复时间启动。

计划以什么身份运行

计划以其所有者的身份运行：即最后保存它的人。每次启动时，控制台都会应用所有者在那一刻的角色，而不是保存时的角色：

  • 如果所有者已不能再运行 Jobs——其角色被移除，或者其账户或服务令牌被删除——就不会启动任何东西。
  • 如果所有者的角色是在特定 Node 组上被授予的，查询或组只会给出这些组中的匹配 Nodes。列表中指定的 Nodes 必须全部仍在这些组中，否则不会启动任何东西。
  • 如果所有者的角色仅限部分 Tasks，计划只会启动他们仍然有权运行的 Tasks，而且只在他们有权运行这些 Tasks 的 Nodes 上启动。为你无权运行的 Task 保存计划会被拒绝，并指出该 Task。

保存对某个计划的更改会使你成为其所有者，当你打开别人的计划时，表单会提示这一点。这就是从已离职的人手中接管计划的方法：打开它并保存。暂停和恢复不会改变所有者。

你可以查看和更改自己拥有的计划。角色在 All Nodes 上被授予的人可以查看和更改所有人的计划。参见用户、角色与令牌。

当计划没有启动时

计划的页面会列出每次到期时发生的情况。

结果 含义
开始 已启动一个 Job。该行会链接到它。
已跳过 因所示原因未启动任何东西。该计划会在下一个时间继续。
已错过 到期时没有控制台在运行调度器，等到有控制台运行时，已经晚了超过 15 分钟。
已中断 负责启动它的控制台实例在启动之前就停止了。

在以下情况下，计划会被跳过：

  • 其查询或组没有匹配到任何 Node，或者没有匹配到所有者有权操作的 Node；
  • 其所有者已不能再运行 Jobs，或者它指定的某个 Node 已离开所有者的 Node 组；
  • 其 Task 或其 Plan 中的某个 Task 已不再被所有者的角色允许（本次触发会注明该 Task，如果是 Plan 还会注明步骤）——参见将角色限制为部分 Tasks；
  • 其 Task、某个 Task 参数、其 Environment 或其 Node 组已不再如计划所描述的那样存在；
  • 无法访问 openvoxdb 或 Puppet 服务器，因而无法确定 Nodes 或 Task；
  • 它上次启动的 Job 仍在运行。

未能启动的触发永远不会重试。原定 02:00 的运行不会因为控制台整夜宕机而在 09:00 启动，而且同一个到期时间的 Task 永远不会被启动两次。错过了多次重复的重复计划只会记录一次错过的触发，并在下一个时间恢复。

被跳过和错过的触发也会记录在活动页面上，计划的 Jobs 列表会显示每个计划最近一次的结果。

计划启动时未连接的 Node 会在该 Job 中以 "agent not connected" 失败，与手动启动的 Job 一样；该 Job 仍会针对其他 Nodes 启动。

计划的 Plan 保留其自己的步骤

当你选择一个 Plan 时，计划会复制其步骤并显示出来。从那时起，计划运行的就是这份副本。更改或删除已保存的 Plan 不会改变计划运行的内容。

若要采用对 Plan 的更改，请编辑该计划，在 Plan 下重新选择该 Plan，然后保存。如果 Plan 保持为「保留下方显示的步骤」，副本会保持原样。

原因在于：计划以其所有者的访问权限运行，而每个能运行 Jobs 的人都能更改 Plan——参见运行 Plans。

如果在计划到期时某个步骤已无法运行——比如其 Task 已从代码中移除——就不会启动任何东西，该次时间会被记录为已跳过，并指出该步骤。

暂停、更改或删除计划

在计划的页面上：

  • 暂停使其不再到期。恢复会让它从下一个尚未到来的时间重新开始；对于已经过去的时间，不会补启动任何东西。不重复的计划如果在暂停期间错过了时间，则需要改设一个新的开始时间。
  • 编辑会打开表单。保存时会像新建计划一样再次检查。
  • 删除会移除它。它启动过的 Jobs 仍保留在 Job 历史记录中，并且依然注明它。

删除 Node 组不会删除以它为目标的计划。这些计划会被跳过，并说明该组已不存在，直到你更改或删除它们为止。

敏感的 Task 参数

被标记为 sensitive 的 Task 参数（密码、令牌）必须保留到计划启动时。控制台会用其机密密钥加密存储它，并在计划或其 Jobs 出现的所有地方显示 Sensitive [value redacted]。计划的 Plan 中 Task 步骤的敏感值也是如此，计划表单会在每个步骤下要求输入这些值。

  • 没有机密密钥时，带有敏感值的计划会被拒绝。请在每个提供控制台服务或运行调度器的实例上设置 CONSOLE_SECRETS_KEY_FILE——参见跟踪漏洞，它使用同一个密钥。
  • 编辑你自己的计划时，将敏感字段留空即可保留已存储的值。
  • 保存别人的计划时，你必须重新输入其敏感值。控制台不会把已存储的机密交给新的所有者。
  • 如果机密密钥发生变化，已存储的值就无法再被读取。该计划会被跳过并说明原因，直到重新带上这些值保存它为止。

通过 API

curl -X POST https://console.example.com/api/v1/orchestrator/schedules \ -H "Authorization: Bearer <access token>" \ -H 'Content-Type: application/json' \ -d '{"name":"Weekly no-op", "kind":"run", "options":{"noop":true}, "group":12, "startAt":"2026-01-04T03:00:00Z", "repeat":{"every":1,"unit":"week"}}'

kind 为 run（带 options）、task（带 task、params、environment 和 timeoutSeconds，与 Task 请求相同）或 plan（带 planName 和 steps，与 Plan 请求相同）。Nodes 由 targets、query 或 group 指定。repeat.unit 为 minute、hour、day 或 week；对于只启动一次的计划，省略 repeat。

请求 作用
GET /api/v1/orchestrator/schedules 列出你能看到的计划
GET /api/v1/orchestrator/schedules/<id> 一个计划，以及它每次到期时发生的情况
PUT /api/v1/orchestrator/schedules/<id> 替换它，并使你成为其所有者
POST /api/v1/orchestrator/schedules/<id>/pause 和 /resume 暂停或恢复它
DELETE /api/v1/orchestrator/schedules/<id> 删除它

被拒绝的请求会以 400（如果是你的 Node 组之外的 Node，则为 403）响应，并附带 error，以及指出与计划的哪一部分有关的 field——如果是 Plan，还会附带被拒绝的 step。由服务令牌拥有的计划，只要该令牌存在且持有 orchestrator:run，就会一直运行。

计划在哪里启动

计划由 all 和 orchestrator 运行模式的实例启动。当有多个实例在运行时，每个到期时间都只由其中一个实例启动。

创建计划 每次都会重新确定 Nodes 时间与重复 计划以什么身份运行 当计划没有启动时 计划的 Plan 保留其自己的步骤 暂停、更改或删除计划 敏感的 Task 参数 通过 API 计划在哪里启动

OpenVox Console 以容器镜像形式发布，每次 push 都会构建 amd64 和 arm64 版本，同时也提供单个二进制文件。安装指南将带你从一台空主机走到一套可用的部署——openvoxserver、openvoxdb、Postgres 和控制台——可以用容器，也可以用软件包。
