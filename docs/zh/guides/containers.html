安装

使用容器安装

使用 Docker Compose 运行 openvoxserver、openvoxdb、两个数据库和控制台，从一台空主机到一个可以接入 Nodes 的控制台。

本指南使用项目的生产 compose 文件和已发布的镜像运行整个堆栈，不在主机上构建任何东西。开始之前，请先按照规划部署确定好各个名称。

你需要一台装有 Docker Engine 和 Compose 插件的 Linux 主机，以及一个无需 sudo 即可运行 docker 的用户。

获取 compose 文件

项目仓库中的 docker-compose.yml 就是生产环境的堆栈：控制台、两个数据库、openvoxserver 和 openvoxdb。把这一个文件复制到主机上一个单独的、归你的用户所有的目录中：

sudo mkdir -p /opt/openvox-console sudo chown "$USER": /opt/openvox-console mkdir -p /opt/openvox-console/secrets /opt/openvox-console/certs cd /opt/openvox-console curl -fsSLO https://raw.githubusercontent.com/avitacco/openvox-console/main/docker-compose.yml

不要从仓库的 checkout 进行部署。checkout 中还带有 docker-compose.override.yml，即开发用的堆栈，直接运行 docker compose up 时它会被悄无声息地加载：一次性密码、开放的数据库端口以及自动证书签名。本指南中的每条命令都传入了 -f docker-compose.yml，以确保只读取生产用的文件。

设置部署自身的值

创建与 compose 文件同目录的 .env。只要前三项中任何一项未设置，compose 文件就会拒绝启动，因此部署不可能带着占位值运行起来：

CONSOLE_BASE_URL=https://console.example.com CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 OPENVOXDB_POSTGRES_PASSWORD=<a strong password> # Every name nodes or the console use to reach openvoxserver, beyond its # own name "openvoxserver" - see Plan a deployment. OPENVOXSERVER_DNS_ALT_NAMES=puppet.example.com # The Puppet server a node should enroll against, written into the node # install script. Must be one of the names above. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # The first admin user, created only while there are no users. Its # password is a secret file, below. Without this name no admin is # created and nobody can log in. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin # The console's plain-HTTP port, published on loopback only, so the # TLS proxy in front of it is the only way in. See "Put TLS in front of # the console" below. CONSOLE_HTTP_PORT=127.0.0.1:8080

选择要运行的控制台镜像。CONSOLE_IMAGE_TAG 默认为 main，跟随最新提交。若希望部署保持不变，请改为固定到某一次提交的不可变标签：

CONSOLE_IMAGE_TAG=sha-a1b2c3d

v1.2.3 这样的版本标签以及 latest 只有在正式发版后才会发布。在此之前，请求 latest 会失败并报 manifest unknown。

写入机密

机密以文件形式存放在 secrets/ 中，每个文件一个值，而不是使用环境变量，因此它们永远不会出现在 docker inspect 中：

printf '%s' '<console database password>' > secrets/console_postgres_password printf 'postgres://console:%s@console-postgres:5432/console?sslmode=disable' '<console database password>' \ > secrets/console_postgres_dsn printf '%s' '<a strong password, 12 characters or more>' > secrets/console_bootstrap_admin_password chmod 600 secrets/*

控制台的数据库连接字符串必须使用与 console_postgres_password 相同的密码。sslmode=disable 是有意为之：Postgres 容器不启用 TLS，而且连接从不离开 compose 网络，要求 TLS 只会让控制台连接失败。

openvoxserver 还需要一个令牌文件 enc_bridge_token，等控制台运行起来后再填写。现在先创建一个空文件，因为缺少它 openvoxserver 无法启动：

: > secrets/enc_bridge_token

启动证书颁发机构

openvoxserver 是其他所有组件证书的来源 CA，因此它最先启动，并且单独启动：

docker compose -f docker-compose.yml up -d openvoxserver

首次启动时它会创建 CA，这需要一两分钟。等待它报告自身正在运行：

docker compose -f docker-compose.yml exec openvoxserver \ curl -ksS https://127.0.0.1:8140/status/v1/simple

返回 running。

openvoxserver-ca 卷就是你的证书颁发机构。丢失它意味着每个 Node 都必须重新注册。请备份它，并且绝不要用 docker compose down -v 删除它。

签发控制台的证书

控制台需要 CA 签发的两张证书，另有一张可选。在运行中的 openvoxserver 容器内签发它们，然后复制到 certs/ 中，compose 文件会把该目录挂载给控制台。

openvoxdb 客户端证书

控制台就是这样向 openvoxdb 进行认证的：

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname console docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console.pem certs/console-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console.pem certs/console-key.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/ca.pem certs/ca.pem

puppetserver ca generate 一开始会打印 Error: Signed certificate console could not be found on the CA。这是它在检查该名称是否可用，并非失败。真正要看的是之后的几行，最后以 Successfully saved certificate 结尾。

Node 传输证书

Nodes 连接控制台时会校验此证书，所以它必须包含 Nodes 所拨号的确切名称：即 CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR 的主机部分。

docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/node-transport.pem certs/node-transport-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/node-transport.pem certs/node-transport-key.pem

Nodes 使用同一 CA 签发的自有证书进行反向认证，因此控制台不需要为它们准备其他文件。

令牌签名密钥

控制台使用一个 ES256 密钥为自己的登录令牌签名。这个密钥并非来自 CA。可在任意一台机器上用 OpenSSL 生成：

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

请备份此文件。丢失它会使所有已签发的令牌失效，从而让所有人退出登录；泄露它则会让任何人都能伪造令牌。要安全地替换它，请参见轮换令牌签名密钥。

直接生成到 certs/ 中：

openssl ecparam -genkey -name prime256v1 -noout -out certs/rbac-signing-key.pem

证书管理员凭据（可选）

有了这个凭据，Nodes 页面才能显示证书状态，并对证书进行签名、吊销和清理。没有它，控制台只会列出已经连接过或上报过的 Nodes。正在等待证书签名的 Node 根本不会出现，因为只有 CA 知道它的存在。

该凭据拥有完整的 CA 管理员权限。openvoxserver 用同一个授权扩展把守所有 CA 端点，因此一张能读取状态的证书也能签名、吊销和清理任何 Node 的证书。不存在只读的变体。请只把它保存在控制台运行的地方，并在签发之前阅读管理 Node 证书。

签发它会写入 CA 状态，而运行中的 openvoxserver 也会写入这些状态，因此请先停止 openvoxserver，再用一个挂载相同卷的一次性容器来签发。Compose 会以项目目录命名卷，所以请先确认卷的确切名称：

docker volume ls | grep openvoxserver

然后，使用它打印出的两个名称：

docker compose -f docker-compose.yml stop openvoxserver docker run --rm --entrypoint "" \ -v openvox-console_openvoxserver-ssl:/etc/puppetlabs/puppet/ssl \ -v openvox-console_openvoxserver-ca:/etc/puppetlabs/puppetserver/ca \ ghcr.io/avitacco/openvox-console-server:main \ puppetserver ca generate --ca-client --force --certname console-ca-client docker compose -f docker-compose.yml start openvoxserver

这里必须加 --force。签名之前，该命令会检查服务器是否确实已停止，而在裸容器中它无法判断，因此不加 --force 时，它会打印 "Could not determine whether Puppet Server is online" 并退出，什么也不创建。请阅读它的输出，而不要想当然地认为它成功了。

它会报告把文件写到了一个很长的 .puppetlabs 路径下。不必理会：在卷中它们位于通常的位置。把它们复制出来：

docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem certs/ca-client-cert.pem docker compose -f docker-compose.yml cp \ openvoxserver:/etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem certs/ca-client-key.pem

然后在 .env 中告诉控制台 CA 在哪里。在 compose 网络内部，控制台通过容器名称访问 openvoxserver，而该名称总是包含在 openvoxserver 的证书中：

CONSOLE_CA_CLIENT_URL=https://openvoxserver:8140

在 openvoxserver 内部确认该凭据被接受：

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console-ca-client.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console-ca-client.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://openvoxserver:8140/puppet-ca/v1/certificate_statuses/all

HTTP 200 表示 CA 接受了它。

Tasks

运行 Puppet Tasks 不需要额外配置。控制台会在 https://openvoxserver:8140 上使用你已经签发的 openvoxdb 客户端证书，向 openvoxserver 询问你已 deploy 的代码中包含哪些 Tasks；openvoxserver 允许其 CA 签发的任何证书读取 Tasks。要关闭 Tasks，请在 .env 中把该地址设为空：

CONSOLE_PUPPET_SERVER_URL=

关于如何运行它们，参见运行 Jobs。

类列表

Node 组的页面会提供你已 deploy 的代码所定义的类及其参数，供你选择而不必手动输入。控制台通过与 Tasks 相同的连接从 openvoxserver 读取它们。

openvoxserver 默认不允许任何证书读取类。compose 文件中的服务器镜像会在每次启动时添加该规则，允许名为 console 的证书——也就是你在上面签发的 openvoxdb 客户端证书——读取类。如果你以其他名称签发了它，请在 .env 中设置该名称：

CLASS_DISCOVERY_CERTNAME=my-console-cert

在 openvoxserver 内部使用控制台的证书检查它。HTTP 200 表示可以读取该列表：

docker compose -f docker-compose.yml exec openvoxserver \ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/puppetlabs/puppet/ssl/certs/console.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/console.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ 'https://openvoxserver:8140/puppet/v3/environment_classes?environment=production'

HTTP 403 表示该规则没有指定这张证书。没有其他功能依赖于它：此时组页面会提示该列表不可用，类需要按名称输入，就像该列表出现之前那样。参见为 Nodes 分类。

启动其余所有服务

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

openvoxdb 首次启动时会向 CA 申请自己的证书。compose 文件会通过一个只包含 openvoxdb 的允许列表，自动签发且仅签发这一个请求；Nodes 绝不会以这种方式被签名。随后 openvoxdb 会等待其数据库，而控制台会等待两者。观察它们启动：

docker compose -f docker-compose.yml ps

每个服务都会在几分钟内达到 healthy。

如果 openvoxdb 一直无法变为健康状态

如果 openvoxdb 的证书请求在两分钟内没有被签名，它就会放弃，并且会把失败信息写入自己的证书文件。此后每次重启都会看到一个证书文件，于是跳过注册，并以 No certs found in 'ssl-cert' file 失败。它无法自行恢复。请重置它的身份，而不是重启它：

docker compose -f docker-compose.yml rm -sf openvoxdb docker volume rm openvox-console_openvoxdb-ssl docker compose -f docker-compose.yml exec openvoxserver \ puppetserver ca clean --certname openvoxdb docker compose -f docker-compose.yml up -d openvoxdb

卷名称取决于项目目录的名称；请用 docker volume ls 确认。如果跳过 ca clean，CA 中会留下一个为 openvoxdb 签发、却没有匹配密钥的证书，重新启动时就会失败并报 No keypair on disk and CA already has signed certificate。

在控制台前面配置 TLS

控制台通过普通 HTTP 提供其 Web 界面和 API。https:// 基础 URL 经由一个终止 TLS 并把请求转发给控制台的反向代理访问。任何反向代理都可以。这里在控制台的主机上使用 Caddy：

Debian 和 Ubuntusudo apt-get install -y caddy RHEL、Rocky 和 AlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

完整的 /etc/caddy/Caddyfile 就是：

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

如果控制台因为与 openvoxdb 共用主机而监听其他端口，请改为在 reverse_proxy 中填写该端口。

对于互联网可以解析的名称，Caddy 会自行获取并续期证书。对于内部名称，请在该配置块中加入一行 tls <cert file> <key file>，为它提供由你自己的 CA 签发的证书。用于试用时，tls internal 会让 Caddy 用它自己的本地 CA 签发一张证书，浏览器会对此发出警告。

只有 Web 界面经过代理。Node 传输（端口 8142）自带 TLS，并会自行校验每个 Node 的证书，因此 Nodes 必须直接访问它。绝不要把它放在代理后面。

首次登录

首次启动时，控制台会创建其数据库 schema，然后趁用户表仍为空时创建引导管理员。启动完成后，其日志中会出现三行：

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

检查它是否报告自身健康：先直接在控制台的主机上检查，再通过 TLS 代理在其基础 URL 上检查：

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

每个应答都会把每个依赖项列为 ok。如果只有第二个失败，说明控制台没有问题，问题出在代理上。如果你把控制台从 8080 移到了其他端口，请在第一个检查中使用控制台自己的端口。然后打开控制台的基础 URL，以引导管理员身份登录，并立即修改其密码。

引导管理员的密码必须至少有 12 个字符，并且不能与其用户名相同。否则不会创建管理员，也就没有人能登录。日志会说明这一点：

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

设置一个更长的密码，然后重新启动控制台。参见密码与锁定。

登录并修改密码后，请从控制台的配置中删除引导管理员相关设置。它们只在用户表为空时才会被读取，但没有理由让密码一直留在那里。

连接分类

openvoxserver 通过 Puppet 标准的 exec node terminus 向控制台询问每个 Node 获得哪些类。一个小程序 enc-bridge 代表 openvoxserver 发出该请求，为此它需要一个令牌。

为 enc-bridge 签发令牌

服务令牌带有一组在创建时选定的固定权限，不涉及任何角色。创建一个只允许读取分类的服务令牌：

  1. 在控制台中打开管理，然后打开服务令牌。
  2. 在新建服务令牌下，将其命名为 enc-bridge，并只授予 enc:read 权限。
  3. 选择创建服务令牌。

令牌只显示一次。请立即复制。

也可以通过 API 完成，使用管理员登录获得的访问令牌：curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

把令牌交给 openvoxserver

openvoxserver 镜像已经包含 enc-bridge、使用它的 Puppet 配置，以及让 Nodes 读取配置数据的 Hiera 函数，因此它只需要令牌。把令牌写入你之前创建的那个空机密文件：

printf '%s' '<the enc:read service token>' > secrets/enc_bridge_token

openvoxserver 在其容器内不以 root 身份运行，而 Compose 挂载机密文件时会沿用主机上的所有权。因此，只有你自己的用户可读的文件，openvoxserver 无法读取，分类就会失败。请改为授予组 0 读取权限，并转而保护该目录：

sudo chgrp 0 secrets/enc_bridge_token chmod 640 secrets/enc_bridge_token chmod 700 secrets

重新创建 openvoxserver，使其读取新令牌：

docker compose -f docker-compose.yml up -d --force-recreate openvoxserver

检查分类

以 openvoxserver 运行 enc-bridge 的方式直接向它发起请求。一条命令即可同时检查程序、令牌、文件权限以及控制台的应答：

docker compose -f docker-compose.yml exec -u puppet:0 openvoxserver \ /usr/local/bin/enc-bridge <a certname>

{} 表示分类正常工作，只是该 Node 尚未匹配任何组。在控制台的组页面上创建一个固定该 certname 的 Node 组，再次运行同一命令，它的类就会返回：

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

这里出现的错误正是需要捕捉的故障。permission denied 表示运行 openvoxserver 的用户无法读取该令牌；401 则表示令牌错误或缺少 enc:read。

如果某个 Node 的下一次 Puppet 运行失败并报 Could not find class <name>，说明分类在正常工作：控制台让 openvoxserver 包含了一个你的 Puppet 代码中尚未定义的类。

openvoxserver 会缓存 Environments，因此添加 Puppet 代码后，请刷新它的缓存，否则同样的错误会一直存在：

docker compose -f docker-compose.yml exec openvoxserver sh -c \ 'curl -ksS -X DELETE \ --cert /etc/puppetlabs/puppet/ssl/certs/openvoxserver.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/openvoxserver.pem \ https://127.0.0.1:8140/puppet-admin-api/v1/environment-cache'

日后升级

要升级到更新的控制台版本，请修改 CONSOLE_IMAGE_TAG（如果跟随 main，则重新拉取），然后再次启动堆栈。Compose 只会重新创建发生变化的部分：

docker compose -f docker-compose.yml pull docker compose -f docker-compose.yml up -d

compose 文件不会发布 openvoxdb 的端口，因此进行下面的检查时，请在其容器内部发起请求：docker compose -f docker-compose.yml exec openvoxdb curl -ksS https://127.0.0.1:8081/status/v1/simple
