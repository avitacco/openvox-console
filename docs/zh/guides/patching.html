使用

查找并应用缺失的更新

扫描 Linux Nodes 上待安装的软件包更新，然后分批为它们打补丁，支持试运行、停止阈值和可选的重启。

补丁管理页面显示每个 Node 缺少哪些更新，以 Node 自己的包管理器所报告的为准。扫描只是查看。补丁运行才会安装它们。

此功能涵盖使用 apt、dnf 或 yum 的 Linux Nodes。Windows、macOS 和 zypper（SUSE）不会被扫描：使用它们的 Node 会被列为无法上报，而绝不会显示为已完全打好补丁。

查看结果需要 nodes:read，且仅限于你的角色所指定的 Node 组。扫描某个 Node 或组、或为其打补丁需要 orchestrator:run，同样仅限于你的角色覆盖的 Nodes。更改控制台的扫描频率需要 nodes:manage。不涉及任何新权限。

扫描做了什么

扫描会让 Node 的代理以不做任何更改的模式运行其包管理器：先刷新软件包列表，然后报告升级将会替换什么。对于每个待安装的更新，你都能看到软件包、已安装版本、可用版本，以及包管理器是否将其标记为安全更新。Node 还会报告它是否已经需要重启。

刷新列表意味着扫描会访问 Node 的镜像源。无法访问镜像源的 Node 会记录扫描失败，并继续显示上一次成功扫描得到的更新，同时标注它们早于最近一次尝试。

有两点需要仔细理解：

  • 安全以包管理器的说法为准。如果系统的仓库不带安全信息，就不会显示任何安全更新，但这并不等于没有安全更新。Ubuntu 和 Debian 在仓库名称中标记安全更新；在 RHEL 系列系统上，控制台会通过 dnf updateinfo 查询安全更新集合。
  • 从未扫描不等于没有待处理的内容。尚未扫描过的 Node 会列为未扫描，且不显示计数。

Node 的代理必须由包含扫描功能的版本构建。较旧的代理会回应说它不认识该请求，在代理升级之前，该 Node 会显示为无法上报：参见保持 Node 代理为最新。

查看机群

打开补丁管理。顶部的数字统计的是你能看到的 Nodes：有待安装更新的、有安全更新的、需要重启的、未扫描的，以及上次扫描已过期的。

当扫描结果早于扫描间隔的两倍时，就被视为已过期，因此悄悄停止被扫描的 Node 会显得很醒目。关闭自动扫描时，以一天为判断标准。

筛选条件：

  • 操作系统，用于一次查看一个系统家族。
  • 组，如果你的角色可以读取 Node 组。
  • 待更新的软件包：把列表切换为那些有名称与之匹配的软件包更新正在等待的 Nodes，并显示已安装版本和可用版本。搜索 openssl 就能找出还有谁需要该修复。

选择一个 Node 以打开其页面。补丁标签页会列出它的更新（安全更新在前），以及上次扫描的时间。

立即扫描

在某个 Node 的补丁标签页上，立即扫描会扫描该 Node。在补丁管理页面上选择一个组，立即扫描此组会扫描该组中你有权操作的每个 Node。返回结果会逐个 Node 说明哪些已被扫描、哪些失败、哪些离线，以及有多少个因不在你的 Node 组内而被排除。

离线的 Node 不会被扫描，并保留原有结果；它重新连接后，会在下一轮中被扫描。组扫描每次只处理少量 Nodes，因此大型组需要一段时间。

你请求的每次扫描都会记录在审计日志中，注明请求者以及对应的 Node 或组。

自动扫描

除非你将其关闭，否则控制台每天扫描一次每个已连接的 Node。在补丁管理页面的自动扫描下（需要 nodes:manage），可以把间隔设置为 15 分钟到 7 天之间的任意值，或者将其关闭。

  • 无论你运行多少个控制台实例，同一时间只有一个实例执行自动扫描，而且在间隔内已被扫描过的 Node 不会被再次扫描。
  • 扫描失败的 Node 会在下一个间隔之后再试，而不是在每一轮都重试。
  • 自动扫描不会为每个 Node 写入审计条目。对间隔的更改会被审计。
  • 使用运行模式时，扫描在 all 和 worker 实例中运行。
  • 90 天内没有任何尝试的 Node，其结果会被删除。

为节点打补丁

补丁运行会在 Linux Nodes 上安装待安装的更新（apt、dnf 或 yum）。可以在补丁管理页面通过为此组打补丁…启动，也可以在某个 Node 的补丁标签页通过立即打补丁…启动。它需要 orchestrator:run，并且与任何运行一样，只要其中有任何 Node 不在你的 Node 组内，就会被整体拒绝，并指出这些 Nodes。

选择：

  • 要应用的更新：仅安全更新、所有待安装的更新或指定的软件包。没有待安装更新的指定软件包会被报告为无需应用，其他任何东西都不会被改动。在 dnf 和 yum 上，仅安全更新需要仓库提供安全信息；没有安全信息时，Node 会让本次运行失败，而不会安装所有更新。
  • 试运行：报告将会升级的内容，不做任何更改、不重启任何服务、不重启任何机器。
  • 打完补丁后重启需要重启的节点：只有当 Node 在成功运行后报告自己需要重启时，才会重启它。试运行或失败的 Node 永远不会被重启。Node 会先交付结果，大约半分钟后再重启。
  • 同时处理的节点数（1 到 100，默认 10）和失败节点达到此数量后停止（默认 3，0 表示永不停止）。

批次与停止

Nodes 按批次打补丁，按 Node 名称排序。一个批次中的 Nodes 同时打补丁，只有在该批次完成后才会开始下一批。当失败的 Node 数量达到阈值时，就不会再启动后续批次：未处理到的 Nodes 会被记录为未启动，也不会向它们发送任何东西。请让第一个批次规模小一些，并放在你承受得起损失的机器上，然后再让其余的跟进。

已经在被另一次运行打补丁的 Node 不会被再次启动：请求会被拒绝，并指出该 Node。

观察运行

该运行会以 Job 的形式打开。它会列出每个 Node 及其批次、状态、退出状态和它升级的软件包（原版本和新版本），并在详情下显示包管理器自身的输出。运行期间页面会不断刷新。Node 的补丁标签页显示该 Node 上最近一次运行，补丁管理页面则列出最近的各次运行。

一次运行可能需要数小时。控制台每 15 秒询问一次每个 Node 的进展，每次应答都被视为运行仍然存活的证明。十分钟内毫无回应的 Node 会被判为失败，四小时后仍在运行的 Node 也是如此，运行会在其他 Nodes 上继续。如果跟踪该运行的控制台实例停止，该 Job 会在最后一次收到消息的十分钟后被判为失败，并记录原因。补丁过程本身会在 Node 上继续，因此请再次扫描它以了解其进展。

之后

Node 完成后，补丁管理页面显示的就是它仍待安装的软件包：Node 自己的扫描会在其运行结束时进行。已重启的 Node 会在重新连接后再次扫描，最多等待十分钟。如果它在这段时间内没有恢复，其快照会显示扫描失败，但本次运行不会因此判为失败。

每次运行在启动时都会被审计，记录启动者、Nodes 的来源以及所选的每个选项，结束时还会再审计一次。两者都会出现在活动日志中。

代理版本过旧、无法打补丁的 Node 会以失败告终，并附上说明原因，且不会在其上安装任何东西：参见保持 Node 代理为最新。

不涵盖的内容

此版本不支持安排补丁窗口或禁止时段、为打补丁而对 Nodes 分组、回滚补丁、为 Windows 或 macOS 打补丁，也不支持把待安装的更新与已知漏洞关联起来：要对照已知公告查看已安装的内容，参见跟踪漏洞。
