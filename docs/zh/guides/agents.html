使用

让 AI 代理使用控制台

为 AI 代理提供专属的受限令牌，让它读取机群并请求更改，并在任何东西运行之前由你亲自批准每项更改。

控制台在 /mcp 上为 AI 代理提供了一个基于 MCP（Model Context Protocol）的端点。连接到它的代理可以查看你的 Nodes、Node 组、Tasks 和 Jobs。当它想要更改什么——运行 Task、运行 Puppet、运行 Plan 或为 Nodes 打补丁——它不会启动任何东西。它会提出请求，请求会在批准页面上等待，直到有人批准。

代理能看到或请求的一切都受其自身令牌的限制：它拥有哪些权限、能访问哪些 Node 组，以及可以请求运行哪些 Tasks。它所做的一切都以它自己的名义记录在审计日志中。

开启端点

该端点默认关闭。在控制台上设置 CONSOLE_MCP_ENABLED=true 并重启。在此之前，/mcp 并不存在：它的应答与任何未知路径相同。

设置 含义 默认值
CONSOLE_MCP_ENABLED 提供 /mcp 关闭
CONSOLE_MCP_RATE_LIMIT 一个令牌每分钟可发起的调用次数 60
CONSOLE_AGENT_REQUEST_TTL 请求等待决定的时长，例如 30m 1h
CONSOLE_AGENT_TOKEN_MAX_DAYS 代理令牌的最长有效期 90

速率限制由每个控制台实例各自维护，因此一个令牌在每个实例上每分钟都可以发起这么多次调用。请像控制台的其余部分一样，把该端点放在 TLS 之后：令牌是一种 bearer 凭据。

为代理签发令牌

代理令牌是一种独立的令牌。它不是服务令牌：它会过期，它仅限于 Node 组，而且只在 /mcp 上有效。泄露的代理令牌无法被用来访问控制台 API 的其余部分。

  1. 打开管理，然后打开代理令牌。
  2. 以令牌所服务的代理来命名令牌，例如 ops-assistant。
  3. 选择其权限。代理令牌只能携带 nodes:read、classifier:read、orchestrator:read、orchestrator:run 和 vulnerabilities:read。orchestrator:run 并不能让代理运行任何东西：它只能让代理提出请求。
  4. 选择它可以访问的 Node 组。没有任何 Node 组的令牌无法访问任何 Node。代理读取或请求的一切都仅限于这些组及其下属组。
  5. 可选：在可请求运行的 Task 下列出它可以请求的 Tasks，每行一个模式，与角色相同。留空则允许所有 Task。Node 组和 Tasks 都在令牌创建时固定。
  6. 设置它的有效天数。令牌必须会过期，且有效期不能超过 CONSOLE_AGENT_TOKEN_MAX_DAYS。三十天是个不错的起点。
  7. 选择创建代理令牌并复制令牌：它只显示一次。

在同一页面上点击吊销会立即在每个控制台实例上终止该令牌。它的请求会作为记录保留在「批准」页面上，其中仍在等待的请求会被标记为失败。

连接代理

把控制台的地址加上 /mcp 后缀提供给代理，并把令牌作为 bearer token。该端点使用 streamable HTTP，并直接应答每条 POST 的消息。以 Claude Code 为例：

claude mcp add --transport http openvox https://console.example.com/mcp \ --header "Authorization: Bearer <the token>"

代理只会获得其令牌允许的工具。

工具 所需权限 它能做什么
list_nodes, get_node, get_node_reports nodes:read 查看 Nodes 及其 Facts 和 Reports
get_node_patches, get_patch_inventory nodes:read 待安装的操作系统更新
list_groups, get_group, get_group_nodes classifier:read Node 组
list_tasks, get_task, list_code_plans, get_code_plan orchestrator:read 已 deploy 的代码提供了什么，以及每一项的参数
list_jobs, get_job orchestrator:read Jobs 及其结果
resolve_targets orchestrator:run 目标将会指向哪些 Nodes
request_task, request_puppet_run, request_plan, request_patch_run, request_code_plan orchestrator:run 请求运行某些东西（见下文）
get_request, list_requests orchestrator:run 代理自己的请求及其决定结果

代理读取的一切都通过控制台自己的端点、使用其令牌获取，因此它看到的内容与拥有该令牌权限和 Node 组的人看到的完全相同，敏感值也会像其他地方一样被遮罩。过长的结果会被截断，并附上提示，告诉代理如何请求更少的数据。

批准代理的请求

当代理调用某个 request_ 工具时，控制台会像检查你的请求一样检查它——Task 及其参数、Nodes、代理的 Node 组和 Task 列表——如果通过检查，就保存该请求，并告诉代理它正在等待批准。不会运行任何东西。未通过检查的请求会被拒绝并给出原因，以便代理进行更正。

打开 Jobs，然后打开批准（该标签页会显示有多少请求在等待，导航栏也是如此）。审阅某个请求即可看到：

  • 是哪个代理在何时发出的请求，以及请求何时过期
  • Task、Plan 或运行类型，以及其 Environment
  • 确切的 Nodes，在代理发出请求时解析
  • 参数，敏感值已遮罩

选择批准并运行以启动 Job，或选择拒绝，可以附上备注：代理会收到通知。批准会以该代理令牌的身份启动你所看到的内容，丝毫不差——参数和 Nodes 在请求发出时就已固定。该 Job 会显示它是由 AI 代理请求的以及由谁批准的，而且 Jobs 可以被筛选为只显示以这种方式启动的 Jobs。

无人决定的请求会过期（默认一小时，除非你设置了 CONSOLE_AGENT_REQUEST_TTL），之后便无法再被批准。一个代理同时持有的等待中请求数量是有上限的。

谁可以批准

两项权限，它们授予人员所用的角色，不能授予代理令牌：

权限 允许某人
agent-requests:read 在「批准」页面上查看请求
agent-requests:approve 批准和拒绝这些请求

批准者还需要对请求所作用的每个 Node 拥有 orchestrator:run，并且有权运行该 Task。你无法批准一个作用于你自己都无法运行该 Task 的 Nodes 上的请求。只能看到部分 Node 组的人，只能看到指向这些组中 Nodes 的请求。

签发某个代理令牌的人不能批准该代理的请求，但可以拒绝。如果只有一个管理员，请另建一个账户用于批准。

新版控制台中新增的权限不会自动添加到现有角色中。升级之后，请在角色页面上把 agent-requests:read 和 agent-requests:approve 授予应当拥有它们的角色。新安装的引导管理员同时拥有这两项权限。

如果在你批准时代理的令牌已被吊销或已过期，就不会启动任何东西，请求中会说明原因。

来自代码的 Plans

request_code_plan 请求运行一个来自你代码中的 Plan。这类 Plan 在运行时自行选择 Nodes（在该代理令牌可访问的范围内），因此批准它需要对该令牌可访问的所有对象拥有 orchestrator:run。Plans 只在 deploy 你的代码的控制台实例上运行，因此请在那个实例上批准，否则请求会因此失败并说明原因。

会记录什么

审计日志会按 orchestrator 类别的级别，记录每个请求以及每次批准、拒绝和过期，以 agent:<token name> 标注代理，并注明做出决定的人以及请求编号。代理进行的读取会像任何读取一样以同一名称接受审计。敏感值永远不会出现在审计日志、活动日志或请求本身中：它们用控制台的机密密钥（CONSOLE_SECRETS_KEY）加密保存，没有该密钥时，携带敏感值的请求会被拒绝。

API 描述

/api/v1/openapi.json 描述了 REST API，供你自己编写的程序使用，任何已登录的人都可以访问。代理令牌不能调用该 API，而使用服务令牌的程序也不会被要求等待批准。若要让代理在有人参与批准的情况下执行操作，请把它连接到 /mcp。

OpenVox Console 以容器镜像形式发布，每次 push 都会构建 amd64 和 arm64 版本，同时也提供单个二进制文件。安装指南将带你从一台空主机走到一套可用的部署——openvoxserver、openvoxdb、Postgres 和控制台——可以用容器，也可以用软件包。
