扩展

运行更多实例

将第二个控制台实例加入集群，把实例拆分为不同的运行模式，并把分类服务部署在编译器旁边。

多个控制台实例共享一个数据库并加入同一个集群。集群是它们相互通知那些必须同时到达每个实例的事件（例如被吊销的登录、被吊销的 Node 证书）的途径，也是在一个实例上启动的 Job 到达连接在另一个实例上的 Node 的途径。

所有持久数据都存放在 Postgres 中，因此一旦组成集群，任何实例都可以处理任何请求，负载均衡器可以把请求发送给任意一个健康的实例。

共享同一数据库的实例必须组成集群。未加入集群的实例只有在下一次从数据库重新读取吊销信息时（最多 30 秒之后）才会得知某个登录已被吊销，而且无法访问连接到其他实例的 Nodes。

实例如何彼此发现

每个实例都运行一个内嵌的 NATS 服务器。核心模式（all、web、orchestrator 和 worker）以路由对等节点的方式彼此直接相连。enc 实例则以 leaf 方式接入：连接只向外发起，从 enc 实例连到某个核心实例，因此核心实例永远不需要进入编译器所在网络的通道。

web-1 --+ web-2 --+-- routed peers (:6222) orch-1 -+ worker -+ ^ | leaf connections, outbound only | (to a core instance's leaf listener, :6223) | enc-1, enc-2 (beside the compilers)

leaf 在实例之间传递控制台自身的消息，例如吊销和状态，但从不传递 Node 流量：enc 实例永远无法访问受管 Node。

开始之前

每条对等连接都经过加密，并通过两种方式进行认证：

  • 双向 TLS，每个实例都使用 CA 签发的证书。默认情况下，实例使用与连接 openvoxdb 相同的证书，即 CONSOLE_OPENVOXDB_CERT_FILE 指定的那张，因此无需签发新证书。拨号连接某个实例的对等节点会检查其证书对所拨号的名称是否有效，因此必须使用实例证书中包含的名称来访问每个实例。
  • 一个共享密钥，在每个核心实例上都相同。受管 Node 同样持有 CA 签发的证书，而正是这个密钥使得仅凭该证书不足以加入集群。

如果你为某个实例提供的是它自己的证书而非共享证书，openvoxserver 还必须允许它读取类列表：该规则指定了它所允许的证书（默认为 console），并以 HTTP 403 拒绝其他任何证书。请把每个 web 和 all 实例的 certname 都加入该规则，否则这些实例上的组页面会提示该列表不可用。参见从软件包和二进制文件安装。

leaf 使用另一个自己的密钥，它必须与集群密钥不同：enc 主机是控制台运行环境中最不受信任的地方，绝不能让它以完整对等节点的身份加入。

生成两个密钥，并使用每项设置的 _FILE 形式，使它们不出现在进程环境中：

openssl rand -base64 32 > cluster-secret openssl rand -base64 32 > cluster-leaf-secret

添加第二个实例

从两个 all 实例开始。这样可以在拆分任何角色之前先验证集群功能。

在第一个实例上，开启对等监听器并重启它：

CONSOLE_CLUSTER_ADDR=:6222 CONSOLE_CLUSTER_SECRET_FILE=/etc/openvox-console/cluster-secret

在第二个实例上，为它配置相同的数据库、相同的令牌签名密钥和相同的密钥，以及它自己的对等监听器，并以第一个实例证书中的某个名称把第一个实例设为对等节点：

CONSOLE_CLUSTER_ADDR=:6222 CONSOLE_CLUSTER_PEERS=console-1.example.com:6222 CONSOLE_CLUSTER_SECRET_FILE=/etc/openvox-console/cluster-secret

只需要一方指定另一方。之后加入的每个实例只要指定任意一个现有实例，集群就会把其余实例连接起来。

如果 Nodes 会连接到第二个实例，它还需要自己的 Node 监听器和 Node 传输证书；而且每个实例都需要相同的 CONSOLE_BASE_URL，以便链接和安装脚本都经由负载均衡器访问。

实例通过集群本身获知彼此的地址，默认情况下这些地址是 IP 地址，而证书中很少包含 IP 地址。如果有三个或更多路由实例且各自持有自己的证书，请在每个实例上把 CONSOLE_CLUSTER_ADVERTISE 设置为其自身证书中的某个名称，例如 console-2.example.com:6222。

检查集群是否已形成

每个实例启动时都会记录 cluster joined，以及为它配置的对等节点。然后，以拥有 status:read 权限的用户身份，在控制台中打开系统。集群状态标签页会列出每个做出应答的实例，并按模式分组；两个实例都会出现在那里。

status:read 不会自动添加到现有角色中。请在角色页面上把它授予应当能看到该页面的角色。

将实例拆分为不同模式

当两个 all 实例一起运行之后，可以根据负载需要拆分角色：后台工作交给 worker，Node 连接交给 orchestrator，人员使用的一切交给 web。在每个实例上设置 CONSOLE_RUN_MODE 并重启；各模式需要什么（包括不签发令牌的模式所需的验证密钥），参见运行模式。

任何模式都可以以多个实例运行：

  • 必须只发生一次的工作，例如漏洞同步、单个 Environment 的代码 deploy 或清理被遗弃的 Jobs，会通过数据库进行协调，因此两个 worker 实例永远不会同时执行它；
  • 吊销会到达每个实例，因此每个实例的视图都保持最新；
  • 活动只会被记录一次，由发生活动的实例记录。

将负载均衡器指向 web 实例以提供控制台及其 API，并通过 CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR 让 Nodes 指向 orchestrator 实例的 Node 传输。

把分类服务放在编译器旁边

enc 实例为其旁边的编译器提供分类应答，并以 leaf 方式接入集群。

在一个或多个核心实例上，开启一个受 leaf 密钥保护的 leaf 监听器：

CONSOLE_CLUSTER_LEAF_ADDR=:6223 CONSOLE_CLUSTER_LEAF_SECRET_FILE=/etc/openvox-console/cluster-leaf-secret

在每个 enc 实例上，接入某个核心实例的 leaf 监听器。它只持有 leaf 密钥，绝不持有集群密钥：

CONSOLE_RUN_MODE=enc CONSOLE_CLUSTER_MODE=leaf CONSOLE_CLUSTER_PEERS=console-1.example.com:6223 CONSOLE_CLUSTER_LEAF_SECRET_FILE=/etc/openvox-console/cluster-leaf-secret CONSOLE_RBAC_VERIFICATION_KEYS_DIR=/etc/openvox-console/rbac-verification-keys

然后用 ENC_BRIDGE_URL 让每个编译器的 enc-bridge 指向它旁边的 enc 实例。

检查整个机群

集群状态标签页的信息是实时收集的：它询问每个实例，并汇总一秒内做出应答的结果。关于它，有两点值得了解：

  • 如果应答的实例少于应有的数量，列表上方会说明，例如 "1 of 4 instances did not reply within 1s"。请认真对待：一个正在运行却无法访问其他实例的实例，通常是卡住了。
  • 每个依赖项（例如 openvoxdb 或 CA）都按提供服务的实例所见的状态显示。各实例看法不一致的依赖项会标记为因实例而异，意思是有些实例能访问它，有些不能。

该页面不会自动刷新；要获得最新情况，请重新加载页面。

留意被丢弃的消息

每个实例 /metrics 上的 console_nats_async_errors_total 统计其集群连接上出现的问题。真正要紧的是订阅者跟不上而丢弃消息；每次发生时还会以 error 级别记录日志 "NATS subscriber fell behind; messages were dropped"。计数持续上升就值得排查。

撤销操作

每一步都可以撤销：设置 CONSOLE_RUN_MODE=all 并删除集群设置即可。数据库中没有任何东西依赖于这种拆分。
