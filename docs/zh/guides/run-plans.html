使用

运行 Plans

构建一个 Plan（按顺序执行的一系列 Puppet 运行和 Tasks），保存它，在你选择的 Nodes 上运行它，并观察每个步骤。

Plan 是在同一批 Nodes 上依次执行的一系列步骤。每个步骤都是一次 Puppet 运行或一个 Task，与你手动启动时完全相同——参见运行 Jobs。Plan 保存在控制台中，因此可以再次运行，并且每次都可以针对不同的 Nodes。

查看 Plans 需要 orchestrator:read。创建、更改、删除和运行 Plans 需要 orchestrator:run。

这里的 Plan 是在控制台中构建的一系列步骤。它不是用 Puppet 语言编写的 Plan，控制台不运行那种 Plan。在你自己的模块中用 YAML 编写的 Plan 可以从同一页面运行：参见运行代码中的 Plans。

构建 Plan

打开 Jobs，然后打开 Plans，再选择新建 Plan。

  1. 为它设置名称，如有需要，再加上说明。一个名称只能被一个 Plan 使用。
  2. 使用添加 Puppet 运行步骤和添加 Task 步骤添加步骤。一个 Plan 包含 1 到 20 个步骤。
    • Puppet 运行步骤接受运行选项：No-op、调试和 Environment。
    • Task 步骤接受 Environment、Task、其参数和超时，与运行 Task 中相同。
  3. 用上移和下移调整步骤顺序。你在某个步骤中输入的内容会随之移动。
  4. 保存 Plan。

保存时，控制台会像你此刻启动该运行或 Task 那样检查每个步骤。被拒绝的步骤会标注原因，你输入的内容不会丢失。

Plan 并不规定它在哪些 Nodes 上运行。每次运行时再进行选择。

敏感的 Task 值

被标记为 sensitive 的 Task 参数（密码、令牌）永远不会保存在 Plan 中。编辑器中不显示其字段，每次运行 Plan 时都会要求输入该值。这是因为 Plan 是共享的：每个能运行 Jobs 的人都能打开它。

谁可以更改 Plan

拥有 orchestrator:run 的每个人都可以更改或删除任何 Plan，无论其角色是在哪些 Node 组上被授予的。Plan 不指定任何 Nodes，因此其中没有可供 Node 组限制的内容。一个人可以在哪些 Nodes 上运行 Plan，则与任何 Job 一样受到限制。角色仅限部分 Tasks 的人，只能保存包含其有权运行之 Tasks 的 Plan。

运行 Plan

在 Plans 页面上，在某个 Plan 旁选择运行，或者打开该 Plan 后选择运行。

  1. 选择 Nodes：列表、查询或 Node 组，与选择 Nodes 中相同。预览 Nodes 会显示它将在哪些 Nodes 上运行。
  2. 输入各步骤所要求的敏感值。每个值都标有其所属的步骤。
  3. 运行 Plan。随即打开该 Plan 的 Job 页面。

Nodes 在 Plan 启动时确定一次，之后每个步骤都在这些 Nodes 上运行。如果你的角色是在特定 Node 组上被授予的，查询或组会被收窄到你的 Nodes，而指定了组外 Node 的列表会被整体拒绝，与任何 Job 相同。

在任何东西启动之前，每个步骤都会被检查。如果某个步骤会被拒绝——比如某个 Task 已经从代码中移除——整个 Plan 就会被拒绝并指出该步骤，什么都不会运行。

如果 Plan 中有某个步骤已无法运行，该步骤上会显示警告。请在运行之前编辑该 Plan。

你的角色不允许的 Tasks

如果你的角色仅限部分 Tasks——参见将角色限制为部分 Tasks——别人保存的 Plan 中可能包含你无权运行的 Task。你仍然能看到每个步骤，你无权运行的步骤会被标记为您的角色不允许 Task ...。该 Plan 的运行按钮会被禁用，API 也会以 403 拒绝，并指出该步骤和 Task。编辑该 Plan 也无济于事，除非删除那些步骤；带着这些步骤保存也会以同样方式被拒绝。

当目标是查询或 Node 组时，Plan 会在每一个 Task 步骤你都有权运行的 Nodes 上运行，因此它的所有步骤仍然共享同一批 Nodes。Puppet 运行步骤不受限制。

观察 Plan 运行

Plan 的 Job 页面会按顺序列出其步骤。每个步骤都会显示它做什么、它的状态、开始和结束时间，以及每个 Node 的结果。Plan 运行期间页面会自动更新。

状态 含义
等待中 之前的某个步骤尚未完成
运行中 已发送到 Nodes，尚未全部应答
成功 已在每个 Node 上完成
失败 至少在一个 Node 上失败
未运行 之前的某个步骤失败了，因此该步骤从未被发送到任何 Node

步骤编号会链接到该步骤自己的 Job 页面，而该页面又链接回 Plan。Jobs 列表把一个 Plan 显示为一行，而不是每个步骤一行。

当步骤失败时

只要某个步骤在其任何一个 Node 上失败（包括未连接的 Node），该步骤就失败。Plan 会在那里停止：之后的步骤会被标记为未运行，也不会为它们向任何 Node 发送任何东西。该 Plan 的 Job 为失败。

没有选项可以越过失败的步骤继续执行、跳过失败的 Nodes 或重试某个步骤。请修复失败的原因后重新运行 Plan；如果某个 Plan 不应重复执行其前几个步骤，可以把它拆成两个。

计划运行 Plan

在「运行 Plan」对话框中选择改为计划，或者创建一个计划并选择运行 Plan——参见计划 Jobs。

计划会保留 Plan 步骤的独立副本，在保存计划时生成。如果之后 Plan 被更改或删除，计划会继续运行保存时的那些步骤。若要采用更改，请编辑该计划，重新选择该 Plan，然后保存。

这是有意为之。计划以其所有者的访问权限运行，而每个能运行 Jobs 的人都能更改 Plan。如果计划跟随 Plan 变化，那么一个仅限少数 Nodes 的人就能改变管理员的计划在每个 Node 上运行的内容。

通过 API

已保存的 Plans：

请求 作用
GET /api/v1/orchestrator/saved-plans 列出 Plans，不含其步骤
GET /api/v1/orchestrator/saved-plans/<id> 一个 Plan 及其步骤
POST /api/v1/orchestrator/saved-plans 创建一个 Plan
PUT /api/v1/orchestrator/saved-plans/<id> 替换一个 Plan
DELETE /api/v1/orchestrator/saved-plans/<id> 删除一个 Plan
curl -X POST https://console.example.com/api/v1/orchestrator/saved-plans \ -H "Authorization: Bearer <access token>" \ -H 'Content-Type: application/json' \ -d '{"name":"Restart web tier", "description":"Check first, then restart", "steps":[ {"kind":"run","options":{"noop":true}}, {"kind":"task","taskName":"service","environment":"production", "params":{"name":"nginx","action":"restart"},"timeoutSeconds":300} ]}'

读取到的 Plan 会在每个 Task 步骤上列出运行时需要提供的敏感参数（needs）；如果其 Task 已找不到，还会给出 problem。

没有按 ID 运行 Plan 的请求。要运行一个 Plan，请发送其步骤（在每个步骤的 params 中加上敏感值）以及 Nodes：

curl -X POST https://console.example.com/api/v1/orchestrator/plans \ -H "Authorization: Bearer <access token>" \ -H 'Content-Type: application/json' \ -d '{"name":"Restart web tier", "group":12, "steps":[ {"kind":"run","options":{"noop":true}}, {"kind":"task","taskName":"service", "params":{"name":"nginx","action":"restart"}} ]}'

Nodes 由 targets、query 或 group 指定。返回的是该 Plan 的 Job。用 GET /api/v1/orchestrator/jobs/<id> 读取它，返回结果中包含其 steps，每个步骤的 state 为 waiting、running、succeeded、failed 或 not_run。

被拒绝的请求会以 400（如果是你的 Node 组之外的 Node，则为 403）响应，并附带 error。如果原因出在某个步骤，还会附带从 1 开始计数的 step；如果涉及 Task 的参数，则附带 fields。

GET /api/v1/orchestrator/jobs 不再把 Plan 的步骤作为独立的 Jobs 列出。添加 ?parent=<plan job id> 即可列出它们。

在拆分部署中

在控制台中启动的 Plan 由接收该请求的实例发送并逐步跟踪：在拆分部署中，这是一个 web 实例（参见运行模式）。如果该实例在 Plan 结束前停止，仍在运行的步骤会被标记为失败，其余步骤会以未运行关闭；请重新启动该 Plan。计划的 Plan 会以同样方式由 orchestrator 实例启动和跟踪。
