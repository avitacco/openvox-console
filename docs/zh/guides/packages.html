安装

从软件包和二进制文件安装

从软件包安装 openvoxserver、openvoxdb 和 Postgres，构建控制台，并将其作为 systemd 服务运行。

本指南从 OpenVox 和发行版的软件包安装 openvoxserver、openvoxdb 和 Postgres，并在 systemd 下以单一二进制文件运行控制台。开始之前，请先按照规划部署确定好各个名称。

命令以 Debian 和 Ubuntu 为准，若有不同，会同时给出 RHEL、Rocky Linux 和 AlmaLinux 的对应命令。各组件可以放在一台主机上，也可以分布在多台主机上；如果某一步需要在特定主机上执行，会明确说明。

安装 openvoxserver

openvoxserver 是其他所有组件证书的来源证书颁发机构，因此最先安装它。添加 OpenVox 8 仓库并安装：

Debian 和 Ubuntu. /etc/os-release curl -fsSL -o /tmp/openvox8-release.deb \ "https://apt.voxpupuli.org/openvox8-release-${ID}${VERSION_ID}.deb" sudo apt-get install -y /tmp/openvox8-release.deb sudo apt-get update && sudo apt-get install -y openvox-server RHEL、Rocky 和 AlmaLinuxsudo dnf install -y https://yum.voxpupuli.org/openvox8-release-el-9.noarch.rpm sudo dnf install -y openvox-server

软件包本身不会创建 CA。它的首次启动会创建 CA 以及这台服务器自己的证书，签发给主机的 certname，通常就是其完全限定域名。在通常情况下，只需启动它即可：

sudo systemctl enable --now puppetserver

不要在已经有 CA 的主机上运行 puppetserver ca setup。它只会创建尚不存在的 CA，在已有 CA 的主机上它会停止并提示 "Existing file at .../ca_crt.pem"。按照提示删除这些文件会摧毁你的 CA 以及它签发过的所有证书，包括每个已接入 Node 的证书。

允许 CA 签发备用名称

控制台的 Node 传输证书，以及这台服务器自己的证书（如果你在下面重新签发它），都包含不止一个名称。默认情况下，CA 会拒绝签发此类请求，并让它一直处于等待状态，因此需要一次性允许它。在 /etc/puppetlabs/puppetserver/conf.d/ca.conf 中，把该设置添加到 certificate-authority 块内：

certificate-authority: { allow-subject-alt-names: true ... } sudo systemctl restart puppetserver

检查其证书中的名称

证书始终对其自身的 certname 有效。如果 Nodes 和控制台都通过 certname 访问这台服务器，就无需做任何更改。否则，请检查该证书已经覆盖了哪些名称：

sudo openssl x509 -in /etc/puppetlabs/puppet/ssl/certs/$(hostname -f).pem \ -noout -subject -ext subjectAltName

如果缺少规划中的某个名称，请只重新签发这台服务器自己的证书，绝不要重建 CA。事后设置 dns_alt_names 不会改变已经存在的证书，因此请在服务器运行期间清理并重新生成它：

sudo /opt/puppetlabs/bin/puppetserver ca clean --certname $(hostname -f) sudo /opt/puppetlabs/bin/puppetserver ca generate --certname $(hostname -f) \ --subject-alt-names puppet.example.com,openvoxserver sudo systemctl restart puppetserver

在全新的主机上，也可以在首次启动前设置好名称，让首次启动时直接用这些名称创建证书：sudo /opt/puppetlabs/bin/puppet config set --section server dns_alt_names puppet.example.com,openvoxserver

检查它是否在运行

curl -ksS https://puppet.example.com:8140/status/v1/simple

返回 running。

安装 openvoxdb 及其数据库

注册 openvoxdb 的主机

openvoxdb 不会自己申请证书：其安装程序会复制其主机已有的证书。如果 openvoxdb 有自己独立的主机，请先向 CA 注册该主机；如果 CA 不自动签名，再在 CA 上为其请求签名：

sudo /opt/puppetlabs/bin/puppet ssl bootstrap --server puppet.example.com # on the CA host: sudo /opt/puppetlabs/bin/puppetserver ca sign --certname <openvoxdb host>

如果 openvoxdb 与 openvoxserver 共用一台主机（该主机已有证书），请跳过此步。

创建它的数据库

openvoxdb 需要一个属于自己的 Postgres 数据库，而软件包不会创建它：

Debian 和 Ubuntusudo apt-get install -y postgresql sudo systemctl enable --now postgresql RHEL、Rocky 和 AlmaLinuxsudo dnf install -y postgresql-server postgresql-contrib sudo postgresql-setup --initdb # Accept passwords over local connections, which are refused by the # default "ident" rules, and store passwords to match. sudo sed -i -E 's/^(host .*)(ident)$/\1scram-sha-256/' /var/lib/pgsql/data/pg_hba.conf echo "password_encryption = 'scram-sha-256'" | sudo tee -a /var/lib/pgsql/data/postgresql.conf sudo systemctl enable --now postgresql

在 RHEL 及其重构发行版上，下面的 pg_trgm 来自 postgresql-contrib，而且修改密码设置必须在创建用户之前完成：在此之前存储的密码无法按新规则进行校验。

sudo -u postgres createuser --pwprompt puppetdb sudo -u postgres createdb --owner=puppetdb puppetdb # openvoxdb refuses to start without this extension, and creating it # needs superuser rights - so it is run as postgres, not as puppetdb. sudo -u postgres psql -d puppetdb -c 'CREATE EXTENSION IF NOT EXISTS pg_trgm;'

检查 Postgres 是否在接受连接：

pg_isready

返回结果以 accepting connections 结尾。

在 Debian 和 Ubuntu 上，systemctl status postgresql 显示 active (exited)，这是正常的：该单元只负责启动真正的、按集群划分的单元。pg_lsclusters 会显示集群本身为 online。

安装并启动 openvoxdb

Debian 和 Ubuntusudo apt-get install -y openvoxdb RHEL、Rocky 和 AlmaLinuxsudo dnf install -y openvoxdb

告诉它数据库在哪里。没有这个文件它将无法启动，并以 No subname set in the "database" config. 退出：

[database] subname = //localhost:5432/puppetdb username = puppetdb password = <the password you set above>

将其保存为 /etc/puppetlabs/puppetdb/conf.d/database.ini（如果数据库在其他主机上，请用数据库主机的名称代替 localhost），并限制其权限：

sudo chown puppetdb:puppetdb /etc/puppetlabs/puppetdb/conf.d/database.ini sudo chmod 640 /etc/puppetlabs/puppetdb/conf.d/database.ini

然后把主机的证书复制到位，并启动它：

sudo /opt/puppetlabs/bin/puppetdb ssl-setup sudo systemctl enable --now puppetdb

如果它启动失败，/var/log/puppetlabs/puppetdb/puppetdb.log 中记录着真正的原因；systemd 自己的错误通常只是其后果。

把 catalog 和 Reports 发送给它

在 openvoxserver 主机上，安装把 catalog 和 Reports 发送到 openvoxdb 的 terminus：

Debian 和 Ubuntusudo apt-get install -y openvoxdb-termini RHEL、Rocky 和 AlmaLinuxsudo dnf install -y openvoxdb-termini

检查它是否在运行

openvoxdb 的 HTTPS 端口必须提供客户端证书，因此请使用主机自己的证书发起请求。没有证书时，返回的是 certificate required：

H=$(hostname -f) sudo curl -sS --cert /etc/puppetlabs/puppet/ssl/certs/$H.pem \ --key /etc/puppetlabs/puppet/ssl/private_keys/$H.pem \ --cacert /etc/puppetlabs/puppet/ssl/certs/ca.pem \ https://$H:8081/status/v1/simple

返回 running。日志中可能会报告 "the read-database user is not configured properly"。这指的是一个本指南没有设置的独立只读用户，openvoxdb 没有它也能运行。

创建控制台的数据库

控制台把自己的数据保存在一个独立于 openvoxdb 的数据库中。它会在首次启动时自行创建 schema；它只需要一个空数据库和一个拥有该数据库的角色。在 Postgres 主机上执行：

sudo -u postgres createuser --pwprompt console sudo -u postgres createdb --owner=console console

如果控制台将运行在另一台主机上，Postgres 还必须在网络上监听。它默认只监听 localhost，因此即使 pg_isready 在本地检查通过，远程连接仍会被拒绝。请允许控制台的主机或子网访问，并相应调整地址范围：

Debian 和 Ubuntusudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /etc/postgresql/*/main/pg_hba.conf sudo systemctl restart postgresql@*-main.service RHEL、Rocky 和 AlmaLinuxsudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';" echo 'host console console 10.0.0.0/24 scram-sha-256' \ | sudo tee -a /var/lib/pgsql/data/pg_hba.conf sudo systemctl restart postgresql

在控制台所在的主机上，检查控制台的角色能否连接（那里的 psql 由 postgresql-client 软件包提供）：

PGPASSWORD='<password>' psql -h <postgres host> -U console -d console -c 'select 1;'

保留单引号。否则包含 $ 的密码会在 psql 看到之前被 shell 展开。

签发控制台的证书

控制台需要 CA 签发的两张证书，另有一张可选。在 openvoxserver 主机上生成它们，然后复制到控制台主机的 /etc/openvox-console/ 中。请先在控制台的主机上，以控制台将要使用的运行用户创建该目录：

sudo useradd --system --home-dir /nonexistent --shell /usr/sbin/nologin openvox-console sudo install -d -m 0750 -o root -g openvox-console /etc/openvox-console

openvoxdb 客户端证书

控制台就是这样向 openvoxdb 进行认证的：

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname console

puppetserver ca generate 一开始会打印 Error: Signed certificate console could not be found on the CA。这是它在检查该名称是否可用，并非失败。真正要看的是之后的几行，最后以 Successfully saved certificate 结尾。

它会写出控制台需要的三个文件。以下列名称把它们复制过去：

在 openvoxserver 主机上 在控制台主机上
/etc/puppetlabs/puppet/ssl/certs/console.pem /etc/openvox-console/console-cert.pem
/etc/puppetlabs/puppet/ssl/private_keys/console.pem /etc/openvox-console/console-key.pem
/etc/puppetlabs/puppet/ssl/certs/ca.pem /etc/openvox-console/ca.pem

Node 传输证书

Nodes 连接控制台时会校验此证书，所以它必须包含 Nodes 所拨号的确切名称：即 CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR 的主机部分。

sudo /opt/puppetlabs/bin/puppetserver ca generate --certname node-transport \ --subject-alt-names console.example.com,node-transport

以同样方式把 certs/node-transport.pem 和 private_keys/node-transport.pem 复制过去，分别命名为 node-transport-cert.pem 和 node-transport-key.pem。Nodes 使用同一 CA 签发的自有证书进行反向认证，因此控制台不需要为它们准备其他任何东西。

令牌签名密钥

控制台使用一个 ES256 密钥为自己的登录令牌签名。这个密钥并非来自 CA。可在任意一台机器上用 OpenSSL 生成：

openssl ecparam -genkey -name prime256v1 -noout -out rbac-signing-key.pem

请备份此文件。丢失它会使所有已签发的令牌失效，从而让所有人退出登录；泄露它则会让任何人都能伪造令牌。要安全地替换它，请参见轮换令牌签名密钥。

在控制台所在的主机上生成它，放入 /etc/openvox-console/。

证书管理员凭据（可选）

有了这个凭据，Nodes 页面才能显示证书状态，并对证书进行签名、吊销和清理。没有它，控制台只会列出已经连接过或上报过的 Nodes。正在等待证书签名的 Node 根本不会出现，因为只有 CA 知道它的存在。

该凭据拥有完整的 CA 管理员权限。openvoxserver 用同一个授权扩展把守所有 CA 端点，因此一张能读取状态的证书也能签名、吊销和清理任何 Node 的证书。不存在只读的变体。请只把它保存在控制台运行的地方，并在签发之前阅读管理 Node 证书。

签发它会写入 CA 状态，而运行中的服务器也会写入这些状态，因此签发期间请停止 openvoxserver：

sudo systemctl stop puppetserver sudo /opt/puppetlabs/bin/puppetserver ca generate --ca-client --certname console-ca-client sudo systemctl start puppetserver

把 certs/console-ca-client.pem 和 private_keys/console-ca-client.pem 复制过去，分别命名为 ca-client-cert.pem 和 ca-client-key.pem。然后在控制台所在的主机上确认 CA 接受它：

curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/ca-client-cert.pem \ --key /etc/openvox-console/ca-client-key.pem \ --cacert /etc/openvox-console/ca.pem \ https://puppet.example.com:8140/puppet-ca/v1/certificate_statuses/all

HTTP 200 表示它工作正常。

构建控制台

控制台是一个内置了 Web 界面的单一二进制文件。它没有软件包，需要从源码仓库构建。你需要 go.mod 中指定版本的 Go，以及 git。

git clone https://github.com/avitacco/openvox-console.git cd openvox-console

控制台还会从自己的软件包仓库提供 Nodes 要安装的 Node 代理，这些代理内置在控制台二进制文件中。请先构建它们，否则每次 Node 安装都会以 404 失败：

make agent-binaries make agent-packages make build

这样就得到了 bin/console 和 bin/enc-bridge。在控制台的主机上安装控制台：

sudo install -m 0755 bin/console /usr/local/bin/console

配置控制台

控制台只通过环境变量进行配置，这些变量写在你为其证书创建的 /etc/openvox-console/ 目录中的一个文件里。

有六项设置是必需的，缺少时控制台会拒绝启动，并指出缺少的是哪一项。把它们放在 /etc/openvox-console/console.env 中：

CONSOLE_POSTGRES_DSN=postgres://console:<password>@<postgres host>:5432/console?sslmode=require CONSOLE_OPENVOXDB_URL=https://<openvoxdb host>:8081 CONSOLE_OPENVOXDB_CERT_FILE=/etc/openvox-console/console-cert.pem CONSOLE_OPENVOXDB_KEY_FILE=/etc/openvox-console/console-key.pem CONSOLE_OPENVOXDB_CA_FILE=/etc/openvox-console/ca.pem CONSOLE_RBAC_SIGNING_KEY_FILE=/etc/openvox-console/rbac-signing-key.pem

sslmode=require 假定你的 Postgres 提供 TLS——一旦连接离开本机，它就应该提供。如果控制台和 Postgres 在同一台主机上且 Postgres 没有证书，请使用 sslmode=disable。

其余设置都是可选的，每个可选功能在未配置时会自行关闭，而不会阻止启动。对于正式部署，请添加：

# Where the console listens, and how the outside world reaches it. It # listens on loopback only: the TLS proxy in front of it is the way in. # On a host shared with openvoxdb, which holds 8080, use 127.0.0.1:8088. CONSOLE_HTTP_ADDR=127.0.0.1:8080 CONSOLE_BASE_URL=https://console.example.com # The first admin user, created only while there are no users. The # password needs at least 12 characters. CONSOLE_BOOTSTRAP_ADMIN_USERNAME=admin CONSOLE_BOOTSTRAP_ADMIN_PASSWORD=<a strong password> # The node transport. ADDR is what the console binds; PUBLIC_ADDR is what # a node dials, and its host must be in the node transport certificate. CONSOLE_NODE_TRANSPORT_ADDR=:8142 CONSOLE_NODE_TRANSPORT_PUBLIC_ADDR=console.example.com:8142 CONSOLE_NODE_TRANSPORT_CERT_FILE=/etc/openvox-console/node-transport-cert.pem CONSOLE_NODE_TRANSPORT_KEY_FILE=/etc/openvox-console/node-transport-key.pem CONSOLE_NODE_TRANSPORT_CA_FILE=/etc/openvox-console/ca.pem # The Puppet server a node should enroll against, written into the node # install script. CONSOLE_PUPPET_SERVER_PUBLIC_ADDR=puppet.example.com # Certificate management from the Nodes page (the optional credential). CONSOLE_CA_CLIENT_URL=https://puppet.example.com:8140 CONSOLE_CA_CLIENT_CERT_FILE=/etc/openvox-console/ca-client-cert.pem CONSOLE_CA_CLIENT_KEY_FILE=/etc/openvox-console/ca-client-key.pem CONSOLE_CA_CLIENT_CA_FILE=/etc/openvox-console/ca.pem # Puppet tasks: where the console asks which tasks your deployed code # contains. Uses the openvoxdb client certificate above unless you name # another with CONSOLE_PUPPET_SERVER_CERT_FILE, _KEY_FILE and _CA_FILE. CONSOLE_PUPPET_SERVER_URL=https://puppet.example.com:8140

Tasks 不需要自己的证书：openvoxserver 允许其 CA 签发的任何证书读取 Tasks，因此 openvoxdb 客户端证书即可胜任。不要让它们使用证书管理员凭据，它能做的远超读取 Tasks 所需。关于如何运行它们，参见运行 Jobs。

让控制台读取类列表

Node 组的页面会提供你已 deploy 的代码所定义的类及其参数，供你选择而不必手动输入。控制台通过与 Tasks 相同的连接从 openvoxserver 读取它们，但在有规则允许之前，openvoxserver 不允许任何证书读取类。

在 openvoxserver 的主机上，把这条规则添加到 /etc/puppetlabs/puppetserver/conf.d/auth.conf 中的 rules 列表里，放在最后的 puppetlabs deny all 规则之前。console 是你在上面签发的 openvoxdb 客户端证书的名称：

{ match-request: { path: "/puppet/v3/environment_classes" type: path method: get } allow: "console" sort-order: 500 name: "openvox console class discovery" },

然后重新加载 openvoxserver：

sudo systemctl reload puppetserver

在控制台所在的主机上检查它。HTTP 200 表示可以读取该列表：

sudo curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \ --cert /etc/openvox-console/console-cert.pem \ --key /etc/openvox-console/console-key.pem \ --cacert /etc/openvox-console/ca.pem \ 'https://puppet.example.com:8140/puppet/v3/environment_classes?environment=production'

HTTP 403 表示该规则缺失或指定的是另一张证书。没有其他功能依赖于这一步：缺少它时，组页面会提示该列表不可用，类需要按名称输入。参见为 Nodes 分类。

把机密保存在文件中

任何设置都可以改为从文件读取：在设置名称后加上 _FILE，并以此指定文件。这样密码就不会出现在进程环境中：

CONSOLE_POSTGRES_DSN_FILE=/etc/openvox-console/postgres-dsn CONSOLE_BOOTSTRAP_ADMIN_PASSWORD_FILE=/etc/openvox-console/bootstrap-admin-password

文件末尾的换行符会被忽略。如果指定的文件无法读取，控制台会拒绝启动，而不会在该值悄然为空的情况下启动。

最后，让每个文件只有控制台的用户可以读取：

sudo sh -c 'chown root:openvox-console /etc/openvox-console/* && chmod 0640 /etc/openvox-console/*'

sh -c 很关键：你自己的 shell 无法列出该目录，因此直接执行 sudo chown ... /etc/openvox-console/* 会失败并报 "No such file or directory"。

在 systemd 下运行

创建 /etc/systemd/system/openvox-console.service：

[Unit] Description=OpenVox Console After=network-online.target Wants=network-online.target [Service] EnvironmentFile=/etc/openvox-console/console.env ExecStart=/usr/local/bin/console Restart=on-failure User=openvox-console Group=openvox-console [Install] WantedBy=multi-user.target

然后启动它：

sudo systemctl daemon-reload sudo systemctl enable --now openvox-console journalctl -u openvox-console -f

在控制台前面配置 TLS

控制台通过普通 HTTP 提供其 Web 界面和 API。https:// 基础 URL 经由一个终止 TLS 并把请求转发给控制台的反向代理访问。任何反向代理都可以。这里在控制台的主机上使用 Caddy：

Debian 和 Ubuntusudo apt-get install -y caddy RHEL、Rocky 和 AlmaLinuxsudo dnf install -y epel-release sudo dnf install -y caddy sudo systemctl enable --now caddy

完整的 /etc/caddy/Caddyfile 就是：

console.example.com { reverse_proxy 127.0.0.1:8080 } sudo systemctl reload caddy

如果控制台因为与 openvoxdb 共用主机而监听其他端口，请改为在 reverse_proxy 中填写该端口。

对于互联网可以解析的名称，Caddy 会自行获取并续期证书。对于内部名称，请在该配置块中加入一行 tls <cert file> <key file>，为它提供由你自己的 CA 签发的证书。用于试用时，tls internal 会让 Caddy 用它自己的本地 CA 签发一张证书，浏览器会对此发出警告。

只有 Web 界面经过代理。Node 传输（端口 8142）自带 TLS，并会自行校验每个 Node 的证书，因此 Nodes 必须直接访问它。绝不要把它放在代理后面。

首次登录

首次启动时，控制台会创建其数据库 schema，然后趁用户表仍为空时创建引导管理员。启动完成后，其日志中会出现三行：

database migrations up to date node transport ready addr=[::]:8142 console ready addr=:8080

检查它是否报告自身健康：先直接在控制台的主机上检查，再通过 TLS 代理在其基础 URL 上检查：

curl -fsS http://127.0.0.1:8080/health curl -fsS https://console.example.com/health

每个应答都会把每个依赖项列为 ok。如果只有第二个失败，说明控制台没有问题，问题出在代理上。如果你把控制台从 8080 移到了其他端口，请在第一个检查中使用控制台自己的端口。然后打开控制台的基础 URL，以引导管理员身份登录，并立即修改其密码。

引导管理员的密码必须至少有 12 个字符，并且不能与其用户名相同。否则不会创建管理员，也就没有人能登录。日志会说明这一点：

CONSOLE_BOOTSTRAP_ADMIN_PASSWORD does not meet the account policy, so no administrator was created

设置一个更长的密码，然后重新启动控制台。参见密码与锁定。

登录并修改密码后，请从控制台的配置中删除引导管理员相关设置。它们只在用户表为空时才会被读取，但没有理由让密码一直留在那里。

连接分类

openvoxserver 通过 Puppet 标准的 exec node terminus 向控制台询问每个 Node 获得哪些类。一个小程序 enc-bridge 代表 openvoxserver 发出该请求，为此它需要一个令牌。

为 enc-bridge 签发令牌

服务令牌带有一组在创建时选定的固定权限，不涉及任何角色。创建一个只允许读取分类的服务令牌：

  1. 在控制台中打开管理，然后打开服务令牌。
  2. 在新建服务令牌下，将其命名为 enc-bridge，并只授予 enc:read 权限。
  3. 选择创建服务令牌。

令牌只显示一次。请立即复制。

也可以通过 API 完成，使用管理员登录获得的访问令牌：curl -X POST https://console.example.com/api/v1/service-tokens -H "Authorization: Bearer <admin access token>" -H 'Content-Type: application/json' -d '{"name":"enc-bridge","permissions":["enc:read"]}'

在 openvoxserver 的主机上安装 enc-bridge

把构建产物中的 bin/enc-bridge 复制到 openvoxserver 主机并安装：

sudo install -m 0755 enc-bridge /usr/local/bin/enc-bridge

把令牌保存在只有 openvoxserver 的用户可以读取的位置：

printf '%s' '<the enc:read service token>' | sudo tee /etc/puppetlabs/enc-bridge-token >/dev/null sudo chown root:puppet /etc/puppetlabs/enc-bridge-token sudo chmod 0640 /etc/puppetlabs/enc-bridge-token

enc-bridge 从其环境变量中读取控制台的位置及其令牌，这些环境变量继承自 openvoxserver。用 sudo systemctl edit puppetserver 把两者都提供给 openvoxserver：

[Service] Environment=ENC_BRIDGE_URL=https://console.example.com Environment=ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token

enc-bridge 会依据 openvoxserver 主机的系统证书库校验控制台的证书。如果代理的证书来自你自己的 CA，请把该 CA 添加到证书库中，否则分类会失败并报 certificate signed by unknown authority：

Debian 和 Ubuntusudo cp <your CA>.crt /usr/local/share/ca-certificates/ sudo update-ca-certificates RHEL、Rocky 和 AlmaLinuxsudo cp <your CA>.crt /etc/pki/ca-trust/source/anchors/ sudo update-ca-trust

然后在 /etc/puppetlabs/puppet/puppet.conf 的 [server] 部分让 Puppet 指向它，并重启 openvoxserver：

[server] node_terminus = exec external_nodes = /usr/local/bin/enc-bridge sudo systemctl restart puppetserver

让 Nodes 读取配置数据

可选。这能让 Nodes 通过 lookup() 读取在 Node 组上设置的配置数据，其优先级高于你的 control 仓库中的 Hiera 数据。该函数会运行 enc-bridge --data，因此它使用与分类相同的控制台地址和令牌，无需额外配置。它需要由此版本构建的 enc-bridge。

该函数必须安装在 Puppet 自己的函数目录中，这是 openvoxserver 加载全局 Hiera 函数的唯一位置。在你构建所用的代码检出目录中执行：

sudo install -m 0644 openvoxserver-init/console_config_data.rb \ /opt/puppetlabs/puppet/lib/ruby/vendor_ruby/puppet/functions/console_config_data.rb

然后把它添加到全局 Hiera 配置 /etc/puppetlabs/puppet/hiera.yaml 中，放在层级的第一位，使控制台数据胜出。软件包会在那里安装一个占位文件；如果你没有改动过它，请用以下内容替换：

--- version: 5 hierarchy: - name: "Console configuration data" data_hash: console_config_data

如果你已经有一个全局的 hiera.yaml，请把该条目添加进去，并把你自己的条目放在它之后。

sudo systemctl restart puppetserver

升级 openvox-agent 软件包后，请检查该文件是否仍在，如果不在就重新安装。如果某个 Node 的运行失败并报 "Unable to find 'data_hash' function named 'console_config_data'"，说明该函数不在那个目录中。容器镜像在每次启动时都会自动完成这一切。

检查分类

以 openvoxserver 的方式运行 enc-bridge：使用它的用户、相同的设置。一条命令即可同时检查程序、令牌、文件权限以及控制台的应答：

sudo -u puppet env ENC_BRIDGE_URL=https://console.example.com \ ENC_BRIDGE_TOKEN_FILE=/etc/puppetlabs/enc-bridge-token \ /usr/local/bin/enc-bridge <a certname>

{} 表示分类正常工作，只是该 Node 尚未匹配任何组。在控制台的组页面上创建一个固定该 certname 的 Node 组，再次运行同一命令，它的类就会返回：

classes: ntp: servers: - time.example.com parameters: role: prodtest environment: production

这里出现的错误正是需要捕捉的故障。permission denied 表示运行 openvoxserver 的用户无法读取该令牌；401 则表示令牌错误或缺少 enc:read。

如果某个 Node 的下一次 Puppet 运行失败并报 Could not find class <name>，说明分类在正常工作：控制台让 openvoxserver 包含了一个你的 Puppet 代码中尚未定义的类。

日后升级

要升级到更新的控制台版本，请拉取源码，按相同顺序重新构建，安装新的二进制文件并重启：

git pull make agent-binaries make agent-packages make build sudo install -m 0755 bin/console /usr/local/bin/console sudo systemctl restart openvox-console
